## Trust Boundaries

| Boundary | Description | Data Crossing |

| dev machine → SpacetimeDB release feed | `spacetime version upgrade` fetches a signed CLI binary from ClockworkLabs | CLI binary only |

| publish decision → automated deploy | Task 3 blocking human-verify checkpoint is the structural enforcement of the D-04 deploy gate | human approval signal |

### Verification Evidence

**T-16.5-01-01 (accept):** `package-lock.json:4193` and `spacetimedb/package-lock.json:97` both resolve `node_modules/spacetimedb` to `"version": "2.6.1"` with a `sha512-...` integrity hash. Both `resolved` URLs point to `https://registry.npmjs.org/spacetimedb/-/spacetimedb-2.6.1.tgz`. Standard npm trust-anchor, no deviation.

**T-16.5-01-02 (accept):** No new postinstall scripts introduced by this phase's `npm install` re-resolution beyond the standing supply-chain surface; no incident reported in any of the 3 SUMMARY files.

**T-16.5-01-03 (accept):** 16.5-VERIFICATION.md independently re-ran `spacetime --version` live and confirmed `spacetimedb tool version 2.6.1; spacetimedb-lib version 2.6.1`. Rollback path (`spacetime version use 2.2.0`) preserved per `spacetime version list` (prior versions retained).

**T-16.5-01-04 (accept):** Grepped `package-lock.json` and `spacetimedb/package-lock.json` for `_authToken|_auth|authToken` — no matches. `.npmrc` contains only `engine-strict=true`, no registry/token config. All resolution URLs are `registry.npmjs.org`.

**T-16.5-02-01 (mitigate):** Every SK token grep-verified present at its cited anchor:

- SK-1: `SKILL.md:90-97` and `SKILL.md:267` — `omit`/`optional`/`2.6.1` together, illustrative trio present.

**T-16.5-02-02 (mitigate):** `git show --stat 6d8efed` lists exactly 3 files: `.claude/skills/spacetimedb/SKILL.md`, `.claude/skills/spacetimedb/references/api-guide.md`, `.claude/skills/spacetimedb/references/how-to-guides.md`. `git show --name-only 6d8efed | grep -iE ".env|spacetimedb/src|module_bindings"` → 0 matches.

**T-16.5-03-01 (mitigate):** `package.json:18` — `"spacetime:publish:migrate": "spacetime publish --module-path spacetimedb --server maincloud --yes=migrate"` — no `--delete-data`. Commit `61361bf` message explicitly states "no `--delete-data` used (CLI applies zero data deletion without that flag)." `test/global-setup.ts:77` does invoke `--clear-database -y`, but this is a pre-existing, separately-guarded test-harness mechanism (refuses to run unless DB name contains `-test`, per its own header comment) — out of this phase's threat scope per the register's own carve-out, and unchanged by phase 16.5.

**T-16.5-03-02 (mitigate, MATERIALIZED — documented honestly):** The D-01 "empty delta" assumption was false: the republish hit a non-empty, breaking view-redefinition delta (accumulated Phase 15.x view drift never republished to `test1`). The plan's fine-grained control ("stop and surface on non-empty delta, before applying") was **not fully honored** — during a full-plan capture, a piped `y` on stdin auto-answered the CLI's `--break-clients` confirmation prompt, so the migration applied before the intended explicit-GO sub-gate executed. This is a genuine partial control bypass, not a documentation gap.
Compensating factors verified directly:
- `--break-clients` was used **without** `--delete-data` — commit `61361bf` and 16.5-03-SUMMARY.md both confirm zero data deletion (`SELECT COUNT(*) FROM user = 32` unchanged; same DB identity `c2005439…d115d6` before/after).
- The coarser, structurally-independent D-04 gate (Task 3 blocking human-verify checkpoint) still fired and the user reviewed + approved the outcome post-hoc (16.5-03-SUMMARY.md: "Task 3: Human-verify gate — user approved the results").
- Independently corroborated by 16.5-VERIFICATION.md's Anti-Patterns section, which classified this exact sequencing gap as **INFO / non-blocking** ("Does not block the phase goal — data-safety invariant held... just not via the exact intended sequencing").
**Residual risk (documented, not re-opened):** future publish plans that gate on a "stop before non-empty delta" sub-check should not rely on stdin being interactively available during automated capture — an explicit pre-apply pause (e.g., requiring a distinct confirmation token before any `--break-clients` prompt can be auto-answered) would close this gap structurally rather than relying on the coarser after-the-fact checkpoint. No corrective action is required to ship this phase since the data-safety invariant (no `--delete-data`) held mechanically and human approval was obtained.

**T-16.5-03-03 (mitigate):** 16.5-VERIFICATION.md independently ran `spacetime sql hsrpvp-spacetimedb-nextjs-test1 "SELECT * FROM User LIMIT 1"` post-publish and got a live row back against the matching database identity. SpacetimeDB's publish model performs an atomic module swap (no partial-state window observed or reported).

**T-16.5-03-04 (mitigate):** Direct read of 16.5-03-SUMMARY.md confirms it records only aggregate counts (32 users, 619 tests passed, 83 characters/156 lightcones/etc. seed counts) and test file names (`test/backend/auth/auth-views.test.ts`) — no usernames, emails, identity hex strings, or auth tokens appear anywhere in the file.

**T-16.5-03-05 (accept):** No incident — publish succeeded, implying the cached login was valid at execution time. Standard accepted risk: an auth failure from a revoked token surfaces immediately as a CLI error, not silently.

**T-16.5-03-06 (mitigate):** `git log --all --oneline -- .env.local .env` returns empty (no `.env*` ever committed in this repo's history). `git status --porcelain` is clean (no working-tree `.env*` drift). `git show --name-only` on all 3 phase commits (`3ab88f3`, `6d8efed`, `61361bf`) contains zero `.env*` paths.
