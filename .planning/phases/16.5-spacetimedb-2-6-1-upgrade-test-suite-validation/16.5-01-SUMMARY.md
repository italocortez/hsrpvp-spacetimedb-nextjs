## Decisions Made
- The PR #4940 forcing break surfaced during `npm run spacetime:generate` (module build), not `npm run test:typecheck` as the plan anticipated. Treated as the same underlying break (same root cause, same D-01/D-03 justification requirement) since it is the identical optional-key codegen widening, just detected one step earlier in the pipeline (module build's internal type-check runs before the client `tsc --noEmit` gate).
- Reverted `spacetimedb/dist/bundle.js` after it was incidentally rebuilt (likely by the `spacetime generate` / `npm test` run touching the module build cache). Per established project precedent (Phase 15.3 Plans 13/14: "Stray dist/bundle.js rebuild reverted/left unstaged — Plan N owns the bundle commit"), bundle rebuilds are reserved for the plan that actually publishes (16.5-03 in this phase). Used `git checkout -- spacetimedb/dist/bundle.js` (single-file revert, not a blanket reset).
- Included the vendored `spacetimedb/node_modules/spacetimedb/` tree changes (230 files) in the same atomic commit as the manifest/lockfile bump. This repo tracks that directory in git (see prior commit `6fbc0be chore(deps): vendor spacetimedb SDK v2.2.0` — `.gitignore`'s `/node_modules` entry is root-anchored and does not cover `spacetimedb/node_modules`). Since `npm install` inside `spacetimedb/` re-resolves the vendored package as a direct side effect of Task 1 Step 4, splitting it into a separate commit would break the "module source 2.6.1 + bindings 2.6.1 ride together" invariant (16.3 D-02) — the vendored SDK itself is part of "module source."

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug, forced by PR #4940] Fixed 4 reducer handler type annotations in achievementManagement.ts**
- **Found during:** Task 2, Step 1 (`npm run spacetime:generate` — the module build failed with 4 `TS2769` overload-resolution errors before bindings could even be written)
- **Issue:** SpacetimeDB v2.6.1's TypeScript codegen widening (PR #4940) changed the inferred payload type for `.optional()`-declared schema fields from a required key with an undefined-inclusive value type (`{field: T | undefined}`) to an optional key (`{field?: T | undefined}`). Four reducers in `achievementManagement.ts` had explicit (non-inferred) parameter type annotations on their handler functions using the old required-key shape. Under `--strictFunctionTypes` contravariant parameter checking, the widened SDK payload type (`field?: T | undefined`) is no longer assignable to the narrower required-key annotation (`field: T | undefined`), so `spacetimedb.reducer(params, fn)` failed overload resolution.
- **Fix:** Added `?` to 8 fields across 4 reducer handler annotations, matching the new widened shape exactly:
  - `create_achievement` (L34-40): `maxAwards?: number | undefined`
  - `update_achievement` (L77-82): `name?: string | undefined`, `description?: string | undefined`
  - `add_achievement_criteria` (L168-177): `filterGameMode?`, `filterCharacterName?`, `filterMatchType?: string | undefined`
  - `set_displayed_achievement` (L316-319): `targetUserId?`, `achievementId?: number | undefined`
  - This is a pure type-annotation change — JavaScript destructuring of an absent object key already yields `undefined` at runtime regardless of the TS optional-key marker, so behavior is byte-identical.
- **Files modified:** `spacetimedb/src/reducers/achievementManagement.ts`
- **Verification:** Re-ran `npm run spacetime:generate` — 0 errors, bindings written successfully (header stamp `cli version 2.6.1`); `npm run test:typecheck` exits 0; `npm test` 197/197 green.
- **Committed in:** `3ab88f3` (Task 2 commit)
