**Researched:** 2026-07-04

## Summary

This is an **upgrade-only** phase: bump the `spacetime` CLI (2.2.0 → 2.6.1), both SDK pins (`spacetimedb/package.json` and root `package.json`, `^2.2.0` → `^2.6.1`), regenerate `src/module_bindings`, and prove the existing test suite stays green. Across the four intermediate minors (2.3, 2.4, 2.5, 2.6), **exactly one** changelog item touches this repo's compiled surface: the v2.6.1 TypeScript **optional-key codegen change** (PR #4940) — and it is a *type-widening*, not a hard break. Every other notable change is Rust-only, C#-only, an unstable feature this project does not use (HTTP handlers, procedures), a server-side/maincloud-managed engine knob (WASM runtime, commitlog buffers), or a non-React framework SDK (Godot, Unity, Vue). `[VERIFIED: npm registry + GitHub releases + codebase grep]`

The repo's exposure was checked directly: zero procedures, zero HTTP handlers, zero `ctx.identity` (the v2.3 Rust deprecation), and all optional reducer args render as runtime `__t.option(...)` schema builders — so the v2.6.1 change surfaces only through the SDK's inferred call-site types, which `npm run test:typecheck` validates definitively. The integration suite connects **live to maincloud** (`wss://maincloud.spacetimedb.com`, database `hsrpvp-spacetimedb-nextjs-test1`), so a clean version story means republishing `test1` with the 2.6.1 CLI via the existing `spacetime:publish:migrate` path (schema is unchanged → identity/no-op migration; **never** `--delete-data`).

**Primary recommendation:** Upgrade CLI → both SDK pins → regenerate bindings with the **CLI path** (`npm run spacetime:generate`, not the cargo `generate` script — no local Cargo workspace exists) → typecheck → `spacetime:publish:migrate` to maincloud → run full unit + integration suites. Expect zero application-code edits; the typecheck + green integration run is the proof. Ship as one bump commit (no drift-fix half this time, unlike 16.3).

## Per-version changelog review (D-02 meticulous pass)

Sources: `github.com/clockworklabs/SpacetimeDB/releases/tag/v2.3.0 … v2.6.1`. Classification: **[B]** breaking-affects-this-repo · **[S]** skill-worthy · **[N]** neither.

### v2.3.0 — 2026-05-27 `[CITED: releases/tag/v2.3.0]`
- **[S]** WebSocket **v3 protocol, batched/pipelined responses** — "pipelines and batches responses using the v3 protocol, significantly reducing per-message overhead under high load." Fully pipelined WS send path (JS + WASM module ops). The transport the phase context flagged; project already on the v3 baseline (16.4 Plan 04), so this is a *reinforcement*, not a regression risk.
- **[N]** HTTP/2 backend support — server/maincloud-side; transparent to clients.
- **[N]** `ReducerContext::identity` **deprecated** → `database_identity` — **Rust API**. Verified: **zero `ctx.identity` usages** in `spacetimedb/src/`. Does not affect TS.
- **[N]** Godot first-party SDK, Blackholio tutorial, Unity 6 WebGL, Vue `useProcedure` — other frameworks; project is Next.js/React.
- **[N]** Rust `DbContext` generic support — Rust only.
- **[N]** Durability/commitlog compression knobs, empty-tail-segment handling — maincloud-managed.
- **[N]** Bug fixes: V8 segfault, connection-lifecycle callbacks, unsubscribe panics, view auto-migration canonical names, prepared-statement rollback, Windows snapshot fsync — engine-side reliability; no client action.

### v2.4.0 — 2026-06-03 `[CITED: releases/tag/v2.4.0]`
- **[N]** **HTTP handlers** (`#[spacetimedb::http::handler]`/`router`, unstable) — available in TS but **gated behind `unstable`** and **not used** (verified: zero `http.handler`/`http.router` in `spacetimedb/src/`). Backlog/skill-note only.
- **[S-minor]** **Reducers now run on a dedicated synchronous WASM runtime** (single OS thread), separate from the async runtime procedures use — reinforces the "reducers must be deterministic / never yield" mental model. Server-side; no code action.
- **[N]** TS fix: "Don't use ReadableStream as an asyncIterator" (#5144) — internal SDK streaming fix; no API surface change.
- **[N]** Bug fixes: silent-data-loss-on-resume (commitlog truncation), V8 heap metrics for procedure workers, commitlog decode context, reverted energy-conversion regression — engine-side.
- **Regression introduced here:** procedures got empty `ctx.sender`/`ctx.connection_id` (fixed in 2.6.1). **N/A** — project has **zero procedures**.

### v2.4.1 — 2026-06-05 `[CITED: releases/tag/v2.4.1]`
- **[S]** **Primary-key support for procedural views (Rust + TypeScript)** — first landing of view PKs for TS. Expanded/finalized in 2.6.0. See v2.6.0 for the skill implication.
- **[N]** Fixed index-schema retrieval from system tables — engine internal.

### v2.5.0 — 2026-06-11 `[CITED: releases/tag/v2.5.0]`
- **[S]** **Procedures graduated to stable** — no longer require `features:["unstable"]`. Corrects the skill's framing (SKILL.md currently notes procedures/`useProcedure` as effectively unused; still true for this repo, but they are no longer "unstable").
- **[S]** **`ctx.http` outgoing HTTP client stabilized** — procedures (not reducers) may now make outbound HTTP. Worth a skill note precisely because it is the *exception* to "reducers are deterministic / no network" — the capability lives in procedures, which this project does not use.
- **[S]** **Event-table automigrations broadened** — event tables now permit column removal, reordering, and type changes that regular tables reject. Directly qualifies the skill's "Dangerous schema changes" table. Project uses event tables (`LobbyCursorEvent`).
- **[S-minor]** CLI: `publish --delete-data` no longer forces a positional db name (config fallback from `spacetime.json`); `spacetime call` accepts hex strings for `Identity` params.
- **[S-minor]** Perf/correctness: non-full pages stored in a `BTreeSet` (sorted by free var-len granules) — fixes accidentally-quadratic bulk insert and makes row insertion locations deterministic across restarts. Informational.
- **[N]** RLS / HTTP handlers / views / webhooks **remain gated behind `unstable`**. C# view-PK parity (Rust/TS already had it).

### v2.6.0 — 2026-06-16 `[CITED: releases/tag/v2.6.0]`
- **[S — significant]** **Primary-key support for procedural views in TypeScript**, column-level `.primaryKey()`, enabling clients to receive **`onUpdate`** events on views (previously insert/delete only). Project has ~35 procedural views (`view_my_profile`, `view_my_lobbies`, …). This is an **adoption opportunity** (deferred under D-01) and a real skill addition.
- **[N]** Commitlog config (`max_segment_size`, `write_buffer_size`, `preallocate_segments`); default write buffer 8KiB → 128KiB (#5074) — maincloud-managed engine config, not client-controllable.
- **[N]** Timestamps usable as PK in **C#** (#5262); event-table layout-altering automigration (#5269, extends 2.5.0).

### v2.6.1 — 2026-07-01 `[CITED: releases/tag/v2.6.1]`
- **[B — the only repo-relevant change]** **TypeScript optional-field codegen fix (PR #4940).** Generated types for `Option<T>` change from a *required key with undefined* to a *truly optional key*:
  - Before: `{ foo: T | undefined }`  →  After: `{ foo?: T | undefined }`
  - Release note: *"If your TypeScript code explicitly passes `undefined` for optional reducer or procedure arguments, or relies on `{ foo: T | undefined }` being a required key, you may need to update your call sites"* — while also stating it requires **"no action from almost all TypeScript users."**
- **[N]** Fixed 2.4 regression: `ctx.sender`/`ctx.connection_id` empty in procedures (#5323) — project has no procedures.
- **[N]** `spacetime init --template` with no args now lists templates (#5264) — project already scaffolded.

## Publish/migrate requirement (D-04)

**Verdict: republish `test1` to maincloud via `npm run spacetime:publish:migrate` — RECOMMENDED (strong), NOT forced by a wire/module-format break. Never `--delete-data`.** `[CITED: releases 2.3–2.6 + VERIFIED: test config connects to maincloud]`

Evidence and reasoning:
1. **No documented module/wire-format break** across 2.3–2.6 forces a republish. The v3 transport (2.3.0) is backward-compatible and already the project baseline; the WASM-runtime split (2.4.0) and commitlog buffers (2.6.0) are maincloud-managed engine internals; there is no module-ABI break enumerated.
2. **But the integration suite runs against a live maincloud module.** `[VERIFIED: test/vitest.integration.config.ts + grep]` every backend test builds `DbConnection.builder().withUri('wss://maincloud.spacetimedb.com').withConfirmedReads(false)` against `hsrpvp-spacetimedb-nextjs-test1`. D-03 requires the full integration suite green. Publishing `test1` with the 2.6.1 CLI (a) proves the 2.6.1 toolchain compiles the module cleanly, (b) keeps the deployed module's version story coherent with the 2.6.1 client SDK, and (c) is a **no-op / identity migration** because D-01 forbids schema changes — so `--yes=migrate` auto-confirms an empty delta with no data loss.
3. **`--delete-data` is prohibited** (D-04) — it would wipe `test1` and require `post-publish.ts` re-seeding + `.env.local` rewrites (which CLAUDE.md forbids touching outside `post-publish.ts`). `spacetime:publish:migrate` preserves data and does not touch `.env*`.
4. **Sequencing:** publish BEFORE running the integration suite so tests execute against a 2.6.1-compiled module (mirrors 16.3 D-04: "pushed-to-remote represents verified working"). Rollback if publish misbehaves: `spacetime version use 2.2.0` + `npm run spacetime:publish` from the pre-bump state.

## Common Pitfalls

### Pitfall 1: Regenerating with a stale/cargo path
**What goes wrong:** running `npm run generate` (cargo) either fails (no `gen-bindings` crate present) or produces bindings from a codegen that doesn't match the 2.6.1 CLI, masking the optional-key shape change.
**How to avoid:** use `npm run spacetime:generate` after `spacetime version upgrade`. Confirm the new header reads `cli version 2.6.1`.
**Warning sign:** `index.ts` header still says 2.2.0 after regen.

### Pitfall 2: Treating the 2.6.1 optional-key change as a required refactor
**What goes wrong:** an agent "adopts" optional-key syntax across call sites, violating D-01.
**How to avoid:** it is a widening — do nothing unless `test:typecheck` fails. Only a call site that *requires* the key would break, which is unusual. Let the typecheck decide.

### Pitfall 3: Reaching for `--delete-data`
**What goes wrong:** wipes `test1`, forces `post-publish.ts` re-seed, and risks `.env.local` edits.
**How to avoid:** schema is unchanged → `spacetime:publish:migrate` only. `--delete-data` is explicitly out of scope (D-04).

### Pitfall 4: Integration-suite flakiness attributed to the upgrade
**What goes wrong:** live-maincloud tests use tiered sleeps + sequential WS connections; network jitter can look like a regression.
**How to avoid:** re-run before triaging; only root-cause a *reproducible* failure to a specific 2.3–2.6 change (D-03). The v3 batching (2.3) can shift timing slightly but the sleep tiers have headroom.

## Risks & sequencing

**Recommended order (single bump commit, no drift-fix half this time):**
1. `spacetime version upgrade` → verify `spacetime --version` = 2.6.1.
2. Edit `spacetimedb/package.json` `^2.2.0`→`^2.6.1`; `cd spacetimedb && npm install`.
3. Edit root `package.json` `^2.2.0`→`^2.6.1`; `npm install`.
4. `npm run spacetime:generate` (CLI path) → confirm 2.6.1 header stamp.
5. `npm run test:typecheck` → **the D-01 gate.** Green = no app-code refactor needed.
6. `npm run spacetime:publish:migrate` (build + identity migration to maincloud `test1`).

**Commit shape:** one commit (unlike 16.3's two) — there is no manifest/lockfile drift to fix first this time; both pins are already coherent at 2.2.0.
