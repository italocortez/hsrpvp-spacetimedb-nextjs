# Phase 16.5: SpacetimeDB 2.6.1 upgrade + test suite validation - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning
**Source:** Inline scope directive at /gsd-plan-phase invocation (no separate discuss-phase)

<domain>
## Phase Boundary

Upgrade the SpacetimeDB toolchain and SDKs from **2.2.0 → 2.6.1** (latest), regenerate
client bindings, and validate that the existing test suite still passes. This is a
**version bump**, not a feature or refactor phase.

Upgrade surface (all currently pinned at 2.2.0):
- `spacetime` CLI: 2.2.0 → 2.6.1 (`spacetime version upgrade`)
- Client SDK — root `package.json` `spacetimedb ^2.2.0` → `^2.6.1`
- Module SDK — `spacetimedb/package.json` `spacetimedb ^2.2.0` → `^2.6.1`
- Regenerate `src/module_bindings` (`npm run spacetime:generate` / `npm run generate`)
- Validate: `npm run test:typecheck`, `npm test` (unit), `npm run test:integration`

Precedent: Phase 16.3 performed the prior v2.1.0→v2.2.0 upgrade
(`.planning/phases/16.3-spacetimedb-v2-1-0-realign-v2-2-0-upgrade-inserted/`); reuse its
plan structure and UAT approach as the template.

</domain>

<decisions>
## Implementation Decisions

### Scope
- **D-01 (LOCKED):** This is an **upgrade-only** phase. Do NOT refactor application code
  (reducers, tables, views, React components, hooks) unless a change is **absolutely
  necessary** to make the code compile, publish, or pass tests under 2.6.1. Every code
  edit outside version pins / regenerated bindings must be justified by a concrete
  2.3–2.6 breaking change. "Nice to have" adoptions of new APIs are explicitly out of
  scope for this phase.

### Changelog → Skill audit (research obligation)
- **D-02 (LOCKED):** During research, **meticulously** review the changelog / release
  notes for **each** intermediate version — 2.3.x, 2.4.x, 2.5.x, 2.6.x — not just a
  2.2→2.6 diff summary. For every notable entry, classify it as:
  (a) **Breaking** — must be addressed by this upgrade (feeds the plan), or
  (b) **Skill-worthy** — a new/changed API, pattern, pitfall, or best practice worth
      capturing in the `spacetimedb` skill (`.claude/skills/spacetimedb/SKILL.md` and/or
      its `references/*.md`), or
  (c) **Neither** — noted and dismissed.
  The research output MUST include an explicit "Skill Update Candidates" section listing
  every (b) item with the target skill file and a one-line rationale. Applying those
  skill edits is planned as its own task in this phase.

### Validation
- **D-03:** Success = clean typecheck + full unit suite + full integration suite green
  under 2.6.1, with bindings regenerated from the upgraded toolchain. Any test failure
  introduced by the upgrade is triaged (root-caused to a specific breaking change) before
  the phase is considered done; failures are reported, never silently suppressed.

### Publishing
- **D-04:** Follow project publishing rules — maincloud is the default target. Whether a
  republish/migration to maincloud is required (vs. local-only validation) is a research
  question: determine if 2.6.1 changes the wire/module format such that the deployed
  module must be republished. Do not `--delete-data`; if a republish is needed use the
  existing `spacetime:publish:migrate` path.

### Claude's Discretion
- Ordering of CLI vs SDK bumps, and whether to bump module + client in one commit or two.
- Exact command sequence for bindings regen (the repo exposes both a `cargo`-based
  `generate` and a CLI-based `spacetime:generate`).

</decisions>
