<interfaces>
From `spacetimedb/src/tables/hsrLightcone.ts` (existing precedent for positioning columns — `posX`/`posY`/`width` already present):

Positioning columns on `HsrLightcone` use `t.i32()` with `0` defaults populated at insert time. D-05a asks the same shape on `HsrCharacter`.

Spine columns do not exist anywhere else in the schema yet; D-05 sets their shape:
```typescript
skelUrl: t.string().optional(),
atlasUrl: t.string().optional(),
atlasImgUrls: t.array(t.string()),  // empty array = no Spine; arrays cannot cheaply be optional
```
</interfaces>

<convention>
- Flat columns over nested structs for filterable data (CLAUDE.md, project feedback memory `feedback_flat_columns`).
- Spine URLs use `optional()` because most characters lack Spine initially; `null` beats `''` as "not set".
- `atlasImgUrls` is NOT optional — it is `t.array(t.string())` with empty-array sentinel because `t.array().optional()` costs more than it's worth.
- Positioning defaults to `0` via required i32 when the JSON upsert omits the `positioning` block — matches `HsrLightcone` shape.
- **Schema migration approach (per RESEARCH.md §Pitfall 7 + A1):** publish via `--clear-database` on next `post-publish.ts` run. Pure additive schema changes on non-empty tables would require a migration spec; we sidestep by reseed.
</convention>
