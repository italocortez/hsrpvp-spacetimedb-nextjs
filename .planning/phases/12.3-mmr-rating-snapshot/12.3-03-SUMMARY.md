# Phase 12.3 Plan 03: BetweenGames MRP Snapshot Update Summary

**select_match_account now carries a monotonic-upward MRP snapshot hook — BetweenGames account swaps extend `accountRatingSnapshot` to `max(existing, newAccount.rating)` via composite-PK delete+insert, while Waiting-stage swaps and stand-in selections are no-ops by construction.**

## Performance

- **Duration:** ~5 min
- **Tasks:** 1 / 1
- **Files modified:** 1

## Accomplishments

- **Monotonic-upward hook added** to `select_match_account` immediately after the tournament/non-tournament if/else block. The hook reads the MRR for this lobby, then the MRP row for `(mr.id, user.id)`, then the fresh `HsrAccount.accountRating`, and applies `Math.max` — writing back via composite-PK delete+insert only when the value increases.
- **Both branches covered by a single hook:** placement after the if/else means the tournament additive path AND the non-tournament replace path both trigger the monotonic update with zero duplication.
- **Existence gating replaces stage gating (D-B-04):** during `Waiting`, no MRR exists yet (MRR is created inside `start_draft`), so the `[...MatchResultRecord.lobby_id.filter(lobbyId)][0]` lookup returns `undefined` and the hook is a silent no-op. No explicit stage check needed inside the hook.
- **Stand-in short-circuit (D-B-05):** stand-ins joining after `start_draft` have an LMA row but no MRP row (MRP is only inserted at `start_draft:204` for members present at that instant). The `if (existingMrp)` guard short-circuits for them — mid-series stand-in MMR attribution is intentionally deferred (D-B-06).
- **DoS mitigation (T-12.3-11):** the `if (newSnapshot !== existingMrp.accountRatingSnapshot)` equality guard skips the delete+insert entirely when the value would not change (e.g., re-selecting the current account or swapping to a lower-rated account). This bounds the worst case to a single read-only reducer invocation.
- **`deselect_match_account` intentionally unchanged:** per D-B-03, removing an account from the current selection can never lower the max, so no hook is needed in deselect. Documented in the hook's comment block so downstream readers understand it is a decision, not an oversight.
- **`auditUpdate` import added** to preserve the standard composite-PK update pattern — `createdBy*` fields are inherited from the existing row, `lastModifiedBy*` fields are stamped with the caller and `ctx.timestamp`.

```typescript
        } else {
            // Non-tournament path (D-07): replace behavior — delete existing + insert new
            for (const existing of [...ctx.db.LobbyMemberAccount.by_lobby_and_user.filter([lobbyId, user.id])]) {
                ctx.db.LobbyMemberAccount.delete(existing);
            }
            ctx.db.LobbyMemberAccount.insert({ lobbyId, userId: user.id, hsrAccountId });
        }

        // D-B-03 (Phase 12.3): monotonic-upward snapshot update for BetweenGames account swaps.
        // Gated by MRP existence, not lobby stage:
        //   - Waiting stage: no MatchResultRecord yet (created at draftClassic.ts:178 inside
        //     start_draft). The lookup returns empty -> this block is a no-op. Pre-draft
        //     swaps are harmless because MRP rows don't exist yet (D-B-04).
        //   - BetweenGames stage: MRR exists, MRP exists -> apply max rule.
        //   - Stand-ins joining after start_draft: LMA row seeded on join but no MRP row
        //     for them (MRP only inserted at start_draft:204). This block short-circuits
        //     at `if (!existingMrp) return;`. Stand-ins are intentionally excluded from
        //     MMR attribution here (D-B-05, D-B-06) — mid-series stand-in MMR is deferred.
        //   - `deselect_match_account` does NOT run this hook (removing an account from
        //     the selection can never lower the max — D-B-03).
        const mr = [...ctx.db.MatchResultRecord.lobby_id.filter(lobbyId)][0];
        if (mr) {
            const existingMrp = [...ctx.db.MatchResultParticipant.by_result_and_user.filter([mr.id, user.id])][0];
            if (existingMrp) {
                const freshAccount = ctx.db.HsrAccount.id.find(hsrAccountId);
                if (freshAccount) {
                    const newSnapshot = Math.max(existingMrp.accountRatingSnapshot, freshAccount.accountRating);
                    if (newSnapshot !== existingMrp.accountRatingSnapshot) {
                        ctx.db.MatchResultParticipant.delete(existingMrp);
                        ctx.db.MatchResultParticipant.insert({
                            ...existingMrp,
                            accountRatingSnapshot: newSnapshot,
                            ...auditUpdate(ctx, existingMrp, user.id),
                        } as any);
                    }
                }
            }
        }

        console.log(`[ACCOUNT] User #${user.id} selected account #${hsrAccountId} for lobby #${lobbyId}`);
```

The hook is placed AFTER the closing `}` of the `if (lobby.isTournamentControlled && lobby.tournamentId)` / `else` block and BEFORE the trailing `console.log`. Indentation is 8 spaces (one level inside the reducer body) — the same level as the `if/else` statement. This placement guarantees it runs regardless of which branch executed.

## Decisions Made

- **Hook placement:** single post-branch hook rather than two duplicated hooks inside each branch. Cleaner, and both branches end with an LMA insert so the snapshot update preconditions are identical.
- **Gating on MRP existence, not lobby stage:** the existing `start_draft` timing guarantees MRR is created at the Waiting→Drafting transition, so `MRR exists` is an exact proxy for "a match has started". Using an explicit `lobby.stage.tag === 'BetweenGames'` check would be equivalent but less robust against future stage-graph changes.
- **Equality short-circuit before delete+insert:** prevents MRP churn for the common cases of (a) user re-selects their current account, (b) user swaps to a lower-rated account. Keeps the T-12.3-11 DoS surface bounded.
- **`auditUpdate` is mandatory:** not using it would leak `createdById`/`createdDate` overwrites, breaking the audit trail. Matches the composite-PK update pattern used in `finalizationHelpers.ts` (MmrRating update, lines 136–148) and across the rest of the codebase.
- **`deselect_match_account` unchanged:** a deliberate decision per D-B-03. Removing an account from the current selection cannot lower a `max`, so a hook there would be dead code.
