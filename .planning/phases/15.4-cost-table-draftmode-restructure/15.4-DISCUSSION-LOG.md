## Area 1 — Synergy PK strategy

**Initial framing:** Three options — composite PK (drop `id`), composite PK + keep `id` as secondary, keep `id` PK + add unique tuple index.

**User redirect:** Asked whether other tables use `synergy.id` as a foreign key, and whether the "split for queryability" idea (per spacetimedb skill) would be served by composite PK itself.

**Investigation findings:**
- `synergy.id` is used internally only — `admin.ts:242-244` (delete_row), `admin.ts:609` (update), `costSetManagement.ts:400,571` (copy/delete). Zero external FK references. `TableExplorer.tsx:40` uses it as a UI row key (cosmetic).
- Skill documents that query speed comes from multi-column btree indexes, NOT from composite PK declarations (`.primaryKey.find()` panics at runtime; composite PK is marked via `table({ primaryKey: [...] })` option).
- Bindings comparison: `HsrCharacterCost` (declares composite PK) generates `constraints: [ ]` (empty). `HsrSynergyCost` (declares single-col `id` PK) generates `constraints: [{ constraint: 'unique', columns: ['id'] }]`.

**User instruction:** "Try a test table in the backend and test if it can be enforced through some script at tmp/."

**Live probe (2026-04-14):**
- Added `spacetimedb/src/tables/pkTest.ts` with `primaryKey: ['a', 'b']`.
- Added `spacetimedb/src/reducers/pkTest.ts` with `pk_test_insert({a, b, v})`.
- Published to maincloud (additive — new table).
- Generated bindings showed `PkTest: { indexes: [ ], constraints: [ ] }`.
- `tmp/test-composite-pk.ts` called the reducer twice with `(x, y, 1)` and `(x, y, 2)`. Both rows persisted. Zero failed reducer calls.

**Definitive conclusion:** `table({ primaryKey: [multi-col] })` is a no-op in SpacetimeDB v2.1.0. Zero uniqueness enforcement, zero index generation, zero accessor.

**Cleanup:** Source files restored with deprecation markers; `pk_test` rows deleted; bindings regenerated. Probe artifacts slated for removal via D-23 (same publish that carries the real schema changes).

**User decision:** Keep `id` PK + 5-col btree `by_tuple`; extend `source_mode` btree with `draftMode`. Documented as D-06/D-07/D-08.

## Area 4 — Reducer arg shape

**Initial framing:** Three options — single `costsJson` + `draftModeTag`, keep both JSON args + `draftModeTag`, single struct arg (no JSON).

**User redirect #1:** "Show me with an example what data would these options accept on a reducer level." → Options re-presented with concrete client call payloads and server reducer bodies in preview format.

**User redirect #2:** "What makes more sense according to the templates that we have already written for character and lightcone?"

**Investigation findings:**
- Template shape from 15.1 D-01: `cost.<mode>.{classic?, auction?}` — each sub-block is optional; absence means "don't write that row".
- `admin_bulk_upsert` takes an array of row-shaped objects (not template-shaped).
- Option A's 1:1 mapping (one sub-block = one row = one reducer call) honors the 15.1 template semantics exactly. Option B forces callers to send both JSON blobs every time even when they only want one, re-introducing the ambiguity that 15.1 D-06 solved via "absence = don't touch".

| Option | User selected |
|---|---|
| Single `costsJson` + `draftModeTag` (Option A) | ✅ |
| Both JSON args + `draftModeTag` | — |
| Single struct arg via `t.object()` | — |

**User decision:** Lock Option A. Documented as D-16/D-17/D-18/D-19.
