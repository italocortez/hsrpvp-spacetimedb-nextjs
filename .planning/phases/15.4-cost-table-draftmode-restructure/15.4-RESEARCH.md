## Summary

Phase 15.4 is a schema-migration phase replacing the parallel `classicCosts` + `auctionBaseBid` column design with a single `costs` struct + `draftMode: DraftMode` discriminator column on all six cost tables (3 live + 3 draft). The PK tuples extend to include `draftMode`; row absence means "not configured for that draft mode." This is a clean-break migration: no backward-compat bridging, single `--delete-data` publish, post-publish reseed.

All architectural decisions are locked in CONTEXT.md. Research scope is: (1) verify exact current code at each change site so plans carry accurate line references; (2) specify precise before/after patterns for every file category; (3) enumerate every change site in the correct dependency order; (4) identify execution pitfalls specific to this migration.

The composite PK no-op finding (live-probed 2026-04-14, documented in the spacetimedb skill) is the primary constraint on the HsrSynergyCost approach — `id` PK is kept, uniqueness is enforced by reducer discipline + btree `by_tuple` index, never by `table({ primaryKey: [...] })`.

**Primary recommendation:** Execute in four plans: schema+reducers+publish → seed+data+templates → harness rewrite → test file rewrites. Each plan ends with a verifiable state (compile-clean, seed-green, harness-green, full suite green).

## Common Pitfalls

### Pitfall 1: Forgetting draftMode in the admin_bulk_upsert tuple match
**What goes wrong:** The new existence check in `admin.ts` must match on 4-tuple `(characterName, gameMode, draftMode, costSetId)` for char/lc and 5-tuple for synergy. If `draftMode` is omitted from the match, a Classic and Auction row for the same character+mode+costSetId will collide and one will silently overwrite the other.
**Why it happens:** Current code (L499-506 for HsrCharacterCost) matches `characterName`, `gameMode.tag`, and `costSetId` — no `draftMode`. Adding the column without updating the match is an easy miss.
**How to avoid:** Use the btree `by_character_mode_and_set` index (which will gain `draftMode` as its 4th column in D-01) and `.filter([characterName, gameMode, draftMode, costSetId])`. No iter() fallback needed after the index is extended.
**Warning signs:** Tests show only one row per character+mode instead of two (one Classic, one Auction) after seeding.

### Pitfall 2: Leaving auctionBaseBid key access in draftAuction.ts
**What goes wrong:** `draftAuction.ts:60-61` currently reads `costRow.auctionBaseBid[eidolonKey]`. After restructure the column doesn't exist — TS compile error. But if the `as any` cast is in place from the old code, this becomes a silent runtime `undefined` → `NaN` cost.
**Why it happens:** The fix requires two changes in the same function: add `draftMode.tag === 'Auction'` filter AND replace `auctionBaseBid` with `costs`.
**How to avoid:** Replace the full `getCharacterBaseCost` function in `draftAuction.ts` — don't patch it in pieces. Pattern becomes: filter by both `gameMode.tag` and `draftMode.tag === 'Auction'`, then read `costRow.costs[eidolonKey]`.
**Warning signs:** Auction draft costs are all 0 or NaN in post-publish testing.

### Pitfall 3: Zero-padding in the new seed pipeline
**What goes wrong:** The old seed (`scripts/seed-data.ts:L220-221`) emits `classicCosts: classicCosts ?? ZERO_EIDOLON` and `auctionBaseBid: auctionBaseBid ?? ZERO_EIDOLON` — both columns always written, zero-padded when absent. After restructure, "absent sub-block = no row" (D-14). If the zero-pad branch is carried forward, auction rows appear for every character even when only classic is configured.
**Why it happens:** Both seed files have the `ZERO_EIDOLON` / `ZERO_SUPERPOSITION` constants and use `?? ZERO_*` fallbacks for the classic→auction copy that 15.1 explicitly removed. They'll need to be deleted or retargeted.
**How to avoid:** The new fan-out emits one row per present sub-block: if `modeBlock.classic` exists → emit a row with `draftMode: 'Classic'`; if `modeBlock.auction` exists → emit a row with `draftMode: 'Auction'`. No `?? ZERO_*` fallback. Rows with absent sub-blocks are skipped entirely.
**Warning signs:** Seed emits 6 rows per character per cost set (3 modes × 2 draft modes) even for classic-only characters.

### Pitfall 4: Stale module_bindings in frontend after publish
**What goes wrong:** After `spacetime publish` + `spacetime generate`, the old `classicCosts` / `auctionBaseBid` accessors vanish from `src/module_bindings/types.ts`. Any frontend file still referencing them produces TS errors. The fix-to-compile pass (D-26) must happen AFTER regen, not before.
**Why it happens:** It's tempting to fix frontend files first to "pre-adapt" them. But `DataHelpers.ts:toEidolonCost` reads `sheet.classicCosts` and `sheet.auctionBaseBid` — after regen those fields don't exist on the type. Pre-adapting before regen produces a different set of errors.
**How to avoid:** Order is: publish → generate → fix-to-compile. Run `npm run build` after fix-to-compile to validate zero TS errors.
**Warning signs:** TS errors in `components/features/` referencing `classicCosts` or `auctionBaseBid`.

### Pitfall 5: CostSetDraftSynergy PK pattern mismatch
**What goes wrong:** `CostSetDraftSynergy` currently uses `primaryKey: ['costSetId', 'sourceName', 'targetName', 'gameMode']` — a composite `primaryKey` declaration (same pattern as the live tables). This is a no-op (same finding as D-06). After 15.4, `draftMode` must be added to the tuple match. If the planner mirrors the live HsrSynergyCost pattern (add `by_tuple` btree + keep composite PK declaration as decorative) consistently, the behavior is correct.
**Why it happens:** D-09 says to "verify during planning whether it uses autoInc id today or composite PK." Confirmed: `costSetDraftSynergy.ts` uses `primaryKey: ['costSetId', 'sourceName', 'targetName', 'gameMode']` — NO autoInc id. It relies on delete-by-row-object (same `ctx.db.CostSetDraftSynergy.delete(existing)` pattern). The `by_tuple` btree in D-09 needs to cover `[costSetId, sourceName, targetName, gameMode, draftMode]` (5 cols for draft table, which has costSetId first vs synergy's id-keyed live table).
**How to avoid:** Add `by_tuple` with `[costSetId, sourceName, targetName, gameMode, draftMode]` to `CostSetDraftSynergy`. The `edit_draft_synergy_cost` reducer will filter by `costSetId` first (already indexed), then add draftMode to the `.find()` predicate.
**Warning signs:** Duplicate synergy rows inserted when editing a draft twice for the same pair + draftMode.

### Pitfall 6: postDraft.ts lightcone cost lookup uses old btree filter
**What goes wrong:** `postDraft.ts:53-54` currently calls `ctx.db.HsrLightconeCost.by_lightcone_mode_and_set.filter([lightconeName, lobby.gameMode, costSetIdToTry])` — 3-column filter. After D-02, the index extends to 4 columns: `[lightconeName, gameMode, draftMode, costSetId]`. The filter call must pass 4 values: `[lightconeName, lobby.gameMode, { tag: 'Classic', value: {} }, costSetIdToTry]`.
**Why it happens:** Multi-column btree `.filter([v1, v2, v3])` maps positionally. Passing 3 values to a 4-column index is likely an API error or silently returns wrong results.
**How to avoid:** Update both the primary and fallback `filter()` call in `postDraft.ts` to pass all 4 positional values. The `classicCosts` field access on line 55-57 must also change to `costs`.
**Warning signs:** Lightcone costs always 0 in post-draft equip phase.

### Pitfall 7: publish_cost_set tuple match misses draftMode
**What goes wrong:** `costSetManagement.ts:351-355` (publish phase A for chars) finds `existingLive` by `characterName` + `gameMode.tag` — no `draftMode`. After restructure, the same character+mode+costSetId can have BOTH a Classic and an Auction live row. The find will match the wrong one (or neither) if draftMode is not included in the predicate.
**Why it happens:** The current code predates draftMode; the 3-field match was sufficient when each (char, mode, costSetId) had exactly one row.
**How to avoid:** All three publish phases (A=chars, B=lcs, C=synergy) must extend their `existingLive` find predicates to include `r.draftMode.tag === draft.draftMode.tag`. Phase C (synergy) already needs this even without the rename because new auction rows will appear for the first time.
**Warning signs:** Only 1 live row per character+mode after publish (expected 2: one Classic, one Auction).

### Pitfall 8: gitignored data files committed via add -A
**What goes wrong:** `test/data/*.json` is gitignored. Plan B rewrites these files locally (they must exist for tests to pass after harness rewrite). A `git add -A` during Plan B commit would include them.
**Why it happens:** The re-migration of `pairing_table.json`, `characters_table.json`, `lightcones_table.json` produces local file changes that tools like `git status` will show as untracked/modified.
**How to avoid:** Per CLAUDE.md Gitignore Guardrail — never `git add -f`, never include `test/data/` in `files_modified` frontmatter. Data files are described as "user runs migration locally" and are NOT committed. Plan B's committed files are `scripts/seed-data.ts`, `test/data-templates/pairing_template.json`, and `test/data-templates/README.md` only.
**Warning signs:** `git status` shows `test/data/*.json` as staged.
