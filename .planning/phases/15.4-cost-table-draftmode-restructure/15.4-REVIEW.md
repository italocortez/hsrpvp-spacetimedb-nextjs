# Phase 15.4: Code Review Report

**Reviewed:** 2026-04-14
**Depth:** standard
**Files Reviewed:** 32
**Status:** issues_found

## Summary

Phase 15.4 restructures 6 cost tables from parallel `classicCosts` + `auctionBaseBid` columns to a unified `costs` struct plus a `draftMode` discriminator. The reducer layer, schema, indexes, seed scripts, and frontend fix-to-compile changes are internally consistent and faithfully implement the documented design. The documented A2_FALLBACK_ITER pattern is applied consistently across `admin.ts`, `costSetManagement.ts`, and `postDraft.ts` — not flagged per phase context.

No critical bugs, security vulnerabilities, or broken reducer flows were found. The findings below are genuine data-correctness concerns (not documented deviations), a duplicate-code concern in `seed-data.ts`/`test/shared/seed-data.ts`, and several smaller quality items. The D-26 fix-to-compile scope and D-31 Classic filter were respected and are not flagged.

## Warnings

### WR-01: `mapToLightconeData` silently drops gameMode axis, producing non-deterministic last-wins cost

**File:** `components/features/game-data/components/DataHelpers.ts:40-66`

**Issue:** `getLightconeCost` aggregates across all `(gameMode, draftMode)` combinations for a given `lightconeName` and writes into a 2-key `{ Classic, Auction }` sheet, so the last row iterated for each draftMode wins and silently overwrites the others. Post-15.4 the live table fans out to up to 3 gameModes × 2 draftModes = 6 rows per lightcone; this code collapses all of them.

Row iteration order from SpacetimeDB is not guaranteed, so which gameMode's values end up in the returned `LightconeCost` is effectively nondeterministic between runs / between clients. The inline comment acknowledges the gameMode axis is lost but frames it as acceptable; "last-row-wins across gameMode" is not a stable contract and can produce different UI numbers for the same lightcone on different clients. This is strictly worse than pre-15.4 where there was only one row per `(name, gameMode)` and the reader also had no gameMode axis — at least that was deterministic.

**Fix:** Either (a) key the returned `LightconeCost` by gameMode (same pattern as `getCharacterCost`), or (b) pick one canonical gameMode (e.g. `MemoryOfChaos`) explicitly and document. If the consumers truly cannot take a gameMode today, pick one deterministically so results are reproducible:
```ts
// Option (b) — deterministic collapse
const CANONICAL_MODE = 'MemoryOfChaos';
for (const row of lcCosts) {
    if (row.gameMode.tag !== CANONICAL_MODE) continue;
    const draftMode = row.draftMode?.tag;
    if (draftMode === 'Classic') sheet.Classic = toCost(row.costs);
    else if (draftMode === 'Auction') sheet.Auction = toCost(row.costs);
}
```
The `useLightconeCostTable` hook (lines 40-49) has the same last-wins-across-gameMode behavior and warrants the same fix.

### WR-02: `timer_expiry_classic` auto-pick ignores `draftMode` filter — allows 0-cost picks when only Auction rows exist

**File:** `spacetimedb/src/reducers/draftClassic.ts:694-703, 749-757`

**Issue:** Both autoRandomPick fallback paths (pick-expiry at :694-699 and ban-expiry at :749-754) build `allChars` by filtering `HsrCharacterCost.cost_set_id.filter(lobby.costSetId)` then matching only on `gameMode.tag`. Post-15.4 a character may have a row with `draftMode='Auction'` but no `draftMode='Classic'` row (row-absence semantic — D-10). In a Classic-mode lobby that character would still appear in `availablePool` and could be auto-picked/auto-banned, and the subsequent `costPaid: 0` line (:726) would lock in a zero cost that doesn't reflect the intended Classic pricing (which is "not configured" = cannot be picked).

By contrast, `pick_character` at :361-367 correctly filters `draftMode.tag === 'Classic'` when reading the cost. The auto-pick available-pool build is inconsistent with that reader.

**Fix:** Add the draftMode filter to both auto-pool builds:
```ts
const allChars = [...new Set(
    costRows
        .filter((r: any) =>
            r.gameMode.tag === lobby.gameMode.tag &&
            r.draftMode.tag === 'Classic'
        )
        .map((r: any) => r.characterName)
)];
```
Apply the same fix at the ban-expiry branch (:749-754). This matches the filter already applied in the normal Classic pick path.

### WR-03: `getAuctionWonCharacters` and `getBannedCharacters` iterate steps from ALL games

**File:** `spacetimedb/src/reducers/draftAuction.ts:12-39`

**Issue:** Both helpers iterate `MatchSessionStep.lobby_id.filter(lobbyId)` without filtering by `gameNumber`. In a best-of-N series (Phase 15 D-14, `session.seriesBestOf > 1`), steps from previous games are not cleared between games — the `gameNumber` column is exactly how they're disambiguated. The current code treats all historical `AuctionSold` and `Ban` steps across all games in the series as "already won" / "already banned" in the current game's auction.

For bestOf=1 this is correct. For bestOf>1, game 2's auction will see every character auctioned in game 1 as unavailable, which is almost certainly not the intended rule. Same issue would also affect any character "already banned" logic that should be per-game rather than per-series.

**Fix:** Filter by `session.currentGameNumber`:
```ts
function getAuctionWonCharacters(ctx: any, lobbyId: number, gameNumber: number): Set<string> {
    const steps = [...ctx.db.MatchSessionStep.lobby_id.filter(lobbyId)]
        .filter((s: any) => s.gameNumber === gameNumber);
    // ... rest unchanged
}
```
Update the two call sites in `nominate_character` to pass `session.currentGameNumber`. `getBannedCharacters` needs the same treatment. Verify intended behavior against the series-scoping contract before fixing — if cross-game persistence of bans/sold is intentional, document it in `docs/match-session/contract.md`.

### WR-04: `equip_lightcone` inserts MatchSessionStep without `gameNumber`

**File:** `spacetimedb/src/reducers/postDraft.ts:90-104, 176-190, 235-249`

**Issue:** `equip_lightcone`, `arrange_lineup`, and `confirm_lineup` all insert `MatchSessionStep` rows omitting `gameNumber`. Every draft-phase step insertion in `draftClassic.ts` / `draftAuction.ts` sets `gameNumber: session.currentGameNumber`. The Equipping-stage step inserts here do not, so they'll rely on whatever the default / `as any` cast leaves — likely `undefined` or `0`. In a best-of-N series (D-14) these steps become ambiguous: which game's equip/lineup does each belong to?

This is a data-integrity issue for match replay and history queries. The inconsistency also suggests a bug rather than a conscious omission.

**Fix:** Add `gameNumber: session.currentGameNumber` to all three MatchSessionStep inserts in `postDraft.ts` (in `equip_lightcone`, `arrange_lineup`, `confirm_lineup`). Reducers already have `session` in scope. Example:
```ts
ctx.db.MatchSessionStep.insert({
    id: 0,
    lobbyId,
    gameNumber: session.currentGameNumber,   // add this
    sequence: nextSequence,
    ...
```

### IN-02: `admin.ts` HsrCharacterCost/HsrLightconeCost delete+insert drops the composite-PK accessor

**File:** `spacetimedb/src/reducers/admin.ts:517-526, 567-575`

**Issue:** On update, both branches `.delete(existing)` then `.insert(...)` the row. Per architecture doc this is the documented "composite PK upsert pattern", but on `HsrSynergyCost` the same reducer uses `ctx.db.HsrSynergyCost.id.update(...)` directly (:616-620). The inconsistency is justified (synergy has an engine-level autoInc PK; char/lc composite PKs are decorative), but the pattern could benefit from a one-line comment explaining why char/lc must delete+insert and synergy can update in place. There's already a comment at :517, but it only says "(no direct PK accessor for composite delete+insert is fine here)" — which is slightly misleading since the PK columns do exist as fields; it's the engine-level enforcement that's absent (Phase 15.4 D-06).

**Fix:** Replace the inline comment with something like: `// Composite PKs on HsrCharacterCost are decorative (Phase 15.4 D-06); no direct composite-PK update accessor exists, so delete+insert is the only upsert path.`

### IN-03: `draftAuction.pass_bid` ignores `Spectator` winning team — budget deduction silently skipped

**File:** `spacetimedb/src/reducers/draftAuction.ts:465-471, 713-719`

**Issue:** Both the `pass_bid` and `timer_expiry_auction` branches branch on `winningTeam.tag === 'Blue'` / `'Red'` without an `else`. If `session.currentBidTeam` is somehow `Spectator` (the initial default set by `start_draft` and the reset value in this same reducer at :507, :547, :748), the budget math is silently skipped and `blueCharactersWon` / `redCharactersWon` stay at their pre-step values — but the `AuctionSold` step is still inserted with `winningTeam: { tag: 'Spectator', ... }`.

The earlier validation at :260 (`if (!session.currentNomination)`) should prevent this because nomination always sets `currentBidTeam` to Blue or Red. But the defense is only one layer deep. A defensive `else throw new SenderError(...)` or at least a `console.error` would make the invariant explicit.

**Fix:** At line 465 (and 713), add an explicit else:
```ts
if (winningTeam.tag === 'Blue') { ... }
else if (winningTeam.tag === 'Red') { ... }
else {
    throw new SenderError(`Unexpected winningTeam tag: ${winningTeam.tag}. Auction state corrupted.`);
}
```

### IN-04: `getNextSequence` spreads filter into array just to compute max

**File:** `spacetimedb/src/reducers/draftAuction.ts:67-71`, and similar idiom in `draftClassic.ts:86-87`, `postDraft.ts:84-87, 170-173, 229-232`

**Issue:** Same pattern repeated: `const steps = [...ctx.db.MatchSessionStep.lobby_id.filter(lobbyId)]; Math.max(...steps.map((s: any) => s.sequence))`. Performance-wise this is fine (not in scope for v1 per review scope), but the idiom is duplicated 5+ times and always does the same thing: compute "next sequence number in this lobby." A shared helper `getNextSequence(ctx, lobbyId)` would dedupe. Not urgent.

**Fix:** Extract to `helpers/matchSessionStepHelpers.ts`:
```ts
export function getNextSequence(ctx: any, lobbyId: number): number {
    let max = -1;
    for (const s of ctx.db.MatchSessionStep.lobby_id.filter(lobbyId)) {
        if (s.sequence > max) max = s.sequence;
    }
    return max + 1;
}
```
This also avoids materializing the full array just to find a max.

### IN-05: `GameDataProvider` `isReady` misses cost-table readiness

**File:** `components/features/game-data/components/GameDataProvider.tsx:91`

**Issue:** `isReady: !!characterRows && !!lightconeRows` — doesn't include `characterCostRows`, `lightconeCostRows`, or `synergyCostRows`. Components reading `isReady` then immediately accessing `characterCosts` / `synergyCosts` could see stale/empty arrays on first render even when `isReady === true`. This is a pre-existing condition that Phase 15.4 didn't introduce, but is worth noting since the restructure increases reliance on the three cost tables for UI rendering (draftMode filtering in `useCharacterCostTable`, `SynergyDisplay` filter, etc.).

**Fix:** Extend the check:
```ts
isReady: !!characterRows && !!lightconeRows
       && !!characterCostRows && !!lightconeCostRows && !!synergyCostRows
```
