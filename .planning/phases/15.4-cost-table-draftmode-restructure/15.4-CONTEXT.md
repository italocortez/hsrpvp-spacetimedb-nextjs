# Phase 15.4: Cost-table draftMode restructure - Context

**Gathered:** 2026-04-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the parallel `classicCosts` + `auctionBaseBid` column design on `HsrCharacterCost` / `HsrLightconeCost` (and their `CostSetDraft*` counterparts) with a single `costs` struct column + a `draftMode: DraftMode` discriminator column. Add `draftMode` to `HsrSynergyCost` and `CostSetDraftSynergy`, introducing first-ever synergy auction support. Extend PK tuples to include `draftMode`. One row = one `(name, gameMode, draftMode, costSetId)` combination. Row absence = "not configured for that draft mode".

Must land before Phase 16 (global subscriptions) and Phase 17 (cost-tables frontend) so downstream code is written once against the clean shape.

**In scope:** 6 tables (3 live + 3 draft), 6 reducers (admin bulk upsert + 3 draft-edit + create_cost_set + publish_cost_set), 3 readers (draftClassic, draftAuction, postDraft), both seed pipelines, template + data files for all three domains (char / lc / pairing), module bindings regen, architecture doc updates, minimal frontend fix-to-compile across ~10 files.

**Not in scope (already deferred):** synergy half-assignment math + broadcast, lobby-creation cost-set coverage validation, CostSetDraft* consolidation review.

</domain>

<decisions>
## Implementation Decisions

### Schema — column shape

- **D-01:** `HsrCharacterCost` drops `classicCosts` + `auctionBaseBid`; adds `costs: EidolonCost` + `draftMode: DraftMode`. PK tuple becomes `(characterName, gameMode, draftMode, costSetId)`.
- **D-02:** `HsrLightconeCost` mirrors D-01 with `SuperimpositionCost`. PK tuple becomes `(lightconeName, gameMode, draftMode, costSetId)`.
- **D-03:** `HsrSynergyCost` keeps `costModifier: f32`; adds `draftMode: DraftMode`. Tuple match becomes `(sourceName, targetName, gameMode, draftMode, costSetId)`. Synergy auction rows are created as rows with `draftMode=Auction` — first-ever synergy auction support, no legacy migration.
- **D-04:** `CostSetDraftCharacter` / `CostSetDraftLightcone` / `CostSetDraftSynergy` mirror D-01/D-02/D-03 respectively.
- **D-05:** Reuse the existing `DraftMode` enum at `spacetimedb/src/types/enums.ts:44` (declared during Phase 15 for draft-mode flags). No new enum.

### Synergy PK strategy (live-probed)

- **D-06:** `HsrSynergyCost` **keeps its `id: t.u32().primaryKey().autoInc()` column**. It is the only engine-enforced unique constraint on the table and the cursor used by `admin.ts:241-244` delete_row and update paths. The composite tuple is NOT declared via `table({ primaryKey: [...] })` because live probe (pk_test experiment, 2026-04-14) proved that declaration is a no-op in v2.1.0 — it generates no unique constraint and no index. Uniqueness on the 5-tuple is enforced by reducer discipline (tuple-match-before-insert), identical to char/LC today.
- **D-07:** Add a 5-column btree index `by_tuple` on `[sourceName, targetName, gameMode, draftMode, costSetId]` for fast exact-tuple lookup. Replaces the current O(n) `[...iter()]` tuple match at `admin.ts:595` with an O(log n) filter.
- **D-08:** Extend the existing `source_mode` btree on `HsrSynergyCost` to include `draftMode` as the third column: `[sourceName, gameMode, draftMode]`. Rename if clarity demands (e.g., `source_mode_draft`). The `target_name` and `cost_set_id` btrees stay unchanged.
- **D-09:** `CostSetDraftSynergy` follows the same pattern — keep `id` PK (if present) + 5-col `by_tuple` btree. (Verify during planning whether it uses autoInc id today or composite PK; mirror the HsrSynergyCost approach either way.)

### Reader behavior on row absence

- **D-10:** Draft reducer readers (`draftClassic.ts:getCharacterBaseCost`, `draftAuction.ts:getCharacterBaseCost`, `postDraft.ts` lightcone lookup) return **0** when no row matches the `(name, mode, draftMode, costSetId)` tuple. Preserves the existing `?? 0` / `if (!costRow) return 0` pattern established in Phase 15.1 D-15. Rationale: lobby-creation coverage validation is in a separate deferred todo; fail-fast in the reader would crash every auction draft using a classic-only cost set until that todo lands.
- **D-11:** Reader filter changes: `draftClassic.getCharacterBaseCost` filters by `draftMode.tag === 'Classic'`; `draftAuction.getCharacterBaseCost` filters by `draftMode.tag === 'Auction'` and **removes the `auctionBaseBid` key access** (the column no longer exists). `postDraft.ts` lightcone cost lookup filters by `draftMode.tag === 'Classic'` (equip happens in the classic draft context).

### Template + seed — pairing extends to sibling-block shape

- **D-12:** `pairing_template.json` extends to the `{ classic?, auction? }` sibling-block shape, parallel to the 15.1 D-01 shape for char/LC. The pairing entry's `cost.<mode>` block becomes `{ classic: { modifier: f32 }, auction: { modifier: f32 } }` with both sub-blocks optional.
- **D-13:** `test/data/pairing_table.json` re-migrated to the new shape. Existing 30 classic values preserved. Every mode block emits an explicit `auction: { modifier: 0 }` sub-block so the seed produces 30 classic + 30 zero-valued auction synergy rows (60 total on default seed). This is the first seeded synergy auction data in project history.
- **D-14:** Seed fan-out rules from Phase 15.1 D-09/D-10 apply uniformly to all three domains (char / lc / pairing): a sub-block present in the template → that row is written; both sub-blocks absent → no row for that mode; one absent → no row for that sub-block's draft mode (NOT zero-padded, because absence now means "not configured" and has its own row-level representation).
- **D-15:** The README transform tables at `test/data-templates/README.md` are rewritten for all three domains (char / lc / pairing) to reflect the new row fan-out: one template sub-block = one DB row.

### Reducer signatures — single costsJson + draftModeTag

- **D-16:** `edit_draft_character_cost` signature becomes `{ costSetId: u32, characterName: string, gameModeTag: string, draftModeTag: string, costsJson: string }`. The JSON parses to an `EidolonCost` struct. One call = one row. Editing classic + auction for a character = two calls. This mirrors the 15.1 template shape 1:1 (one sub-block = one row = one reducer call).
- **D-17:** `edit_draft_lightcone_cost` mirrors D-16 with `SuperimpositionCost` semantics: `{ costSetId, lightconeName, gameModeTag, draftModeTag, costsJson }`.
- **D-18:** `edit_draft_synergy_cost` signature becomes `{ costSetId: u32, sourceName: string, targetName: string, gameModeTag: string, draftModeTag: string, costModifier: f32 }`. No JSON shape needed because synergy's payload is a single f32.
- **D-19:** `admin_bulk_upsert` row shape becomes one row per `(name, gameMode, draftMode, costSetId)` combination. Rewrites the `HsrCharacterCost` / `HsrLightconeCost` / `HsrSynergyCost` cases at `admin.ts:487-624`. Tuple match uses the new 4-tuple (char/lc) or 5-tuple (synergy) via the respective multi-col btree indexes. No zero-padding branch — absent row = not configured, per D-14.
- **D-20:** `create_cost_set` clone logic: each source draft row's `draftMode` carries through unchanged. Filter-by-costSetId still works (existing `cost_set_id` btree covers all three draft tables).
- **D-21:** `publish_cost_set` copy logic: draft → live row shape is identical post-restructure, so the copy is a direct struct map. No transformation needed between shapes.

### Migration + cutover

- **D-22:** Single publish with `spacetime publish --delete-data=always` (or `--delete-data=on-conflict`) performs the cutover — no incremental/backward-compat bridging code. Establishes the same local reset pattern as Phase 15.1. After publish, `post-publish.ts` seeds from the rewritten `test/data/*.json` files through the unchanged-interface `admin_bulk_upsert` router (with the internal D-19 row-shape update).
- **D-23:** The probe artifacts from the composite-PK experiment (`spacetimedb/src/tables/pkTest.ts`, `spacetimedb/src/reducers/pkTest.ts`, `pk_test` table on maincloud) are removed as part of this phase's publish — the `--delete-data` flag fires because of the real schema changes, and removing the PkTest source files makes the migration plan drop `pk_test` in the same step. Delete the probe tables/reducers source files; keep `tmp/test-composite-pk.ts` as a documented reference script (already noted in `memory/reference_composite_pk_decorative.md`).

<specifics>
## Specific Ideas

- **User's PK-safety intuition was correct.** When presented with a "composite unique constraint" option in discussion, the user asked to verify whether it would actually work. The live probe (published `PkTest` table with `primaryKey: ['a', 'b']`, inserted duplicate `(x, y, 1)` and `(x, y, 2)`) confirmed both rows persisted with no constraint in the generated bindings. This drove D-06 and established a durable pattern: for future schema decisions, grep `src/module_bindings/index.ts` for the `constraints: [...]` array to see what the engine actually enforces.
- **User preference: template shape dictates reducer shape.** When evaluating Option A vs Option B for reducer args, the user redirected to "what makes sense according to the templates?" — locking Option A because 15.1 templates already express classic/auction as separate optional sub-blocks. One sub-block = one row = one reducer call is the honest mapping. This is a carryover principle worth applying to future reducer signature decisions when a template layer exists.
- **Synergy auction is first-class from this phase onward.** D-03 + D-13 introduce 30 zero-valued synergy auction rows into the default seed even though `draftAuction.ts` doesn't yet read synergy costs (that's the separate `synergy-half-assignment-math-and-broadcast` deferred todo). The row shape lands now so downstream phases have a populated column to query against; values get tuned later.
- **Minimal frontend churn.** D-26's "make TS compile, no structural refactor" is a deliberate scope limit. Phase 17 is named "Cost tables — data" specifically because it's the phase that writes the cost-tables frontend against the clean shape. Doing that work in 15.4 would balloon the blast radius and delay the schema foundation.
