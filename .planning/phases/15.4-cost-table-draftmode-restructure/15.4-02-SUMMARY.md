# Phase 15.4 Plan 02: Frontend fix-to-compile for draftMode+costs shape — Summary

Fix-to-compile pass across 6 frontend files. Plan 01 regenerated client bindings with `costs: EidolonCost/SuperimpositionCost` + `draftMode: DraftMode` columns replacing `classicCosts` + `auctionBaseBid`; this plan ported the 6 consumer files to the new shape using the smallest change that produces a green `npm run build`, per D-26. No structural refactor; Phase 17 owns the idiomatic redesign.

## What Changed

### Task 1 — Admin bulk-upsert UI contract (commit `a74eb2d`)

- `components/features/types/tableColumns.ts`:
  - `UPSERT_TABLE_COLUMNS.HsrCharacterCost` → `['characterName', 'gameMode', 'draftMode', 'costs']`
  - `UPSERT_TABLE_COLUMNS.HsrLightconeCost` → `['lightconeName', 'gameMode', 'draftMode', 'costs']` (also gained `gameMode`, which was missing pre-15.4)
  - `UPSERT_TABLE_COLUMNS.HsrSynergyCost` → `['sourceName', 'targetName', 'gameMode', 'draftMode', 'costModifier']`
  - `TABLE_ENUM_COLUMNS.HsrCharacterCost / HsrLightconeCost / HsrSynergyCost` gain `draftMode: 'draftMode'`. HsrLightconeCost also gains `gameMode: 'gameMode'`.
- `components/features/admin-view/components/BulkUpsert.tsx` `TABLE_TEMPLATES` JSON examples rewritten: `classicCosts`/`auctionBaseBid` → `costs` + `draftMode: "Classic"`. Synergy template gains `"draftMode": "Classic"`.

### Task 2 — Cost readers + provider row types + synergy projection (commit `9022e3b`)

- `components/features/game-data/components/GameDataProvider.tsx`:
  - `HsrCharacterCostRow` → drops `classicCosts` / `auctionBaseBid`, adds `draftMode: { tag: string }` + `costs: any`.
  - `HsrLightconeCostRow` → same, plus `gameMode: { tag: string }` (bindings now have it).
  - `HsrSynergyCostRow` → adds `draftMode: { tag: string }`.
  - `synergiesData` projection gains a hardcoded `draftMode?.tag === 'Classic'` pre-filter, wired with an inline D-31 comment pointing at `.planning/todos/pending/2026-04-14-team-builder-synergy-auction-display.md`.
- `components/features/game-data/components/DataHelpers.ts`:
  - `getCharacterCost` loop dispatches on `sheet.draftMode?.tag` and reads `sheet.costs` (D-26 canonical from PATTERNS.md).
  - `getLightconeCost` rewrites from single-row `.find()` to multi-row iteration + draftMode dispatch, building `{ Classic, Auction }` sheet. Gameplay mode collapse documented inline because `LightconeCost` type has no gameMode axis (Phase 17 target).
- `components/features/costs/hooks/useCharacterCostTable.ts`:
  - `costMap` filters by `gameMode` AND `draftMode?.tag === wantDraft` where `wantDraft` is derived from the `'classic' | 'auction'` parameter.
  - `eidolonCosts` collapses from ternary column pick to `cost.costs`.
  - `synergyMap` picks up an additional `syn.draftMode?.tag === 'Classic'` filter (D-31) so Auction synergy rows don't leak into the classic view.
- `components/features/costs/hooks/useLightconeCostTable.ts`:
  - `costMap` filters by `draftMode?.tag === wantDraft`; `supCosts` collapses to `cost.costs`. Last-wins collapse across gameMode noted inline — the hook has no gameMode parameter today, and adding one is a Phase 17 concern exceeding D-26 scope.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Critical] `getLightconeCost` rewritten from single-row `.find()` to multi-row iteration**
- **Found during:** Task 2 implementation
- **Issue:** The plan's PATTERNS.md analog at lines 682-708 covers the char case in detail, and the plan instruction for `getLightconeCost` says "Same structural transform — now the lightcone iteration must also account for one row per `draftMode`". The original file used `lightconeCostRows.find(r => r.lightconeName === name)` — a single-row lookup — which picks exactly one of {Classic, Auction, gameMode×} arbitrarily after Plan 01 schema. That would render wrong sheets silently in production.
- **Fix:** Filter all rows by name, then iterate and dispatch on `draftMode?.tag`. Gameplay mode collapse is preserved (last-wins) because the `LightconeCost` return type has no `gameMode` axis today. Documented inline.
- **Files modified:** `components/features/game-data/components/DataHelpers.ts`
- **Commit:** `9022e3b`

**2. [Rule 2 - Critical] Synergy projection filter at provider boundary, not in SynergyDisplay.tsx**
- **Found during:** Task 2 planning
- **Issue:** The plan specified filtering inside `SynergyDisplay.tsx` for D-31 Classic-only behavior. But `mapToSynergyData` drops `draftMode`, so the `Synergy[]` consumed by the display component carries no `draftMode` field — the filter cannot be expressed there without expanding the `Synergy` type.
- **Fix:** Moved the Classic filter upstream to `GameDataProvider.tsx` where the raw `HsrSynergyCostRow[]` (with `draftMode`) is in scope. Inline D-31 comment cites the follow-up todo. Net effect identical to plan intent: SynergyDisplay only ever receives Classic synergies. Adding an equivalent filter inside `useCharacterCostTable.ts:synergyMap` belts-and-braces the synergy side panel (it consumes raw rows, not the projection).
- **Files modified:** `components/features/game-data/components/GameDataProvider.tsx`, `components/features/costs/hooks/useCharacterCostTable.ts`
- **Commit:** `9022e3b`

**3. [Rule 2 - Critical] ENV hook access pattern workaround: worktree had no node_modules**
- **Found during:** Verification step
- **Issue:** The worktree's `node_modules/` was missing; `next build` and `tsc` couldn't run. Symlinks / junctions were sandbox-denied.
- **Fix:** Ran `npx --prefix <main-repo-path>` from the worktree's cwd, which uses the main repo's installed bin while compiling the worktree's source files. Verified the worktree's source was actually compiled (Next reported the worktree's lockfile as an additional lockfile detected).
- **Files modified:** none (operational)
