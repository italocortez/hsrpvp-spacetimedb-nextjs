# Phase 12.2: SDK Upgrade Audit (2.0.3 -> 2.1.0) - Research

**Researched:** 2026-04-09
**Domain:** SpacetimeDB SDK upgrade audit, view export migration, frontend auth rework, confirmed reads
**Confidence:** HIGH

## Summary

Phase 12.2 is an audit-and-migration phase with four workstreams: (1) export all 31 unexported views so they register in `st_view` and generate typed client bindings, (2) rework the frontend auth flow (`useAuth.ts`) to read from typed `conn.db.view_my_profile` instead of `conn.db.User`, (3) disable confirmed reads (new 2.1.0 default), and (4) add `_then()` error callbacks to reducer calls touched during the auth refactor.

The riskiest change is the auth flow rework. Currently `readProfileFromConnection` uses `conn.db.User.id.find()` and `conn.db.User.username.find()` for 3-strategy profile resolution. Views have no PK/unique indexes on the client -- only `.iter()` -- so the resolution must switch to reading the single row from `conn.db.view_my_profile.iter()`. The 3-fallback strategy that resolves from the User table must remain (it covers connection recovery paths), but private fields (discordId, discordUsername) now come from the view instead of being undefined.

The view export migration is mechanical but large-scoped. The exploration commit (20ffbd3) proved the full pipeline: `export const view_xxx = spacetimedb.view(...)` in source, re-export from `index.ts`, publish, generate bindings, verify `conn.db.view_xxx` accessible. After all 32 views appear in `tablesSchema`, `subscribeToAllTables()` (used by the test harness) will automatically subscribe to them all.

**Primary recommendation:** Execute view export first (mechanical, low risk), then binding regeneration (automated), then auth rework (highest risk), then confirmed reads + error handling (trivial). Run the full test suite after the backend publish to catch any SDK 2.1.0 regressions before touching frontend code.

### Pattern 2: Client-Side View Access After Export

**What:** After export and `spacetime generate`, views appear in `tablesSchema` alongside tables. Client accesses them via `conn.db.view_xxx` with standard table accessors. [VERIFIED: src/module_bindings/index.ts line 1009-1015, view_my_profile_table.ts]

**Key difference from tables:** Views have NO indexes or unique constraints in generated bindings. The generated `view_xxx_table.ts` file defines only the row schema. Available client-side methods: `.iter()`, `.count()`, `.onInsert()`, `.onUpdate()`, `.onDelete()`, `.removeOnInsert()`, `.removeOnUpdate()`, `.removeOnDelete()`. NO `.id.find()` or `.username.find()`. [VERIFIED: src/module_bindings/view_my_profile_table.ts has zero indexes/constraints; src/module_bindings/index.ts line 1011-1014 shows empty indexes and constraints arrays]

**Impact on auth flow:** `readProfileFromConnection` currently uses `conn.db.User.id.find()` and `conn.db.User.username.find()` for profile resolution. After migration, it must use `[...conn.db.view_my_profile.iter()][0]` or equivalent to read the single profile row. The view returns at most one row (the caller's own profile) because it's filtered by `ctx.sender` server-side. [VERIFIED: securityViews.ts line 217-251 shows `t.option(MyProfileRow)` return type]

### Pattern 3: subscribeToAllTables Includes Views

**What:** `subscribeToAllTables()` iterates `remoteModule.tables` which includes ALL entries in `tablesSchema` -- both tables AND views. After all 32 views are in the generated bindings, `subscribeToAllTables()` will auto-subscribe to all of them. [VERIFIED: spacetimedb/node_modules/spacetimedb/src/sdk/subscription_builder_impl.ts lines 142-148]

**Impact on test harness:** The test harness at `test/shared/connection.ts` line 72 calls `subscribeToAllTables()`. After view export + regeneration, it will automatically subscribe to all 32 views. No test harness changes needed for view subscriptions. [VERIFIED: test/shared/connection.ts line 72]

**Impact on production frontend:** The production frontend does NOT use `subscribeToAllTables()` -- it uses selective subscriptions in `useAuth.ts` (3 SQL queries) and `useTable()` in `GameDataProvider.tsx` (5 tables). ### Pattern 4: Auth Profile Resolution Migration

**Current flow (useAuth.ts):**
```typescript
// Lines 27-41: Three separate subscriptions
conn.subscriptionBuilder()
    .onApplied(() => { setProfileReady(true); readProfileFromConnection(conn); })
    .subscribe('SELECT * FROM view_my_profile');
conn.subscriptionBuilder().subscribe('SELECT * FROM view_my_identity');
conn.subscriptionBuilder()
    .onApplied(() => { readProfileFromConnection(conn); })
    .subscribe('SELECT * FROM user');

// Lines 100-134: 3-strategy profile resolution reads from conn.db.User
// Strategy 1: conn.db.User.id.find(Number(cachedId))
// Strategy 2: conn.db.User.username.find(guestUsername)
// Strategy 3: conn.db.User.username.find(sessionName)

// Lines 59-60: Table callbacks on User table

conn.db.User.onUpdate(onUserUpdate);
```
[VERIFIED: components/features/auth/hooks/useAuth.ts]

**After migration (D-06, D-09):**
```typescript
// Subscription: keep SQL subscriptions for now, but use typed view data for reads
// The SQL string 'SELECT * FROM view_my_profile' can be replaced with
// typed binding subscription (conn.subscriptionBuilder().subscribe('SELECT * FROM view_my_profile'))
// since the view is in tablesSchema. The SQL string form still works.

// Profile resolution: read from view instead of User table
const profileRows = [...conn.db.view_my_profile.iter()];
const profile = profileRows[0];  // At most 1 row (filtered by ctx.sender)
if (profile) {
    setResolvedUser({
        id: profile.id,
        username: profile.username,
        displayName: profile.displayName,
        isGuest: profile.isGuest,
        // ... all User fields plus UserPrivate fields
        discordId: profile.discordId,       // NOW POPULATED from view merge
        discordUsername: profile.discordUsername,  // NOW POPULATED from view merge
    });
}

// Fallback: Keep User table subscription + callbacks for the 3-strategy
// resolution fallback (guest username, session name). The view subscription
// may not have data yet during rapid connection/reconnection.
```
[Based on: D-09, D-10 decisions + verified view schema at securityViews.ts line 192-215]

**Critical subtlety:** The `view_my_profile` subscription populates `conn.db.view_my_profile` -- a SEPARATE accessor from `conn.db.User`. The User table subscription populates `conn.db.User`. The auth hook currently subscribes to both. After migration, the primary data source shifts to `conn.db.view_my_profile` for the current user's data (including private fields), but `conn.db.User` remains useful for the 3-strategy fallback resolution (which uses PK/username indexes that views don't have). ### Anti-Patterns to Avoid

- **Using `useTable(tables.view_my_profile)` for view data:** Per D-07, do NOT use `useTable` for views. `useTable` creates its own subscription internally. Views should be subscribed via `subscriptionBuilder().subscribe()` and read via `conn.db.view_xxx`. [CITED: CONTEXT.md D-07; SKILL.md line 194]
- **Assuming view accessors have PK indexes:** View bindings generate with empty indexes/constraints arrays. Using `.id.find()` on a view accessor will not work. Use `.iter()`. [VERIFIED: view_my_profile_table.ts]
- **Mixing `subscribeToAllTables` and `subscribe` on the same connection:** The SDK explicitly warns against this. The test harness uses `subscribeToAllTables()`; the production frontend uses selective `subscribe()`. Do not mix them. [VERIFIED: subscription_builder_impl.ts lines 134-140]

## Common Pitfalls

### Pitfall 1: View Not Registering After Export
**What goes wrong:** View is `export const`-ed in its source file but not re-exported from `index.ts`. The `[registerExport]` symbol never fires, view is absent from `st_view`, no bindings generated.
**Why it happens:** The SpacetimeDB bundler walks module exports starting from `index.ts`. A re-export chain must exist from `index.ts` -> source file -> view constant.
**How to avoid:** After adding `export const` to all views, add matching re-exports in `index.ts`. Verify with `spacetime sql "SELECT name FROM st_view"` after publish.
**Warning signs:** `spacetime generate` produces no `view_xxx_table.ts` file; `conn.db.view_xxx` is undefined at runtime.
[VERIFIED: SKILL.md line 194; exploration commit 20ffbd3 proved this]

### Pitfall 2: Using `.find()` on View Accessors
**What goes wrong:** Code tries `conn.db.view_my_profile.id.find(userId)` and gets a runtime error because views have no indexes.
**Why it happens:** Tables generate with PK/unique/btree indexes in `tablesSchema`. Views generate with empty indexes/constraints. The accessor API is different.
**How to avoid:** Use `.iter()` for views. `[...conn.db.view_my_profile.iter()][0]` gets the single profile row.
**Warning signs:** TypeScript errors about `.id` not existing on the view accessor; runtime `Cannot read properties of undefined` errors.
[VERIFIED: view_my_profile_table.ts has zero indexes; module_bindings/index.ts lines 1011-1014]

### Pitfall 3: Subscription Data Race on Profile Resolution
**What goes wrong:** `readProfileFromConnection` runs before `conn.db.view_my_profile` data arrives, reads empty iter(), concludes no user found, shows LOGIN.
**Why it happens:** The `onApplied` callback fires for view_my_profile subscription, but the actual data may not be in the client cache yet (combined subscription timing). The User table subscription fires separately.
**How to avoid:** Use the `onApplied` callback on the view_my_profile subscription to gate `setProfileReady(true)`. This is already the current pattern (useAuth.ts line 28-31). The migration must preserve this: `onApplied` -> `readProfileFromConnection` (which now reads from view instead of User table).
**Warning signs:** Intermittent flashes of LOGIN screen on page load; `[useAuth] No user found` log messages that resolve on subsequent renders.
[VERIFIED: useAuth.ts lines 27-31 current pattern]

### Pitfall 4: Confirmed Reads Latency After SDK Upgrade
**What goes wrong:** All reducer calls feel 200ms+ slower after upgrading to v2.1.0.
**Why it happens:** v2.1.0 TypeScript connector defaults confirmed reads to ON (was effectively OFF in v2.0.x). Each transaction must be durably confirmed before the client sees subscription updates.
**How to avoid:** D-11: Add `.withConfirmedReads(false)` to the connection builder in `providers.tsx`.
**Warning signs:** Noticeable lag between clicking a button and seeing the result; 200ms+ round-trip times even on localhost.
[VERIFIED: how-to-guides.md lines 110-130; PR #4682]

### Pitfall 5: Breaking the 3-Fallback Profile Resolution
**What goes wrong:** During migration, developer collapses the 3-strategy resolution into a single view-based lookup, breaking reconnection for returning users (cached PK), fresh guests (identity hex), and Discord-linked users (session name).
**Why it happens:** Each strategy covers a different connection recovery path. They look redundant but aren't.
**How to avoid:** CONTEXT.md Phase 12 provenance explicitly states these are NOT redundant. Keep all 3 strategies but retarget them: Strategy 1 reads from view (PK in localStorage -> view iter -> match by id), Strategy 2 reads from User table (guest username -> `conn.db.User.username.find()`), Strategy 3 reads from User table (session name -> `conn.db.User.username.find()`). The User table subscription remains necessary for Strategies 2 and 3.
**Warning signs:** Returning users see LOGIN instead of their profile; guest users fail to resolve after fresh connection.
[VERIFIED: useAuth.ts lines 100-141; CONTEXT.md Phase 12 Architecture Provenance]

### Pitfall 6: anonymousView Export Different From view Export
**What goes wrong:** Developer assumes `spacetimedb.anonymousView()` needs different export syntax than `spacetimedb.view()`.
**Why it happens:** Both `view()` and `anonymousView()` return the same type with `[registerExport]`. The export pattern is identical.
**How to avoid:** Same `export const` pattern for both:
```typescript
export const view_lobby_browser = spacetimedb.anonymousView(...)
export const view_public_accounts = spacetimedb.anonymousView(...)
```
**Warning signs:** None -- this is a misconception pitfall, not a runtime error. Just apply the same pattern.
[VERIFIED: api-guide.md lines 731-738; both types use the same export mechanism]

## Open Questions

1. **view_my_identity typed subscription (D-17)**
   - What we know: After export, `conn.db.view_my_identity` will be a typed accessor. Currently subscribed via SQL string at useAuth.ts:34.
   - What's unclear: Whether the `view_my_identity` subscription is still needed at all after the auth rework. If the profile resolution only reads from `view_my_profile` (which includes userId), the identity mapping may be redundant on the frontend.
   - Recommendation: Keep the subscription for now (it's lightweight -- at most 1 row). Removing it is an optimization for a future phase. If it turns out the frontend never reads from `conn.db.view_my_identity`, it can be dropped.

2. **Table callbacks after view migration**
   - What we know: `conn.db.User.onInsert` and `conn.db.User.onUpdate` are registered for reactive profile updates (useAuth.ts lines 59-61).
   - What's unclear: Whether `conn.db.view_my_profile.onInsert/onUpdate` should replace or supplement `conn.db.User` callbacks. View data changes when the underlying User or UserPrivate tables change, but the timing of view update delivery vs table update delivery is unclear.
   - Recommendation: Register callbacks on BOTH `conn.db.view_my_profile` and `conn.db.User`. The view callback handles the primary path; the User callback handles the fallback strategies. Both call `readProfileFromConnection()`.
