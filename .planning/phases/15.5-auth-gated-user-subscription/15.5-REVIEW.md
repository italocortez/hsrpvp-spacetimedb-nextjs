## Summary

The Phase 15.5 Stage 1/Stage 2 subscription split is architecturally sound. ## Warnings

### WR-01: Signature field list does not match setResolvedUser — `email` and audit columns silently excluded from dedupe

**File:** `components/features/auth/hooks/useAuth.ts:17-31` vs `178-190`

**Issue:** `extractProfileSignature` is documented as needing to include "every field copied into currentUser by setResolvedUser." `setResolvedUser` copies eleven fields from the row. But `view_my_profile` returns additional fields that the server can update — specifically `email`, `isOnline`, `displayedAchievementId`, `createdById`, `createdDate`, `lastModifiedById`, `lastModifiedDate` — that are present on the profile row but absent from both the `User` type and the signature.

The more important direction is the inverse: if any field present in the signature is updated on the server but NOT copied into `currentUser` by `setResolvedUser`, the signature flips and `setResolvedUser` runs, but the state does not actually change — a wasted render. Conversely, if any field copied by `setResolvedUser` is absent from the signature, a server-side update to that field will not flip the signature, so the update is silently dropped. Auditing the actual lists:

- **In `setResolvedUser` but not in signature:** none currently missing — the eleven fields match.
- **In signature but not in `setResolvedUser`:** none — clean.
- **In `MyProfileRow` (server view) but not in `User` type or signature:** `isOnline`, `displayedAchievementId`, `email`, audit columns.

`email` is the near-term risk: it exists in `view_my_profile` (`identityViews.ts:52`), is NOT in the `User` type (`types.ts:11-23`), is NOT in `extractProfileSignature`, and is NOT copied by `setResolvedUser`. If a user's email is updated server-side, `view_my_profile.onUpdate` fires, `readProfileRef.current` is called, the signature does NOT change (email absent), and the update is silently dropped. This is acceptable only if email is intentionally excluded from the frontend `User` type. The concern is that the comment on line 9-13 guarantees a stronger invariant than actually exists, which will mislead future authors.

**Fix:** Either (a) narrow the comment to say "every field in the `User` interface" rather than "every field copied by setResolvedUser", making the contract accurate; or (b) extend `User` to include `email` and add it to both `extractProfileSignature` and `setResolvedUser` if email display is a future need. The actionable minimum is (a):

```typescript
// MUST include every field present in the User interface that setResolvedUser
// copies into currentUser. Fields present in view_my_profile but absent from
// User (email, isOnline, displayedAchievementId, audit columns) are intentionally
// excluded — they are not rendered or depended on by the frontend.
```

### WR-02: NavBar renders two admin gear links — one always-visible, one role-gated

**File:** `components/globals/layout/NavBar.tsx:160-170`

**Issue:** There are two separate `<Link href="/admin-view">` gear icon links rendered adjacently. Lines 160-164 are role-gated (`{isAdmin && ...}`). Lines 167-170 are unconditional — every user sees this second gear link, regardless of role. This is a security UX issue: non-admin users see an admin panel link that will presumably reject them server-side, but the link should not be visible at all. One of these is clearly a duplicate introduced during the refactor.

```tsx
{/* Admin link */}
{isAdmin && (
  <Link href="/admin-view" className={styles.iconButton} title="Admin Panel">   // line 162 — gated: correct
    <GearIcon size={20} color="currentColor" />
  </Link>
)}

{/* Admin panel link */}
<Link href="/admin-view" className={`${styles.iconButton} ${styles.gearButton}`} aria-label="Admin Panel">  // line 168 — ungated: wrong
  <GearIcon size={20} color="currentColor" />
</Link>
```

**Fix:** Remove lines 167-170 (the unconditional link). The role-gated block at lines 160-164 is the correct implementation.

```tsx
{/* Admin link — role-gated */}
{isAdmin && (
  <Link href="/admin-view" className={styles.iconButton} title="Admin Panel">
    <GearIcon size={20} color="currentColor" />
  </Link>
)}
// Delete the unconditional duplicate below it.
```

### WR-03: Modal overlay stays open after guest login succeeds — no auto-close

**File:** `components/globals/layout/NavBar.tsx:188-198`

**Issue:** `loginGuest` is wired as `loginGuest={() => { loginGuest(); }}` — it calls the reducer but does not call `setShowLogin(false)`. The Discord path correctly closes the modal (`loginDiscord={() => { loginDiscord(); setShowLogin(false); }`). The guest path does not. When `guestLoginPending` flips to `true`, the button disables and the spinner shows inside the still-open overlay. When `currentUser` resolves, `isAuthenticated` becomes `true`, which collapses the conditional `{showLogin && !isAuthenticated && ...}`, so the overlay does disappear — but only indirectly through the `isAuthenticated` flip, not through an explicit close.

This means: if the reducer call fails (network error, reducer rejects), `guestLoginPending` returns to `false`, `isAuthenticated` stays `false`, and the modal remains open showing the normal buttons again. That is acceptable UX. However, if the connection drops between `loginAsGuest()` firing and `currentUser` resolving, the overlay persists indefinitely because `isAuthenticated` never flips and no timeout/error path calls `setShowLogin(false)`.

Additionally, there is no `useEffect` that calls `setShowLogin(false)` when `isAuthenticated` transitions from `false` to `true` via a different code path (e.g., page load after a prior guest session is recovered). In that scenario `showLogin` could be `true` while `isAuthenticated` is also `true`, causing the `{showLogin && !isAuthenticated && ...}` guard to suppress the modal — correct behavior — but `showLogin` state is now stale-true, which would immediately reopen the modal if the user logs out.

**Fix:** Add an explicit close call in `loginGuest` inside NavBar, and add a cleanup effect:

```tsx
// In NavBar:
loginGuest={() => { loginGuest(); setShowLogin(false); }}

// And add a guard effect:
useEffect(() => {
  if (isAuthenticated) setShowLogin(false);
}, [isAuthenticated]);
```

### WR-04: Stage 2 effect re-entry risk — `stage2Ref` reset on cleanup runs before re-subscription on fast reconnect

**File:** `components/features/auth/hooks/useAuth.ts:162-168`

**Issue:** The Stage 2 cleanup (line 165) sets `stage2Ref.current = false`. The dep array is `[isActive, stage2Gate, getConnection]`. On a fast reconnect (`isActive` briefly goes `false` then `true`), the cleanup fires and resets the ref, then the effect body re-runs. If `stage2Gate` is still `true`, Stage 2 re-subscribes — which is generally correct. However, if the cleanup runs while the onApplied callback from the previous subscription is still queued in the JS event loop (the WS connection is async), both the old `onApplied` and the new subscription's `onApplied` will call `readProfileRef.current(conn)` on the same connection object.

More concretely: `conn` is captured via `getConnection()` at the time the effect body runs. After a reconnect, `getConnection()` should return a new connection object. However, the old subscription's `onApplied` closure holds the old `conn`. If `conn.db` outlives the WS teardown, the old `onApplied` calling `readProfileRef.current(oldConn)` after reconnect would iterate stale cache — `view_my_profile.iter()` on a disconnected connection. This path would produce a stale-miss, fall through to strategies 1-3, and potentially call `setResolvedUser` with the wrong identity's data.

This is a low-probability race (requires the specific timing of WS reconnect + pending callback), but `stage2Ref` being reset in cleanup without a subscription cancellation API means there is no mechanism to discard the in-flight `onApplied`. The Stage 1 cleanup has the same pattern at lines 103/100-105.

**Fix:** Add a per-subscription cancel flag to guard stale callbacks:

```typescript
// In the Stage 2 effect body, after const conn = getConnection():
let cancelled = false;

conn.subscriptionBuilder()
  .onApplied(() => {
    if (cancelled) return;
    // ... existing onApplied body
  })
  .subscribe('SELECT * FROM user');

return () => {
  cancelled = true;
  conn.db.User.removeOnInsert(onUserInsert);
  conn.db.User.removeOnUpdate(onUserUpdate);
  stage2Ref.current = false;
};
```

Apply the same pattern to Stage 1's `onApplied` closure.

### IN-03: `auth-subscriptions.test.ts` authenticated test asserts harness's own userId present, but harness uses `subscribeToAllTables()` not Stage 2 gate

**File:** `test/backend/auth/auth-subscriptions.test.ts:87-92`

**Issue:** The test at line 73 is titled "Stage 2 delivers User rows" and models the `useAuth` post-auth path. But `createTestHarness` (connection.ts:127) calls `.subscribeToAllTables()`, which subscribes to every table unconditionally — it does not model the gated Stage 2 subscription in `useAuth`. The test therefore validates server-side table accessibility (User table returns rows to authenticated callers) rather than the frontend gate logic (Stage 2 effect only fires when `stage2Gate` is true).

This is not a bug in the gate itself (the gate is tested by the anon test at line 27, which correctly omits the User subscription), but the test name and comment imply it's testing the gate. A future refactor of the gate logic could break the frontend behavior without this test catching it.

**Fix:** Add a comment clarifying the test's actual scope:

```typescript
// NOTE: The harness uses subscribeToAllTables() — this tests server-side row delivery
// to authenticated callers, NOT the useAuth Stage 2 gate logic. Gate logic is covered
// by the anonymous test above (which verifies that NOT subscribing yields an empty cache).
```
