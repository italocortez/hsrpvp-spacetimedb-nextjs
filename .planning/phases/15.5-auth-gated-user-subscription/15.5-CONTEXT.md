# Phase 15.5: Auth-Gated User Subscription - Context

**Gathered:** 2026-04-16 (seed-bootstrapped, refined via /gsd-discuss-phase 15.5 same day)
**Status:** Ready for planning
**Origin:** `.planning/seeds/phase-15.5-auth-gated-user-subscription.md` (planted during Phase 15.2 UAT Test 4)

<domain>
## Phase Boundary

Close the real bandwidth leak that Phase 15.2 UAT Test 4 exposed: `components/features/auth/hooks/useAuth.ts` fires `SELECT * FROM user` unconditionally on connection, pre-auth — streaming the full User directory to every anonymous visitor. Split the `useAuth` subscriptions into a two-stage lifecycle so anonymous visitors receive zero User rows until they explicitly authenticate.

Simultaneously retire the now-dead `view_user_directory` (zero frontend subscribers; SpacetimeDB's `view` vs `anonymousView` does NOT produce caller rejection, so the 15.2 D-06 "auth flip" was cosmetic). Rename `view_public_accounts` to `view_public_hsr_accounts` to make the projection target explicit. Document the "projection view vs subscription gate" pattern in `docs/auth/architecture.md` so future phases don't recreate the leak.

**In scope:**
- `useAuth.ts` two-stage subscription split + new `guestLoginPending` narrow state for spinner UX
- `view_user_directory` full retirement (type + export + bindings + doc references)
- `view_public_accounts` → `view_public_hsr_accounts` rename
- New `docs/auth/architecture.md` "Subscription Lifecycle" section naming gate rules + anonymous-view exceptions
- Harness integration test modeling the Stage 2 gate
- Retire `test/backend/auth/auth-views.test.ts` VIEW-01 placeholders (D-15/D-16 from 15.2 — assert `expect(true).toBe(true)` and document an enforcement model that doesn't exist)

**Out of scope (deferred):**
- Gating `view_lobby_browser` / `view_public_hsr_accounts` behind auth — they're intentional anonymous views (projections do the filtering); gating would regress pre-auth lobby discovery and profile browsing
- `User.public = false` + on-demand read reducers (inherits 15.2 D-01 rejection — adversarial direct `SELECT * FROM user` subscribers still receive rows; 15.5 scopes only "our frontend auto-subscribes only post-auth")
- `useGatedSubscription(sql)` helper hook — YAGNI until a second gated subscription lands
- `GameDataProvider` unconditional subscriptions (static reference data, not user-scoped)
- Phase 16 FOUND-03 re-scope — handoff note only, executed in Phase 16 discuss

</domain>

<decisions>
## Implementation Decisions

### Seed-locked (from `.planning/seeds/phase-15.5-auth-gated-user-subscription.md`)

- **S-01:** `view_user_directory` deleted, not kept. No defense-in-depth value given `User.public=true` and zero client subscribers.
- **S-02:** No new view. `view_my_profile`'s `ctx.sender` filter already provides anonymous-safe access to private data.
- **S-03:** Two-stage subscription pattern in `useAuth.ts`. Stage 1 = `view_my_profile` (always, self-filtering). Stage 2 = `SELECT * FROM user` (gated — exact signals in D-01 below).
- **S-04:** `User.public = true` stays (inherits 15.2 D-01). Adversarial direct-query subscribers are out of scope.
- **S-05:** Test via harness integration modeling our frontend gate, NOT server rejection (server doesn't reject — accepted).

### Stage 2 gate signals (discuss-phase)

- **D-01:** Stage 2 opens when `currentUser != null || hadTokenOnMount.current || hadSessionCookie.current`. Composition matches the existing `isWaitingForData` flag at `useAuth.ts:295`. Rationale: the loading UI already trusts this signal set to decide "is a returning user coming back?" — Stage 2 should open on the same evidence, not a stricter subset. Token/cookie absence still means Stage 2 never fires until `view_my_profile` produces a row. If any of the three signals is stale/revoked, the SpacetimeDB connection itself fails at handshake and `isActive` stays false, so Stage 2 can't fire regardless — defense is layered.

### `view_user_directory` retirement (discuss-phase)

- **D-02:** Delete cleanly. Remove the `UserDirectoryRow` row type, the `view_user_directory` export, the re-export in `spacetimedb/src/index.ts`, regenerate both module bindings (drops `view_user_directory_table.ts` + `ViewUserDirectoryRow` imports), and remove references from `docs/views/{architecture,contract}.md` + `docs/auth/{architecture,contract}.md`. "Preserve as anonymous bookmark" rejected — dead code today with no concrete near-term use case (YAGNI).

### First-time guest login UX (discuss-phase)

- **D-03:** Inline spinner in the Login button, **strictly scoped to the `loginAsGuest`-pending window**. New narrow state (ref or boolean, planner's call) set true in `loginGuest()` callback, cleared when `currentUser` resolves OR the `loginAsGuest` reducer promise rejects. The spinner MUST NOT be driven by `isLoadingData`, `isWaitingForData`, `isConnecting`, or `isLinkingDiscord` — those cover returning-user reconnect, Discord linking, and initial connection flows, and reusing them would bleed the spinner into cases the user explicitly wants it absent from. User constraint quote: *"Inline spinner is fine. We should make sure we don't see that spinner on other cases unless it is absolutely necessary or unavoidable."*

### `view_public_accounts` rename (discuss-phase)

- **D-04:** Rename `view_public_accounts` → `view_public_hsr_accounts`. Keeps the `public` prefix (marks anonymous intent, consistent with `view_lobby_browser`), adds `hsr_` to name the underlying `HsrAccount` table the view projects. Rename touches: `spacetimedb/src/views/identityViews.ts` (declaration), `spacetimedb/src/index.ts` (re-export), both `module_bindings/` index files + generated `view_public_hsr_accounts_table.ts` file, `docs/views/{architecture,contract}.md`, `docs/roster/contract.md`, `docs/FRONTEND-HANDOFF.md`. Phase 10.4 archive docs left untouched (historical).

### Anonymous-view scope (discuss-phase)

- **D-05:** `view_lobby_browser` and `view_public_hsr_accounts` stay `anonymousView` — they're intentional public-projection views. `view_lobby_browser` filters out config details (timers, budgets, penalties) + Finished lobbies server-side; `view_public_hsr_accounts` filters by `isRosterPublic` / `isRatingPublic` user opt-ins. Their gating model is **server-side projection**, not client-side subscription timing. Applying Stage 2 would regress pre-auth lobby discovery and profile browsing. Document this distinction in `docs/auth/architecture.md`'s new "Subscription Lifecycle" section — name the two views as intentional anonymous exceptions and state the rule: any future raw-table or per-user subscription added by frontend code MUST go through the Stage 2 gate.

### Claude's Discretion

- Exact shape of the `useAuth.ts` refactor (two separate `useEffect` hooks with separate refs `stage1Ref`/`stage2Ref`, or one effect with a nested condition) — planner decides. Seed's preference: two separate effects. Anti-pattern: relying on useState for gate (use refs to prevent double-subscribe on re-render).
- Spinner component choice — existing Button component's pending state if one exists, or a small inline `<span aria-busy>` fallback. Designer of the Login button decides at execution time.
- Placement of the `onUserInsert` / `onUserUpdate` table callbacks currently at `useAuth.ts:63-80` — they are recovery-path fallbacks tied to the User subscription and must move into the Stage 2 effect (cannot register on `conn.db.User` before the subscription delivers rows). Planner specifies exact lifecycle.
- Exact wording of `docs/auth/architecture.md` "Subscription Lifecycle" section — researcher + planner draft per template.
- Regen mechanics: single-shot `spacetime generate` after both the retirement and rename land, to avoid churned intermediate bindings.

</decisions>

<code_context>
## Existing Code Insights

### Reusable assets
- **`subscribedRef` pattern** (`useAuth.ts:17, 24, 76-82`) — existing guard against double-subscribe on re-mount. Two-stage split needs two analogous refs (`stage1Ref`, `stage2Ref`) following the same pattern.
- **`readProfileFromConnection`** (`useAuth.ts:113-170`) — already event-driven with 3 fallback strategies (cached id → User.id PK, guest username → User.username index, session name → User.username index). Invoked from both subscription `onApplied` callbacks today. Stage 1/Stage 2 split preserves both invocation paths.
- **`hadTokenOnMount` / `hadSessionCookie` refs** (`useAuth.ts:292-293`) — already compute the "returning user" signal D-01 needs. Zero new infrastructure required.
- **`isWaitingForData` composition** (`useAuth.ts:295`) — already ORs the three signals D-01 specifies. The Stage 2 gate condition is literally this boolean, reusable as-is.
- **Reducer error pattern** (`useAuth.ts:313-315`) — `.catch()` on `conn.reducers.loginAsGuest({})`. The `guestLoginPending` state (D-03) clears in this catch block + in the success path via `currentUser` resolution.

### Established patterns
- **Single `useEffect` per subscription lifecycle with cleanup** — useAuth today has three effects (subscribe, link Discord, soft-delete). Adding a Stage 2 effect keeps this pattern.
- **Refs over state for subscription tracking** — avoids re-render churn and double-subscribe races. D-01 gate condition evaluates refs + a state value (`currentUser`), which re-renders when resolved.
- **SpacetimeDB SDK handles disconnect cleanup** — no manual `.unsubscribe()` in the codebase; subscriptions tear down with the connection. Logout flow (`useAuth.ts:324-329`) clears localStorage + cookie and triggers `signOut()` reload. Stage 2 teardown inherits this.
- **Server-side projection as privacy gate** — `view_lobby_browser` (field exclusion) and `view_public_hsr_accounts` (isRosterPublic filter) both use this. D-05 names it explicitly for the first time in docs.

### Integration points
- `useAuth.ts` is the single source of truth for auth state. No other component calls `subscriptionBuilder()` for `User` or `view_my_profile`. Stage 2 split is local to this hook.
- `GameDataProvider` (static reference data subscriptions) is orthogonal — it subscribes to characters/lightcones/synergies/costs, which are `public: true` reference tables. Not affected by 15.5.
- Phase 16's `providers.tsx` rework (FOUND-03) will relocate subscription ownership; 15.5 lands first to establish the gate pattern it inherits.

</code_context>

<specifics>
## Specific Ideas

- User's explicit constraint on spinner scope (D-03): *"Inline spinner is fine. We should make sure we don't see that spinner on other cases unless it is absolutely necessary or unavoidable."* Translates to: `guestLoginPending && !currentUser` only — nothing else triggers it. No bleed into `isLoadingData`, `isWaitingForData`, `isConnecting`, or `isLinkingDiscord`.
- User's clarifying framing on anon views (Q4 dialogue): the distinction between *projection-based privacy* (view body filters what's returned) and *subscription-based privacy* (gate decides when subscription fires). D-05 documentation must make this split explicit so future phases don't conflate them.
- Rename preference (D-04): kept `public` prefix to signal anonymous intent, paired with table-name fragment `hsr_` for clarity. Sibling naming pattern: `view_lobby_browser` uses `browser` suffix for the same anonymous-projection role.

</specifics>
