## Summary

Phase 15.5 has three moving pieces that must land in sequence: (1) backend cleanup deleting `view_user_directory` and renaming `view_public_accounts`, followed by a single `spacetime generate` regenerating both `spacetimedb/src/module_bindings/` and `src/module_bindings/`; (2) frontend refactor splitting `useAuth.ts`'s single `useEffect` into two separate effects with separate `stage1Ref`/`stage2Ref` refs, plus a new `guestLoginPending` boolean; (3) test updates deleting VIEW-01 placeholder tests and adding a new `auth-subscriptions.test.ts` that models the frontend gate.

The critical implementation insight is that all three signals of D-01's gate condition (`currentUser`, `hadTokenOnMount.current`, `hadSessionCookie.current`) already exist in `useAuth.ts:292-295` as `isWaitingForData`. The Stage 2 effect literally reuses these refs as its gate — zero new infrastructure. The `onUserInsert`/`onUserUpdate` table callbacks at `useAuth.ts:63-80` are the highest-risk relocation: they register against `conn.db.User` and must move into Stage 2's effect to ensure the `SELECT * FROM user` subscription is active before the callbacks fire.

`spacetime generate` is a full regeneration, not a diff tool. When a view export is removed and another is renamed, it wipes and rewrites the entire `module_bindings/` directory. Both bindings dirs (`spacetimedb/src/module_bindings/` and `src/module_bindings/`) must regenerate in sequence. After regen, `view_user_directory_table.ts` will be absent and `view_public_hsr_accounts_table.ts` will appear in its renamed form — the `index.ts` in each dir is fully rewritten to match the current module schema.

**Primary recommendation:** Two separate `useEffect` hooks with `stage1Ref`/`stage2Ref` — matches the existing `subscribedRef` pattern at `useAuth.ts:17,24`, avoids nested conditions, and keeps Stage 1/Stage 2 lifetimes cleanly separated.

### Pattern 1: Two-Stage `useEffect` Split

**What:** Two separate `useEffect` hooks, each with its own `useRef` guard against double-subscribe on re-render or re-mount.

**When to use:** Any time subscription lifecycles have different trigger conditions. Avoids nested conditions in a single effect and keeps cleanup semantics independent.

**Source:** Derived from existing `subscribedRef` pattern at `useAuth.ts:17,21,24,76-82` [VERIFIED: repo].

```typescript
// Source: components/features/auth/hooks/useAuth.ts (existing pattern — stage1Ref mirrors subscribedRef)

const stage1Ref = useRef(false);
const stage2Ref = useRef(false);

// Stage 1: always-on, fires when isActive becomes true
useEffect(() => {
    if (!isActive || stage1Ref.current) return;
    const conn = getConnection();
    if (!conn) return;
    stage1Ref.current = true;

    conn.subscriptionBuilder()
        .onApplied(() => {
            setProfileReady(true);
            readProfileFromConnection(conn);
        })
        .subscribe('SELECT * FROM view_my_profile');

    // view_my_profile callbacks
    const onViewProfileInsert = (ctx: any, row: any) => { /* ... */ };
    const onViewProfileUpdate = (ctx: any, oldRow: any, row: any) => { /* ... */ };
    conn.db.view_my_profile.onInsert(onViewProfileInsert);
    conn.db.view_my_profile.onUpdate(onViewProfileUpdate);

    return () => {
        conn.db.view_my_profile.removeOnInsert(onViewProfileInsert);
        conn.db.view_my_profile.removeOnUpdate(onViewProfileUpdate);
        stage1Ref.current = false;
        setProfileReady(false);
    };
}, [isActive, getConnection]);

// Stage 2: gated — fires only when D-01 signals confirm auth presence
const stage2Gate = currentUser != null || hadTokenOnMount.current || hadSessionCookie.current;

useEffect(() => {
    if (!isActive || !stage2Gate || stage2Ref.current) return;
    const conn = getConnection();
    if (!conn) return;
    stage2Ref.current = true;

    conn.subscriptionBuilder()
        .onApplied(() => {
            readProfileFromConnection(conn);
        })
        .subscribe('SELECT * FROM user');

    // MOVED from Stage 1 — User callbacks must register AFTER SELECT * FROM user subscription
    const onUserInsert = (ctx: any, row: any) => { /* ... */ };
    const onUserUpdate = (ctx: any, oldRow: any, row: any) => { /* ... */ };
    conn.db.User.onInsert(onUserInsert);
    conn.db.User.onUpdate(onUserUpdate);

    return () => {
        conn.db.User.removeOnInsert(onUserInsert);
        conn.db.User.removeOnUpdate(onUserUpdate);
        stage2Ref.current = false;
    };
}, [isActive, stage2Gate, getConnection]);
```

**Dependency array note:** `stage2Gate` is a derived boolean (`const stage2Gate = currentUser != null || hadTokenOnMount.current || hadSessionCookie.current`) computed inline in the hook body before the effect. React re-runs the effect when `stage2Gate` flips from `false` → `true`. The `hadTokenOnMount.current` and `hadSessionCookie.current` refs are set once at mount time and never change — they evaluate at the moment React runs the effect, which is correct behavior.

### Pattern 2: `guestLoginPending` Narrow State (D-03)

**What:** A boolean ref or `useState` tracking only the `loginAsGuest` reducer promise window. Distinct from all other loading/connecting flags.

**When to use:** `loginGuest()` callback only. NOWHERE else.

**Gate rule:** Spinner shows only when `guestLoginPending && !currentUser`. Once `currentUser` resolves (Stage 2 onApplied → readProfileFromConnection → setCurrentUser), the stage2Gate becomes true and Stage 2 fires — at that point currentUser will no longer be null.

```typescript
// Source: useAuth.ts:307-316 (existing loginGuest pattern — D-03 wraps this)

const [guestLoginPending, setGuestLoginPending] = useState(false);

const loginGuest = useCallback(() => {
    const conn = getConnection();
    if (!conn) return;
    setGuestLoginPending(true);                          // <- NEW: start pending
    conn.reducers.loginAsGuest({})
        .catch((err: any) => {
            console.error('[useAuth] loginGuest failed:', err);
            setGuestLoginPending(false);                 // <- NEW: clear on error
        });
    // Success path: cleared reactively when currentUser resolves (useEffect on currentUser)
}, [getConnection]);

// Clear guestLoginPending when user resolves (success path)
useEffect(() => {
    if (currentUser) {
        setGuestLoginPending(false);
    }
}, [currentUser]);
```

**Isolation rule:** The spinner in the Login button should use only `guestLoginPending` as its trigger. `isLoadingData` covers the returning-user reconnect window; `isConnecting` covers the initial WS connection; `isLinkingDiscord` covers Discord OAuth. None of these must bleed into the guest-login spinner. [VERIFIED: useAuth.ts:289-296, D-03 constraint]

### Pattern 3: `spacetime generate` Sequencing (Retirement + Rename in One Pass)

**What:** Single `spacetime generate` invocation after BOTH the `view_user_directory` deletion and the `view_public_accounts` rename are committed to source.

**Why single pass:** `spacetime generate` reads the live module schema from the SpacetimeDB server after publish. Running it once after a combined publish produces the correct final state. Running it after only the deletion would produce an intermediate bindings state that immediately becomes stale when the rename publish lands — creating unnecessary churn in both bindings dirs.

**Sequencing:**

```
Wave 1:
  1. Delete view_user_directory (body, type, export from identityViews.ts)
  2. Remove from spacetimedb/src/index.ts re-export block
  3. Rename view_public_accounts → view_public_hsr_accounts in identityViews.ts
     (rename const name, rename spacetimedb.anonymousView({ name: '...' }), rename export)
  4. Update spacetimedb/src/index.ts export: view_public_accounts → view_public_hsr_accounts
  5. Publish: spacetime publish
  6. Regen server bindings:
     npx spacetime generate --project-path spacetimedb --lang typescript --out-dir spacetimedb/src/module_bindings
  7. Regen client bindings:
     npx spacetime generate --project-path spacetimedb --lang typescript --out-dir src/module_bindings
  8. Verify: view_user_directory_table.ts ABSENT from both dirs
  9. Verify: view_public_hsr_accounts_table.ts PRESENT in both dirs
  10. Verify: view_public_accounts_table.ts ABSENT from both dirs
  11. TSC / build clean
```

**What `spacetime generate` actually does on rename + deletion:** The tool fully rewrites every file in the output directory. After publish, the server module schema no longer registers `view_user_directory` or `view_public_accounts`. Generate reflects this: `view_user_directory_table.ts` is not emitted; `view_public_accounts_table.ts` is not emitted; `view_public_hsr_accounts_table.ts` is emitted fresh; `index.ts` in both dirs is fully rewritten without the old imports/entries. No stale files linger from the previous generate run because generate writes a complete new snapshot. [VERIFIED: Phase 15.2 SUMMARY confirms full-overwrite behavior; Phase 15.4 experience confirms `--project-path` flag usage]

**Commands from Phase 15.2 precedent** [VERIFIED: 15.2-04-PLAN.md:179-184]:
```bash
npx spacetime generate --project-path spacetimedb --lang typescript --out-dir spacetimedb/src/module_bindings
npx spacetime generate --project-path spacetimedb --lang typescript --out-dir src/module_bindings
```

**Note on `npm run spacetime:generate`:** The package.json script at line 15 uses `--out-dir src/module_bindings` only (single target). Phase 15.2 used the explicit `--project-path` variant to target both dirs independently. Use the explicit form, not the npm script.

### Pattern 4: Harness Test for Frontend Gate (S-05)

**What:** Integration test in `test/backend/auth/auth-subscriptions.test.ts` that models `useAuth`'s gate by using the harness infrastructure selectively.

**Key insight from harness review:** `createTestHarness()` at `connection.ts:44` always calls `loginAsGuest({})` and then `subscribeToAllTables()`. This means the harness ALWAYS has User rows in `conn.db.User` — it models an authenticated guest, NOT an anonymous visitor. To model the anonymous visitor path, the test must build a raw connection without calling `loginAsGuest` and without subscribing to `user`.

**Two test scenarios (matching S-05 + D-01):**

1. **Anonymous visitor — Stage 2 never fires:** Connect without `loginAsGuest`. Subscribe only to `view_my_profile`. Assert `conn.db.User.iter().length === 0` after `sync()`. This matches what `useAuth` does for a truly anonymous visitor — Stage 1 fires, Stage 2 gate is `false`, so the `SELECT * FROM user` subscription is never issued.

2. **Authenticated user — Stage 2 fires:** Use `createTestHarness()` (which calls `loginAsGuest`). After sync, assert `conn.db.User.iter().length > 0`. This confirms that after auth, User rows are available.

**Harness skeleton:**
```typescript
// Source: new test/backend/auth/auth-subscriptions.test.ts
// Pattern derived from: test/shared/connection.ts (createTestHarness pattern)
// and test/backend/auth/auth-views.test.ts (structurally)

import { describe, it, expect, afterAll } from 'vitest';
import { createTestHarness, hasServerToken, TestHarness } from '../../shared/connection';
import { DbConnection } from '@/src/module_bindings';

describe('Auth Subscription Gate (S-05)', () => {
  const harnesses: TestHarness[] = [];

  afterAll(async () => {
    for (const h of harnesses) {
      await h.disconnect().catch(() => {});
    }
  });

  it('anonymous visitor (no loginAsGuest) — subscribing to view_my_profile only yields 0 User rows', async () => {
    // Models useAuth Stage 1 only. Stage 2 gate is false (no currentUser, no token, no cookie).
    // The harness must NOT call loginAsGuest — that would flip the gate.
    // Note: server still delivers rows to ANY subscriber of SELECT * FROM user (User.public=true).
    // This test asserts our frontend CHOICE not to subscribe, not server rejection.

    await new Promise<void>((resolve, reject) => {
      const timeout = setTimeout(() => reject(new Error('Timeout')), 20000);
      const uri = process.env.SPACETIMEDB_URI || 'wss://maincloud.spacetimedb.com';
      const db = process.env.SPACETIMEDB_DB || process.env.SPACETIMEDB_DB_NAME || 'hsrpvp-spacetimedb-nextjs-test1';

      DbConnection.builder()
        .withUri(uri)
        .withDatabaseName(db)
        .withConfirmedReads(false)
        .onConnect(async (conn) => {
          conn.subscriptionBuilder()
            .onApplied(() => {
              try {
                // Stage 1 only: view_my_profile subscribed, user NOT subscribed
                // Anonymous caller gets 0 view_my_profile rows (ctx.sender filter)
                const userRows = [...conn.db.User.iter()];
                // User table is NOT subscribed — iter() returns nothing from cache
                expect(userRows.length).toBe(0);
                clearTimeout(timeout);
                conn.disconnect();
                resolve();
              } catch (err) {
                clearTimeout(timeout);
                conn.disconnect();
                reject(err);
              }
            })
            .subscribe('SELECT * FROM view_my_profile');  // Stage 1 only — no user subscription
        })
        .onConnectError((_ctx, err) => { clearTimeout(timeout); reject(err); })
        .onDisconnect(() => {})
        .build();
    });
  });

  it.skipIf(!hasServerToken())(
    'authenticated harness (loginAsGuest called) — Stage 2 delivers User rows',
    async () => {
      // Models useAuth Stage 2 firing after loginAsGuest resolves.
      // createTestHarness calls loginAsGuest + subscribeToAllTables (includes user).
      const h = await createTestHarness();
      harnesses.push(h);
      await h.sync(1000);

      const userRows = [...h.conn.db.User.iter()];
      expect(userRows.length).toBeGreaterThan(0);
      // The test user itself plus SYSTEM user are present
      const myUser = userRows.find((u: any) => u.id === h.userId);
      expect(myUser).toBeDefined();
    }
  );
});
```

**Note on `it.skipIf(!hasServerToken())`:** Test 2 uses `createTestHarness()` which skips verification. `hasServerToken()` is used as the gate convention for integration tests that touch maincloud with state. Test 1 does NOT require a server token — it connects without auth.

### Anti-Patterns to Avoid

- **Using `useState` for double-subscribe guard instead of `useRef`:** State changes trigger re-renders; using a state bool as the "already subscribed" gate causes the subscription effect to re-run on every state change, potentially subscribing multiple times. Use `useRef` — as the existing `subscribedRef` at `useAuth.ts:17` does. [VERIFIED: useAuth.ts:17,24]

- **Registering `conn.db.User.onInsert` / `conn.db.User.onUpdate` in Stage 1:** These callbacks read from the User subscription cache. If registered before `SELECT * FROM user` subscription is active, they will fire on initial data delivery (tag=`SubscribeApplied`) from a subscription that hasn't been issued yet — the callbacks effectively become dead code. The existing code guards against `SubscribeApplied` via `isLiveChange()` check, but the correct architectural fix is to move them into Stage 2 where the User subscription is active. [VERIFIED: useAuth.ts:43-46, 63-80]

- **Running `spacetime generate` between backend changes:** Running regen after only the deletion but before the rename produces intermediate bindings that immediately go stale on the next publish. Batch deletion + rename into one publish, then regen once.

- **Manually editing files under `*/module_bindings/`:** All `*_table.ts` files and `index.ts` in both bindings dirs are generated artifacts (header comment: "THIS FILE IS AUTOMATICALLY GENERATED BY SPACETIMEDB. EDITS TO THIS FILE WILL NOT BE SAVED"). Hand-editing them will be overwritten on next `spacetime generate`. The only exception is when a publish hasn't happened yet and a manual trim is needed for TSC compliance — but even then it's temporary and must be marked as such. [VERIFIED: src/module_bindings/view_user_directory_table.ts:1-4, Phase 15.2 precedent]

- **Relying on `subscribeToAllTables()` for Stage 2 modeling:** The harness's `subscribeToAllTables()` subscribes to every public table including `user`. The gate test for Stage 2 must use an explicit `subscribe('SELECT * FROM view_my_profile')` call without the all-tables subscription, otherwise the test conflates "our frontend chose to subscribe" with "all tables subscribed regardless."

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Double-subscribe guard | Custom subscription state machine | `useRef` boolean (existing `subscribedRef` pattern) | Ref is synchronous, doesn't trigger re-renders, is already the established pattern in this codebase |
| Subscription gate abstraction | `useGatedSubscription(sql)` hook | Inline Stage 2 effect with `stage2Gate` boolean | D-03 explicitly deferred — only one gated subscription exists. YAGNI. |
| Anonymous-path test | Custom mock of SpacetimeDB SDK | Raw `DbConnection.builder()` without `loginAsGuest` | SDK connection without auth IS the anonymous path — no mocking needed |
| Bindings surgery | Manual edits to `*_table.ts` files | `npx spacetime generate` after publish | Generator fully rewrites; hand edits are wiped on next regen |
| Cookie parsing | Custom regex for `stdb_session` | `lib/session-cookie.ts` `getSessionCookieClient()` | Already exists; `hadSessionCookie.current` in useAuth.ts already uses `document.cookie.includes('stdb_session')` at line 292 |

**Key insight:** The entire Stage 2 infrastructure reuses existing refs (`hadTokenOnMount`, `hadSessionCookie`) and the existing boolean composition from `isWaitingForData`. The planner should not invent new signal infrastructure — the gate condition is literally the `isWaitingForData` boolean at `useAuth.ts:295`.

## Common Pitfalls

### Pitfall 1: Stale Bindings After `spacetime generate` — Missing Second Dir

**What goes wrong:** Developer runs `spacetime generate` targeting only `src/module_bindings/` (the client dir). The server bindings at `spacetimedb/src/module_bindings/` still reference `view_user_directory_table.ts`. The SpacetimeDB TypeScript module then fails to compile (`tsc --noEmit -p spacetimedb/tsconfig.json`) because `identityViews.ts` no longer exports `view_user_directory` but the old server bindings still register it.

**Why it happens:** Two separate bindings dirs. The package.json `npm run spacetime:generate` script only targets `src/module_bindings/`. Phase 15.2 established the pattern of running both dirs explicitly.

**How to avoid:** Always run generate for both dirs in sequence. Verification step: `ls spacetimedb/src/module_bindings/ | grep view_user_directory` must return nothing after regen.

**Evidence:** Phase 15.2 SUMMARY confirms both dirs require regen; 15.2-04-PLAN.md:177-184 shows the two explicit commands. [VERIFIED: repo]

---

### Pitfall 2: `onUserInsert` / `onUserUpdate` Callbacks Left in Stage 1

**What goes wrong:** The callbacks at `useAuth.ts:63-80` remain in Stage 1's effect cleanup. Since `conn.db.User.onInsert` fires when User rows arrive via subscription, and Stage 1 never issues the `SELECT * FROM user` subscription, these callbacks become dead code for anonymous visitors. The subtle bug: if an anon visitor triggers a code path that causes a User row to arrive through some OTHER mechanism (e.g., a future view that embeds user data), the callbacks would fire without the User subscription cache being populated correctly.

**Why it happens:** The callbacks are co-located with the subscription effect setup. Moving them requires splitting the effect AND the cleanup return.

**How to avoid:** Stage 2 effect's cleanup (`return () => {}`) must include `conn.db.User.removeOnInsert(onUserInsert)` and `conn.db.User.removeOnUpdate(onUserUpdate)`. Stage 1 cleanup only removes view_my_profile callbacks.

**Evidence:** CONTEXT.md §Claude's Discretion explicitly flags this: "Placement of the onUserInsert / onUserUpdate table callbacks currently at useAuth.ts:63-80 — they are recovery-path fallbacks tied to the User subscription and must move into the Stage 2 effect." [VERIFIED: CONTEXT.md]

---

### Pitfall 3: `stage2Gate` Re-Renders Before Stage 2 Ref Is Set

**What goes wrong:** `stage2Gate` is a derived boolean computed inline in the hook. If `currentUser` becomes non-null and React re-renders the component multiple times in quick succession (e.g., StrictMode double-invoke in dev), `stage2Ref.current` may not be set before the second render checks the guard. The existing `subscribedRef` has this same guard but it works because `subscribedRef.current = true` is set synchronously at the top of the effect body (before any async work).

**How to avoid:** Set `stage2Ref.current = true` as the FIRST line inside the if-guard in Stage 2 effect, before calling `getConnection()` or registering any callbacks — exactly as `subscribedRef.current = true` is set at `useAuth.ts:24`. [VERIFIED: useAuth.ts:21-24]

---

### Pitfall 4: `guestLoginPending` Not Cleared on `currentUser` Resolution

**What goes wrong:** `setGuestLoginPending(true)` fires in `loginGuest()`. The reducer promise resolves successfully (no `.catch()` path). But the effect that clears `guestLoginPending` on `currentUser` is absent or depends on a state that lags. Result: spinner stays visible after the user is authenticated and Stage 2 has fired.

**How to avoid:** Add a dedicated `useEffect(() => { if (currentUser) setGuestLoginPending(false); }, [currentUser])`. This is the clearest pattern — it mirrors how `deletionHandledRef` is handled at `useAuth.ts:276`. [VERIFIED: useAuth.ts:276-287]

---

### Pitfall 5: `view_public_accounts` References in Docs Not Fully Updated

**What goes wrong:** `spacetime generate` renames the binding type. TypeScript compilation catches direct code references. But documentation and FRONTEND-HANDOFF.md prose references to `view_public_accounts` persist silently — they don't cause a build error. Future developers reading `docs/FRONTEND-HANDOFF.md:109` see `view_public_accounts` and write code against a non-existent view name.

**How to avoid:** Grep docs explicitly before marking the rename task complete. Canonical doc sites [VERIFIED via grep]:
- `docs/views/architecture.md` — view definition + Phase 15 reorg table (line 150)
- `docs/views/contract.md` — view reference (line 433, 451)
- `docs/roster/contract.md` — integration reference (line 433, 451)
- `docs/FRONTEND-HANDOFF.md` — key views table (line 109) + prose "Roster Visibility" section (line 187)
- `docs/auth/architecture.md` — View Definitions table (line 108 references `view_user_directory` which is deleted; no current `view_public_accounts` entry but the deletion of `view_user_directory` row is needed)

---

### Pitfall 6: VIEW-01 Placeholder Test Block Left Structurally

**What goes wrong:** The VIEW-01 `describe` block in `auth-views.test.ts` (lines 23-65) contains two `it` tests that both assert `expect(true).toBe(true)`. These tests document an enforcement model that doesn't exist (`spacetimedb.view()` rejects anonymous subscribers — which Phase 15.2 UAT Test 4 proved false). Leaving them after 15.5 deletes `view_user_directory` would be misleading — they'd document a view that no longer exists.

**How to avoid:** Delete the entire VIEW-01 `describe` block (lines 23-65). VIEW-02, VIEW-03, VIEW-04 blocks remain unchanged. [VERIFIED: auth-views.test.ts:23-65]

---

### Pitfall 7: `hadSessionCookie.current` Evaluation Timing

**What goes wrong:** `hadSessionCookie.current` is initialized with `typeof document !== 'undefined' && document.cookie.includes('stdb_session')` at `useAuth.ts:292`. This runs once at component mount (useRef initializer). If `stage2Gate` is evaluated in the same render cycle as mount, it correctly reads the initial cookie state. The risk: if this line is accidentally moved inside an effect (rather than staying as a `useRef` initializer), it would re-evaluate on every render and potentially miss the initial cookie state.

**How to avoid:** Do not touch `hadSessionCookie` or `hadTokenOnMount` ref declarations. They are already correct at `useAuth.ts:292-293`. Stage 2 effect reads `hadTokenOnMount.current` and `hadSessionCookie.current` by referencing these existing refs — no new declarations needed. [VERIFIED: useAuth.ts:292-295]

## Open Questions (RESOLVED)

1. **Spinner component choice for `guestLoginPending`**
   - What we know: D-03 requires inline spinner in Login button, scoped to `guestLoginPending && !currentUser`
   - What's unclear: Does the existing Button/Login component have a built-in `loading` or `isLoading` prop (HeroUI button pattern), or does it need an `<span aria-busy>` injection?
   - Recommendation: Planner should read the Login button component at execution time and choose the lowest-LOC option that doesn't introduce a new dependency. If HeroUI Button has an `isLoading` prop, use it. Otherwise, `<span className="..." aria-busy="true" />` inline.
   - **RESOLVED:** Plan 02 Task 2.2 (`AuthSelector` button) ships the inline `<span className={styles.spinner} aria-busy="true" />` approach scoped to `guestLoginPending && !currentUser` — chosen because the existing Login button does not expose an `isLoading` prop and adding a new dependency was rejected.

2. **`readProfileFromConnection` dependency in Stage 2 effect**
   - What we know: Stage 2 `onApplied` calls `readProfileFromConnection(conn)`. The function is defined as a `useCallback` with `[identity, session, setResolvedUser]` deps, and its stable ref is kept via `readProfileRef.current`.
   - What's unclear: Stage 2 effect should call `readProfileRef.current(conn)` (stable ref) or `readProfileFromConnection(conn)` directly? If `readProfileFromConnection` is in the dep array, any change to `identity` / `session` would re-trigger Stage 2 — potentially double-subscribing.
   - Recommendation: Stage 2 `onApplied` should call `readProfileRef.current(conn)` (the stable ref), matching the pattern used by `onUserInsert`/`onUserUpdate` at `useAuth.ts:67,72`. This keeps Stage 2 effect deps as `[isActive, stage2Gate, getConnection]` without adding `readProfileFromConnection`.
   - **RESOLVED:** Plan 02 Task 2.1 (Stage 2 effect implementation) calls `readProfileRef.current(conn)` and keeps the dep array at `[isActive, stage2Gate, getConnection]`, exactly per the recommendation. `readProfileFromConnection` is intentionally excluded from Stage 2 effect deps to prevent re-subscribe loops on identity/session changes.
