## Execution Deviations from Plan

Documented per the CLAUDE.md rule: "After execution completes, update the contract with any additions — tag every new entry with `Phase X execution`."

1. **D-01 gate signal revised** (commit `790a39c`).
   Plan specified `hadTokenOnMount` using `SPACETIMEDB_TOKEN_KEY`. UAT Scenario 1 revealed the SDK auto-persists an anonymous identity token on first WS connect (`app/providers.tsx:12-15`), so token presence is not a valid "has authenticated" signal. Swapped to `hadUserIdOnMount` reading `spacetimedb_user_id` (only written by `setResolvedUser`). Updated gate expression, diagnostic log strings, and `isWaitingForData` derivation. Module-level helper comment + SEED-001 note added so Phase 17/21 don't repeat the mistake.

2. **NavBar modal auto-close** (commit `5002c1c`).
   Plan removed `setShowLogin(false)` from the NavBar `loginGuest` wrapper, expecting the NavBar's `isAuthenticated`-driven rendering to naturally hide the overlay. The actual render was guarded only by `showLogin`. Changed `{showLogin && (...)}` → `{showLogin && !isAuthenticated && (...)}` at NavBar.tsx:188 so the modal hides the moment `currentUser` resolves.

3. **Signature-based profile dedupe** (commits `02d25c6`, `6d73b5b`, `aad6b06`).
   Plan did not specify dedupe; UAT Scenario 2 surfaced 3× `View hit` + 2× clearing-log noise because Stage 1 and Stage 2 both deliver the caller's own row + both onApplied callbacks feed into `readProfileFromConnection`. Added:
   - Module-level `extractProfileSignature(user)` helper — single source of truth covering 11 UI-visible fields.
   - `resolvedSignatureRef` — tracks last-resolved signature; short-circuits repeat resolves silently.
   - BigInt-safe JSON replacer: `(_k, v) => typeof v === 'bigint' ? v.toString() : v` — SpacetimeDB timestamp columns (`lastLoginAt`, `deletedAt`) are bigint at the SDK layer and vanilla `JSON.stringify` throws.
   - Stage 2 `onApplied` closure dedupe (`if (currentUser) return`) — complementary fast-path for the fresh-guest flow.
   - Reset of `resolvedSignatureRef.current = null` in the "no user found" path to ensure future resolves are treated as new.

4. **Diagnostic logging** (commit `980ae01`).
   Added 7 `console.log` lines with the `[useAuth]` prefix to make Stage 1/Stage 2 gate decisions and `guestLoginPending` transitions visible in DevTools for UAT. Not in plan, but required by the user for Scenario 1/2 verification. Retained in shipped code — low noise, high diagnostic value.

5. **Clearing-effect log guard** (commit `9f7b63e`).
   The `useEffect([currentUser])` clearing effect fired on every `currentUser` reference change and logged `guestLoginPending → false` unconditionally — misleading when `guestLoginPending` was never true (reconnect, Discord relink). Changed guard to `if (currentUser && guestLoginPending)` + added `guestLoginPending` to deps. Now logs only on actual true→false transitions.

## `readProfileRef` / Dep-Array Churn Notes

`readProfileFromConnection`'s dep array is `[identity, session, setResolvedUser]`. Adding `currentUser` was considered but avoided — it would cause the callback to churn on every currentUser change. Instead, `readProfileRef.current = readProfileFromConnection` is updated at line 276 on every render so table callbacks always see the latest version without re-subscribing. This pattern was preserved from pre-refactor code.
