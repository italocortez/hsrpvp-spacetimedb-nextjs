# Phase 15.5 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| anonymous WS client → SpacetimeDB module | Unauthenticated caller subscribes to any registered view/table; server enforces only via view body `ctx.sender` predicates and table `public:` flag | User table rows (public:true), public views |
| browser DOM → useAuth hook state | DevTools can mutate React component state; no auth trust placed on client state | UI booleans (guestLoginPending), refs, derived state |
| useAuth → SpacetimeDB WS connection | Client-side subscription decisions (Stage 1 / Stage 2 split); server honors or rejects via view body + table `public:` flag | Subscription queries, identity token |
| stdb_session cookie → Stage 2 gate | Cookie presence opens Stage 2 as UX optimization; server still enforces auth via WS token handshake | Session hint flag (no token material in cookie) |
| developer workstation → maincloud | `spacetime publish` uploads new module schema; data preservation depends on non-destructive migration | Schema definitions, view registrations |
| test harness → maincloud | Integration tests hit maincloud DB; `SPACETIMEDB_SERVER_TOKEN` gates verified-user tests | Reducer calls, table writes during tests |

## Threat Register

| Threat ID | Category | Component | Disposition | Mitigation | Status |
|-----------|----------|-----------|-------------|------------|--------|
| T-15.5-01 | Information Disclosure | Adversarial raw `SELECT * FROM user` subscription bypassing frontend Stage 2 gate (client connects directly via SDK, not via useAuth) | accept | Inherits 15.2 D-01: `User.public=true` stays. Closing requires `User.public=false` + on-demand read reducers (deferred). Phase 15.5 scope is "our frontend does not auto-subscribe anonymous," not "adversarial clients cannot query User." Documented in `docs/auth/architecture.md:227-229` "Accepted Tradeoff" paragraph. | closed |
| T-15.5-02 | Spoofing (cosmetic) | `setGuestLoginPending(true)` invoked via DevTools to show spinner when no reducer is pending | accept | Spinner state is purely visual — no auth decision reads `guestLoginPending`. Cannot elevate privilege, cannot cause data exposure. Worst case: user confuses themselves about pending state. Verified isolation via grep at `useAuth.ts` — `guestLoginPending` is never combined via `\|\|` or `&&` with `isLoadingData`, `isWaitingForData`, `isConnecting`, or `isLinkingDiscord`. | closed |
| T-15.5-03 | Elevation of Privilege | Stale `stdb_session` cookie or `spacetimedb_user_id` localStorage value sets `hadSessionCookie.current = true` / `hadUserIdOnMount.current = true`, opening Stage 2 after token revocation | mitigate (defense-in-depth) | Stage 2 effect's first guard at `useAuth.ts:116` is `if (!isActive) return;` — `isActive` is the SpacetimeDB SDK's WS handshake result. Revoked or invalid token fails handshake, `isActive` stays false, effect early-returns regardless of stale UX-hint values. Effect deps `[isActive, stage2Gate, getConnection]` re-run on `isActive` flip. Cookie/localStorage presence alone CANNOT fire Stage 2 without a valid WS handshake. ASVS L1 acceptable. | closed |

*Status: open · closed*

### Audit 2026-04-17 — Verification Evidence

**T-15.5-02 (Spoofing — cosmetic):**
- ✓ `useAuth.ts` grep confirms `guestLoginPending` is NEVER combined via `||` or `&&` with `isLoadingData`, `isWaitingForData`, `isConnecting`, or `isLinkingDiscord` (Plan 02 SUMMARY self-check item 6).

- ✓ `useAuth.ts:181` Effect deps include `isActive` — flip to false re-runs and skips.
- ✓ Plan 02 D-01 execution-deviation note: SDK auto-persists anonymous identity token on first WS connect; signal swapped from `SPACETIMEDB_TOKEN_KEY` → `USER_ID_KEY` (only written by `setResolvedUser`) to prevent false positives. Defense-in-depth integrity preserved.
