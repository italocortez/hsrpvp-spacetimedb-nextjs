## GA-1: Template JSON shape

| Option | Description | Selected |
|--------|-------------|----------|
| (a) Parallel sibling blocks | `cost.<mode>.classic.{E0-E6}` + `cost.<mode>.auction.{E0-E6}` | ✓ |
| (b) Flat sibling modes | Separate `cost.<mode>` (classic) + `cost.<mode>_auction` keys at the mode level | |
| (c) Top-level split | `cost.auction_cost.<mode>.{E0-E6}` mirroring `cost` | |

**User's choice:** (a) Parallel sibling blocks.
**Rationale:** Maps 1:1 to the DB, which already carries `classicCosts` + `auctionBaseBid` as sibling struct columns of the same type. Readers in `draftClassic.ts:367` and `draftAuction.ts:60` consume them independently — no semantic mismatch.

## GA-3: Fallback policy when auction block is absent

| Option | Description | Selected |
|--------|-------------|----------|
| (i) Silent copy classic → auction | Auto-populate auction from classic when organizer omits it | |
| (ii) Warn + copy | Log warning, copy classic to auction | |
| (iii) Hard error | Require both blocks | |
| (iv) Zero-pad on insert, preserve on update | Missing sub-block → zeros on first insert; missing sub-block → no change on subsequent updates | ✓ |

**User's choice:** (iv) Zero-pad on insert, preserve on update.
**Rationale:** User explicitly rejected silent copy: *"I only expect to have classic filled and draft can be filled with 0s."* Zero is semantically equivalent to "not configured" in all existing readers (`draftAuction.ts:61` returns `?? 0`). Default cost set ships with real classic + zero auction; real auction values arrive via later hand-tuning or a balancing phase. Custom sets follow the same rule — organizer sends only the side they care about.

**Downstream implication:** Default cost set invariant "all 3 game modes × both draft modes fully populated" is relaxed to "all 3 game modes × classic populated; auction lands as zeros." Existing draft tests keep passing because they hit the default set and read classic.

## Schema optionality debate (originally D-03, revised twice)

**Initial proposal:** Make `classicCosts` and `auctionBaseBid` `.optional()` on live + draft tables; make `costModifier` and new `auctionCostModifier` optional on synergy; reducer args become optional strings. Row absence = game mode not configured; field null = draft mode not configured within that game mode.

**Blast-radius audit revealed:**
- Schema change affects 6 tables (3 live + 3 draft).
- Reducer signatures would change for `edit_draft_character_cost`, `edit_draft_lightcone_cost`, `edit_draft_synergy_cost` (optional JSON args).
- Reader null guards required in `draftClassic.ts:368`, `draftAuction.ts:61` (current `?? 0` tolerates missing struct keys but not a null struct).
- Frontend `DataHelpers.ts:30-31,53-54` + `useCharacterCostTable.ts:92` + `useLightconeCostTable.ts:52` would need null guards.
- Module bindings regenerate — breaking TS change.

**User's counter-proposal (adopted):** Keep schema required. Use zero-padding on insert, partial-update preservation on update. All existing readers already treat "no data" as 0 cost. No schema change, no reducer signature changes, no frontend guards, no module-binding break.

**Result:** D-03 through D-09 revised to the zero-padding model. Significantly smaller diff.

## draftMode column design (deferred to 15.4)

**User raised late in discussion:** *"The initial idea was that synergy would only be a classic cost, not auction, hence why it doesn't have it. If we add another column called 'draftMode' and put either classic or auction on it, we can truly make that table surgical to what is needed for each draft mode right?"*

**Analysis surfaced:**
- The `draftMode` column pattern IS architecturally correct — row absence = "not configured for that draft mode" is cleaner than zero-padding.
- Applying the pattern only to synergy creates inconsistency; the right design applies it to characters/lightcones too.
- Full refactor scope: 6 tables restructured, PK tuple extended, `admin_bulk_upsert` rewritten (3 cases), `edit_draft_*` signatures changed (3 reducers), readers updated (`draftClassic.ts`, `draftAuction.ts`, `postDraft.ts`, plus frontend hooks), tests rewritten.
- Must land **before Phase 16 / Phase 17** so the cost-tables frontend is written once against the clean shape, not rewritten after.

**Path decision:**
| Path | Description | Selected |
|------|-------------|----------|
| A (expand 15.1) | Do the full restructure now | |
| A-lite (surgical 15.1 + 15.4 follow-on) | 15.1 closes IN-10 only; 15.4 does the restructure before Phase 16/17 | ✓ |

**User's choice:** A-lite.
**Rationale:** Throwaway cost of A-lite → 15.4 is ~1-2 hours (zero-padding seed logic gets replaced by per-draft-mode fan-out). Template JSON + data files + Phase 17 frontend all survive the future restructure unchanged. Insert Phase 15.4 explicitly before Phase 16/17.
