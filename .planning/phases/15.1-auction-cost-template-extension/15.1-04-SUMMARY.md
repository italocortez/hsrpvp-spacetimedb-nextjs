## Deviations from Plan

### Plan Clarification: D-06 "Key-absent" vs "null" Semantics

**Found during:** Task 1 (read_first of `spacetimedb/src/reducers/admin.ts`)

**Issue:** The plan describes D-18-4 as testing "key-absent → preserve" and instructs to "omit the `auctionBaseBidJson` key entirely." The actual reducer has two relevant constraints:

1. `validateKeys()` enforces that EVERY row must have EXACTLY `[characterName, gameMode, classicCosts, auctionBaseBid, costSetId]`. A row missing `auctionBaseBid` would throw `"Row N key mismatch: missing: [auctionBaseBid]"`.
2. `mergeForUpdate()` uses `if (incoming[key] != null)` — both `null` and `undefined` trigger the preserve path.

**Fix:** D-18-4 sends `auctionBaseBid: null` (not absent). This is semantically identical to "key-absent" at the intent level — the caller expresses "preserve this column" — but the actual wire contract requires the key to be present.

**Why not escalate (Rule 4 check):** No architectural change required. The test correctly exercises the D-06 preserve-existing contract. The plan's `auctionBaseBidJson` terminology applies to `editDraftCharacterCost` (a different reducer); `admin_bulk_upsert` uses struct objects directly with null as the preserve signal.

**Files modified:** test/backend/reducers/admin/partial-update.test.ts (comment documents the distinction)

**Classification:** Rule 1 (plan's pseudocode would have caused a runtime throw from validateKeys; test adapted to actual reducer contract)

### D-18-5 Scoped to "acheron" Instead of allChars.length * 3

**Found during:** Task 1 test run

**Issue:** The plan instructs `expect(defaultRows.length).toBe(chars.length * 3)`. The live DB accumulates extra characters from other test runs (`cs-test-char`, `pu-test-char`, `pu-insert-defaults`). With `SKIP_DB_CLEAR=1`, the count assertion fails because `allChars.length` includes those non-seed characters.

**Fix:** Assert that the known-seeded character "acheron" has exactly 3 default-set rows. This is the correct Nyquist sample — it proves the per-character 3-row invariant holds without being brittle to accumulated test state.

**Classification:** Rule 1 (test would have been flaky against any non-fresh-DB state)
