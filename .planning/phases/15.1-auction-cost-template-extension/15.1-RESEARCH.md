## Summary

Phase 15.1 is a surgical shape-change: migrate `cost.<mode>` blocks in the character and lightcone templates from the flat `{E0..E6}` / `{S1..S5}` form to a parallel sibling-block form `{ classic: {E0..E6}, auction: {E0..E6} }`. Propagate the shape through both seed pipelines (`scripts/seed-data.ts` and `test/shared/seed-data.ts`), delete the Phase 15 `auctionBaseBid = {...classicCosts}` placeholder, add D-18 regression tests for partial ingestion, and rewrite the two affected transform tables in `test/data-templates/README.md`. No schema changes, no reducer signature changes, no module-binding regeneration.

The critical risk on this re-execution is **not** technical — the first attempt's substantive code was correct. The risk is commit hygiene: two executor agents force-added files under gitignored paths (`tmp/` and `test/data/`). This research section treats gitignore-boundary enforcement as a first-class plan constraint, not a side note.

**Primary recommendation:** Split into 5 plans. Only 3 produce commit deliverables (template extension, seed + tests, README). The production-data re-migration is a local-dev-only step driven by an uncommitted script under `/tmp/` — it has **zero files in its `files_modified` frontmatter**. The planner MUST treat any non-empty `files_modified` on the migration plan as a defect.

### Pattern 1: Sibling-block cost shape (D-01)

**What:** Each `cost.<mode>` block in a character or lightcone template JSON becomes a dict with two optional sub-blocks: `classic` and `auction`. Both sub-blocks hold the same struct shape (`{E0..E6}` for characters, `{S1..S5}` for lightcones).

**When to use:** Every new template JSON entry written after Phase 15.1. Every existing entry migrated by the migration script. Existing flat-shape entries (`cost.<mode>.E0` directly) are invalid after Phase 15.1.

**Example (character, both sub-blocks present):**

```json
{
  "cost": {
    "cost_set_id": 0,
    "memory_of_chaos": {
      "classic": { "E0": 7, "E1": 8, "E2": 11, "E3": 11.5, "E4": 12.5, "E5": 13, "E6": 15 },
      "auction": { "E0": 70, "E1": 80, "E2": 110, "E3": 115, "E4": 125, "E5": 130, "E6": 150 }
    },
    "apocalyptic_shadow": {
      "classic": { "E0": 7, "E1": 8, "E2": 11, "E3": 11.5, "E4": 12.5, "E5": 13, "E6": 15 }
    }
  }
}
```

**Example (lightcone, classic only — the default-seed case):**

```json
{
  "cost": {
    "cost_set_id": 0,
    "memory_of_chaos": {
      "classic": { "S1": 1.5, "S2": 1.5, "S3": 1.5, "S4": 1.5, "S5": 1.5 }
    }
  }
}
```

### Pattern 2: Classic/auction extractor (seed pipeline rewrite — D-07, D-08, D-09)

**What:** Both `scripts/seed-data.ts` and `test/shared/seed-data.ts` currently fan out each mode block once and assign `auctionBaseBid: { ...costs }` (the placeholder). The rewrite reads `classic` and `auction` sub-blocks independently and zero-pads the missing side on insert.

**When to use:** Replaces the current inner loops in `normalizeCharacterCosts` (`scripts/seed-data.ts:161-194`) and `normalizeLightconeCosts` (`scripts/seed-data.ts:212-243`). Mirror the changes in `test/shared/seed-data.ts:128-155` (char) and `:174-199` (lc).

**Example pseudocode (characters):**

```ts
const ZERO_EIDOLON = { e0: 0, e1: 0, e2: 0, e3: 0, e4: 0, e5: 0, e6: 0 };

function extractEidolonCost(block: { E0?: number; /* ... */ E6?: number } | undefined) {
  if (!block || typeof block !== 'object') return undefined;
  return {
    e0: block.E0 ?? 0, e1: block.E1 ?? 0, e2: block.E2 ?? 0,
    e3: block.E3 ?? 0, e4: block.E4 ?? 0, e5: block.E5 ?? 0, e6: block.E6 ?? 0,
  };
}

for (const rawMode of modes) {
  const modeBlock = c.cost[rawMode] as { classic?: ...; auction?: ... } | undefined;
  if (!modeBlock || typeof modeBlock !== 'object') continue;

  const classicCosts = extractEidolonCost(modeBlock.classic);
  const auctionBaseBid = extractEidolonCost(modeBlock.auction);

  // D-09 rule: both absent → skip entirely (no row for this mode)
  if (!classicCosts && !auctionBaseBid) continue;

  const gameMode = snakeToPascalMode(rawMode);
  if (!gameMode) { console.warn(...); continue; }

  rows.push({
    characterName: c.name,
    gameMode,
    classicCosts: classicCosts ?? ZERO_EIDOLON,        // D-07 zero-pad on insert
    auctionBaseBid: auctionBaseBid ?? ZERO_EIDOLON,    // D-07 zero-pad on insert
    costSetId: csId,
  });
}
```

Key changes vs. the Phase 15 code:
- Read two sub-blocks per mode, not one flat block.
- Delete the `auctionBaseBid: { ...costs }` placeholder (D-08).
- Zero-pad each side independently on insert (D-07).
- Skip the mode entirely when both sub-blocks are absent (D-09).

Note on partial-update semantics (D-06): the seed pipeline emits full `{classicCosts, auctionBaseBid}` rows because it runs against a fresh DB after `--clear-database`. The zero-pad guarantees the insert is valid. Upstream `admin_bulk_upsert` in `spacetimedb/src/reducers/admin.ts:487-538` already handles partial-update preservation on existing rows (Phase 15 D-08), so when an organizer submits a partial row later via admin panel, the router preserves unchanged fields. Nothing in the router needs changing.

### Pattern 3: Local-only migration script (D-11, D-12, D-14)

**What:** A one-off TypeScript script that reads `test/data/characters_table.json` + `test/data/lightcones_table.json`, transforms each entry's `cost.<mode>` block from flat `{E0-E6}` to `{ classic: {E0-E6} }`, and writes back in place. Idempotent (safe to re-run; detects already-migrated entries).

**Where it lives:** `tmp/migrate-cost-sub-blocks.ts` — **uncommitted**, `/tmp` is gitignored.

**When to use:** The developer runs this once locally after Wave 1 ships the template extension and before Wave 3 ships the seed rewrite. Its output is uncommitted data files staying on the developer's local disk. Verification is by reading a few migrated entries manually or by running the D-18 test suite (which exercises fixtures in `test/data-templates/`, not the production data).

**Critical framing for the planner:** The plan that describes this step has an **empty `files_modified` frontmatter**. The plan body describes the developer action ("run `npx tsx tmp/migrate-cost-sub-blocks.ts`"), acknowledges the script is gitignored, and states the post-migration data files stay on local disk.

**Idempotency check inside the script:**

```ts
function needsMigration(modeBlock: unknown): boolean {
  if (!modeBlock || typeof modeBlock !== 'object') return false;
  const keys = Object.keys(modeBlock);
  // Migrated if already has classic/auction sub-blocks; otherwise the flat shape has E0-E6 or S1-S5 keys.
  return !keys.includes('classic') && !keys.includes('auction') &&
         (keys.some(k => /^E\d$/.test(k)) || keys.some(k => /^S\d$/.test(k)));
}
```

## Common Pitfalls

### P-01: Force-adding gitignored files (CRITICAL — the rollback trigger)

**What goes wrong:** An executor agent generates the migration script under `tmp/`, sees that `git status` doesn't show it, decides the gitignore is "in the way", and invokes `git add -f tmp/migrate-cost-sub-blocks.ts` + `git add -f test/data/*.json`.
**Why it happens:** The executor sees "I produced work, I should commit it" as an unbroken chain. Gitignore is treated as a defect rather than a boundary.
**How to avoid:**
1. The migration plan has **empty `files_modified` frontmatter** — the plan itself does not authorize committing anything.
2. The plan body explicitly states: "the script lives at `tmp/migrate-cost-sub-blocks.ts` which is gitignored; after running it, DO NOT stage or commit any file. Migrated data files stay on local disk only."
3. The executor's three-question answer (from `.continue-here.md`) must name this anti-pattern and the empty-frontmatter mechanism.
4. The plan-checker refuses any plan containing `tmp/` or `test/data/` in `files_modified`.
**Warning signs:** Any commit whose diff includes `tmp/*.ts` or `test/data/*.json`. Any agent message containing `git add -f`.

### P-02: Re-introducing the `auctionBaseBid: { ...costs }` placeholder

**What goes wrong:** When rewriting extractors, an agent preserves the old line out of caution and adds the classic/auction sub-block parse alongside it, producing a hybrid that double-writes auction with classic values.
**Why it happens:** Large diffs feel risky; agents hedge by keeping old code "for backward compat".
**How to avoid:** The Phase 15 D-08 explicitly mandates deletion of the placeholder. Grep-verify post-edit that the strings `auctionBaseBid: { ...costs }` and `auctionBaseBid: { ...eidolonCost }` and `auctionBaseBid: supCost` do not appear in either pipeline. (Phase 15 code has three variants across the two files.)
**Warning signs:** D-18 test #1 (classic-only → auction all zeros) fails with auction equal to classic values.

### P-03: Forgetting the D-09 "both absent → skip" rule

**What goes wrong:** Extractor always emits a row, zero-padding both sides when a mode block is bare `{}`. Result: DB has 3 rows per character/lightcone with empty-cost for unintended modes.
**Why it happens:** The skip condition is subtle — "mode block present but both sub-blocks absent" is an edge case that doesn't come up in the default-seed data.
**How to avoid:** D-18 test #3 is the explicit guard. The extractor code must `if (!classicCosts && !auctionBaseBid) continue;` before pushing the row.
**Warning signs:** Row count in `HsrCharacterCost` or `HsrLightconeCost` exceeds expected seed count (83 × 3 = 249 / 156 × 3 = 468).

### P-04: Breaking `cost-set-lifecycle.test.ts` or `cost-set-pk.test.ts`

**What goes wrong:** These tests send `classicCostsJson` and `auctionBaseBidJson` as complete payloads via `edit_draft_character_cost` / `admin_bulk_upsert`. They should keep passing unchanged (D-19). If a seed-pipeline refactor leaks into shared test fixtures, they can break.
**Why it happens:** Agent "cleans up" fixture files or touches shared helpers unnecessarily.
**How to avoid:** `test/shared/fixtures.ts` is on the "audit" list in CONTEXT.md canonical_refs — audit for leaked flat-at-mode assumptions but do not rewrite if no such assumption exists. Inspection reveals it contains no cost shape code (verified: only UID fixtures, character batch helpers). Leave it alone.
**Warning signs:** Existing test names fail; Phase 15 D-19 guardrail tripped.

### P-05: Forgetting to remove the README L84 placeholder note

**What goes wrong:** README transform tables get rewritten to sibling-block shape but the "auctionBaseBid uses the same values as classicCosts for now (placeholder; the auction format may diverge in a later phase)" note at L84 remains as stale documentation.
**Why it happens:** Scrolling rewrite of the tables while the note is out of the visual field.
**How to avoid:** Delete L84 explicitly as part of the README rewrite (D-17 is unambiguous). Grep-verify post-edit: the substring `"placeholder; the auction format may diverge"` does not appear.
**Warning signs:** Stale note survives into commit.

### P-06: Regenerating module bindings unnecessarily

**What goes wrong:** Agent sees "schema-adjacent work" and runs `spacetime generate` to be safe.
**Why it happens:** Overcaution; D-03 and D-04 are explicit that no regeneration is required.
**How to avoid:** No plan touches `src/module_bindings/**`. If bindings regenerate, the diff should be empty — but the plan should not include the regeneration step.
**Warning signs:** Diff in `src/module_bindings/**` on a Phase 15.1 commit.
