## Decisions Made

- **Explicit version pin for the lockfile.** Plain `npm install` against `^2.1.0` re-resolved to `spacetimedb@2.2.0` (the latest published 2.x.x — npm caret semantics resolve to the highest compatible major). Letting that land in Commit A would have silently absorbed the v2.2.0 bump that D-01 explicitly assigns to Commit B (Plan 02). To preserve the audit-trail boundary, the lockfile was re-resolved a second time via `npm install spacetimedb@2.1.0 --save`, which pinned the lockfile entry to 2.1.0 without changing the `^2.1.0` caret in `package.json`. The lessons-learned aspect of this is captured in `patterns-established` above — future SDK floor-bump phases should anticipate caret resolution to the latest 2.x and pin explicitly when commit boundaries matter.
- **No bindings regen.** D-02 places bindings regen with the v2.2.0 bump. Existing `src/module_bindings/` stamp is `2.1.0` which matches the new manifest, so regen here would produce zero meaningful diff and would muddy the Commit B regen narrative.
- **No tests gated this commit.** The manifest moved from a value (^2.0.3) that already didn't reflect reality to one (^2.1.0) that does. The existing test suite was already running against installed 2.1.0 and stays green; the commit changes audit-trail truthfulness, not behavior.
