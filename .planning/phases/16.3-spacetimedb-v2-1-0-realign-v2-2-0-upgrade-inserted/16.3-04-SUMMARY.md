**4. [Rule 1 - Bug / Probe SQL schema mismatch] Probe SQL substituted because `st_sequence` / `st_table` columns named in PLAN don't exist on this engine**

- **Found during:** Plan 04 Task 2 Step 3 (prior executor)
- **Issue:** PLAN.md Task 2 Step 3 specified `SELECT table_name, sequence_name, value FROM st_sequence WHERE table_name IN ('user', 'lobby') ORDER BY table_name, sequence_name`. Maincloud's SQL parser rejected this — `st_sequence` has no `table_name` or `value` column on this engine, and `IN (...)` + `ORDER BY` is unsupported. The actual `st_sequence` schema is `(sequence_id, sequence_name, table_id, col_pos, increment, start, min_value, max_value, allocated)`. Likewise `MAX(id)` and `ORDER BY id DESC LIMIT 1` aggregates are rejected by SpacetimeDB SQL.
- **Fix:** Substitute query selects by `sequence_name` (`'user_id_seq'`, `'lobby_id_seq'`) and reads `allocated` (highest currently-allocated value) instead of `value`. The "max(id)" denominator was proven via existence proof: `SELECT id FROM user WHERE id > 8000` returning empty + `SELECT id FROM user WHERE id > 4097` returning only `4098, 4099`. Cross-check semantics (`allocated > max(id) ⇒ #4902 fix applied`) preserved exactly.
- **Files modified:** `.planning/phases/16.3-.../16.3-04-PLAN.md` Probe Evidence subsection (Task 2 Step 4 embedded both the substitute SQL and the substitution-rationale prose)
- **Verification:** Probe A ✓ PASS (`user_id_seq.allocated = 8193 > max observed user.id = 4099`); Probe B ✓ PASS (both `user` and `lobby` show `table_primary_key = Some(0)`).
- **Committed in:** Commit B (`208f1a6`) body acknowledges this as a "Probe SQL substitution note".
