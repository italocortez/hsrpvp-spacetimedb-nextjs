Four sequenced operations behind a human-verify push gate:
0. **CLI upgrade precondition** — bump local `spacetime` CLI from v2.1.0 to v2.2.0 via `spacetime version upgrade` so the verification chain runs against a v2.2.0 CLI (D-16, per-machine, idempotent, reversible).
1. **Republish to maincloud** from the local v2.2.0 working tree (D-04 — pre-push, no `--clear-database`).
2. **Probe maincloud via `spacetime sql`** to confirm v2.2.0 engine fixes #4902 (autoinc) + #4666 (PK migration), embed output as markdown tables inside Task 2's `<acceptance_criteria>` block in this plan file (D-05, D-06).
3. **Human-verify checkpoint** (D-08): user reviews probe output and gives one of two signals — "approved" → finalize Commit B + push, or "rollback" → execute D-07 procedure.

Purpose: This is the verification + finalization gate of Phase 16.3. Per D-04, the republish happens locally BEFORE the remote push so the pushed-to-remote branch represents "verified working" not "about to verify" (matches Phase 12.2 commit `20ffbd3` precedent). Per D-05 + D-06, evidence lives in this plan file as markdown tables (CLAUDE.md UAT format) — no separate evidence file. Per D-08, the push is gated on user approval — this is the "cross-boundary action" CLAUDE.md autonomous-execution rules require pausing for.

Output (success path): 1 atomic Commit B on `feature_nath_claude`, branch pushed to `origin/feature_nath_claude`.
Output (failure path): rollback to Plan 01's drift-fix commit + maincloud restored to v2.1.0; no remote push.
</objective>

<sequencing_note>
**Why republish runs BEFORE Commit B is finalized (joint D-04 / D-06 constraint).**

D-04 mandates that the republish runs from the v2.2.0 bump commit so the pushed-to-remote branch represents "verified working." D-06 mandates that probe output (`spacetime sql` results) is embedded directly in this PLAN.md file as markdown tables — no separate evidence file. These two decisions JOINTLY require running the republish + probes BEFORE finalizing Commit B, because the probe output IS part of the commit's contents (this plan file is in `files_modified`). If we committed first, then republished, then probed, we would have to amend or rewrite history to embed the probe tables — violating D-01's atomicity.

Resulting sequence: **CLI upgrade precondition (Task 0, D-16) → stage Commit B working tree (Task 1) → republish to maincloud (Task 2) → run SQL probes (Task 2) → embed probe markdown tables in this plan's Task 2 `<acceptance_criteria>` → human-verify checkpoint (Task 3) → finalize Commit B + push (Task 4)** (or rollback per D-07).

The D-04 safety invariant ("the push to remote represents verified working, not about-to-verify") is preserved exactly: `git push` only happens AFTER the human-verify checkpoint (D-08 gate) approves the embedded probe output. The republish is local-to-remote-engine (not a git push), and rollback (D-07) cleanly handles a failed republish or rejected probes since no commit has been finalized yet.
</sequencing_note>
