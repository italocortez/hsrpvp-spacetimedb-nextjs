# Phase 16.4 audit notes

This file is the durable output of Plan 02's read-mostly audit task. It documents WHY
`AuthCtx` does NOT replace the project's `requireServer` / `getAuthenticatedUser` patterns,
and WHY the chosen hardening for SC#2 is `ctx.senderAuth.isInternal` on the 3 scheduled
reducers (and only the scheduled reducers). Future SDK-bump readers find both the project's
auth-model decisions AND the v2.2.0 audit findings in one place.

## AuthCtx applicability audit — D-13

### (a) Why `AuthCtx` does NOT replace `requireServer(ctx)`

Different concepts. `ctx.senderAuth.isInternal` (per `dist/lib/reducers.d.ts:47-89`) means
"this reducer was dispatched by the SpacetimeDB scheduler, not by an external client."
The project's `requireServer(ctx)` (in `spacetimedb/src/helpers/ensurePermissions.ts`)
means "the calling identity matches the registered SERVER_TOKEN identity stored in the
`ServerIdentity` table." These are non-overlapping:

- `post-publish.ts` calls reducers as the registered server-token identity. From the SDK's
  perspective `isInternal === false` (it is an external WebSocket client). Replacing
  `requireServer` with `isInternal` would lock out the post-publish bootstrap.
- The scheduler can dispatch a reducer with no caller identity check at all — `isInternal`
  would be true but the project's `ServerIdentity` row may or may not exist for the
  scheduler dispatch (it does not).

Conclusion: keep `requireServer` (project business logic — SERVER_TOKEN identity check).
Use `isInternal` for the orthogonal "engine-only" check on scheduled reducers.

### (b) Why `AuthCtx` does NOT replace `getAuthenticatedUser(ctx)`

Different model. The project auth pipeline is:
```
ctx.sender → UserIdentity.identity (lookup) → User.id → role.tag (lookup)
```
This is project business logic, not JWT-claims-based. `AuthCtx.jwt` (when `hasJWT === true`)
exposes a `JwtClaims` payload — useful for native OIDC flows, but the project intentionally
does NOT use native OIDC. Discord OAuth flows through the Next.js bridge
(`/api/auth/link-discord` → `server_link_provider`) for guest-play UX (frictionless guest →
optional Discord linking). Native OIDC would sacrifice this UX (no clean upgrade path from
anonymous to authed identity). See CONTEXT.md `<deferred>` section.

Conclusion: keep `getAuthenticatedUser` (project auth model). `AuthCtx` is the engine's
JWT envelope; the project does not consume JWT claims at the engine layer.

### (c) Why `deletedAt` stays as UX flag, NOT authorization gate

`deletedAt` on the User row is a 5-second client-side UX-window flag — not a runtime
authorization gate. Per:
- `.planning/phases/15.2-user-directory-view-performance/15.2-CONTEXT.md` line 157 (D-03):
  "deletedAt exists for the 5-second 'your account is being deleted' notification window."
- `docs/auth/contract.md` lines 164-166: documents the `deletedAt` precondition for
  `performUserDeletion` as part of the contract's *Given*, NOT enforced as a runtime check.
- `.planning/phases/15.2-user-directory-view-performance/15.2-CONTEXT.md` line 160:
  Phase 15.2 explicitly preserved `userDeletion.ts` shape ("no changes to userDeletion.ts
  needed"). The lack of a caller `deletedAt` check is inherited from 12.x design,
  not (re-)decided in 15.2.

Adding `if (!user.deletedAt) throw` inside `performUserDeletion` would change documented
semantics and lock out future writers that legitimately skip the UX window.

Conclusion: leave `performUserDeletion` (`spacetimedb/src/helpers/userDeletionHelper.ts`)
UNCHANGED. The `isInternal` guard on `run_user_deletion` (the scheduled-reducer entry point)
is the right place to add the external-invocation defense — without touching helper
semantics that other call paths depend on.

### (d) Why `isInternal` is the right hardening

Phase 12.1's documented engine-only assumption (12.1-RESEARCH.md Pitfalls 1-8) explicitly
enumerates 8 pitfalls of scheduled reducers — none of which discuss external invocation.
The original 12.1 Plan 02 split admin variants (`admin_gc_lobbies`, `admin_gc_identities`)
from scheduled variants (`run_lobby_gc`, `run_identity_gc`); admin variants gate with
`ensureModerator(ctx)`, scheduled variants left ungated under the engine-only assumption.

v2.2.0's `ctx.senderAuth.isInternal` (PR #4649) lets the project encode that assumption as
a runtime check rather than relying on it implicitly. This is a defense-in-depth move:
if a future SpacetimeDB version exposed scheduled-reducer entry points to external clients
(intentionally or via bug), the project's hardening still rejects forged calls.

Conclusion: `if (!ctx.senderAuth.isInternal) throw new SenderError(...)` is the right
hardening — orthogonal to existing project gates, no helper changes, no auth model
changes, no docs changes.

## isInternal hardening — sites + verbatim guard

| File | Reducer | Existing import? | Guard placement |
|---|---|---|---|
| `spacetimedb/src/reducers/lobbyGc.ts` | `run_lobby_gc` | YES (line 7) | First statement, BEFORE `performLobbyGc(ctx)`. |

Verbatim guard text (consistent across all 3 sites for grep / log analysis):
```typescript
if (!ctx.senderAuth.isInternal) {
    throw new SenderError(
        'Forbidden: scheduled reducer; cannot be invoked externally.'
    );
}
```

the property is `senderAuth: AuthCtx`, NOT `auth` (per D-15 wording correction).

## v0.6 Update — Plan 07 Diagnostic Reversal

**Date:** 2026-05-03
**Owner:** Plan 07 hotfix (commits `9c634bc`, `f24fd86`, `ead065d`, plus this amendment)
**Trigger:** D-1 in `deferred-items.md` — `user-deletion.test.ts` D-17 cascade tests failed in
the integration suite; isolation rerun (after `--clear-database` republish) reproduced the
failure deterministically against a clean DB, refuting the original "test-infra state
accumulation" theory.

### What changed

The 3 `if (!ctx.senderAuth.isInternal) throw new SenderError(...)` guards installed by
Plan 02 in `userDeletion.ts`, `lobbyGc.ts`, and `identityGc.ts` (commits `bb314db`,
`3a2253c`) were **REVERTED** by Plan 07 hotfix commit `9c634bc`. The reducer bodies are
otherwise unchanged; the rest of Plan 02's deliverable (AUDIT applicability findings,
`SenderError` import handling, regression sensor test) is preserved.

### Root cause — finding (d) was wrong

Finding (d) above ("`isInternal` is the right hardening") rested on the assumption that
SpacetimeDB v2.2.0's `ctx.senderAuth.isInternal` returns `true` for engine-dispatched
scheduled reducers. **That assumption is incorrect for v2.2.0** — SDK source-level analysis
proves the factory that sets `isInternal: true` is unreachable from any code path that
produces `ctx.senderAuth`.

#### SDK source-level proof

File: `spacetimedb/node_modules/spacetimedb/dist/server/index.mjs` (v2.2.0)

```js
// AuthCtxImpl exposes ONE constructor that sets isInternal=true:
static internal() {                                          // line 6383-6388
  return new _AuthCtxImpl({ isInternal: true, ... });
}

// fromSystemTables ALWAYS sets isInternal=false (both branches):
static fromSystemTables(connectionId, sender) {              // line 6390-6402
  if (connectionId === null) {
    return new _AuthCtxImpl({ isInternal: false, ... });     // line 6394
  }
  return new _AuthCtxImpl({ isInternal: false, ... });       // line 6400
}

// ReducerCtxImpl.senderAuth ONLY calls fromSystemTables — internal() unreachable:
get senderAuth() {                                           // ~line 6442
  return this.#senderAuth ??= AuthCtxImpl.fromSystemTables(this.connectionId, this.sender);
}
```

`AuthCtxImpl.internal()` is unreachable from `ctx.senderAuth`. **Therefore
`ctx.senderAuth.isInternal` is ALWAYS `false` in v2.2.0**, including for engine-dispatched
scheduled reducer invocations. Plan 02's regression sensor test
(`scheduled-reducer-isInternal-rejection.test.ts`) only passed because external WS callers
already cannot invoke scheduled reducers at all — the engine returns "no such reducer"
before any application code runs — giving false confidence in the guard's correctness for
the internal-dispatch path.

#### Smoking-gun maincloud logs

Captured during Plan 07 isolation rerun (`tmp/16.4-07/maincloud-cascade-evidence.log`):

```

2026-05-03T16:49:05.272509Z ERROR: run_user_deletion: Forbidden: scheduled reducer; cannot be invoked externally.
2026-05-03T16:49:17.038847Z INFO:  admin_delete_row: [ADMIN] User #4 marked for deletion. Cascade scheduled in 5s.
2026-05-03T16:49:22.038610Z ERROR: run_user_deletion: Forbidden: scheduled reducer; cannot be invoked externally.
2026-05-03T17:03:49.434643Z ERROR: run_lobby_gc:        Forbidden: scheduled reducer; cannot be invoked externally.
```

The Plan 02 guard fired on legitimate engine-dispatched invocation, breaking the cascade
for user-deletion and lobby-GC. The `run_lobby_gc` ERROR at 17:03:49 (15 minutes after
publish, when `LobbyGcJob` first fires) confirms ALL 3 hardening sites were affected — not
just user-deletion.

### What replaces the guard

The actual external-invocation defense is **engine-level**: SpacetimeDB v2.2.0 returns
`"no such reducer"` for external WS calls to scheduled reducer names, BEFORE any
application code runs. This was already documented in Plan 02 SUMMARY ("external WS callers
receive 'no such reducer' from the engine BEFORE our guard fires") — the application-level
guard was only defense-in-depth, and that defense-in-depth is what is broken in v2.2.0.

The regression sensor test (`test/backend/scheduled-reducer-isInternal-rejection.test.ts`)
was updated by Plan 07 commit `f24fd86` to document the engine-level rejection as the
operational defense; the assertion regex still accepts both rejection messages
(`/no such reducer|Forbidden/i`) for future-compat.

### What stayed

- Findings (a), (b), (c) above remain valid — `AuthCtx` is not a substitute for
  `requireServer`, `getAuthenticatedUser`, or role-based `ensureXxx` gates; `deletedAt`
  remains a UX-window flag. None of these were touched by the hotfix.
- The audit-surface inspection (7 files) and "3 productive sites" finding remain valid as
  the original Plan 02 audit deliverable.
- The Plan 02 regression sensor test still passes (with the engine-level rejection path).
- `SenderError` imports were retained in `lobbyGc.ts` and `identityGc.ts` (still used by
  the seed reducers); `userDeletion.ts` had its `SenderError` import removed (no other
  use after guard removal).

### What was removed

- The 3 application-level `if (!ctx.senderAuth.isInternal) throw` guards.
- The "isInternal hardening — sites + verbatim guard" table above is now historical.
- Finding (d) above ("`isInternal` is the right hardening") is **superseded** by this
  v0.6 Update — left in place above for the audit trail; the conclusion no longer holds.

### Future-revisit conditions

Re-evaluate this finding if any of the following occur:
1. SpacetimeDB releases a version where `ctx.senderAuth.isInternal` correctly returns
   `true` for engine-dispatched scheduled reducers (verify against SDK source).
2. SpacetimeDB exposes scheduled-reducer names to external WS callers (engine no longer
   returns "no such reducer" for them) — the engine-level defense would no longer hold.
3. A different working signal for "this invocation came from the scheduler, not an
   external client" becomes available in the SDK.

In any of those cases, re-add an application-level guard in the 3 scheduled reducers and
update the SKILL.md rule + this AUDIT-NOTES section accordingly.
