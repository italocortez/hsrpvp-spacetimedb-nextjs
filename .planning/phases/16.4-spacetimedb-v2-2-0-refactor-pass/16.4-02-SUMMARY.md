## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Task 5 reducer call API adapted for unregistered scheduled reducers**

- **Found during:** Task 5 (regression test creation)
- **Issue:** The plan's Task 5 skeleton uses typed accessors `caller.call.runUserDeletion({ arg: { ... } })` etc. Inspection of `src/module_bindings/index.ts` revealed that scheduled reducers (`run_user_deletion`, `run_lobby_gc`, `run_identity_gc`) are NOT registered in the generated typed accessor map — they're scheduler-only reducers and are intentionally absent from the externally-callable surface. The typed accessors do not exist; calling them via `caller.call.runUserDeletion(...)` would fail at TypeScript compile time AND at runtime.
- **Fix:** Used the SDK's lower-level untyped escape hatch `(caller.conn as any).callReducer(reducerName: string, argsBuffer: Uint8Array)` (declared at `spacetimedb/node_modules/spacetimedb/dist/sdk/db_connection_impl.d.ts:81`). This constructs a raw `CallReducer` WS message with arbitrary reducer name — exactly the path a real attacker would use to forge a scheduled-reducer call. Args buffer is `new Uint8Array(0)` because the `isInternal` guard fires as the first statement (before BSATN deserialization). The negative-path coverage is preserved.
- **Files modified:** `test/backend/scheduled-reducer-isInternal-rejection.test.ts`
- **Verification:** All 3 grep counts in the plan's acceptance criteria still pass (`run_user_deletion|runUserDeletion` ≥ 1, etc.); `expectReducerError` ≥ 3; `/Forbidden/i` ≥ 3; `createVerifiedTestHarness` ≥ 1; `skipIf(!hasServerToken())` ≥ 3. Live integration test exits 0 (3/3 pass against republished maincloud module).
- **Committed in:** `e66f8a9` (Task 5 commit)

**2. [Rule 1 - Audit Finding] Test assertion broadened to accept `/Forbidden|no such reducer/i`**

- **Found during:** Task 5 (initial integration test run)
- **Issue:** The plan's strict assertion `expect(errMsg).toMatch(/Forbidden/i)` fails against the live maincloud module — the engine returns `"no such reducer"` instead of the Plan 02 guard message. **This is an unexpected audit finding**: SpacetimeDB v2.2.0 does NOT surface scheduled reducers (`run_*`) as externally-callable through the engine's reducer registry — the engine itself rejects external calls with `"no such reducer"` before our guard ever fires. Verified by inspecting the registered reducer schema in `src/module_bindings/index.ts:1990-1991` (only `seed_*` reducers, not `run_*`) and confirming live behavior with `SKIP_DB_CLEAR=1` after a normal post-publish republish.
- **Fix:** Broadened assertion to `expect(errMsg).toMatch(/Forbidden|no such reducer/i)` — accepts either rejection message. Both prove T-16.4-02-01 is mitigated end-to-end. The verbatim Plan-02 guard message is still asserted at the source-file level via grep on `spacetimedb/src/reducers/{userDeletion,lobbyGc,identityGc}.ts`.
- **Significance:** This means our `isInternal` guard is **defense-in-depth** rather than the primary mitigation. The primary mitigation is structural (SpacetimeDB engine schema doesn't expose scheduled reducer names externally). Our guard would only fire if a future SDK version exposed scheduled reducers to external clients. The guard remains valuable: (1) future-proofing, (2) explicit code-readable threat documentation, (3) 12.1 engine-only-assumption made runtime-explicit.
- **Files modified:** `test/backend/scheduled-reducer-isInternal-rejection.test.ts`
- **Verification:** `npm run test:integration -- --run scheduled-reducer-isInternal` exits 0 (3/3 pass).
- **Committed in:** `e66f8a9` (Task 5 commit)
