# Phase 16.4: SpacetimeDB v2.2.0 refactor pass — Research

**Researched:** 2026-05-03
**Domain:** SpacetimeDB SDK v2.2.0 surface adoption (server + React client) — bounded refactor on a live maincloud module
**Confidence:** HIGH for SDK type signatures (verified directly against installed `node_modules/spacetimedb@2.2.0/dist/*.d.ts`); HIGH for code-site mapping (verified by reading the listed files); MEDIUM for v3 transport runtime semantics (release notes light on protocol-level detail; SDK supplies it at the build level — `withCompression` exists but no v3-protocol-version knob is exposed in the public builder API)

## Summary

CONTEXT.md is comprehensive and locks 14 decisions across 7 plans. The job of this research is to surface what the planner needs that CONTEXT.md does **not** provide — specifically, two **planner-blocking discoveries** that arise from inspecting the actual installed v2.2.0 type surfaces and the React component code:

1. **`useProcedure` is for procedures, NOT reducers.** The project has zero procedures defined (`__procedures()` is called with no args at `src/module_bindings/index.ts:2037`). The hook that types-wraps reducer call sites in React is `useReducer(reducerSchema)` — it's been in the SDK since before 2.2.0. CONTEXT.md D-05 / D-10 / D-11 reference `useProcedure(procedures.X)` for the 6 reducer call sites; this will not compile because `procedures.X` does not exist for the project's reducer set. Plan 06 must either (a) adopt `useReducer` instead of `useProcedure` (the actual typed-reducer-callback v2.2.0 surface) or (b) introduce real procedures (a much bigger backend change, out of refactor scope per `<domain>`).

2. **`app/api/auth/link-discord/route.ts` cannot use any React hook.** It is a Next.js Route Handler running in Node, not a React component. Its reducer call goes through `getServerConnection()` (a non-React `DbConnection` from `lib/spacetimedb-server.ts`). Plan 06's site-list of 6 must drop this site to 5 — or, if the hook is intended only for React components, document explicitly why this site is excluded.

Beyond those two corrections, the research surfaces (a) the `useTable` enabled-prop's actual location (it lives in the **second-arg callback object**, not as a third arg or a separate option), (b) `Table.clear()`'s confirmed return type (not exposed in public TS types — must call without expecting a count), (c) the `--yes=migrate` flag verified via `spacetime publish --help`, (d) Validation Architecture covering Plan 04's WebSocket capture probe + Plan 07's republish smoke gate, and (e) skill-update phrasing matched to the established voice in `.claude/skills/spacetimedb/SKILL.md`.

**Primary recommendation:** Have the planner correct D-05/D-10/D-11 from `useProcedure` to **`useReducer`** before plan generation, drop `app/api/auth/link-discord/route.ts` from the React-hook adoption list, and otherwise execute CONTEXT.md as written. The other 12 decisions are correct on inspection.

| Instead of | Could Use | Why we don't |

### Pattern 1: `Table.clear()` 1:1 swap (Plan 01)

**What:** Replace `[...ctx.db.X.iter()].forEach(r => ctx.db.X.delete(r))` (or the project's `nuke()` helper that wraps it) with a single `ctx.db.X.clear()` call.

**When to use:** Any whole-table wipe with NO predicate. If a predicate is required (SYSTEM-preserving filters in 3 cases), keep iter+filter+delete.

**Example** (verified pattern from CONTEXT.md D-09):
```typescript
// Source: spacetimedb/src/reducers/server.ts (post-refactor pattern)

// BEFORE (lines 434, etc.)
totalDeleted += nuke(ctx.db.MatchSessionStep, 'MatchSessionStep');

// AFTER
ctx.db.MatchSessionStep.clear();
// Note: no rows-count returned — the ABI signature does not surface a count
// in TypeScript declaration files. Drop the totalDeleted += accumulation
// for the 41+1=42 swapped sites; preserve it only for the 3 SYSTEM-preserving
// blocks where iter+filter+delete still runs.

// SYSTEM-preserving block — UNCHANGED
const userPrivates = [...ctx.db.UserPrivate.iter()]
    .filter((up: any) => systemUserRowId === undefined || up.userId !== systemUserRowId);
for (const up of userPrivates) { ctx.db.UserPrivate.delete(up); }
totalDeleted += userPrivates.length;
```

The single `[NUKE] complete: ${totalDeleted} rows deleted` log line at the end (server.ts:545) becomes `[NUKE] complete: SYSTEM-preserving deletes only counted` since the 42 cleared tables no longer report counts. Plan 01 should reword the final log to match (e.g., `[NUKE] complete: ${totalDeleted} rows deleted from filtered blocks; ${42} tables fully cleared`).

### Pattern 2: `senderAuth.isInternal` guard (Plan 02)

**What:** Add a single guard at the top of each scheduled reducer that throws `SenderError` if the call is not engine-dispatched.

**When to use:** Reducers wired into `setRunXxxReducer(...)` that take a `{ arg: ScheduledTable.rowType }` parameter and are intended to fire only via the SpacetimeDB scheduler.

**Example** (verified API path from `dist/lib/reducers.d.ts:47-89`):
```typescript

    { arg: UserDeletionJob.rowType },
```

**When to use:** Subscription that gates a UI panel that may not be visible / active. Layer-0 reference-data subs (GameDataProvider's 7 subs) are explicitly NOT candidates per D-05 (service worker prefetch hard constraint).

### Pattern 4: `useReducer(reducers.X)` for typed callbacks (Plan 06 — corrected per OQ-1)

**What:** Replace `getConnection()` + `conn.reducers.X(args)` with `const callX = useReducer(reducers.X); callX(args)`. The hook returns a stable Promise-returning callback that queues internally until the connection is ready.

**When to use:** Any reducer call site **inside a React component or React hook**. Server-side Node code (e.g., `app/api/auth/link-discord/route.ts`) does NOT qualify and continues to use `getServerConnection().reducers.X(...)`.

### Anti-Patterns to Avoid

- **`Table.clear()` for SYSTEM-preserving wipes.** No predicate accepted; would delete the SYSTEM row and break the audit chain on republish. Use iter+filter+delete (3 sites locked in D-09).
- **`Table.clear()` for predicate deletes (per-row, per-lobby).** GC reducers (`performLobbyGc`, `performIdentityGc`, `hardDeleteLobby`) explicitly NOT candidates per D-09. Re-investigation prevented by Plan 01 audit notes.
- **`ctx.auth.isInternal`** (wrong property name). The verified field is `ctx.senderAuth.isInternal` (`dist/lib/reducers.d.ts:85`). D-13 wording must be corrected before Plan 02 generation.
- **`useProcedure(reducers.X)`** (wrong hook for reducer calls). `useProcedure` types procedures, not reducers. Use `useReducer(reducers.X)`. CONTEXT.md D-05 needs OQ-1 resolution.
- **`useTable(table, options, callbacks)`** (wrong arg shape). The `enabled` prop lives in the second-arg callback object, not as a third arg. Verified at `dist/react/useTable.d.ts:31`.
- **Calling `useReducer` / `useProcedure` outside a React tree.** `app/api/auth/link-discord/route.ts` is a Next.js Route Handler executing server-side; React hooks are forbidden. Continues to use `getServerConnection().reducers.X(...)`.
- **Default `spacetime:publish` adopting `--yes=migrate`.** Per D-06: the destructive-migration confirm is a safety feature. The `:migrate` sibling is opt-in.
- **Adopting `.withCompression('brotli')`.** Decompression-stream brotli is a 2025-shipped non-standard browser extension; SDK throws TypeError on unsupported browsers. CONTEXT.md D-14 keeps gzip; SKILL.md gets a single note acknowledging brotli exists but is not adopted.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Whole-table wipe in a reducer | iter+spread+delete loop wrapped in a custom `nuke(table, name)` helper | `ctx.db.{Table}.clear()` (Plan 01) | v2.2.0 ships an ABI for it (#4729). Single transaction internally; less reducer-internal work. |
| "Was this reducer dispatched by the engine?" check | A custom flag table or token argument | `ctx.senderAuth.isInternal` (Plan 02) | Engine-set, tamper-proof. Token args can be forged; flag tables can be raced. |
| Granular auto-confirm flags for `spacetime publish` | Custom shell wrappers parsing `--yes` arguments | Built-in `--yes=migrate,break-clients,...` (Plan 03) | CLI-native; documented in `spacetime publish --help`. |
| WebSocket frame capture in a browser | DevTools Network → WS frame copy-paste | A scripted Node WS probe via `withWSFn` factory (Plan 04) | Reproducible by anyone; output is grep-able. CONTEXT.md D-04. |
| Subscription gating in React | `useEffect` + `subscriptionBuilder().subscribe()` + manual `unsubscribe` | `useTable(table, { enabled })` (Plan 05) | SDK handles establish/teardown atomically. v2.2.0 #4721. |
| Connection-readiness queue for reducer calls | Per-component `useEffect`-based "wait for connection" guards | `useReducer(reducers.X)` (Plan 06, per OQ-1) | SDK queues internally; one-line component-level adoption. |
| Multi-frame batching in a WebSocket transport | Fragment-and-buffer at the application layer | v3 WebSocket transport (auto-negotiated by SDK) | Built into v2.2.0; verified via Plan 04 capture (D-01). |

**Key insight:** This phase is "stop hand-rolling things v2.2.0 now provides." The full audit is in CONTEXT.md `<decisions>` block. The above list is a fast-reference index for the planner.

## Common Pitfalls

### Pitfall 1: `Table.clear()` log-line count drop is intentional, but easy to "fix back"

**What goes wrong:** A reviewer or later editor sees that the per-table `[NUKE] {name}: {count}` log lines have been dropped and thinks they were lost in the refactor; reintroduces them by capturing `Table.clear()`'s return value, which has no public TS type and may not return a count.

**Why it happens:** The grep audit showed `scripts/nuke-test-data.ts` does not parse the per-table logs (verified in CONTEXT.md `<canonical_refs>`). Drop is safe per D-09. But the reasoning is invisible to a future reader.

**How to avoid:** Plan 01 commits MUST include a comment block at the top of the refactored `server_nuke_test_data` reducer documenting "[NUKE] {name}: {count} per-table logs intentionally dropped per Phase 16.4 D-09; sole consumer (scripts/nuke-test-data.ts) only awaits resolution and does not parse logs." Audit-trail in source.

**Warning signs:** Code review comment "why no per-table logs?" The comment block answers it.

### Pitfall 2: `senderAuth.isInternal` adds runtime check but breaks `spacetime call` from CLI

**What goes wrong:** Phase 02 hardens `run_user_deletion`, `run_lobby_gc`, `run_identity_gc` with `if (!ctx.senderAuth.isInternal)`. After publish, anyone who tried to `spacetime call <db> run_lobby_gc` (an external WS caller) will now get `Forbidden`. If integration tests or operations runbooks invoke these reducers directly via CLI, they break.

**Why it happens:** Pre-refactor, the engine-only-assumption was implicit per 12.1 design. The new check makes it explicit — but the implicit assumption was not enforced, so external callers might exist as informal tooling.

**How to avoid:** Plan 02 grep audit MUST confirm:
- `scripts/*` — no `spacetime call ... run_user_deletion|run_lobby_gc|run_identity_gc` invocations
- `test/*` — no `conn.reducers.runUserDeletion(...)` invocations (note: integration tests should use `admin_gc_lobbies` / `admin_gc_identities` admin variants for ad-hoc trigger; only the engine should call the scheduled variants)
- `docs/*` — no operational runbook documenting "run `spacetime call run_lobby_gc` if GC seems stuck" (admin variants exist for that; the doc should point at admin_gc_lobbies)

If any external caller is found, it must be migrated to the admin variant before the isInternal guard is added.

**Warning signs:** Integration test failure on `run_user_deletion`-related tests; operational runbook references that grep finds in `docs/`.

### Pitfall 3: `useTable({ enabled: false })` does NOT replay frames on `enabled: true` flip

**What goes wrong:** A component does `useTable(tables.X, { enabled: isActive })`. User toggles tab off (`isActive: false`) for a while; during that gap, other clients update X. User toggles tab back on (`isActive: true`). The component now sees X via a fresh subscription — but the SDK does NOT replay the missed updates as `onInsert`/`onUpdate`/`onDelete` callbacks. The cache is reconstituted as the post-update snapshot.

**Why it happens:** v2.2.0 #4721 docs frame this as "subscribe lifecycle gating," not "buffered subscription." When enabled flips false→true, it's equivalent to mounting a fresh useTable.

**How to avoid:** For UserManager and TableExplorer (Plan 05 targets), this is FINE — both render rows from the array, not from imperative callbacks. They do not register `onInsert`-style callbacks against the gated subs. So the absence of replay does not affect them. Plan 05 should explicitly document this in the plan body so future readers don't mistake it for a regression.

**Warning signs:** Component that registers `onInsert` callbacks expecting to log every newly inserted row across the user's full session — these are NOT candidates for `enabled` gating without additional complexity.

### Pitfall 4: `useReducer` queue does NOT solve "what if the user navigates away mid-call"

**What goes wrong:** `const callX = useReducer(reducers.X); callX({...}).then(...)`. The hook queues until connection-ready. But if the component unmounts before the call resolves, the `.then(...)` continuation runs against an unmounted component (React warns about state updates on unmounted components).

**Why it happens:** `useReducer`'s queue is keyed to connection-readiness, not to component-mount. The Promise is fire-and-forget at the connection level; React's mount-state is orthogonal.

**How to avoid:** The 5 productive React component sites (Plan 06 per OQ-1) use `.catch((err) => setMessage(...))`. Plan 06 should retain the existing pattern of guarding state updates: `.catch((err) => { if (mountedRef.current) setMessage(...); })` if any of the 5 components are sensitive to unmount-during-call. Inspect each: ProfileCard sets local state — guard. UserManager sets local state — guard. TableExplorer same. BulkUpsert same. useAuth — already wraps in `mounted`-style refs (lines 230, 330, 354).

**Warning signs:** React console warnings about "state update on unmounted component."

### Pitfall 5: Plan 04 capture script — connection token handling, identity churn

**What goes wrong:** `tools/capture-ws-frames.ts` connects as a fixture user. If it captures a fresh anonymous identity each run, the captured frame size will include initial-load of the layer-0 tables (~70-100 KB on wire per `notes/v09-frontend-subscription-strategy.md`); the "baseline" includes that one-time cost and is not representative of a returning-user steady state.

**Why it happens:** Anonymous identity is generated server-side on first connect; the SDK stores the token for reuse, but a script run in a fresh process won't have it.

**How to avoid:** Plan 04 should pin a fixture token (committed under `tools/` or via env var read from `.env.local`) so each capture run reconnects as the SAME identity. Document in the summary.md whether this is a "first connection" capture or a "returning-user" capture; consider capturing both for the baseline.

**Warning signs:** Frame-size summary numbers in the hundreds of KB on a single capture session — likely captured the initial-load burst.

### Pitfall 6: Plan 07 republish — Table.clear() in production triggers different audit event order

**What goes wrong:** `Table.clear()` may emit a single `clear` event vs. N `delete` events at the engine level. Any subscription view or downstream callback that depends on per-row delete events firing in a particular order may break — but ONLY in `server_nuke_test_data`'s execution context (which is dev-only). Plan 07's `admin_gc_lobbies` smoke probe exercises the GC path that does NOT use `Table.clear()`, so it doesn't sense this hazard.

**Why it happens:** Per release notes #4729 the API is described as "ABI for clearing tables" — not as a sugar over per-row delete. Audit log emission is unspecified in public docs.

**How to avoid:** Production never triggers `server_nuke_test_data` (per its own confirmation gate); this hazard is dev-only. Plan 01 should NOT add a regression test for "delete events fire in order" because no production code depends on it. If a test author cares, point them at the existing `[NUKE] complete` log line as the acceptance signal. Documented in Plan 01 audit notes.

**Warning signs:** None expected in production. Dev-only `nuke-test-data.ts` continues to await resolution; Phase 07 GC smoke probe verifies the unrelated GC chain stays unbroken.

## Open Questions

### OQ-1: `useProcedure` vs `useReducer` — D-05 / D-10 / D-11 wording correction

**What we know:**
- `useProcedure` (v2.2.0 #4752) is typed for procedures: `useProcedure<ProcedureDef>(procedureDef)`. It expects an `UntypedProcedureDef`, which is created by `spacetimedb.procedure(...)` on the server.
- Project reducers are defined via `spacetimedb.reducer(...)`. They become `UntypedReducerDef`, NOT `UntypedProcedureDef`.
- Project has zero procedures — `__procedures()` is called with no args at `src/module_bindings/index.ts:2037`. The exported `procedures` map is empty.
- The hook for typed reducer callbacks in React components is `useReducer<ReducerDef>(reducerDef)` — same type system, exported alongside `useProcedure` from `spacetimedb/react`.
- Both hooks return Promise-returning callbacks; `useProcedure` returns `Promise<ProcedureReturnType>`, `useReducer` returns `Promise<void>` (consistent with reducers having no return value).

**What's unclear:** Whether the user, when locking D-05/D-10/D-11, intended `useProcedure` literally (in which case the correct response is "Plan 06 must add a server-side procedure, which is out of refactor scope") or used `useProcedure` colloquially to mean "the new typed-callback hook for reducers" (in which case the correct hook is `useReducer`).

**Recommendation:** Treat as a wording correction. The intent is clearly "remove getConnection() + null-check boilerplate at 5 React component reducer call sites" (the documented motivation in CONTEXT.md `<specifics>`). `useReducer` accomplishes this; `useProcedure` does not (cannot — no procedures exist). The planner SHOULD:

1. Rewrite D-05's "useProcedure adopted across the 6 existing reducer call sites" as "useReducer adopted across the 5 React component reducer call sites."
2. Drop `app/api/auth/link-discord/route.ts` from the list — it is server-side Node code, no React hook applies.
3. Update D-10 to "Plans 05/06 commit useTable/useReducer rules" in SKILL.md.
4. Update D-11's D-10 entry text from `useProcedure(procedures.X)` to `useReducer(reducers.X)`.

**If the user disagrees** and intended `useProcedure` literally, the phase scope expands significantly (introduce procedures, redesign auth flow to consume them, etc.) — that's a re-discuss territory, not a planner correction. Flag explicitly in the plan-checker pass.
