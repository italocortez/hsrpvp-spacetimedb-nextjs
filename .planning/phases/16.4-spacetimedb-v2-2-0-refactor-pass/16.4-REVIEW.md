**Reviewed:** 2026-05-03

## Summary

Phase 16.4 covers the SpacetimeDB v2.2.0 refactor pass: server.ts nuke now uses `ctx.db.X.clear()` (Plan 01), the misguided `isInternal` guards are reverted (Plan 07 hotfix — the regression sensor and call-sites all consistently document engine-level "no such reducer" defense), and 5 React sites adopt `useTable({ enabled })` + `useReducer(reducers.X)` (Plans 05/06). The reverted reducer files (`userDeletion.ts`, `lobbyGc.ts`, `identityGc.ts`) match the pre-Plan-02 state with appropriate audit-trail comments, and the regression sensor `scheduled-reducer-isInternal-rejection.test.ts` correctly asserts engine-level rejection. SKILL.md additions (`useTable enabled`, `useReducer`, `Table.clear()`, AuthCtx warning, publish:migrate) are internally consistent and cross-reference the audit notes.

The blockers are NOT in the v2.2.0 refactor sites — they were introduced in `TableExplorer.tsx` (Plan 05's enabled-gating refactor surface). The component's `getPrimaryKeyJson` produces payloads that do not match the server's `admin_delete_row` JSON contract for three composite-key tables (`HsrLightconeCost`, `HsrCharacterCost`, `MatchSessionStepHistory`). One of these will throw `SyntaxError` on every delete attempt; another silently deletes the wrong row.

## Blocker Issues

### BL-01: HsrLightconeCost delete will throw SyntaxError on every attempt

**File:** `components/features/admin-view/components/TableExplorer.tsx:45`
**Issue:** The PK builder returns the raw `lightconeName` string, but `admin_delete_row` (in `spacetimedb/src/reducers/admin.ts:229-241`) parses the payload as JSON and reads `key.lightconeName` and `key.gameModeTag`. `JSON.parse("momentofvictory")` throws `SyntaxError: Unexpected token o in JSON at position 1`. Every admin delete on the HsrLightconeCost table fails before the server ever resolves a row, regardless of which row is selected.

There is also a logical mismatch: HsrLightconeCost is a 4-tuple composite key (lightconeName, gameMode, draftMode, costSetId) — the reducer is matching on only 2 (lightconeName, gameModeTag), so even if the JSON were correct, deletes could target the wrong row.

**Fix:**
```typescript
// TableExplorer.tsx
case 'HsrLightconeCost':
    return JSON.stringify({
        lightconeName: row.lightconeName,
        gameModeTag: row.gameMode.tag,
        draftModeTag: row.draftMode.tag,
        costSetId: row.costSetId ?? 0,
    });

// admin.ts case 'HsrLightconeCost' — extend the predicate to include all 4 fields,
// matching the table's actual composite key.
```

### BL-02: MatchSessionStepHistory delete sends a non-existent field

**File:** `components/features/admin-view/components/TableExplorer.tsx:47`
**Issue:** The PK builder returns `row.matchId`, but the table column is `matchHistoryId` (verified in `spacetimedb/src/tables/matchSessionStepHistory.ts:5`). `row.matchId` is `undefined`. The `admin_delete_row` reducer (admin.ts:294-301) calls `JSON.parse(undefined)` which throws.

Even if the field name were corrected, the table's PK is a 3-tuple `[matchHistoryId, gameNumber, sequence]` (matchSessionStepHistory.ts:23) but the reducer treats it as a 2-tuple `[stepPK[0], stepPK[1]]`. So delete-by-PK can match multiple rows and pick the wrong one (the `.find(r => r.sequence === stepPK[1])` lookup ignores `gameNumber`).

**Fix:**
```typescript
// TableExplorer.tsx
case 'MatchSessionStepHistory':
    return JSON.stringify([row.matchHistoryId, row.gameNumber, row.sequence]);

// admin.ts case 'MatchSessionStepHistory' — extend predicate to all 3 fields:
const stepPK = JSON.parse(primaryKeyJson);
const stepRow = [...ctx.db.MatchSessionStepHistory.by_match_history.filter(stepPK[0])]
    .find((r: any) => r.gameNumber === stepPK[1] && r.sequence === stepPK[2]);
```

### BL-03: HsrCharacterCost delete can target the wrong row

**File:** `components/features/admin-view/components/TableExplorer.tsx:38-39` (and `spacetimedb/src/reducers/admin.ts:216-227`)
**Issue:** The HsrCharacterCost table has a 4-field composite key `(characterName, gameMode, draftMode, costSetId)` — verified by the bulk-upsert path at `admin.ts:486-490` ("15.4 D-19: Match existing rows on the FULL composite tuple (characterName, gameMode, draftMode, costSetId)"). But the client sends only `{characterName, gameModeTag}` and the delete reducer matches on those two fields only, then breaks out of the iter loop on the first hit.

If a row exists for `(march7th, MemoryOfChaos, Classic, costSetId=0)` and the admin clicks delete on `(march7th, MemoryOfChaos, Auction, costSetId=2)`, the reducer iterates and deletes whichever row was inserted first matching the 2-field tuple — silently wrong target. No error fires.

This is a data-integrity blocker for any non-default cost set or non-Classic draft mode.

**Fix:**
```typescript
// TableExplorer.tsx
case 'HsrCharacterCost':
    return JSON.stringify({
        characterName: row.characterName,
        gameModeTag: row.gameMode.tag,
        draftModeTag: row.draftMode.tag,
        costSetId: row.costSetId ?? 0,
    });

// admin.ts case 'HsrCharacterCost' — extend predicate to all 4 fields.
```

### BL-04: ProfileCard reports "Profile updated!" before async reducer completes

**File:** `components/features/profile/components/ProfileCard.tsx:40-63`
**Issue:** `handleSave` fires `updateUsername({...}).catch(...)` and `updateDisplayName({...}).catch(...)` (both async, returned Promise discarded), then synchronously calls `setMessage({ type: 'success', text: 'Profile updated!' })` on line 62 — BEFORE either reducer has reached the server.

If a reducer fails on the server (e.g., username already taken, SenderError), the `.catch` callback runs LATER and overwrites the success message with the error. But during the in-flight window the user sees "Profile updated!" which is a lie. Worse, if the user clicks Save and immediately navigates away or refreshes, the error toast never shows.

This violates the "fire-and-forget, react to events" contract documented in SKILL.md (cheat sheet § "The SpacetimeDB mindset"): success should only be reported when the User row actually updates (via the `useTable` subscription / `_then()` callback).

**Fix:** Use `.then().catch()` chains and set success only after each Promise resolves. Track per-field state:
```typescript
const handleSave = () => {
    setMessage(null);
    const tasks: Promise<void>[] = [];
    if (usernameChanged) {
        const trimmed = username.trim();
        if (!trimmed || trimmed.length > 32) {
            setMessage({ type: 'error', text: 'Username must be 1-32 characters.' });
            return;
        }
        tasks.push(
            updateUsername({ newUsername: trimmed }).catch((err: any) => {
                throw new Error(err?.message || 'Failed to update username.');
            })
        );
    }
    if (displayNameChanged) {
        const trimmed = displayName.trim();
        if (!trimmed || trimmed.length > 32) {
            setMessage({ type: 'error', text: 'Display name must be 1-32 characters.' });
            return;
        }
        tasks.push(
            updateDisplayName({ newDisplayName: trimmed }).catch((err: any) => {
                throw new Error(err?.message || 'Failed to update display name.');
            })
        );
    }
    Promise.all(tasks)
        .then(() => setMessage({ type: 'success', text: 'Profile updated!' }))
        .catch((err: any) => setMessage({ type: 'error', text: err.message }));
};
```

## Warnings

### WR-01: useAuth render-diagnostic console.log left in production code

**File:** `components/features/auth/hooks/useAuth.ts:62-68`
**Issue:** A `console.log('[useAuth] render', { ... })` fires on every render of `useAuth`. The hook has 9 known consumers (per the comment on line 380); each render of any consumer that propagates state up will fan out additional renders. In production this becomes a continuous log stream — and at the same time the file logs at lines 120, 136, 140, 153, 168, 175, 237, 260, 275, 314, 331, 335 for normal flow events, so the noise is significant.

Diagnostic logs of this density should be gated behind a debug flag.

**Fix:** Wrap the render log in `if (process.env.NODE_ENV !== 'production')` or a project-level debug flag. The flow logs (Strategy 1 hit / View hit / etc.) at debug level (`console.debug`) so production filters them out by default.

### WR-03: Misleading "seconds" log unit in identity GC

**File:** `spacetimedb/src/reducers/identityGc.ts:78`
**Issue:** The log line is:
```javascript
console.log(`[IDENTITY_GC] Deleted stale identity for user #${userId} (idle: ${BigInt(idleMicros) / 1_000_000n}s)`);
```
Two issues:
1. `idleMicros` is already a BigInt (computed on line 75 from BigInt subtraction). The `BigInt(idleMicros)` cast is redundant and slightly misleading.
2. Dividing micros by 1_000_000 produces seconds — but for a 90-day TTL the value is ~7,776,000s. The log says "Ns" which a reader may misread as a small unit (millis). At 90-day-default scale, "days" or "hours" would be more readable.

**Fix:**
```javascript
const idleDays = idleMicros / (1_000_000n * 86_400n);
console.log(`[IDENTITY_GC] Deleted stale identity for user #${userId} (idle: ${idleDays} days)`);
```

### WR-04: capture-ws-frames passes `{}` to no-arg reducer

**File:** `tools/capture-ws-frames.ts:267`
**Issue:** `await conn.reducers.loginAsGuest({})` passes an empty object to `login_as_guest`, which has no schema params (verified `src/module_bindings/login_as_guest_reducer.ts:13` exports `default {}` schema). SKILL.md (lines 252) explicitly documents: "Empty-param reducers (no schema params) are called as `callX()`, not `callX({})` — Passing `{}` is a TypeScript error."

This compiles only because the file uses `as any` factory cast on line 240 (`.withWSFn(factory as any)`) which suppresses some type-narrowing context. Even so, the typed accessor `conn.reducers.loginAsGuest` should reject `{}`.

**Fix:** Change to `await conn.reducers.loginAsGuest()`.

### WR-05: capture-ws-frames token-equality check is silently bypassed when SPACETIMEDB_SERVER_TOKEN is unset

**File:** `tools/capture-ws-frames.ts:60-68`
**Issue:** The "refuse admin token" guard:
```javascript
if (fixtureToken === process.env.SPACETIMEDB_SERVER_TOKEN) { ... }
```
fails open when `SPACETIMEDB_SERVER_TOKEN` is not present in `process.env` — both sides become `undefined` if you somehow set `fixtureToken=''` (and `loadEnvFile` wouldn't override an empty string because `process.env[key]` is truthy-checked on line 38), but more practically: if a developer edits `.env.local` without `SPACETIMEDB_SERVER_TOKEN` defined and pastes the admin token into `CAPTURE_WS_FIXTURE_TOKEN` from elsewhere, the check passes and the admin token is used.

The threat model from RESEARCH.md OQ-2 was "admin token would skew bandwidth" — not catastrophic. But the guard advertises a property it doesn't reliably enforce.

**Fix:** Require `SPACETIMEDB_SERVER_TOKEN` to be defined to perform the check, and document the contract:
```javascript
if (!process.env.SPACETIMEDB_SERVER_TOKEN) {
    console.warn('SPACETIMEDB_SERVER_TOKEN not set — cannot verify CAPTURE_WS_FIXTURE_TOKEN is not the admin token.');
} else if (fixtureToken === process.env.SPACETIMEDB_SERVER_TOKEN) { ... }
```

### WR-06: BulkUpsert silently accepts non-JSON files

**File:** `components/features/admin-view/components/BulkUpsert.tsx:171-184`
**Issue:** `handleFileRead` parses the file content as JSON and on `JSON.parse` failure falls through to `setJsonText(text)` with no user-visible feedback (no `setMessage(...)`). The user gets the raw text loaded into the textarea and then the (separate) `validateJson` runs on the next render — but the original "file failed to parse as JSON" signal is lost. The user only sees the downstream validation error, which is generic.

**Fix:**
```javascript
reader.onload = (e) => {
    const text = e.target?.result as string;
    try {
        const parsed = JSON.parse(text);
        setJsonText(JSON.stringify(parsed, null, 2));
        setMessage(null);
    } catch (err: any) {
        setJsonText(text);
        setMessage({ type: 'error', text: `File is not valid JSON: ${err.message}` });
    }
};
```

### WR-07: server_set_datetime bypasses updateWithAudit for createdDate

**File:** `spacetimedb/src/reducers/server.ts:283-289` and `299-305`
**Issue:** When updating `user_identity.createdDate` or `lobby.createdDate`, the code manually constructs the update with hand-rolled audit columns:
```javascript
ctx.db.UserIdentity.identity.update({
    ...row,
    createdDate: ts,
    lastModifiedById: SYSTEM_USER_ID,
    lastModifiedDate: ctx.timestamp,
});
```

The project convention (CLAUDE.md and `helpers/auditColumns.ts`) is to use `auditUpdate(ctx, existing, userId)` for ALL row updates. Hand-rolled audit-column writes break the convention and will diverge if the audit schema ever changes (e.g., a new `lastModifiedReason` column added).

The reason given is that `auditUpdate` would refuse to overwrite `createdDate`. But that's the point — this reducer is a test utility writing `createdDate` directly. A better solution is a dedicated audit helper for "I am intentionally backdating createdDate" so the convention is preserved.

**Fix:** Add a helper `auditUpdateAllowingCreatedDate(ctx, existing, userId)` that explicitly preserves `createdById` but allows `createdDate` overwrite, OR add a comment on the manual writes pointing readers to the helper. Either way the inconsistency should be acknowledged.

### WR-08: TableExplorer uses unsafe `as any[]` and ignores useTable's `isReady`

**File:** `components/features/admin-view/components/TableExplorer.tsx:83-84`
**Issue:** `const [rows] = useTable(TABLE_MAP[selectedTable], { enabled: isActive });` discards the second tuple element (`isReady`). The component then proceeds to render whatever `rows` returns, including the case where `enabled` flips `false → true` and the subscription is re-establishing. During that window `rows` is empty, and the "X rows" counter and table body show stale-empty state.

This is a direct contradiction of the SKILL.md guidance (line 122): "Tuple! [rows, isReady]" and it disables the loading-state UX that the v2.1.0 fix (#4580) made reliable.

**Fix:**
```typescript
const [rows, isReady] = useTable(TABLE_MAP[selectedTable], { enabled: isActive });
const allRows = (rows ?? []) as any[];
// Render a "Loading..." state when isActive && !isReady.
```

The same applies to `UserManager.tsx:36`.

### WR-09: TableExplorer renderCell is rebuilt every time selectedTable changes

**File:** `components/features/admin-view/components/TableExplorer.tsx:140-164`
**Issue:** `handleDelete` is wrapped in `useCallback` with `[selectedTable, columns, currentUser]`, which is correct. But every change to `selectedTable` rebuilds `handleDelete`, which rebuilds `renderCell` (because `[handleDelete]` is the dep), which forces every cell to re-render even though most cells don't depend on the per-row delete handler. Combined with the `(rows || []) as any[]` cast that disables React's identity-based skip, the table re-renders fully every keystroke in the search box.

This is a code-quality issue, not a correctness one — but on large tables (e.g., 5000-row HsrCharacterCost) the cost is noticeable.

**Fix:** Inline the handleDelete call inside `renderCell` and depend only on `selectedTable` / `currentUser` / `columns` directly. Or split the actions cell into its own memoized component.
