# Phase 15.2: User Directory View Performance - Context

**Gathered:** 2026-04-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Close IN-07 from the Phase 15 code review: `view_user_directory` iterates the entire `User` table on every subscription delta (`spacetimedb/src/views/identityViews.ts:48-66`), with cost that grows unbounded as soft-deleted users accumulate.

The root cause is `userDeletionHelper.performUserDeletion`'s non-guest-with-history branch, which updates the User row in place (`username='deleted_<id>'`) rather than evicting it. Over time these "ghosts" accumulate in the live User table, bloating every User iteration (not just the directory view).

This phase (a) stops ghost accumulation by evicting archived users to a new `DeletedUser` table, (b) closes one latent privacy policy gap by flipping `view_user_directory` to auth-required, and (c) fixes a latent bug where two soft-delete writers never trigger the scheduled cascade. Scope is backend-only; Phase 16 handles frontend subscription lifecycle.

Out of scope: flipping `User.public` to false; new on-demand directory reducers (`search_users`, `get_user_public_profile`); `UserPresence` subscription-invalidation split; `UserAudit`/`UserPublic` schema refactor.

</domain>

<decisions>
## Implementation Decisions

### Schema
- **D-01:** `User.public` stays `true`. Anonymous-access control is enforced at the view layer (D-06) and in the frontend subscription manager (Phase 16), not at the DB table level.
- **D-02:** Drop `User.isPrivate` column entirely. Dead code: written twice (`auth.ts:41`, `server.ts:46`), read once (`view_my_profile` passthrough), never gated or filtered. Per-account privacy already lives on `HsrAccount.isRosterPublic` / `isRatingPublic`. Remove field from schema, both initializers, and `MyProfileRow` projection.
- **D-03:** Keep `User.deletedAt` as a **transient pending-deletion flag**. At any moment at most ~1 row has it set (the 5-second window between soft-delete and scheduled cascade). Not a long-lived ghost marker.
- **D-04:** Keep all four audit columns on `User` (`createdById, createdDate, lastModifiedById, lastModifiedDate`). Client-subscribable exposure accepted; preserves project-wide audit convention.
- **D-05:** Add new private table `DeletedUser` (not `public`) with columns `{ id: u32 (PK), displayName: string, isGuest: bool, deletedAt: timestamp }`. Archives users that have history references (the non-guest branch of `performUserDeletion`). Client never subscribes; only server-side `resolveUserLabel` and the nuke flow touch it.

### View Layer
- **D-06:** Flip `view_user_directory` from `spacetimedb.anonymousView(...)` to `spacetimedb.view(...)` in `identityViews.ts:48`. Structurally rejects anonymous subscribers; the frontend lifecycle policy ("subscribe only after login") now has a server-side anchor.
- **D-07:** `UserDirectoryRow` projection shape is unchanged. Still the D-16 safe subset: `id, username, displayName, role, avatarCharacterName, isOnline, isGuest, hasDiscordLinked, displayedAchievementId`.
- **D-08:** `view_my_profile`'s `MyProfileRow` drops `isPrivate` (removed from schema per D-02). Remaining fields unchanged. Frontend bindings regen will strip the field from generated types.

### Cascade Refactor
- **D-09:** Rewrite `userDeletionHelper.performUserDeletion:83-90` non-guest-with-history branch. Instead of the current in-place update:
  ```ts
  ctx.db.User.id.update({ ...user, username: `deleted_${userId}`, deletedAt: ..., ... })
  ```
  do the eviction:
  ```ts
  ctx.db.DeletedUser.insert({ id: user.id, displayName: user.displayName, isGuest: user.isGuest, deletedAt: user.deletedAt ?? ctx.timestamp })
  ctx.db.User.id.delete(user.id)
  ```
  The guest-no-history branch (hard-delete) is unchanged.
- **D-10:** **R1 latent bug fix** — two soft-delete writers currently set `deletedAt` without scheduling `UserDeletionJob`, so their cascades never run:
  - `index.ts:138-142` (ban-on-reconnect in `clientConnected`)
  - `banAdmin.ts:61-65` (`admin_ban_user`)
  
  Both paths gain a `UserDeletionJob.insert({...scheduledAt: now + 5s...})` call matching `admin.ts:183-188`'s pattern. This aligns all three soft-delete writers on the same two-phase pattern and incidentally closes the bug.
- **D-11:** Nuke flow in `server.ts` adds `DeletedUser` cleanup alongside the existing User/UserIdentity/UserPrivate cleanup (around line 530).

### Server-Side Helper
- **D-12:** New helper `resolveUserLabel(ctx, userId) → { displayName: string, isDeleted: bool }`:
  1. `ctx.db.User.id.find(userId)?.displayName` → if live user
  2. `ctx.db.DeletedUser.id.find(userId)?.displayName` → if archived user
  3. `` `User #${userId}` `` → fallback for truly unknown IDs
  
  Called at sites currently using inline `user ? user.displayName : \`User#${id}\`` fallback logic:
  - `lobbyViews.ts:228` (view_my_lobby_members)
  - `finalizationHelpers.ts:353` (match step actor label)
  - `finalizationHelpers.ts:399` (match participant label)
  - `lobbyLifecycle.ts:636, 708` (kick/ban target label)
  
  Sites that only reference live users (`lobbyLifecycle.ts:386, 482, 548` chat announcements; `tournamentRegistration.ts:85` self-registration) are **not** candidates — the user is always the caller and is always live by construction.

### Init Payload Trims
- **D-13:** `auth.ts:41` remove `isPrivate: false`; `auth.ts:47` remove `deletedAt: undefined` (optional column, default undefined already).
- **D-14:** `server.ts:46` remove `isPrivate: false`; `server.ts:52` remove `deletedAt: undefined`.

### Tests
- **D-15:** Existing `test/backend/auth/auth-views.test.ts` VIEW-01 test (which validates the D-16 projection) is updated to reflect the authenticated-only calling convention.
- **D-16:** Add regression test: an anonymous SpacetimeDB subscription attempt on `view_user_directory` is rejected.
- **D-17:** Add integration test: `performUserDeletion` on a non-guest-with-history user inserts a `DeletedUser` row with preserved `displayName` and removes the User row. Verify history table FK references remain intact by ID.
- **D-18:** Add unit/integration test: `resolveUserLabel` returns live displayName, archived displayName, and `User #N` fallback across the three lookup paths.
- **D-19:** Add tests for R1 fix: `admin_ban_user` and the ban-on-reconnect path in `clientConnected` both insert a `UserDeletionJob` row after setting `deletedAt`.

### Claude's Discretion
- Internal layout of the `DeletedUser` table file (single source vs. co-located with `User`).
- Exact helper module placement for `resolveUserLabel` (likely `spacetimedb/src/helpers/userLabel.ts`, matching `userDeletionHelper.ts` convention).
- Test file organization (one new test file vs. extending existing backend/auth tests).
- Wave/commit structure during planning.
- Documentation update cadence (docs/views, docs/auth) — handled via the standard verify-work doc-update checkpoint.

<code_context>
## Existing Code Insights

### Reusable Assets
- **`performUserDeletion`** (`userDeletionHelper.ts:42-92`) — already the single entry point for cascade deletion. D-09 modifies only the non-guest-with-history branch; the guest-no-history branch, `UserPrivate` cascade, `UserIdentity` cascade, `HsrAccount`/`HsrAccountCharacter` cascade, and `deleteAllCalendarDataForUser` all stay intact.
- **`hasHistoryReferences`** (`userDeletionHelper.ts:21-30`) — the authoritative list of tables that gate the guest hard-delete vs. archive decision. `DeletedUser` doesn't change this list; it's where non-guest archival rows land.
- **Two-phase soft-delete pattern** from `admin.ts:174-188` — set `deletedAt`, then `UserDeletionJob.insert({ scheduledAt: now + 5s })`. D-10 extends this pattern to the two writers (`banAdmin.ts`, `index.ts: clientConnected`) that currently diverge.
- **`anonymousLabel` precedent in chat/match views** — shows the pattern for server-side label resolution with fallbacks. `resolveUserLabel` (D-12) follows the same convention.

### Established Patterns
- **`ctx.db.<Table>.iter()` is server-side only.** None of it leaks into client subscription cost. The IN-07 concern is specifically about the `view_user_directory` reducer body, not about reducer reads of `User.id.find()`.
- **`public: true` vs `anonymousView` vs `view`**:
  - `public: true` on a table → clients can subscribe via SDK (auth-agnostic)
  - `anonymousView` → callable by unauthenticated clients
  - `view` → callable only by authenticated clients (`getAuthenticatedUser` inside the reducer body)
  D-06 flips from the second to the third. `User.public=true` (D-01) is orthogonal.
- **Audit pattern uniformity.** `auditInsert` / `auditUpdate` are used across ~40 tables. Keeping User's audit columns (D-04) preserves this uniformity even though User's audit data is largely ceremonial (always SYSTEM or the user themselves).
- **Soft-delete 5-second UX window.** The `deletedAt` flag exists specifically so the client can render a "your account is being deleted" notification before the cascade severs their UserIdentity. D-03 preserves this.

### Integration Points
- **`UserDeletionJob` scheduled reducer** fires `run_user_deletion` which calls `performUserDeletion`. D-09's change to `performUserDeletion` propagates through this path automatically — no changes to `userDeletion.ts` needed.
- **`ensurePermissions.ts:40` `if (user.deletedAt)` check** remains reachable during the 5s pending-deletion window (UserIdentity is not yet cascaded). Keep unchanged; still live access-control code.
- **Nuke flow** (`server.ts:~554-557`) iterates `User` for the dev reset path. D-11 adds a parallel iteration for `DeletedUser`.
- **`view_lobby_browser`** and **`view_public_accounts`** (both anonymous views) project no user-level identity data. No change here — they remain anonymous-callable. The only anonymous path this phase closes is `view_user_directory`.
- **Phase 16 FOUND-03** (subscription plan in `providers.tsx`) will implement the frontend-lifecycle side of the D-06 policy: subscribe to `view_user_directory` only after the session authenticates. Captured as a handoff, not scope for this phase.

### Privacy Model Note
`User.public=true` means an adversarial client with the SpacetimeDB endpoint can, in theory, subscribe to the raw `User` table and see all columns including `deletedAt` and audit fields. This phase does **not** close that gap (D-01). The view flip (D-06) closes the `view_user_directory`-specific anonymous path and anchors the frontend's "subscribe after login" policy. Closing the raw-table anonymous subscription would require `User.public=false`, which was explicitly rejected for this phase.

</code_context>

<specifics>
## Specific Ideas

- "I dont want anonymous users to automatically subscribe through the front end, we do that subscription for them once they are logged" — primary framing for D-06. The policy lives in the frontend subscription manager; D-06 gives it a server-side anchor.
- "keep the audit columns on user table" — framing for D-04 after a brief consideration of moving them to a `UserAudit` private table.
- "last login is fine to keep it at user" — framing for not splitting `lastLoginAt` into a side-table.
- "we may keep some soft deleted users anyway because not everything gets hard deleted, we keep the soft deleted users if they are part of histories and so on" — the insight that forced rethinking the iter-cost math and ultimately produced the DeletedUser archive approach (D-05, D-09).
- "I still would like to improve that iter, i dont wanna have it, is there no way?" — pushed the discussion to recognize that the ghost-accumulation in the in-place-update branch was the actual cost driver, not the filter itself.
- Phase 12 `view_user_directory` projection design (D-16 field list) is preserved verbatim — no desire to revise the safe subset.

</specifics>

<deferred>
## Deferred Ideas

- **`search_users(prefix, limit)` and `get_user_public_profile(username)` on-demand reducers.** Proposed during discussion as the replacement for a live directory subscription if we had made `User.public=false`. Since `User.public=true` stays (D-01) and `view_user_directory` is still subscribable (by authenticated clients), these reducers are unnecessary at current scale. Revisit when the User table grows past ~10k rows and a full client-side directory subscription becomes bandwidth-unfriendly.
- **`UserPresence` split** — move `isOnline` to a separate table so `view_user_directory` doesn't invalidate on every connect/disconnect. Real subscription-amplification optimization, but orthogonal to ghost accumulation. Revisit when actual subscription-recompute cost shows up in energy-budget metrics.
- **`User.public=false`** — full server-enforced privacy. Rejected for this phase (D-01). If a future audit shows adversarial subscriptions to the raw table happening, revisit with a fuller refactor including the on-demand reducers listed above.
- **`isActive: bool` btree on User** (Option B from STATE.md's original deferral note). Superseded by the DeletedUser move (D-09), which eliminates ghosts from User entirely rather than just indexing around them.
- **`User.deletedAt` btree** (reviewer's original suggestion, noted in STATE.md). Rejected: SpacetimeDB btrees cannot filter on `IS NULL`. Superseded by D-05/D-09.
- **`UserAudit` or `UserMeta` private table** — considered as an audit-column hiding mechanism. Rejected: audit column exposure accepted per D-04. Audit data isn't sensitive enough to justify the schema-split blast radius.
- **Denormalizing `displayName` into history rows** (match, MMR, stats) — eliminates the need for `resolveUserLabel` fallback at render sites. Much wider refactor with write-amplification cost on every displayName change. Revisit only if render-site lookups become a measured hot spot.
- **Phase 16 frontend subscription wiring** — capturing the Phase 16 FOUND-03 decision that `view_user_directory` is subscribed only post-authentication. Lives in that phase, not this one.

</deferred>
