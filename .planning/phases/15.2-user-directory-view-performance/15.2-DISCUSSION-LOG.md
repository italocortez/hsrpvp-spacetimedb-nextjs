## Path Through the Discussion

### 1. Intent clarification
- STATE.md marks phase DEFERRED ("iter+JS filter acceptable at v0.9-v1.0 scale, revisit at 1k+ users"); ROADMAP.md inserts it as urgent work between 15.1 and 15.3 with "Urgent work - to be planned".
- User chose to execute now to avoid shipping a perf foot-gun into Phase 16's foundation, not because scale has changed.

### 2. What the view actually is
- Question: is `view_user_directory` used by the auth flow or by many reducers? Answer: neither — it's a client-side subscription projection for display; reducers use `ctx.db.User.id.find(userId)` directly. Zero current frontend subscribers.
- Reframes the perf concern: the iter only matters once Phase 16 wires the frontend to subscribe.

### 3. First perf math (wrong)
- Initial framing assumed soft-deleted users hard-delete after 5s (per `user.ts:16` comment).
- Claude concluded savings from the filter were a rounding error and suggested killing the phase as cosmetic.
- User corrected: soft-deleted users with history stay indefinitely (`userDeletionHelper.ts:73-91`). Ghosts accumulate monotonically.
- Revised math: at 10k active users + 5k ghosts, Option B saves 33%; at 10k + 10k ghosts, 50%. Scales with ghost ratio, which only grows.

### 4. "Move ghosts out of User" proposal
- User suggested relocating soft-deleted users to a separate table as "dead weight later".
- Claude compared Options B (isActive btree), C (materialized mirror), D (DeletedUser table).
- D emerged as the cleanest end-state — eliminates ghosts from every User iteration, not just the directory. Directory view's iter cost collapses to O(active_users).

### 5. "Can we eliminate the iter entirely?"
- User pushed past "optimize" to "remove". Discussion turned to replacing the view with direct table subscription (Option F: split User schema, drop view).
- Then considered Option G: no directory subscription at all, replace with on-demand reducers (`search_users`, `get_user_public_profile`) and scoped views.
- Mid-branch, user asked whether the view makes sense for anonymous users specifically.

### 6. `isPrivate` audit
- User recalled `isPrivate` was for hiding roster; verified per-account flags (`HsrAccount.isRosterPublic`, `isRatingPublic`) already do this.
- Full grep sweep: 6 source references, zero reads of the flag, zero frontend touches. Confirmed dead code.

### 7. Audit-column decision
- Claude proposed moving audit columns + `lastLoginAt` to a private `UserAudit` or `UserMeta` table.
- User: keep audit columns on User (accepts client-subscribable exposure). Simplifies phase considerably — no new audit table.

### 8. Auth flow trace
- User requested a direct code trace of auth paths (not speculation).
- Read: `index.ts` (clientConnected/clientDisconnected), `auth.ts` (login_as_guest), `server.ts` (register_server, server_link_provider), `admin.ts` (admin_delete_row), `banAdmin.ts`, `ensurePermissions.ts`.
- Confirmed: every auth path uses server-side `ctx.db.*` access. Zero paths depend on client subscription state. `public` flag on User is orthogonal to the auth flow.

### 9. Anonymous subscription policy
- User clarified: the policy is "frontend doesn't auto-subscribe anonymous clients to User"; Phase 16's subscription manager enforces it at the frontend lifecycle.
- Claude noted that `view_user_directory` is currently `anonymousView` — callable by unauthenticated clients. Flipping to `view` (auth-required) anchors the policy server-side without touching the `public` flag on the User table.
- User accepted.

### 10. Bundled-fix audit (R1-R6)
Surfaced during the auth trace:
- **R1:** `index.ts:138-142` and `banAdmin.ts:60-65` set `deletedAt` without scheduling `UserDeletionJob` — cascade never runs. Latent bug since Phase 12. Fix bundled into this phase; costs one line per site.
- **R2:** `ensurePermissions.ts:40` `deletedAt` check is live (fires during 5s window before UserIdentity cascades). Keep unchanged.
- **R3:** SpacetimeDB autoInc monotonically increases regardless of deletion. `DeletedUser.id` collision risk limited to restore→re-delete edge case (handle idempotently).
- **R4:** Tests referencing the `deletedAt`-filter pattern need updating. Planner enumerates.
- **R5:** `UserDeletionJob` fires scheduled cascade 5s after soft-delete. `run_user_deletion` → `performUserDeletion`. Two-phase pattern must be preserved (5s window is a UX feature).
- **R6:** Phase 16 provider subscription list must subscribe `view_user_directory` only post-authentication. Captured as handoff.

### 11. Scope of new reducers
- Claude initially proposed `search_users(prefix, limit)` and `get_user_public_profile(username)` as part of Option G (no live directory).
- User questioned what they'd actually do — Claude admitted they were speculative since `User.public=true` + auth-required view means clients still have the live directory.
- Both dropped from scope. Deferred until scale demands them.

### 12. Final plan locked
- User accepted the consolidated plan. CONTEXT.md captures: D-01 (User.public=true stays), D-02 (drop isPrivate), D-03-D-04 (keep deletedAt + audit cols), D-05 (DeletedUser table), D-06 (view flip to authenticated), D-09 (cascade refactor to move-not-update), D-10 (R1 fix), D-12 (resolveUserLabel helper), plus payload trims, tests, docs.
