## User Constraints (from CONTEXT.md)

### Locked Decisions

**Schema**
- D-01: `User.public` stays `true`. Anonymous-access control enforced at view layer (D-06) and frontend subscription manager (Phase 16).
- D-02: Drop `User.isPrivate` column entirely. Dead code — written twice (`auth.ts:41`, `server.ts:46`), read once (`view_my_profile` passthrough), never gated. Per-account privacy on `HsrAccount`.

## Summary

Phase 15.2 is a pure backend refactor with three closely coupled parts: (1) prevent ghost-user accumulation in the live `User` table by evicting soft-deleted non-guests to a new `DeletedUser` archive table, (2) flip `view_user_directory` from anonymous to authenticated-only access, and (3) fix a latent bug where two of the three soft-delete writers miss scheduling `UserDeletionJob`.

All changes are in `spacetimedb/`. There is zero frontend work. After publication and binding regeneration the only visible client-side effect is that `User.isPrivate` disappears from the generated types — the frontend must be compilable with that field gone, but that compilation fix is also within this phase scope.

**Primary recommendation:** Work in two waves — Wave 1: schema changes (new `DeletedUser` table, drop `User.isPrivate`, publish, regenerate bindings). Wave 2: behavior changes (view flip, cascade refactor, R1 bug fix, helper extraction, tests). The publish/regen gate between waves ensures bindings are always in sync with implementation.

### Pattern 1: Private Table Definition (DeletedUser)

Modeled on `userPrivate.ts` — explicit `public: false`, no audit columns (lean archive table).

```typescript
// Source: verified against spacetimedb/src/tables/userPrivate.ts in repo
import { table, t } from 'spacetimedb/server';

export const DeletedUser = table({
    name: 'deleted_user',
    public: false,       // MUST be explicit per CR-01 project convention
}, {
    id: t.u32().primaryKey(),   // same ID as was the User.id — preserves FK semantics
    displayName: t.string(),
    isGuest: t.bool(),
    deletedAt: t.timestamp(),
});
```

**Why no audit columns:** This is a write-once archive row inserted by the scheduler. No update path exists, so `lastModified*` would always equal `created*`. Keeping it lean matches the project convention for internal infrastructure tables (`UserDeletionJob` has audit columns because admins create it; `DeletedUser` is system-only).

**Why no btree index:** `resolveUserLabel` does point lookups by `id` (the PK). PK lookups are O(1) without an additional index.

export function resolveUserLabel(ctx: any, userId: number): { displayName: string; isDeleted: boolean } {
    const liveUser = ctx.db.User.id.find(userId);

### Anti-Patterns to Avoid

- **Do NOT add audit columns to `DeletedUser`.** This is a write-once archive row; no update path exists. Audit columns imply update semantics that will never happen here.
- **Do NOT add a btree index on `DeletedUser.deletedAt`.** Only PK lookups happen; no range queries planned.
- **Do NOT call `getAuthenticatedUser()` inside `view_user_directory` after the flip.** The `spacetimedb.view(...)` wrapper handles anonymous rejection at the framework level — adding an explicit call is redundant and misleading.
- **Do NOT keep `.filter(u => !u.deletedAt)` as a dead filter** if D-09 is implemented in the same wave. Document the removal explicitly so it doesn't cause confusion in review.
- **Do NOT update `hasHistoryReferences` in `userDeletionHelper.ts`.** That function governs the guest-vs-non-guest decision at cascade time, not the archive mechanism. Its table list is unchanged.
- **Do NOT touch `userDeletion.ts`** (the scheduled reducer file). Its body just calls `performUserDeletion` — the D-09 change propagates automatically.
- **Do NOT add `DeletedUser` to the `hasHistoryReferences` check set.** `DeletedUser` is the destination of eviction, not a history reference table that blocks hard-deletion.

## Common Pitfalls

### Pitfall 1: Leaving the `.filter(u => !u.deletedAt)` filter after D-09
**What goes wrong:** The filter becomes a no-op (ghosts are evicted, not marked) but still signals to future readers that `deletedAt` can be truthy during normal query time — false after D-09.
**Why it happens:** Mechanical refactor, easy to forget to remove the filter.
**How to avoid:** Remove the filter when changing the eviction strategy in the same wave.
**Warning signs:** Code review sees `filter(u => !u.deletedAt)` still present after D-09 lands.

### Pitfall 2: ScheduleAt import from wrong package
**What goes wrong:** `ScheduleAt is not defined` runtime error in the scheduled reducer or at the UserDeletionJob.insert site.
**Why it happens:** `ScheduleAt` lives in `spacetimedb` (the root package), not `spacetimedb/server`.
**How to avoid:** Follow the import in `admin.ts` — `import { ScheduleAt } from 'spacetimedb'`.
**Warning signs:** TypeScript compile error or runtime panic on `ScheduleAt.time(...)`.

### Pitfall 3: Using `DeletedUser.id.delete(du.id)` vs `DeletedUser.delete(du)`
**What goes wrong:** Wrong delete API; only PK-accessor deletes exist for tables defined without `.rowType` exports.
**Why it happens:** Mixing SpacetimeDB delete API styles.
**How to avoid:** Use the `<Table>.<pkColumn>.delete(<pkValue>)` pattern (`ctx.db.DeletedUser.id.delete(du.id)`) — matches how UserPrivate is deleted (`ctx.db.UserPrivate.userId.delete(userId)`).
**Warning signs:** TypeScript error on delete call.

### Pitfall 4: view bindings not regenerated after schema change
**What goes wrong:** `User.isPrivate` still exists in frontend TypeScript types; compilation may silently pass if the field is optional or any-typed elsewhere.
**Why it happens:** Schema changed but `spacetime generate` not run.
**How to avoid:** Publish + regen bindings as the first wave gate before touching anything that depends on the new/removed columns.
**Warning signs:** `isPrivate` still appears in `src/module_bindings/` after publish.

### Pitfall 5: Binding accessor name for DeletedUser PK
**What goes wrong:** `ctx.db.DeletedUser.id.find(...)` fails at runtime because the accessor name generated for the PK column depends on the column name.
**Why it happens:** SpacetimeDB accessor names are camelCase of column name; `id` → `.id` accessor. This is correct and consistent with `User.id.find(...)`.
**How to avoid:** Confirm accessor against generated bindings after publish. The pattern `ctx.db.DeletedUser.id.find(userId)` matches every other u32-PK table in this project.

### Pitfall 6: `admin_ban_user` — using `user.id` vs `admin.id` as actorId in auditInsert
**What goes wrong:** Job row has wrong `createdById`; audit trail shows banned user created their own deletion job.
**Why it happens:** `banAdmin.ts` already has `admin` in scope but the natural copy-paste from the user branch might use `user.id`.
**How to avoid:** `...auditInsert(ctx, admin.id)` — the admin initiated the ban, not the banned user. Matches the BanRecord insert on line 51 of the same file.

### Pitfall 7: clientConnected actorId in auditInsert
**What goes wrong:** Wrong actor in the UserDeletionJob audit trail.
**Why it happens:** `clientConnected` detects a ban on the user's own reconnect; the actor is the system enforcing the ban automatically. Use `user.id` (the affected user) since no human admin is present — consistent with how `clientConnected` audits the `isOnline` update on line 123.
**How to avoid:** `...auditInsert(ctx, user.id)` — matches existing pattern in that handler.

### Pitfall 8: Test harness cannot test view authentication rejection via SQL
**What goes wrong:** Writing a test that tries `spacetime sql "SELECT * FROM view_user_directory"` and expecting it to fail — views are not physical tables, SQL CLI has no sender context.
**Why it happens:** Confusion between views (virtual) and tables (physical).
**How to avoid:** D-16 regression test uses the WebSocket subscription path (`conn.db.viewUserDirectory...`) from a guest harness, not SQL. The existing `auth-views.test.ts` pattern (`expect(true).toBe(true)` with explanatory comment) is the established approach for view tests that can't be automated. Update VIEW-01 comment to document authenticated-only behavior. For D-16, use `createTestHarness()` (guest) and attempt a subscription, expecting rejection.

## Open Questions

1. **Should `resolveUserLabel` return `{ displayName, isDeleted }` or just `displayName: string`?**
   - What we know: All current call sites only use the displayName string.
   - What's unclear: Future sites (e.g. HIST-02 match detail) might want to know if the label is a fallback to show "(deleted)" indicator.
   - Recommendation: Return the struct with `isDeleted` flag — zero cost at call sites that destructure only displayName, and available for future use without changing the helper signature.

2. **Is the `clientConnected` `UserDeletionJob` insert safe if the user reconnects during the 5-second window?**
   - What we know: `admin.ts:148` already blocks deletion if `user.deletedAt` is set ("already pending deletion"). The `clientConnected` ban-on-reconnect check already guards `if (isBanned && !user.deletedAt)` (index.ts:137).
   - What's unclear: If the user manages to reconnect a second time before the scheduler fires, `!user.deletedAt` would be false (already set), so no second job would be inserted.
   - Recommendation: No issue. The existing guard prevents double-insert.
