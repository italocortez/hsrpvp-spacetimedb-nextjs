## Summary

Phase 15.2 is a well-structured backend refactor. The three anchor deliverables — `view_user_directory` auth flip, `DeletedUser` archive table, and the R1 two-phase delete fix — are all implemented correctly and consistently. The `ScheduleAt` import source is correct (`'spacetimedb'`, not `'spacetimedb/server'`) at all three writer sites. The `resolveUserLabel` helper correctly implements the three-path lookup. No critical security or correctness issues were found.

Two warnings are raised: a stale JSDoc in `userDeletionHelper.ts` that describes the old ghost-user pattern (not the new eviction pattern), and a stale file-level comment in `identityViews.ts` that still labels `view_user_directory` as "anonymous." Both mislead future readers about the actual behavior. Two info items: the test at `user-deletion.test.ts:63` uses wrong SQL column names for `mmr_history` (the INSERT is guarded by a `.catch(() => {})` so it fails silently rather than crashing the test, but it means the "has history references" precondition is not actually established by that SQL path), and `view_my_profile` exposes `deletedAt` to the caller while they are in the 5-second soft-delete pending window (correct by design, documented here for awareness, not a flag).

## Warnings

### WR-01: Stale JSDoc in `performUserDeletion` describes old ghost-user pattern

**File:** `spacetimedb/src/helpers/userDeletionHelper.ts:36`
**Issue:** The JSDoc summary for `performUserDeletion` (lines 32-40) still reads:
```
All others → soft-delete: username='deleted_<id>', discordId cleared, displayName preserved.
```
This describes the pre-Phase-15.2 in-place ghost mutation. The actual implementation (lines 81-88) now does `DeletedUser.insert + User.id.delete` (eviction, not in-place update). The word "soft-delete" in the summary conflicts with the eviction semantics documented in the phase history. Any engineer reading the JSDoc first will have a false model of what the function does and may introduce callers that assume `User.username.find('deleted_42')` still works.

**Fix:** Replace the stale summary line:
```typescript
/**
 * Cascade-delete active-state rows, then evict or hard-delete the User row.
 *
 * Cascade: UserPrivate, calendar data, UserIdentity, HsrAccount, HsrAccountCharacter.
 * Guest users with no history references → hard-delete User row (no archive).
 * All others → insert DeletedUser archive row (preserving displayName), then
 *   hard-delete User row. Ghost users no longer accumulate in User.iter() (D-09).
 *
 * Safe to call even if UserIdentity rows were already deleted (e.g. identity re-pointed
 * during Discord linking) — the filter returns 0 rows and the loop is a no-op.
 */
```

### IN-01: Test SQL INSERT for `mmr_history` uses wrong column names — silently no-ops

**File:** `test/backend/auth/user-deletion.test.ts:63-66`
**Issue:** The D-17 integration test attempts to insert a synthetic `mmr_history` row to force `hasHistoryReferences()` to return `true`. The SQL uses column names `character_name`, `rating_before`, `rating_after`, `match_result_id` — none of which exist on the actual `MmrHistory` table. The real columns are `game_mode`, `match_history_id`, `previous_rating`, `new_rating`, `delta`. The insert is wrapped in `.catch(() => {})` which means it silently fails. The comment on lines 65-67 acknowledges this with "If it fails, we continue" — so the test still runs, but the precondition (user has history references) is not actually established by this INSERT. The test then relies on `server_link_provider` having created records, which may or may not be true depending on test state.

The test is not broken in the sense that it still exercises the deletion path, but the `hasHistoryReferences` precondition is effectively unverified. If a non-guest user happens to have no history records at deletion time, the guest fast path fires instead and the `DeletedUser` assertion at line 117 fails with `expect(deletedRows.length).toBe(1)`.

**Fix (for future test hardening):** Correct the SQL column list to match the schema, or use a table that has simpler SQL semantics. The correct INSERT would be:
```sql
INSERT INTO mmr_history
  (user_id, game_mode, match_history_id, previous_rating, new_rating, delta,
   created_by_id, created_date, last_modified_by_id, last_modified_date)
VALUES
  ({userId}, 'MemoryOfChaos', 0, 1500, 1510, 10, 0, '1970-01-01T00:00:00Z', 0, '1970-01-01T00:00:00Z')
```
Note: do NOT modify test files without an explicit task (per project rules). Recording here as a deferred hardening item.

### IN-02: `view_my_profile` exposes `deletedAt` to caller during 5-second pending window

**File:** `spacetimedb/src/views/identityViews.ts:126`
**Issue:** `view_my_profile` includes `deletedAt: user.deletedAt` in its projection. During the ~5-second window between `admin_ban_user`/`clientConnected` soft-delete and the `UserDeletionJob` cascade firing, a user can subscribe to `view_my_profile` and observe their own `deletedAt` is set. This is correct-by-design (it drives the client-side auto-logout path in `useAuth.ts`) and is documented in the architecture. Recording here for completeness as it is a non-obvious intentional exposure — the field is excluded from `view_user_directory` (D-16 projection), so it does not leak to other users.

No fix needed. This is the designed two-phase logout signal.
