## P5 Conditional Preservation (critical for Wave 3 planner)

**rosterMutations.ts L55** — `applyBatchUpsert` inner loop:

```typescript
ctx.db.HsrAccountCharacter.insert({
    hsrAccountId: accountId,
    characterName: item.characterName,
    eidolonLevel: item.eidolonLevel,
    ...(existing ? auditUpdate(ctx, existing, actingUserId) : auditInsert(ctx, actingUserId)),
} as any);
```

Both `auditInsert` and `auditUpdate` imports remain from `auditColumns`. The expression cannot be split without changing semantics — per D-06, the `existing` branch carries `createdBy/Date` from the existing row (upsert semantics), and the `else` branch uses the acting user as `createdBy` (insert semantics). Neither `updateWithAudit` nor `insertWithAudit` can express "merge existing audit OR stamp new audit" in a single conditional expression; splitting into `if (existing) { updateWithAudit } else { insertWithAudit }` would duplicate the entire row literal.

**Wave 3 input:** this is the second of the canonical 5-6 P5 sites that keep `auditInsert` exported (first: finalizationHelpers.ts L148). Option α (keep auditInsert exported indefinitely) remains the correct Wave 3 path.

## Decisions Made

### D-04-01: Task 3 is a zero-edit preservation task
rosterMutations.ts has exactly one audit call site and it's the P5 conditional that D-06 mandates preserving. Task 3's acceptance is the absence of changes, not the presence of them. No commit created for this task — the plan structure does not require commits for validation-only tasks per the Plan 15.3-03 Task 3 precedent.

### D-04-02: lobbySettings SAME-SHAPE dominance correction (plan text said "mostly P2 direct")
The plan guidance stated "Most lobbySettings.ts sites are P2 direct updates." Actual breakdown post-migration: 2 Lobby.id.update P2 + 8 LobbyMember SAME-SHAPE composite-PK (reset-all, slot-change, confirm/unconfirm, captain promote/demote). LobbyMember has composite PK (lobbyId + userId) with no `.pk.update()` accessor, forcing every mutation through `.delete(composite)` + `.insert(updated)`. This matches the Plan 15.3-01 D-01-ADJUNCT pattern exactly — no deviation from the established cookbook.

### D-04-03: Transient test-harness flakiness on first run (resolved on second run)
First vitest run produced 6 timeouts (60s threshold) in `lobby-presets.test.ts` across the `update_lobby_preset` and `delete_lobby_preset` describe blocks. Second run on identical code: 103/103 pass in 619s. Pattern matches the match-results teardown race from deferred-items.md — cross-test spacetimedb-instance contention during sequential preset CRUD. Not introduced by this plan; the code path touched (LobbyPreset.id.update with 30+ fields) compiles and executes correctly when the harness is not contention-bound.

### D-04-04: Tagged-enum per-field casts retained (D-16 scope)
sites where the caller writes a tagged-union field (`{ tag: 'Spectator', value: {} }`) still require `as any` on that field because the SDK's tagged-union narrowing cannot infer the literal string tag from the helper's generic `T`. Moved from wrapping the entire insert expression to scoping the cast per field. These 20+ remaining `as any` are out-of-scope per D-03b and will be addressed by a separate `backend-tagged-enum-type-hygiene-followup` phase.
