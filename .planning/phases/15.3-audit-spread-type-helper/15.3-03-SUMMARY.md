## Decisions Made

### D-03-01: P4 carry-site count clarification (plan aspirational ≠ actual file structure)

Plan 15.3-03 Task 1 acceptance said `grep -c "auditUpdate" characterStatsIncrement.ts >= 6`. Actual post-migration count is 4 (3 call sites + 1 import line). The discrepancy: the plan text counted generously assuming each carry site might have multiple `auditUpdate` references, but each helper function actually has exactly 1 carry site (one if-branch per public function). For characterStatsIncrement (3 public functions) the correct count is 3 carry sites → 4 grep hits. For statsIncrement (2 public functions) it's 2 carry sites → 3 grep hits. For globalCharacterStatsIncrement (1 public function) it's 1 carry site → 2 grep hits. **All three counts match the truthful file structure post-migration; plan's ">=N" numbers were inflated but the invariant they were testing (carry sites preserved, auditInsert removed, plain sites on new helper) is satisfied.**

### D-03-02: flagTransferHelpers LobbyMember sites are SAME-SHAPE (not P4 canonical)

All 4 LobbyMember delete+insert sites in flagTransferHelpers spread `...member` and change a single flag (isCaptain, isReferee). This is structurally SAME-SHAPE (Plan 01 D-01-ADJUNCT) — semantically a partial update. Migrated to `updateWithAudit(ctx, member, { isCaptain/isReferee: newVal }, SYSTEM_USER_ID)` used directly as the `.insert()` payload. Helper's return type `T & AuditFields` satisfies the `.insert()` signature (composite-PK table has no direct `.pk.update()` accessor). Distinct from stats helpers' P4 canonical pattern where caller builds an explicit new-shape row, requiring the `auditUpdate` primitive.

### D-03-03: Zero null→undefined fixups needed in Cluster C

Unlike Plan 01's calendarEvents.ts (4 fixups), no Cluster C file had latent `null` writes to optional table columns. Stats and accounting tables in this cluster have non-optional columns for all fields touched.

### D-03-04: flagTransferHelpers captain/host transfer is actually 2 SAME-SHAPE operations in sequence

The captain-transfer path ALWAYS does 2 LobbyMember mutations (promote new captain + demote leaver). Both must atomically apply `isCaptain: true/false`. The original code spread `...member` into each delete+insert block, and migration via `updateWithAudit(ctx, newCaptain, { isCaptain: true }, SYSTEM_USER_ID)` preserves this exactly — no behavior change. Verified by inspection; no stats-delta tests needed here (no stats mutation happens).
