## Implementation Decisions

### Scope reality check
- **D-01:** Actual blast radius is **385 audit call sites across 57 files**. STATE.md L103 said 323/56 — the numbers grew since Phase 15.5 shipped. Source of truth command: `grep -rn "auditInsert\|auditUpdate" spacetimedb/src --include="*.ts" | grep -v auditColumns.ts | wc -l`.
- **D-02:** Explicit `as any` eliminated by the refactor is **6 sites** total (not 50-100 as STATE.md claimed). 5 of the 6 lived in `admin.ts`; 1 in `bracketHelpers.ts`. Both files are migrated in Wave 0. The remaining ~420 `as any` in `spacetimedb/src/**` are unrelated (tagged enums, table-handle types, `mergeForUpdate`).
- **D-03:** The real benefit is (a) eliminating the 6 explicit `as any`, (b) type-checked audit fields at call sites, (c) consistent single-call site shape vs 3-line spreads, (d) improved narrative typing for future AI/human readers. Cosmetic/ergonomic win, not a correctness or performance win — but user's direction is to ship the full refactor for consistency and AI-readability.

### Helper API shape
- **D-04:** **Data-only helpers.** `insertWithAudit<T>(ctx, row: T, userId): T & AuditFields` and `updateWithAudit<T>(ctx, existing: T, changes: Partial<T>, userId): T & AuditFields`. Caller still writes `ctx.db.X.insert(...)` / `ctx.db.X.pk.update(...)` — preserves grep-ability for "who writes to this table". Rejected: operation-wrapper (loses grep surface), table-bound factory (adds a second concept). **Validated in Wave 0.**

### Update helper signature
- **D-05:** **Partial-update shape** for direct `.update()` sites: helper takes `existing + changes` and produces the merged row with audit stamped. **Validated in Wave 0** across all hard cases (direct `.update()`, `mergeForUpdate` + `.update()` passing `merged` as `changes`, update-inside-delete-then-insert with intermediate `updated1` variable). Applies cleanly to ~159 direct `.update()` sites.

### Fate of old `auditInsert` / `auditUpdate` (FINALIZED after pilot)
- **D-06:** **Keep `auditUpdate` as an exported primitive; delete `auditInsert`.** Two patterns genuinely require the `auditUpdate` primitive to stay callable:
  1. **Composite-PK delete+insert with audit carry** (~30 sites across ~15 files): caller `.delete(existing)` then builds a full explicit row passed to `.insert()`, with `...auditUpdate(ctx, existing, userId)` spread at the end to preserve `createdBy/Date`. Cannot migrate to `updateWithAudit` because no merge-into-existing happens — caller builds the row explicitly. Cannot migrate to `insertWithAudit` because that would overwrite `createdBy/Date`. Introducing a third helper `insertWithAuditCarry` is possible but adds API surface for a pattern the primitive already serves cleanly.
  2. **Conditional `existing ? auditUpdate(...) : auditInsert(...)`** (3 sites: `finalizationHelpers.ts` L148, `rosterMutations.ts` L55, possibly `eloCalculation.ts`): the conditional needs both primitives in the same expression. Migrating would require splitting the conditional — not worth the churn for 3 sites.
  - **Validated in Wave 0** on admin.ts: the 2 delete+insert-carry sites (HsrCharacterCost L521, HsrLightconeCost L569) kept the `auditUpdate` primitive cleanly; all other 14 sites migrated to new helpers.
  - **`auditInsert` deletion:** every current `auditInsert` call site migrates to `insertWithAudit` (no carry semantics to preserve). Planner should verify zero remaining `auditInsert` references before deleting it from `auditColumns.ts`.

### Migration strategy (FINALIZED after pilot)
- **D-07:** **Wave 0 complete.** Helpers created + pilot migration of `admin.ts` (14 sites migrated, 2 primitive kept) + `bracketHelpers.ts` (9 sites migrated). Type check clean. 6 of 6 explicit audit-merge `as any` eliminated. Committed before planning.
- **D-08:** Remaining 55 files migrate in planned waves. Suggested wave structure for `/gsd-plan-phase 15.3`:
  - **Wave 1 — Batch-mechanical files (51 files).** Plain `.insert()` / `.update()` sites with deterministic substitution. Group by domain for review ergonomics (e.g., reducers/draft\*, reducers/lobby\*, reducers/tournament\*, reducers/calendar\*, helpers/\*Stats\*, helpers/\*Mutations\*, helpers/roster\*). One plan file per domain cluster, each covering 5-10 files.
  - **Wave 2 — Individual-audit files (4 files).** One plan file each. See `<code_context>` for which files and why.
  - **Wave 3 — `auditColumns.ts` cleanup.** Delete `auditInsert` export after Wave 1+2 land; confirm zero callers. Keep `auditUpdate` + `SYSTEM_USER_ID` + `AuditFields` (latter re-exported from `auditHelpers.ts`).
  - **Wave 4 — Wave B placeholder-tests cleanup.** 6 test files, mechanical `expect(true).toBe(true)` → `it.todo(...)` conversion. Independent of Wave A waves.
  - **Wave 5 — Publish + integration test pass.** Single maincloud publish. Full `npm run test:integration` green. No schema changes, so this is a non-destructive deploy.
- **D-09:** No rollback of Wave 0. The pilot commits are validated net-positive work; resetting them would throw away proven migrations. Wave 1 builds on Wave 0.
- **D-10:** If any wave reveals new friction (type errors that don't resolve cleanly, unexpected behavior in integration tests), scope-shrink rather than ship broken. Honest escape hatches:
  - **Option X1:** Ship Wave 0 + Wave 2 (individual-audit files) only — high-value files, minimal batch work.

<specifics>
## Specific Ideas

- User's SDK-strictness instinct (from discussion) drove the pilot-first approach. Pilot outcome confirmed the instinct was correct: Wave 0 would have risked the whole refactor without the validation. Two pilots (bracketHelpers.ts happy-path + admin.ts hard-cases) were sufficient to validate the full pattern inventory.
- AI-readability benefit (from discussion) is load-bearing for the "do the full refactor" decision. User explicitly stated consistency matters — every write site reads the same way after migration. Mixed-state codebase would undermine this argument.
- The two-tier API (new helpers for 98% of sites + `auditUpdate` primitive for 3% delete+insert-carry + conditional) is the clean compromise between helper ergonomics and covering the full pattern space without forcing inelegant fits.
- Wave 3 (`auditInsert` deletion) is intentionally a separate wave: it forces a post-migration audit confirming zero remaining callers before deletion. Prevents partial-migration states from silently regressing.

</specifics>
