## Architecture Patterns

### System Data Flow

```
Reducer body
  ├─► Read existing row (ctx.db.Table.pk.find)
  │
  ├─► [plain INSERT] ─► ctx.db.Table.insert(insertWithAudit(ctx, {...row}, userId))
  │
  ├─► [direct UPDATE] ─► ctx.db.Table.pk.update(updateWithAudit(ctx, existing, {changes}, userId))
  │
  ├─► [mergeForUpdate + UPDATE] ─► merged = mergeForUpdate(existing, incoming, FIELDS)
  │                              ─► ctx.db.Table.pk.update(updateWithAudit(ctx, existing, merged, userId))
  │
  ├─► [composite-PK delete+insert-carry] ─► ctx.db.Table.delete(existing)
  │                                     ─► ctx.db.Table.insert({...explicit row, ...auditUpdate(ctx, existing, userId)})
  │                                        // auditUpdate PRIMITIVE stays (D-06)
  │
  └─► [conditional existing?update:insert] ─► ctx.db.Table.insert({
                                              ...row,
                                              ...(existing ? auditUpdate(ctx, existing, userId) : auditInsert(ctx, userId))
                                            })
                                            // auditUpdate PRIMITIVE stays; auditInsert CALLERS migrate
                                            // Exception: 3 conditional sites keep both primitives
```

## Common Pitfalls

### Pitfall 1: Migrating a delete+insert-carry site to `insertWithAudit`
**What goes wrong:** `insertWithAudit` stamps `createdById` and `createdDate` to the acting user and `ctx.timestamp` — overwriting the original creation metadata that the delete+insert-carry pattern is specifically trying to preserve.
**Why it happens:** Composite-PK tables don't have a working `.pk.update()` accessor — caller must `.delete(existing)` then `.insert({...fullExplicitRow, ...auditUpdate(...)})` to keep the original createdBy/createdDate. Migrator sees "insert" and reaches for `insertWithAudit`.
**How to avoid:** Before migrating any `.insert()` site, check if there's a `.delete(existing)` call above it on the same row. If yes, keep the `auditUpdate` primitive.
**Warning signs:** Audit field in git diff shows createdById jumping from a stable ID to the new actor's ID after migration.

### Pitfall 2: Simplifying the conditional `existing ? auditUpdate : auditInsert`
**What goes wrong:** Either the update branch loses createdBy/createdDate preservation, or the insert branch gets stamped with wrong actor semantics.
**Why it happens:** The conditional is awkward-looking and tempting to split. CONTEXT.md D-06 explicitly says don't split.
**How to avoid:** Leave conditional sites untouched. They keep both primitives callable.
**Warning signs:** Git diff shows the `?:` ternary replaced with an `if/else` or with a single helper call.

### Pitfall 3: Moving tagged-enum `as any` from outside the insert to inside the payload
**What goes wrong:** D-16 pattern: `{tag: X, value: {}} as any` moves INTO the row passed to `insertWithAudit`, rather than wrapping the whole `ctx.db.X.insert(...)`. Wave 0 validated this on admin.ts (L529-530). If the migrator leaves the cast on the outer call, they lose the type-safety win and potentially double-cast.
**How to avoid:** When migrating a site with both tagged-enum cast AND trailing `} as any)`, move the tagged-enum cast INTO the payload field (narrower scope), delete the trailing `as any`.
**Warning signs:** Git diff shows `as any` still on the `insert(...)` closing paren after migration.

### Pitfall 4: Forgetting Wave 3 pre-delete grep
**What goes wrong:** `auditInsert` gets deleted from `auditColumns.ts` while a Wave 1 or 2 file still references it (maybe in a comment, maybe in an overlooked conditional) — build breaks.
**How to avoid:** Mandatory pre-delete grep. Must return zero before editing auditColumns.ts.
**Warning signs:** TypeScript error on module import in file X. Fix: migrate the stray site before retrying Wave 3.

### Pitfall 5: Pre-migrating Wave 2b sites during Wave 1
**What goes wrong:** bracketAdvancement.ts is in Wave 1 Cluster F. If the Cluster F plan tries to type the variables AND migrate the audit spread in the same commit, it bundles Wave 1 + Wave 2b work — making Wave 2b harder to scope independently.
**How to avoid:** In Cluster F, migrate ONLY the audit spreads (old pattern → new helpers). Leave `let updatedMatch: any` and `const updates: any` untouched. Wave 2b handles them.
**Warning signs:** Git diff in Wave 1 Cluster F shows type annotations on variable declarations. Undo and re-commit.

### Pitfall 6: Touching server.ts `server_set_datetime` manual audit-field writes
**What goes wrong:** L297-298, L304-305, L320-321 in server.ts have manual `lastModifiedById: SYSTEM_USER_ID, lastModifiedDate: ts` writes (where `ts` is a CUSTOM timestamp, not ctx.timestamp). If migrator mistakes these for audit-helper sites and swaps in `updateWithAudit`, the custom timestamp argument is LOST — `updateWithAudit` forces `ctx.timestamp`.
**How to avoid:** The plan for Wave 2 File 2 (server.ts) must explicitly list the L295-325 range as NO-TOUCH, with reasoning.
**Warning signs:** Git diff in server.ts shows L297-321 changed. Revert.

### Pitfall 7: Not running integration tests after Wave 2 File 2 (server.ts)
**What goes wrong:** server.ts is the first-boot path. If migration breaks SYSTEM user creation, every subsequent integration test fails because the harness depends on SYSTEM existing. Symptom cascades.
**How to avoid:** The plan for server.ts must include a fresh-DB smoke test checkpoint (recipe in Wave 2 File 2 section above) before running the rest of the integration suite.
**Warning signs:** Entire test suite fails immediately post-publish with "SYSTEM user not found" or similar.
