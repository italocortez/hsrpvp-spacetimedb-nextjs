## Helper API Shape

| Option | Description | Selected |
|--------|-------------|----------|
| Data-only | Helper returns a fully-typed row with audit fields stamped. Caller still writes `ctx.db.X.insert(...)` — preserves grep-ability. | ✓ |
| Operation-wrapper | Helper takes table handle + data and performs the insert/update itself. Tersest call sites, but loses the `ctx.db.X.insert(...)` grep pattern + couples helper to handle types. | |
| Table-bound factory | Factory returns helpers bound to one table: `const chars = withAudit(ctx.db.HsrCharacter); chars.insert(ctx, row, userId)`. Ergonomic but adds a second concept. | |

**User's choice:** Data-only.
**Notes:** User selected "Recommended" with preview showing one-line call site and fully-typed return. Grep-ability argument (being able to find "who writes to this table") was the deciding factor.

## Update Helper Signature

| Option | Description | Selected |
|--------|-------------|----------|
| Partial-update | Helper takes existing row + partial changes, merges + stamps audit internally. One function call per update site. | ✓ |
| Full-row stamp | Helper assumes caller has built the merged row (via spreads or `mergeForUpdate`). Helper only stamps audit fields. | |
| Both variants | Ship `updateWithAudit` (partial) AND `updateWithAuditRow` (full-row) so each site picks the right one. | |

**User's choice:** Partial-update.
**Notes:** Consistent with data-only insert helper. During codebase scout AFTER the decision, ~56 delete+insert-with-audit-carry sites were discovered that do NOT fit the partial-update shape — deferred to the "fate of old helpers" question.

## Fate of Old Helpers (DEFERRED to pilot)

User asked a clarifying question before selecting: "are these old helpers just part of the test suite?"

Claude answered: No — 56 production files use them. Only 2 test-side references (one comment, one `vi.fn()` mock for isolation).

Before the follow-up selection, the user pivoted: "isn't this much much more big than the actual scope we had before? is it really worth the change?"

This prompted a scope-reality audit:

| Claim in STATE.md | Verified reality |
|-------------------|------------------|
| "Eliminates ~50-100 `as any` suppressions" | **6** explicit `as any` on audit-merge sites |
| "323 sites / 56 files" | **385** sites / **57** files (grew since 15.5) |

User counter-argued: "would doing this as any change help all future AI that read the code? could we test with 1 reducer change and 1 file edit see if it works? spacetimedb sdk with typescript variants has been pretty picky about erroing and 'as any' solved many issues when we started"

This reframed the decision: pilot-first is cheaper and de-risks the full migration. AI-readability benefit was accepted as real.

**Provisional decision captured in CONTEXT.md D-06:** keep `auditInsert` / `auditUpdate` as internal primitives. Reason: the 56 delete+insert sites + 5 conditional sites + 8 `mergeForUpdate` sites all benefit from the primitives staying callable. **Finalize after pilot.**
