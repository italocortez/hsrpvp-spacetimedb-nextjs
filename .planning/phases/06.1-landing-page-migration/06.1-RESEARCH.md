# Phase 06.1: Landing Page Migration - Research

**Researched:** 2026-03-22
**Domain:** Next.js frontend migration (CSS modules, design tokens, auth wiring, asset handling)
**Confidence:** HIGH

## Summary

This phase migrates a fully designed landing page from `D:\AI Playground\ImportPecilToCode` into the current HSRPVP project. The source project is a Next.js app using CSS modules with a comprehensive design token system (~80 CSS custom properties). The source components are well-isolated, self-contained, and use no external dependencies beyond React and CSS modules -- making migration straightforward.

The primary complexity lies in three areas: (1) the existing Header component is rendered in the **root layout** (`app/layout.tsx`), not just in route-group layouts, so NavBar must replace it globally across all three layouts that import it; (2) the `icon-lucide` CDN font used in ContactSection is blocked by the project's Content-Security-Policy (`font-src 'self' data:`), requiring conversion to inline SVG; and (3) the source project uses JetBrains Mono font which must be added to the root layout's font configuration.

**Primary recommendation:** Replace Header with NavBar in all three layouts, convert the two `icon-lucide` usages in ContactSection to inline SVGs, add JetBrains Mono font, and copy everything else nearly as-is since CSS modules provide full style isolation.

### Pattern 1: Header-to-NavBar Replacement (Global)
**What:** The existing Header component is rendered in the root layout (`app/layout.tsx` line 31), not just in route-group layouts. The landing-page layout imports Header but does NOT render it (the JSX is commented out at line 18). The authenticated layout imports Header but also does NOT render it in JSX.
**When to use:** When replacing the global navigation.
**Critical detail:** All three files import Header. The root layout is the ONLY one that actually renders `<Header />` in JSX. The sub-layouts import but don't use it (likely leftover from refactoring). This means:
- `app/layout.tsx`: Change `<Header />` to `<NavBar />` in both import and JSX
- `app/(landing-page)/layout.tsx`: Remove unused Header import
- `app/(authenticated)/layout.tsx`: Remove unused Header import

### Pattern 2: CSS Token Integration
**What:** Source project uses `tokens.css` with ~80 CSS custom properties (:root scope). Target project has its own `:root` variables in `globals.css`.
**When to use:** Integrating the design system.
**Key finding -- NO naming conflicts:**
- Source tokens: `--color-void`, `--color-space`, `--bg-page`, `--bg-nav`, `--text-heading`, etc.
- Target globals: `--color-light`, `--color-dark`, `--color-cost`, `--gradient-5star`, `--border-5star`, etc.
- The namespaces are completely disjoint. Safe to import tokens.css without any variable renaming.

### Pattern 3: Font Variable Wiring
**What:** Source components reference `var(--font-primary)` (JetBrains Mono) and `var(--font-secondary)` (Inter). These CSS variables resolve via `tokens.css` to `var(--font-jetbrains-mono)` and `var(--font-inter)` respectively, which are set by Next.js `next/font/google` in the root layout via the `variable` option.
**When to use:** Making the design tokens work end-to-end.
**Implementation:**
```typescript
// In app/layout.tsx — add JetBrains Mono alongside existing Inter
import { Inter, JetBrains_Mono } from "next/font/google";

const inter = Inter({
  variable: "--font-inter",  // CHANGE: add variable option
  subsets: ["latin"],
});

const jetbrainsMono = JetBrains_Mono({
  variable: "--font-jetbrains-mono",
  subsets: ["latin"],
});

// In <html> tag:
<html lang="en" className={`dark ${inter.variable} ${jetbrainsMono.variable}`}>
```
**Note:** The target currently configures Inter WITHOUT the `variable` option (it uses `inter.className` pattern, commented out). The source project uses `variable: "--font-inter"` to expose it as a CSS custom property. The migration must switch to the `variable` approach so `var(--font-inter)` resolves in tokens.css.

### Pattern 4: NavBar Auth Wiring
**What:** Source NavBar has a static `<a href="#login">LOG IN</a>` link. Must wire to `useAuthContext()`.
**When to use:** Making the NavBar functional with auth state.
**Implementation approach:**
```typescript
// NavBar.tsx additions
import { useAuthContext } from '@/components/features/auth/components/AuthProvider';
import Link from 'next/link';

// Inside component:
const { isAuthenticated, user, loginGuest } = useAuthContext();

// In rightSection JSX — replace static loginCta:
{isAuthenticated ? (
  <Link href="/profile" className={styles.userInfo}>
    {user?.displayName}
  </Link>
) : (
  <button className={styles.loginCta} onClick={loginGuest} type="button">
    LOG IN
  </button>
)}
```

### Pattern 5: Nav Item Routing
**What:** Source NavBar uses button state toggle (`onClick={() => setSelected(...)}`). Target needs Next.js Link navigation.
**When to use:** Connecting nav items to routes.
**Route map:**
| Nav Item | Route | Status |
|----------|-------|--------|
| LOBBIES | /lobby | Active link |
| TEAM BUILDER | /teambuilder | Active link |
| COST TABLES | /costs | Active link |
| TOURNAMENTS | # | Placeholder (no onClick needed) |
| EVENTS | # | Placeholder (no onClick needed) |

**Implementation:** Convert routable items from `<button>` to Next.js `<Link>`, keep TOURNAMENTS/EVENTS as `<button disabled>` or `<button>` with no action. The `selected` state should derive from `usePathname()` instead of local state.

### Anti-Patterns to Avoid
- **Duplicating auth logic in NavBar:** Use `useAuthContext()` from existing AuthProvider, do not re-implement auth checks
- **Importing Header in new components:** Delete Header completely, update all imports
- **Adding CDN links for icon-lucide:** Blocked by CSP; convert to inline SVG
- **Using Tailwind in migrated components:** D-06 explicitly forbids this; keep CSS modules approach
- **Changing existing route paths:** D-17 says sub-routes stay as-is

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Auth state in NavBar | Custom auth checking | `useAuthContext()` from AuthProvider | Already handles all auth states (guest, discord, connecting, loading) |
| Font loading | Manual @font-face | `next/font/google` with `variable` option | Zero CLS, automatic subsetting, self-hosted |
| Route-aware nav highlighting | Manual pathname parsing | `usePathname()` from `next/navigation` | Built-in Next.js hook, SSR-safe |
| Icon font (lucide) | CDN link tag | Inline SVG in JSX | CSP blocks CDN fonts; inline SVGs are zero-dependency |

## Common Pitfalls

### Pitfall 1: Root Layout Header Renders Globally
**What goes wrong:** Replacing Header only in route-group layouts leaves the root layout still rendering the old Header on every page.
**Why it happens:** Easy to miss that `app/layout.tsx` (root) renders `<Header />` at line 31. The sub-layouts import Header but DON'T render it.
**How to avoid:** Replace Header with NavBar in root layout. Remove dead imports from sub-layouts.
**Warning signs:** Old Header still visible above the new NavBar.

### Pitfall 2: CSP Blocks icon-lucide CDN Font
**What goes wrong:** ContactSection icons render as empty boxes or missing glyphs.
**Why it happens:** `next.config.ts` has CSP header `font-src 'self' data:` which blocks `cdn.jsdelivr.net`. The source project loads lucide font via `<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/lucide-static@latest/font/lucide.min.css" />`.
**How to avoid:** Convert the TWO `icon-lucide` usages in ContactSection to inline SVG. The icons used are: (1) copy icon `&#xe869;` and (2) server icons `&#xea1e;`, `&#xe9b5;`, `&#xea1b;`. Replace with Lucide SVG equivalents or simple inline SVGs.
**Warning signs:** Console CSP violation errors; blank icon slots in the Contact section.

### Pitfall 3: Font Variables Not Resolving
**What goes wrong:** All text renders in browser default fonts. Design looks completely wrong.
**Why it happens:** `tokens.css` references `var(--font-jetbrains-mono)` and `var(--font-inter)`, but these CSS variables are only set when `next/font/google` is configured with the `variable` option AND the variable classes are applied to the HTML element.
**How to avoid:** Configure both fonts with `variable` option in `app/layout.tsx` and apply both variable class names to `<html>`.
**Warning signs:** Browser DevTools shows `--font-primary` resolving to empty string.

### Pitfall 4: globals.css main Selector Constrains Landing Page Width
**What goes wrong:** Landing page sections (Hero, Features, Contact) are constrained to `width: min(94%, 90rem)` instead of full-width.
**Why it happens:** `globals.css` line 144 applies `main { width: min(94%, 90rem); margin-inline: auto; }` globally. The source landing page uses a full-width `<main>` tag.
**How to avoid:** Either (a) don't wrap landing page in `<main>` (use `<div>` instead), or (b) add a CSS override for the landing page's main element, or (c) the source page.tsx already uses `<main className={styles.page}>` which sets `width: 100%` -- CSS modules class specificity should win if the global `main` rule doesn't use `!important`.
**Warning signs:** Landing hero section has horizontal margins/padding it shouldn't have.

### Pitfall 5: Video .mov Format Browser Compatibility
**What goes wrong:** Video doesn't play in Firefox or older browsers.
**Why it happens:** `.mov` (QuickTime) format has limited browser support outside Safari/Chrome. Firefox may not play it.
**How to avoid:** For now, accept the limitation per D-13/D-14 (keep .mov as-is). The HeroSection already handles the loading state gracefully with a loader animation. Consider converting to .mp4 (H.264) in a future phase for broader support.
**Warning signs:** Video loader spins indefinitely in Firefox.

### Pitfall 6: Root Layout Renders Header + Footer Outside Route Groups
**What goes wrong:** After migration, the NavBar appears twice -- once from root layout, once from wherever the page composition puts it.
**Why it happens:** Root layout (`app/layout.tsx`) renders `<Header />` and `<Footer />` OUTSIDE of route groups. The landing page composition (per D-15) also includes NavBar at the top.
**How to avoid:** The NavBar should be rendered ONLY in the root layout (replacing Header). The landing page `page.tsx` should NOT include NavBar in its own composition -- it gets NavBar from the root layout. Alternatively, remove NavBar from root layout and put it in each route-group layout instead. The cleanest approach: keep NavBar in root layout, remove it from page.tsx composition.
**Recommendation:** Move NavBar out of root layout and into each route-group layout for flexibility (landing-page layout vs authenticated layout may want different NavBar configs). This aligns better with how Header was being split across layouts before the current state where it's only actually rendered in root.

### NavBar Route Wiring
```typescript
import Link from 'next/link';
import { usePathname } from 'next/navigation';

const NAV_ITEMS = [
  { label: 'LOBBIES', href: '/lobby' },
  { label: 'TEAM BUILDER', href: '/teambuilder' },
  { label: 'COST TABLES', href: '/costs' },
  { label: 'TOURNAMENTS', href: null },  // placeholder
  { label: 'EVENTS', href: null },       // placeholder
] as const;

// Inside component:
const pathname = usePathname();

// In JSX:
{NAV_ITEMS.map((item) => {
  const isSelected = item.href ? pathname.startsWith(item.href) : false;
  const Tag = item.href ? Link : 'button';
  const linkProps = item.href ? { href: item.href } : { type: 'button' as const };
  return (
    <Tag
      key={item.label}
      className={`${styles.navItem}${isSelected ? ` ${styles.selected}` : ''}`}
      {...linkProps}
    >
      <span className={styles.navItemBorder} />
      {item.label}
    </Tag>
  );
})}
```

### icon-lucide to Inline SVG Conversion (ContactSection)
The ContactSection uses `icon-lucide` in exactly two places:
1. **Copy icon** (`&#xe869;` = Lucide "copy" icon) -- replace with inline SVG
2. **Server icons** (`&#xea1e;`, `&#xe9b5;`, `&#xea1b;`) -- replace with inline SVGs

```typescript
// Before (blocked by CSP):
<span className={`icon-lucide ${styles.copyIcon}`}>&#xe869;</span>

// After (inline SVG):
<svg className={styles.copyIcon} viewBox="0 0 24 24" fill="none"
     stroke="currentColor" strokeWidth="2" strokeLinecap="round" strokeLinejoin="round">
  <rect width="14" height="14" x="8" y="8" rx="2" ry="2" />
  <path d="M4 16c-1.1 0-2-.9-2-2V4c0-1.1.9-2 2-2h10c1.1 0 2 .9 2 2" />
</svg>
```

For server icons, the simplest approach is to replace the icon-font glyphs with small inline SVGs or Unicode symbols that don't require the font. The server icons are decorative and can use simple geometric SVGs.
