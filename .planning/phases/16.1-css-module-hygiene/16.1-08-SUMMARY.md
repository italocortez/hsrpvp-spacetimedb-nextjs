# Phase 16.1 Plan 08: NavBar Link prefetch policy (improvised during D-11 verify) Summary

**Next.js `<Link>` default prefetch disabled on heavy NavBar routes (/teambuilder, /costs, /profile, /admin-view) via a single consolidated `NAV_ITEMS` config object with per-entry `heavy` flag. Closes ROADMAP success criterion 4 — no Firefox 'preloaded using link preload but not used within a few seconds' warning on homepage first paint. Improvised during Plan 07's D-11-analog verify after CSS co-location alone proved insufficient; four atomic refactor commits iterated the shape (inline flag + 4 literals → HEAVY_ROUTES Set + prefetchFor helper → single NAV_ITEMS object with heavy flag → href also centralised) without a formal PLAN.md.**

## Decisions Made

- **Next.js <Link> prefetch policy is the real lever for the Firefox "preloaded but not used" warning, not CSS co-location.** Phase 16.1's 7 prior plans closed every R8 Rule 6 violation (leaf→trunk imports, cross-feature imports, page.module.css dead rules). The Firefox warning persisted because Next's <Link> default-prefetches every route whose link is in the viewport: on the homepage, the NavBar's 4 heavy-route Links trigger <link rel=preload> for their CSS chunks regardless of whether the user navigates. `prefetch={false}` on the Link call sites is the structural fix. CSS co-location reduces chunk size; prefetch policy controls whether the chunk is fetched at all. They are orthogonal concerns; Phase 16.1 needed both.
- **Consolidate NavBar config into a single NAV_ITEMS object rather than a separate HEAVY_ROUTES Set.** Three iterations arrived at the canonical endpoint: (a) per-entry heavy flag on NAV_ITEMS + 4 inline literals — split knowledge; (b) HEAVY_ROUTES Set + prefetchFor() helper — consolidated the flag but split NavBar config across two constants; (c) single NAV_ITEMS object with `heavy: boolean` per entry — every Link reads from the same shape, zero split, forward-compat slot for dynamic tabs. Atomic refactor commits let reviewer feedback drive shape without losing the working fix.
- **Forward-compat `lobbyInstance` slot in NAV_ITEMS today, with no consumer.** Phase 28+ will append runtime lobby instance tabs (/lobby/[id]) to the center scroll row from useLobbies(). These tabs share a single prefetch policy — the lobby route is heavy. Reserving the slot now costs a 3-line object literal with zero logic cost; when the dynamic path lands, the renderer reads `NAV_ITEMS.lobbyInstance.heavy` with no reshape. Pre-empts a future re-edit of the NAV_ITEMS type.
- **public/sw.js left untouched.** The SW from Plan 16-04 is reactive (cache-first on intercept, no precache manifest). Disabling Link prefetch does not regress asset warming — images enter the SW cache only once the route mounts and <img> tags render. Net UX: homepage first paint is faster (no cascade of CSS/JS preloads); first nav to a heavy route carries a ~100ms CSS/JS cost mostly absorbed into the Stage 2 SpacetimeDB subscription wait (already gating authenticated render per 15.5 D-07).
- **No PLAN.md written.** Plan 08 was improvised during Plan 07's D-11-analog verify when the user observed the Firefox warning persisted. Single-file single-behavior fix; writing a formal PLAN.md → /gsd-execute-plan cycle would have been ceremony without value. Four atomic commits landed directly on feature_nath_claude per autonomous-execution rules; this retrospective SUMMARY + STATE + ROADMAP update is the documentation layer.

## Lessons Learned

- **Phase 16.1's CSS co-location work alone couldn't resolve the preload warning — Next.js <Link> prefetch policy was the real lever.** The phase's planned work (Plans 01-07) addressed a different anti-pattern (leaf→trunk + cross-feature imports causing shared chunks across route groups). Shared-chunk size shrunk and R8 Rule 6 enforcement grep surface closed, but <Link> default-prefetches every route-group chunk whose link is in the viewport regardless of chunk topology. A homepage NavBar that links to 4 heavy routes triggers 4 preloads regardless of how well each heavy route's CSS is co-located. The D-11 visual check is what surfaced the gap; the improvised plan closed it.
- **Improvised-during-verify plans are legitimate phase members.** Plan 08 has no PLAN.md, was triggered by Plan 07's verify checkpoint, and landed 4 atomic commits directly on the feature branch. It produces this SUMMARY, counts in the phase's plan ledger (8/8 not 7/7), and satisfies `/gsd-verify-work`'s "every commit accounted for in a SUMMARY" invariant. Phase 16.1's posture was already lean on ceremony (each plan a 2-commit atomic pair); an improvised follow-up within the same phase fits that posture. Alternative (spawn Phase 16.2 for a single-file follow-up) would have been excessive for a root-cause-obvious, single-call-site-class fix.
- **Atomic refactor commits let reviewer feedback drive shape without losing the working fix.** The initial commit 31fd2c4 already closed the user-facing warning; commits 594d3e1 / ec3daa8 / 8337475 are pure shape iterations. Each is a revertible step: if commit 3 turned out to over-consolidate, reverting it would return to the HEAVY_ROUTES Set + prefetchFor helper shape of commit 2, which was itself a viable endpoint. This is the canonical pattern for "the first commit works but can be shaped better" — iterate in atomic refactors rather than amending the original or bundling shape changes into a single mega-commit.
- **Single-config-object NavBar pattern generalizes.** Future work that wants to add a new NavBar entry (Phase 17+ tabs, admin sub-views, etc.) now has a single place to edit: `NAV_ITEMS`. The forward-compat `lobbyInstance` slot demonstrates the pattern for dynamic tab groups: add a named field to NAV_ITEMS for the group's shared prefetch policy, and the renderer reads it when building the dynamic tab list. Same posture as `tech-stack.patterns` bullet 2.
