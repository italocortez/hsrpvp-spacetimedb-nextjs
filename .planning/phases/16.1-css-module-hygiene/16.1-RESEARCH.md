## Summary

Phase 16.1 is a pure mechanical refactor: redistribute ~530 lines of CSS from one page-level module into five sibling component modules, resolve one cross-component cascade via JS state, duplicate four classes into a new costs module, and delete confirmed-dead rules. No new dependencies. No visual change.

The Firefox "preloaded but not used within a few seconds" warning is a real Next.js 15 App Router issue caused by CSS chunks being preloaded for routes that share importers. When five components in `components/features/team-builder/` all import `page.module.css`, Next.js treats that CSS as potentially needed by any route that touches those components. Co-locating styles with the components that consume them is the established fix — the CSS chunk scope narrows to the route that actually mounts the component.

The partition is fully pre-decided in CONTEXT.md (D-01 through D-13). Research validates those decisions technically and identifies execution traps the planner must account for.

**Primary recommendation:** Execute D-01–D-13 exactly. The technical patterns are sound; the pitfalls are mechanical (keyframe scope, responsive block splits, hover cascade, dead-rule enumeration). No new libraries, no new tooling.

### Pattern 1: CSS Module Co-location (the core pattern)

**What:** Each component file has a sibling `.module.css` file. The component imports only its own module. No component imports a module from a parent route or a different feature directory.

**When to use:** Always, for every component in `components/features/`.

**Example (before → after for SynergyDisplay):**

```typescript
// BEFORE: SynergyDisplay.tsx (violation)
import styles from "@/app/(public)/teambuilder/page.module.css";

// AFTER: SynergyDisplay.tsx (correct)
import styles from "./SynergyDisplay.module.css";
```


### Pattern 2: Cross-component hover via JS state (D-06)

**What:** When `.roster:hover .clearButton { opacity: 1 }` spans two component files (`.roster` in TeamRoster, `.clearButton` in Teamslot), the cascade cannot survive the CSS module scope boundary. JS state is the standard resolution.

**When to use:** Any descendant CSS selector that spans a component boundary after CSS module partition.

**Example:**

```typescript
// TeamRoster.tsx — adds hover tracking
import { useState, useCallback } from "react";

export function TeamRoster({ ... }: TeamRosterProps) {
  const [isRosterHovered, setIsRosterHovered] = useState(false);

  return (
    <div
      className={`${styles.roster} Box`}
      onMouseEnter={() => setIsRosterHovered(true)}
      onMouseLeave={() => setIsRosterHovered(false)}
    >
      {/* ... */}
      <TeamSlot
        isRosterHovered={isRosterHovered}
        // ... other props unchanged
      />
    </div>
  );
}
```

```typescript
// Teamslot.tsx — consumes the signal
interface TeamSlotProps {
  // ... existing props
  isRosterHovered: boolean;  // NEW
}

// Inside render, clear button:
<button
  onClick={() => onRemove(index)}
  className={`${styles.clearButton}${isRosterHovered ? ` ${styles.clearButtonVisible}` : ""}`}
  title={`Remove ${character.displayName}`}
>
```

```css
/* Teamslot.module.css */
.clearButton {
  /* ... existing styles ... */
  opacity: 0;
  transition: all 200ms ease;
}
.clearButtonVisible {
  opacity: 1;
}
```

Note: The existing `Teamslot.tsx` already has `const [isHovered, setIsHovered] = useState<boolean>(false)` and `data-slot-hover` wiring on the slot root — that is per-slot hover, NOT the roster-level hover. The new `isRosterHovered` is a separate prop from the parent. No conflict.

### Pattern 3: `@keyframes` scope in CSS Modules

**What:** CSS Modules hashes class names per file, but `@keyframes` names in different files get compiled to the same global name only in some bundler configurations. In Next.js, `@keyframes` defined in a `.module.css` file are locally scoped — they do NOT automatically share scope across files.

**Consequence:** If `.imposition { animation: fade-in 300ms; }` is in `Teamslot.module.css` but `@keyframes fade-in` is defined in `page.module.css`, the animation silently fails (the hashed keyframe name doesn't match the hashed reference in the different module).

**Fix (D-03):** `@keyframes fade-in` moves to `Teamslot.module.css` alongside `.imposition`. This is the consumer-co-location rule for keyframes.

[ASSUMED: Next.js 15 CSS Modules locally scope `@keyframes` names, causing cross-file animation references to silently fail. This is well-established CSS Modules behavior, but the exact hash strategy for keyframes in Next.js 15 was not verified against official docs in this session. The risk-if-wrong: animation works fine cross-file, making the co-location unnecessary but harmless. Low risk.]

### Anti-Patterns to Avoid

- **Leaf-imports-trunk:** `components/**` importing `app/**/page.module.css`. This is the entire anti-pattern being fixed. After this phase, the grep `rg -n "from ['\"]@/app/.*\.module\.css['\"]" components/` must return zero.
- **Cross-feature CSS import:** Any component in `components/features/X/` importing `components/features/Y/*.module.css`. After this phase, `rg` cross-referenced with feature directory confirms zero cross-feature CSS imports.
- **Keeping dead rules:** Rules with zero `styles.<className>` references across the codebase must be deleted, not relocated. Moving dead rules creates a different file of dead rules.
- **Shared `@keyframes` across modules:** Do not define a keyframe in `page.module.css` and reference it from a component module. The animation silently fails due to CSS Modules name scoping.
- **`:global()` as cascade escape hatch:** Using `:global(.clearButton)` to preserve the `.roster:hover .clearButton` cascade leaks the class name globally. CSS Modules isolation is violated. JS state (D-06) is the correct resolution.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Import violation detection | Custom AST linter or script | `rg -n "from ['\"]@/app/.*\.module\.css['\"]" components/` | ripgrep is instant, zero setup, already in the project's grep workflow. The violation pattern is a verbatim string match — no AST needed. |
| Dead rule detection | CSS parser script | `rg -rn "styles\.<className>" app/ components/` per class | Same: dead-rule check is a text search across the repo. Grep confirms zero references. |
| Bundle size delta | Custom build diff script | `npm run build` output, `First Load JS` column | Next.js build output already reports per-route First Load JS. Compare `/teambuilder` and `/costs` rows before and after. |
| Cross-component CSS cascade | `:global()` or `@layer` tricks | JS-driven hover state (D-06) | `:global()` leaks names; cascade tricks depend on import order which Next.js may reorder. React state is deterministic and survives any CSS bundler change. |

**Key insight:** All verification in this phase is grep + build output. No tooling investment needed. The deferred ESLint rule (D-24 deferral from Phase 16) is the right long-term answer; grep is the right one-phase answer.

## Common Pitfalls

### Pitfall 1: Forgetting the `@keyframes` must travel with the consumer

**What goes wrong:** `.imposition { animation: fade-in 300ms; }` is moved to `Teamslot.module.css` but `@keyframes fade-in` stays in `page.module.css`. The imposition animation silently stops working.

**Why it happens:** CSS Modules hashes both class names AND keyframe names per file. The `animation:` property in `Teamslot.module.css` references a hashed name from that file; the keyframe defined in `page.module.css` gets a different hash. No match.

**How to avoid:** In commit 1 (Teamslot), move `@keyframes fade-in` into `Teamslot.module.css` in the same operation as `.imposition`. They are inseparable.

**Warning signs:** After commit 1, navigate to `/teambuilder`, add a lightcone to a slot — the imposition dropdown should fade in. If it appears instantly (no animation), the keyframe is missing or mislocated.

### Pitfall 2: Split `@media` blocks must carry ALL overrides for the component

**What goes wrong:** The `@media (max-width: 800px)` block in `page.module.css` at lines 545–561 overrides four classes: `.charactersContainer`, `.path`, `.verticals`, `.clearButton`. If the executor moves only `.charactersContainer` to `TeamRoster.module.css` and forgets `.path`/`.verticals`/`.clearButton`, those three responsive overrides are orphaned — they remain in `page.module.css` referencing hashed names from a different file, so they apply to nothing.

**Why it happens:** The `@media` block looks like a single unit but its selectors span multiple components.

**How to avoid:** In commit 2 (TeamRoster), split the `@media (max-width: 800px)` block explicitly:
- `.charactersContainer` override → `TeamRoster.module.css`
- `.path`, `.verticals`, `.clearButton` overrides → `Teamslot.module.css` (commit 1 should include them, or commit 2 adds them to Teamslot)

The `@media (max-width: 1070px)` block (lines 563–570) overrides `.portrait` and `.clearButton` → both go to `Teamslot.module.css`.

**Warning signs:** At `max-width: 800px`, the character grid should switch to 2 columns. If it stays at 4 columns, the `.charactersContainer` media override is missing. The path icon should fill full slot height at narrow width — if it doesn't, the `.path` media override is missing.

### Pitfall 3: The `isRosterHovered` prop must be wired before commit 1 is complete

**What goes wrong:** Commit 1 moves `Teamslot` styles to `Teamslot.module.css` and changes the import. But the `clearButton` opacity behavior (`.roster:hover .clearButton { opacity: 1 }`) is now broken because that rule is a cross-file cascade that no longer works. The hover-reveal fails silently — the clear button is permanently hidden (opacity: 0) until the JS state wiring is added.

**Why it happens:** Commit 1 (Teamslot) and Commit 2 (TeamRoster) are separate commits. The cascade break happens at commit 1; the JS fix lands at commit 2. In between, the feature is visually broken.

**How to avoid:** Two options — either (a) wire the `isRosterHovered` prop stub into `Teamslot` in commit 1 and complete the `TeamRoster` `onMouseEnter`/`onMouseLeave` + prop propagation in commit 2, OR (b) defer the `clearButton` opacity change until commit 2 (keep `opacity: 0` with a comment noting it wires in commit 2). Option (a) is cleaner: commit 1 adds the `isRosterHovered?: boolean` prop to `Teamslot`'s interface (defaulting to false), adds the conditional class to the clearButton, adds `clearButtonVisible { opacity: 1 }` to `Teamslot.module.css`. Commit 2 adds the `useState` + event handlers to `TeamRoster` and starts passing the real prop value.

**Warning signs:** After commit 1, hovering over the roster should still reveal clear buttons (even before commit 2, the old `page.module.css` cascade should still be active if `page.module.css` is not modified yet). Check the per-commit impact carefully.

### Pitfall 4: Dead rules enumerated in CONTEXT.md D-02 — do not miss `confirmationOverlay` and `confirmationModal`

**What goes wrong:** The CONTEXT.md D-02 lists `.confirmationTitle`, `.confirmationMessage`, `.confirmationActions`, `.confirmationCancel`, `.confirmationConfirm` as dead. The executor deletes those but overlooks `.confirmationOverlay` and `.confirmationModal` — the parent containers — which are also dead (confirmed: zero matches for `styles.confirmationOverlay` and `styles.confirmationModal` across the codebase).

**Why it happens:** The `page.module.css` has a visible "Confirmation Modal" section with `confirmationOverlay` and `confirmationModal` as structural containers — they look "important" even though nothing references them.

**How to avoid:** The sweep commit (commit 7) runs grep for each dead class before deletion. `rg -rn "styles\.confirmationOverlay" app/ components/` returns no output → safe to delete.

**Warning signs:** N/A — silent risk. The grep step is the prevention.

### Pitfall 5: `LightconeCostTable.tsx` uses `poolStyles.*` variable name — rename at the call site

**What goes wrong:** `LightconeCostTable.tsx` currently declares `import poolStyles from '@/...'`. After the fix, the import changes to `import styles from './LightconeCostTable.module.css'`. But the JSX references `poolStyles.filters`, `poolStyles.paths`, `poolStyles.searchBar`, `poolStyles.clearButton`. If the import alias changes to `styles` but the call sites still say `poolStyles.*`, TypeScript will error.

**How to avoid:** In commit 6, change both the import line AND all four `poolStyles.X` → `styles.X` (or the chosen local alias) in a single atomic edit. There are exactly 4 call sites (lines 76, 78, 92, 97 of `LightconeCostTable.tsx`).

**Warning signs:** `npm run build` or `npm run test:typecheck` will error with "Cannot find name 'poolStyles'" if any call site is missed.

### Pitfall 6: The `paths > button` child-selector rules in CharacterPool.module.css are NOT needed in LightconeCostTable.module.css

**What goes wrong:** The executor copies the entire `.paths` block from `CharacterPool.module.css` including the `.paths > button`, `.paths > button:not(.selected):hover`, and `.paths > button:last-child` selectors. These target `button` children directly, but `LightconeCostTable.tsx` renders `<FilterButtonGroup>` inside `styles.paths` — `FilterButtonGroup` manages its own button rendering and internal styles.

**How to avoid:** Copy only the `.paths` container rule (flex-grow, height, overflow-x, display, justify-content, align-items, border, background-color, border-radius, box-shadow, transition). The child-button selectors are inside `CharacterPool.module.css` because `CharacterPool` owns the button children. `LightconeCostTable` delegates button rendering to `FilterButtonGroup`.

**Warning signs:** If the path filter buttons look broken (wrong hover, wrong sizing) after commit 6, the duplication included conflicting child rules. Forward-fix: remove the extra selectors.

## Why Redistributing CSS Fixes the Preload Warning

**Mechanism** [CITED: github.com/vercel/next.js/issues/51524, discussions/70168]:

Next.js App Router preloads CSS chunks for routes during prefetching (triggered when hovering over links or router.prefetch). When `page.module.css` is imported by both `page.tsx` AND five `components/features/team-builder/` files, Next.js must treat that CSS chunk as "potentially needed by any route that could render those components" — including `/costs` and `/teambuilder`. This causes preload `<link>` elements to be emitted on page load even for routes where those components are not mounted.

Firefox reports: "The resource was preloaded using link preload but not used within a few seconds from the window's load event."

**Fix mechanism** [VERIFIED: confirmed by WebSearch results + official discussion]: When each component imports only its own sibling `.module.css`, Next.js can scope each CSS chunk to the exact route segment that mounts the component. The `/teambuilder` route loads `Teamslot.module.css`, `TeamRoster.module.css`, etc. only when `/teambuilder` is the active route. No preload is emitted for `/costs`.

**Confidence:** MEDIUM — the mechanism is confirmed by community discussion and the official Next.js CSS chunking documentation. The exact internal bundler logic is not fully public, but the co-location fix is the established solution cited across multiple Next.js issues.

## ESLint/Lint Tool Landscape for CSS Import Restrictions

Research question: Is there an existing ESLint rule for "no cross-feature CSS imports" or "no `@/app/*.module.css` imports from `components/`"?

**Findings:**

1. **`eslint-plugin-import` `no-restricted-paths`** — This rule CAN enforce the pattern. It uses a `zones` configuration where `from` patterns are forbidden in `target` directories. However: (a) it operates on JS import paths, so `*.module.css` imports are handled the same as JS; (b) the configuration requires explicit zone definitions per feature boundary; (c) the project has deferred this per D-24.

2. **`eslint-plugin-boundaries`** — Designed for monorepo/layer-boundary enforcement. Can be configured to forbid `components/features/X/` from importing `components/features/Y/`. But requires element-type configuration and adds install/config overhead. Not installed in this project. Deferred per D-24.

3. **`eslint-plugin-css-modules`** — Checks that CSS class references exist in the imported module. Does NOT enforce import path restrictions.

4. **Native ESLint `no-restricted-imports`** — Can restrict specific import paths but requires listing them explicitly (not a glob-based "no imports from a different feature" rule).

**Conclusion:** No tool exists that trivially enforces "no cross-feature CSS imports" as a single npm install + one-line config. The closest is `eslint-plugin-import` `no-restricted-paths` with custom zone config, but it requires explicit configuration that is project-setup work — correctly deferred per D-24.

**For this phase:** No tooling needed. Use `rg` as specified in the verification commands above.

## Duplicate-vs-Extract Threshold

**Decision basis:** From CONTEXT.md D-08 and ROADMAP cross-phase commitments.

The threshold is: **duplicate locally UNLESS ≥20 identical lines repeat across ≥3 sites**.

**For LightconeCostTable:** 4 classes × ~10 lines each = ~40 lines total, but only 1 outside-drafting consumer. Well below the 3-site threshold. Duplication is correct.

**Defensibility of the threshold:** This is a team convention established in ROADMAP (not derived from an external source). The ≥20 lines threshold ensures only substantial shared CSS earns a shared location. The ≥3 sites threshold ensures real reuse (not premature optimization).
