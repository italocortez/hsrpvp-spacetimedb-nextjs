## Decisions Made

- **No class renames.** Source class names (`filters`, `paths`, `searchBar`, `clearButton`) preserved 1:1 in the new local module. D-08's Claude's Discretion explicitly permitted renaming, but keeping the same names makes the duplication trivially cross-referenceable against the source and keeps the TSX delta confined to the alias swap (`poolStyles` → `filterStyles`), not the class-identifier suffix. Matches Plans 01-05 precedent.
- **Keep same-feature `styles` import.** PATTERNS.md lines 193-198 recommended keeping `import styles from './CharacterCostTable.module.css'` and introducing `filterStyles` as a new alias for the new module. The alternative (copy `rarityBadge` + `tableWrapper` into the new module + drop the styles import) would have broadened Plan 06's scope to same-feature CSS churn — not in scope. Dual-same-feature imports are explicitly permitted; only cross-feature imports were the R8 violation.
- **Container-only .paths rule.** The source `.paths` rule participates in a 3-selector group (`.roles, .elements, .paths { ... }`) plus `.paths > button` / `.paths > button:not(.selected):hover` / `.paths > button:last-child` child-selector rules lower in CharacterPool.module.css. LightconeCostTable.tsx renders `<FilterButtonGroup>` which provides its own internal button markup + styling — the child-button rules would be dead rules inside the new module. Pitfall 6 explicitly warned against copying them; the verify grep (`.paths > button` → 0) confirmed compliance.
- **Atomic Task 2 commit.** The import swap and all 4 call-site renames landed in a single commit. An intermediate state (import swapped but call sites still reference `poolStyles`) would not compile — `poolStyles` would be undefined. An opposite intermediate state (call sites renamed but import still imports as `poolStyles`) would also not compile. The atomic shape is a correctness requirement, not a stylistic preference.
- **D-11 visual verification deferred to orchestrator report.** Plans 01-05 each reported D-11 to the orchestrator for user approval without a dedicated commit; Plan 06 follows the same canon. The code commits land; SUMMARY + state updates proceed; the user approves the visual state out-of-band and the orchestrator advances.
