# Phase 10.4: Account Selection Per Match - Context

**Gathered:** 2026-04-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Players choose which enrolled HSR account(s) to use per match. Tournament setting controls how many accounts per player (default: 1). Multi-account mode enables asymmetric formats like 1v2. Account selection happens at lobby join (auto-populated with active account), changeable during Waiting and BetweenGames stages. Drop redundant `TournamentEnrolled.hsrAccountId`. Stand-ins get accounts locked on lobby join. HsrAccount and HsrAccountCharacter tables made private with view layer replacing raw subscriptions. Anonymous mode gap fixed in roster visibility view.

Requirements: ACCT-01, ACCT-02, ACCT-03, ACCT-04, ACCT-05

</domain>

<decisions>
## Implementation Decisions

### Account Storage Model
- **D-01:** New `LobbyMemberAccount` join table (PK: `[lobbyId, userId, hsrAccountId]`). Non-public table. Follows composite-PK pattern used by TournamentPlayerAccount and MatchResultParticipant.
- **D-02:** Non-public (no `public: true`) — opponents cannot see which accounts a player selected via raw subscription. Server-side code (reducers, views) can still read it. This is the critical anonymous mode protection.
- **D-03:** Btree indexes: `by_lobby_and_user` (lobbyId, userId), `by_account` (hsrAccountId) for reverse lookups and deletion guards.

### Selection Timing & Flow
- **D-04:** `join_lobby` auto-creates `LobbyMemberAccount` row with the player's current active HsrAccount. For tournament lobbies: validates against TournamentPlayerAccount — if active account isn't locked, falls back to first locked account.
- **D-05:** `select_match_account` unified reducer works for both tournament and non-tournament lobbies. Tournament path validates against `TournamentPlayerAccount` (locked accounts). Non-tournament path validates against `HsrAccount` ownership (any account the player owns).
- **D-06:** Stage guard: Waiting + BetweenGames only. NOT Shelved — unshelving returns to BetweenGames where account changes are allowed. No redundant Shelved handling.
- **D-07:** For non-tournament lobbies, `select_match_account` always replaces (not adds) — enforces max 1 account without needing a column on Lobby.

### Enforcement Matrix
- **D-08:** `start_draft` gate: if lobby is Ranked OR tournament has `countTowardsMmr=true`, require all players to have at least one `LobbyMemberAccount` row. Casual non-ranked lobbies: no enforcement (account row is display-only).
- **D-09:** All lobby types (casual, ranked, tournament) create `LobbyMemberAccount` rows at join. One consistent code path for `validateCharacterOwnership` and roster visibility views.

### Tournament.maxAccountsPerPlayer
- **D-10:** New column on Tournament table: `maxAccountsPerPlayer` (u8, default 1). Controls how many accounts a player can have in `LobbyMemberAccount` for tournament lobbies.
- **D-11:** `select_match_account` for tournament lobbies checks this limit. Non-tournament lobbies always max 1 (enforced by replace behavior, D-07).

### Multi-Account Draft Pool
- **D-12:** Union of characters across all selected accounts. If a character exists on multiple accounts, highest eidolon level wins. Player cannot pick the same character twice.
- **D-13:** Only characters are merged — lightcone ownership is not validated during drafting (existing behavior, unchanged).
- **D-14:** `validateCharacterOwnership` refactored: checks characters from `LobbyMemberAccount` entries only (not all locked TournamentPlayerAccount entries). Non-tournament path also reads `LobbyMemberAccount` (D-09 consistency).

### Roster Visibility with Selected Accounts
- **D-15:** `view_my_roster_visibility` updated to filter by `LobbyMemberAccount` — only characters from selected account(s) shown. View returns per-account data (not merged), letting frontend decide display.
- **D-16:** Visibility rules scoped to selected accounts:
  - `ClosedNoRating`: nothing shown
  - `ClosedWithRating`: selected account(s) rating only
  - `OpenRoster`: selected account(s) rating + characters
- **D-17:** All selected accounts' ratings returned in the view — frontend decides how to display (per-account list, average, etc.).

### Anonymous Mode Fix
- **D-18:** When `lobby.isAnonymousPlayers=true`, force `ClosedNoRating` for opponents in `view_my_roster_visibility` regardless of `rosterVisibility` setting. Own team + referee still see full data (existing D-14 behavior).
- **D-19:** `LobbyMemberAccount` being non-public (D-02) means account IDs never leak to opponents via subscription. The view anon fix (D-18) closes the remaining gap for OpenRoster anonymous lobbies.

### HsrAccount + HsrAccountCharacter Made Private
- **D-20:** Both `HsrAccount` and `HsrAccountCharacter` tables changed from `public: true` to private (no `public` key). Server-side code (reducers, views, helpers) unaffected — only client subscriptions blocked.
- **D-21:** `spacetime generate` still produces type definitions for private tables (types always included). Subscription/query code NOT generated by default. Use `--include-private` flag for admin tools or testing if needed.
- **D-22:** Three new views replace raw table subscriptions:
  - `view_my_roster` — authenticated, returns caller's own HsrAccounts + characters (for self roster management)
  - `view_public_accounts` — anonymous view, returns all HsrAccount rows where `isRosterPublic=true` (for profile browsing, with characters if public, rating if `isRatingPublic`)
  - `view_tournament_registrant_accounts` — authenticated, returns locked accounts for tournaments caller is enrolled in. Respects tournament's `rosterVisibility` setting. TO + assistants always see all.

### TournamentEnrolled.hsrAccountId Removal
- **D-23:** Remove `hsrAccountId` column from `TournamentEnrolled`. Column was only written at registration (tournamentRegistration.ts:79), never read by any reducer or validation logic. `TournamentPlayerAccount` is the source of truth for locked accounts.

### HsrAccount Deletion Guard
- **D-24:** `delete_hsr_account` and `admin_delete_hsr_account` both blocked if the account has any `LobbyMemberAccount` rows (active lobby usage) or `TournamentPlayerAccount` rows for active tournaments (not Completed/Cancelled).
- **D-25:** Both user and admin variants blocked equally. Admins must remove lobby/tournament references before deleting an account.

### Stand-In Account Flow
- **D-26:** When a stand-in joins a tournament lobby via `join_lobby` (after `approve_stand_in`), snapshot their active account(s) into `TournamentPlayerAccount` at that moment — same locking as registration, just deferred.
- **D-27:** `select_match_account` validates against these TPA entries (same as regular tournament players).

### Cascade & Cleanup
- **D-28:** `hardDeleteLobby` cascade extended: delete all `LobbyMemberAccount` rows for the lobby.
- **D-29:** `leave_lobby`: delete `LobbyMemberAccount` rows immediately for departing member (no preservation for finalization — account selection is ephemeral).
- **D-30:** `lobby_gc` cleanup: `LobbyMemberAccount` rows deleted as part of `hardDeleteLobby` cascade.
- **D-31:** Tournament cancel cascade: `LobbyMemberAccount` cleaned up via `hardDeleteLobby` on linked lobbies (existing Phase 10.1 D-18 cascade).

### Schema Changes Summary
- **D-32:** New table: `LobbyMemberAccount` (lobbyId u32, userId u32, hsrAccountId u32) — non-public, composite PK, 2 btree indexes.
- **D-33:** New column: `Tournament.maxAccountsPerPlayer` (u8, default 1).
- **D-34:** Remove column: `TournamentEnrolled.hsrAccountId`.
- **D-35:** Table privacy: `HsrAccount` and `HsrAccountCharacter` set to private (remove `public: true`).
- **D-36:** Requires `--clear-database` publish (column removal + privacy change).

### Claude's Discretion
- Exact `select_match_account` reducer error messages
- Whether `view_public_accounts` returns characters inline or just account metadata with a separate character sub-query
- `view_tournament_registrant_accounts` return type (flat rows vs grouped by user)
- Index naming conventions for `LobbyMemberAccount`
- Test file organization (new test file vs appending to existing)
- Order of schema changes within plans

</decisions>

- Btree index naming: `by_lobby_and_user`, `by_account` follows existing `by_tournament_and_user` convention
- View registration: all views in securityViews.ts or anonymousViews.ts, registered via schema.ts imports
- Anonymous view pattern: anonymousViews.ts contains all `anonymousView()` calls

- `runFinalization` (finalizationHelpers.ts) — cleanup step deletes lobby via hardDeleteLobby, which cascades LobbyMemberAccount
- `schema.ts` — table and view registration for new LobbyMemberAccount table and 3 new views

<specifics>
## Specific Ideas

- Account rating is the primary UI display concern — rating calculation formula to be discussed in Phase 11
- "Bandwidth and security over all" — LobbyMemberAccount non-public, HsrAccount/HsrAccountCharacter private, views replace raw subscriptions
- `--include-private` flag on `spacetime generate` is available for admin tooling if needed
- Tournament registrant view respects tournament's rosterVisibility setting — puts control in TO's hands
- Multi-account union (highest eidolon) is for ownership validation only — views return per-account data so frontend can display individually

</specifics>
