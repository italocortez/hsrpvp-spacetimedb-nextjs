# Phase 10.4: Account Selection Per Match - Research

**Researched:** 2026-04-04
**Domain:** SpacetimeDB backend -- new join table, reducer, views, schema modifications, cascade cleanup
**Confidence:** HIGH

## Summary

Phase 10.4 introduces per-match HSR account selection, replacing the current "all locked accounts" ownership model with a targeted "selected accounts for this match" model. The core addition is a `LobbyMemberAccount` join table (non-public, composite PK) that tracks which account(s) a player has activated for a given lobby. A unified `select_match_account` reducer handles both tournament and non-tournament lobbies with different validation paths.

The phase also makes `HsrAccount` and `HsrAccountCharacter` tables private (bandwidth reduction), adds 3 new views to replace raw subscriptions, fixes an anonymous mode gap in roster visibility, adds a deletion guard to `delete_hsr_account` / `admin_delete_hsr_account`, removes the redundant `TournamentEnrolled.hsrAccountId` column, and adds `Tournament.maxAccountsPerPlayer`. All decisions are locked in CONTEXT.md with 36 numbered decisions.

**Primary recommendation:** Execute as a single plan with 6-7 waves ordered by dependency: (1) schema changes, (2) new reducer + helpers, (3) view updates/additions, (4) cascade/cleanup wiring, (5) deletion guards, (6) docs, (7) publish + test updates.

## Architecture Patterns

### New Table: LobbyMemberAccount

Follows established non-public composite-PK join table pattern (same as LobbyPassword, CostSetDraft* tables).

```typescript
// Source: Verified against lobbyPassword.ts (canonical non-public pattern) and
// tournamentPlayerAccount.ts (composite PK join table pattern)
import { table, t } from 'spacetimedb/server';

export const lobbyMemberAccountColumns = {
    lobbyId: t.u32(),
    userId: t.u32(),
    hsrAccountId: t.u32(),
    createdById: t.u32(),
    createdDate: t.timestamp(),
    lastModifiedById: t.u32(),
    lastModifiedDate: t.timestamp(),
};

export const LobbyMemberAccount = table({
    name: 'lobby_member_account',
    // Intentionally NOT public -- never broadcast to clients (D-02)
    primaryKey: ['lobbyId', 'userId', 'hsrAccountId'],
    indexes: [
        { accessor: 'by_lobby_and_user', algorithm: 'btree', columns: ['lobbyId', 'userId'] },
        { accessor: 'by_account', algorithm: 'btree', columns: ['hsrAccountId'] },
    ],
}, lobbyMemberAccountColumns);
```

**Key pattern notes:**
- No `public: true` key at all (not `public: false`) -- matches LobbyPassword and CostSetDraft* convention
- Audit columns included per SCHM-03 pattern
- Triple composite PK allows a player to have multiple accounts selected per lobby (multi-account mode)
- `by_lobby_and_user` index used for "get all selected accounts for this player in this lobby"
- `by_account` index used for reverse lookup (deletion guard: "is this account used in any lobby?")

1. **`view_my_roster`** (authenticated, securityViews.ts) -- Returns caller's own HsrAccounts + characters. Pattern: `ctx.sender -> UserIdentity -> userId -> HsrAccount.user_id.filter -> HsrAccountCharacter.hsr_account_id.filter`. Same structure as `view_my_player_stats`.

### validateCharacterOwnership Refactoring

Current implementation in `ownershipValidation.ts` (45 lines):
- Tournament path: scans ALL `TournamentPlayerAccount` entries for the user
- Non-tournament path: checks only the active HsrAccount

Refactored implementation:
- Both paths: read `LobbyMemberAccount.by_lobby_and_user.filter([lobbyId, userId])` to get selected account IDs
- For each selected account: check `HsrAccountCharacter.by_account_and_character.filter([accountId, characterName])`
- Multi-account union: if character found on ANY selected account, it's valid
- Highest eidolon level: when character exists on multiple accounts, the check only needs to confirm existence (eidolon level is read separately for draft pool, not in ownership validation)

### Cascade Cleanup Pattern

`hardDeleteLobby` in lobbyGc.ts needs a new step between step 1 (ChatMessage) and step 2 (LobbyMember):

```typescript
// 1b. Delete all LobbyMemberAccount rows (D-28)
for (const lma of [...ctx.db.LobbyMemberAccount.by_lobby_and_user.filter([lobbyId, /* need all users */])]) {
    ctx.db.LobbyMemberAccount.delete(lma);
}
```

**Implementation note:** The `by_lobby_and_user` index is a 2-column btree on `[lobbyId, userId]`. To delete ALL rows for a lobby regardless of userId, we need to iterate LobbyMember rows first (already fetched in step 2) and use the index per-user, OR use a different approach. Best approach: iterate via the LobbyMember rows already being collected:

```typescript
// Before deleting LobbyMember rows, delete their LobbyMemberAccount rows
for (const member of [...ctx.db.LobbyMember.lobby_id.filter(lobbyId)]) {
    for (const lma of [...ctx.db.LobbyMemberAccount.by_lobby_and_user.filter([lobbyId, member.userId])]) {
        ctx.db.LobbyMemberAccount.delete(lma);
    }
}
```

This is the cleanest pattern because it uses the 2-column btree index prefix and the LobbyMember lobby_id index already in use.

### Deletion Guard Pattern

Both `delete_hsr_account` and `admin_delete_hsr_account` need guards before the existing cascade:

```typescript
// D-24: Block if account is used in any active lobby
const lobbyUsage = [...ctx.db.LobbyMemberAccount.by_account.filter(hsrAccountId)];
if (lobbyUsage.length > 0) {
    throw new SenderError('Cannot delete this account while it is selected in an active lobby.');
}

// D-24: Block if account is locked in any active tournament
const tpaUsage = [...ctx.db.TournamentPlayerAccount.by_user.filter(/* need per-account check */)];
// Need to filter TPA by hsrAccountId -- current index is by_user which returns all user's TPAs
// Filter further: check tournament stage is not Completed/Cancelled
```

**Index gap identified:** `TournamentPlayerAccount` has `by_tournament_and_user` and `by_user` indexes, but no `by_account` (hsrAccountId) index. The deletion guard needs to find "all TPA rows for this specific hsrAccountId." Options:

1. **Add a `by_account` btree index to TournamentPlayerAccount** -- cleanest, O(1) lookup
2. **Filter from `by_user`** -- get all user's TPAs, filter by hsrAccountId in JS -- works but less efficient

Recommendation: Add `by_account` index to TournamentPlayerAccount. It's a one-line change and enables efficient reverse lookup. The `LobbyMemberAccount` table already has this index per D-03.

### join_lobby Auto-Creation

The `join_lobby` reducer in `lobbyLifecycle.ts` needs modification in two places:

1. **New join (line 307-319):** After inserting LobbyMember, insert LobbyMemberAccount:
   - Non-tournament: use player's active HsrAccount (may be undefined for guests/no-account users -- skip if none)

2. **Reconnect (line 227-282):** Do NOT re-create LobbyMemberAccount on reconnect -- the existing selection persists.

2. If stand-in: snapshot their current HsrAccounts into TournamentPlayerAccount (same as register_for_tournament does)

|---------|-------------|-------------|-----|
| Composite PK updates | Custom find+update logic | Delete+re-insert pattern | Established pattern throughout codebase (LobbyMember, TournamentPlayerAccount, TournamentEnrolled) |

## Common Pitfalls

### Pitfall 1: Cascade Order in hardDeleteLobby
**What goes wrong:** Deleting LobbyMember rows before LobbyMemberAccount rows loses the userId needed to look up LMA rows via the `by_lobby_and_user` index.
**Why it happens:** LobbyMemberAccount has no single-column lobbyId index (only `by_lobby_and_user` 2-column).
**How to avoid:** Delete LobbyMemberAccount rows BEFORE LobbyMember rows. Iterate LobbyMember.lobby_id.filter first, use each member.userId for the LMA lookup.
**Warning signs:** Orphaned LobbyMemberAccount rows after lobby cleanup.

### Pitfall 2: Stand-In TPA Creation Timing
**What goes wrong:** LobbyMemberAccount validation checks TournamentPlayerAccount BEFORE the stand-in's TPA entries exist.
**Why it happens:** Stand-in account locking (D-26) must happen at lobby join, but the LMA auto-creation (D-04) also happens at lobby join.
**How to avoid:** In join_lobby, detect stand-in status FIRST, create TPA entries, THEN create LobbyMemberAccount. Sequential within the same reducer transaction.
**Warning signs:** Stand-in gets "account not locked for tournament" error on join.

### Pitfall 3: Non-Tournament Lobby Account Selection
**What goes wrong:** LobbyMemberAccount created at join_lobby for a non-tournament lobby references an HsrAccount the user later deletes.
**Why it happens:** Non-tournament lobbies don't lock accounts -- the active account reference is a snapshot at join time.
**How to avoid:** The deletion guard (D-24) prevents deleting accounts with active LobbyMemberAccount rows. Combined with LobbyMemberAccount cleanup on leave/kick/ban/close, orphan rows are prevented.
**Warning signs:** LobbyMemberAccount referencing a deleted HsrAccount.

### Pitfall 4: hsrAccountId Removal Breaking Views
**What goes wrong:** `view_my_tournament_enrolled` (TO view from Phase 10.3) returns TournamentEnrolled.rowType which includes hsrAccountId.
**Why it happens:** The rowType auto-reflects schema changes, but client code expecting the column might break.
**How to avoid:** This is a `--clear-database` publish, so all clients reconnect. No backwards compatibility concern. The generated bindings will reflect the new schema.
**Warning signs:** None in server code; only client-side if bindings aren't regenerated.

### Pitfall 5: Multi-Account Character Deduplication in Draft Pool
**What goes wrong:** Player with 2 selected accounts picks a character that exists on both -- validation allows it twice.
**Why it happens:** Each LobbyMemberAccount is checked independently.
**How to avoid:** `validateCharacterOwnership` only checks existence (can pick this character?), not quantity. The draft itself prevents picking the same character twice via step history (existing `allowMirrorPicks` logic). Ownership validation just needs to confirm the character exists on ANY selected account.
**Warning signs:** N/A -- draft sequence already prevents duplicate picks.

### Pitfall 6: TournamentPlayerAccount Index Gap for Deletion Guard
**What goes wrong:** Deletion guard needs "find all TPA rows for this hsrAccountId" but no per-account index exists.
**Why it happens:** TPA was designed for per-user and per-tournament queries, not per-account reverse lookups.
**How to avoid:** Add a `by_account` btree index to TournamentPlayerAccount (same pattern as LobbyMemberAccount D-03).
**Warning signs:** Full table scan via iter() on TPA table.

```typescript
                    hsrAccountId: account.id,
                    uid: account.uid,
                    region: account.region,
                    displayLabel: account.displayLabel,
                    isActive: account.isActive,
                    isRosterPublic: account.isRosterPublic,
                    isRatingPublic: account.isRatingPublic,
                    accountRating: account.accountRating,
                    characterName: char.characterName,
                    eidolonLevel: char.eidolonLevel,
                });
            }
            // Include account even if it has no characters (sentinel row)
            if ([...ctx.db.HsrAccountCharacter.hsr_account_id.filter(account.id)].length === 0) {
                results.push({
                    hsrAccountId: account.id,
                    uid: account.uid,
                    region: account.region,
                    displayLabel: account.displayLabel,
                    isActive: account.isActive,
                    isRosterPublic: account.isRosterPublic,
                    isRatingPublic: account.isRatingPublic,
                    accountRating: account.accountRating,
                    characterName: '',
                    eidolonLevel: 0,
                });
            }
        }
        return results;
    }
);
```

## Open Questions

1. **view_public_accounts character inclusion**
   - What we know: D-22 says it returns HsrAccount rows where `isRosterPublic=true`, optionally with characters if public
   - What's unclear: Should characters be included inline (flat rows like view_my_roster) or just account metadata?
   - Recommendation: Include characters inline for consistency with view_my_roster pattern. Accounts with `isRosterPublic=false` would be excluded entirely. Use same flat row structure.

2. **view_tournament_registrant_accounts grouping**
   - What we know: Returns locked accounts for tournaments caller is enrolled in. TO + assistants see all.
   - What's unclear: Flat rows (one per account-character pair) vs grouped by user?
   - Recommendation: Flat rows with userId column, same as other views. Client groups by userId.

3. **create_lobby LobbyMemberAccount creation**
   - What we know: D-09 says "all lobby types create LobbyMemberAccount rows at join." The host joins in create_lobby.
   - What's unclear: Should create_lobby also auto-create LobbyMemberAccount for the host?
   - Recommendation: Yes. Host goes through the same auto-creation flow. For non-tournament lobbies, use active account. This keeps the code path consistent.
