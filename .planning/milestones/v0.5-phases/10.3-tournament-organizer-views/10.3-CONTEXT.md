# Phase 10.3: Tournament Organizer Views - Context

**Gathered:** 2026-04-04 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Server-side SpacetimeDB views scoped to tournament organizers — replacing full-table client subscriptions with TO-filtered views. The frontend subscribes to these views instead of raw tables, receiving only rows relevant to the TO's own tournaments. No aggregation or dashboard logic server-side; the frontend does all presentation.

</domain>

<decisions>
## Implementation Decisions

### Philosophy: Row Filtering, Not Column Projection
- **D-01:** All views return full `.rowType` (all columns) — the bandwidth win is row filtering (only my tournaments), not column reduction. TOs tinker with settings, brackets, and match state frequently — they need every column.
- **D-02:** No custom `t.object()` projected structs needed. Views return the same shape as the underlying table, just filtered to the TO's tournaments.
- **D-03:** No server-side aggregation. The "dashboard" is raw filtered rows — the frontend counts participants, teams, and match statuses. This gives the frontend full flexibility for v1 UI without requiring backend changes.

### View Scope: Organizer + Assistant
- **D-04:** A tournament belongs to a TO if they are the `organizerId` OR have a `TournamentAssistant` entry. Both paths use existing btree indexes (`Tournament.organizer_id`, `TournamentAssistant.user_id`). This matches the `ensureTournamentAccess` helper pattern.
- **D-05:** Views are authenticated (`spacetimedb.view()`), not `anonymousView`. Tournament data isn't a security risk to expose publicly, but filtering by caller identity requires authentication. Other users can still see tournament data via raw table subscriptions if tables remain public.

### View Set
- **D-06:** One view per table that TOs need filtered access to. The core set replaces 5+ full-table subscriptions:
  1. `view_my_tournaments` — Tournament rows where caller is organizer or assistant (TO-VIEW-01)
  2. `view_my_tournament_enrolled` — TournamentEnrolled rows for caller's tournaments
  3. `view_my_tournament_teams` — TournamentTeam rows (+ TournamentTeamMember rows) for caller's tournaments
  4. `view_my_tournament_matches` — BracketMatch rows for caller's tournaments (TO-VIEW-03)
  5. `view_my_tournament_match_results` — MatchResultRecord rows for caller's tournaments
  6. `view_my_tournament_lobbies` — Lobby rows linked to caller's tournament bracket matches (for stage info)
- **D-07:** Views 2-6 all resolve the TO's tournament set first (same logic as view 1), then filter the target table by `tournament_id` index. For Lobby and MatchResultRecord which lack a direct `tournament_id`, navigate via BracketMatch → `Lobby.bracket_match_id` and `MatchResultRecord.bracket_match_id`.

### File Organization
- **D-08:** Add views to `securityViews.ts` where all 13 existing authenticated per-user views live. No new file needed — follows established convention.

### Index Strategy
- **D-09:** All required btree indexes already exist: `Tournament.organizer_id`, `TournamentAssistant.user_id`, `TournamentAssistant.tournament_id`, `TournamentEnrolled.tournament_id`, `TournamentTeam.tournament_id`, `BracketMatch.tournament_id`, `Lobby.bracket_match_id`, `MatchResultRecord.bracket_match_id`. No new indexes needed.
- **D-10:** N+1 index lookups are acceptable at project scale (100 users, 8-32 match brackets typical). Same pattern as existing `view_my_roster_visibility`.

### Claude's Discretion
- Exact view count — if some views can be merged or if additional tables need TO-scoped views (e.g., GroupPhaseRecord), add them following the same pattern
- Whether to include TournamentTeamMember as a separate view or combine with TournamentTeam view
- Return type for views that join across tables (e.g., tournament lobbies) — if raw Lobby.rowType works, use it; if a join is needed for navigation, use minimal projection

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ensureTournamentAccess` helper: organizer + assistant two-path check — same logic needed for view scope resolution
- `cascadeCleanupTournament` helper: demonstrates efficient iteration over all tournament-scoped tables using btree indexes — confirms all indexes work at scale
- `buildVisibleMatchIds` in anonymousViews.ts: shared helper pattern for views that need the same base filter

### Established Patterns
- All views follow: `ctx.sender` → `UserIdentity.identity.find()` → userId → btree filter
- Views return `t.array(RowType)` for multi-row results, `t.option(RowType)` for single-row
- Anti-pattern: `iter()` on any table — always use btree index `.filter()` calls
- For tables without direct tournament_id index: navigate via BracketMatch.tournament_id → bracket match IDs → target table's bracket_match_id index

### Integration Points
- Views registered in `schema.ts` via existing imports (securityViews.ts already imported)
- Client bindings auto-generated via `spacetime generate` — new view types appear as subscribable
- Existing `view_my_lobbies` only returns lobbies where caller is a member; `view_my_tournament_lobbies` extends this to all lobbies linked to caller's tournaments

</code_context>
