# Phase 10.3: Tournament Organizer Views - Research

**Researched:** 2026-04-04
**Domain:** SpacetimeDB server-side views, tournament data scoping, btree index navigation
**Confidence:** HIGH

## Summary

This phase adds 6 authenticated SpacetimeDB views to `securityViews.ts` that scope tournament-related table data to the calling tournament organizer (TO). The views follow the exact same pattern used by the 13 existing authenticated views: resolve `ctx.sender` to a userId via `UserIdentity`, then filter tables using btree indexes. The key innovation is the two-path TO resolution (organizer OR assistant) which mirrors the existing `ensureTournamentAccess` helper logic.

All required btree indexes already exist on all 8 target tables. No schema changes, no new tables, no new indexes needed. The views return full `.rowType` (not projected structs), keeping implementation simple. Two views (Lobby and MatchResultRecord) lack a direct `tournament_id` column and must navigate through BracketMatch as an intermediary.

**Primary recommendation:** Extract a shared `getMyTournamentIds(ctx)` helper that resolves the calling user's tournament set via `Tournament.organizer_id` + `TournamentAssistant.user_id`, then reuse it across all 6 views. This is the same DRY pattern as `buildVisibleMatchIds()` in `anonymousViews.ts`.

### Pattern 1: Shared Tournament Set Resolution (DRY Helper)
**What:** Extract the TO's tournament ID resolution into a shared helper, similar to `buildVisibleMatchIds()` in anonymousViews.ts.
**When to use:** All 6 views need the same "which tournaments does this caller manage?" logic.
**Example:**
```typescript
// Source: Derived from ensureTournamentAccess pattern + buildVisibleMatchIds DRY pattern
function getMyTournamentIds(ctx: any): Set<number> {
    const mapping = ctx.db.UserIdentity.identity.find(ctx.sender);
    if (!mapping) return new Set();
    const userId = mapping.userId;

    const tournamentIds = new Set<number>();

    // Path 1: Organizer (Tournament.organizer_id btree)
    for (const t of ctx.db.Tournament.organizer_id.filter(userId)) {
        tournamentIds.add(t.id);
    }

    // Path 2: Assistant (TournamentAssistant.user_id btree)
    for (const a of ctx.db.TournamentAssistant.user_id.filter(userId)) {
        tournamentIds.add(a.tournamentId);
    }

    return tournamentIds;
}
```

### Pattern 2: Direct tournament_id Filter (Views 1-4)
**What:** Tables with a direct `tournament_id` column and btree index.
**When to use:** TournamentEnrolled, TournamentTeam, BracketMatch, GroupPhaseRecord.
**Example:**
```typescript
// Source: Existing view_my_draft_character_costs pattern (filter by owner's set, then by FK)
spacetimedb.view(
    { name: 'view_my_tournament_enrolled', public: true },
    t.array(TournamentEnrolled.rowType),
    (ctx) => {
        const tournamentIds = getMyTournamentIds(ctx);
        if (tournamentIds.size === 0) return [];
        const results: any[] = [];
        for (const tid of tournamentIds) {
            for (const row of ctx.db.TournamentEnrolled.tournament_id.filter(tid)) {
                results.push(row);
            }
        }
        return results;
    }
);
```

### Pattern 3: Indirect Navigation via BracketMatch (Views 5-6)
**What:** Tables that lack a direct `tournament_id` and must navigate through BracketMatch.
**When to use:** MatchResultRecord (has `bracket_match_id`), Lobby (has `bracket_match_id`).
**Example:**
```typescript
// Source: D-07 navigation pattern; BracketMatch.tournament_id -> bracketMatchId -> target table
spacetimedb.view(
    { name: 'view_my_tournament_lobbies', public: true },
    t.array(Lobby.rowType),
    (ctx) => {
        const tournamentIds = getMyTournamentIds(ctx);
        if (tournamentIds.size === 0) return [];
        const results: any[] = [];
        for (const tid of tournamentIds) {
            // Get all bracket matches for this tournament
            for (const bm of ctx.db.BracketMatch.tournament_id.filter(tid)) {
                // Navigate to lobby via bracket_match_id index on Lobby
                for (const lobby of ctx.db.Lobby.bracket_match_id.filter(bm.id)) {
                    results.push(lobby);
                }
            }
        }
        return results;
    }
);
```

### Pattern 4: TournamentTeamMember (Discretion: Separate View)
**What:** TournamentTeamMember has a `tournamentId` column but only a `by_tournament_and_user` 2-column btree -- not a single-column `tournament_id` btree. However, it also has a `team_id` btree.
**Recommendation:** Add as a 7th view (`view_my_tournament_team_members`). Navigate via TournamentTeam.tournament_id -> teamId -> TournamentTeamMember.team_id. This keeps TournamentTeam and TournamentTeamMember separate (cleaner client subscription model -- frontend subscribes to the one it needs).
**Example:**
```typescript
spacetimedb.view(
    { name: 'view_my_tournament_team_members', public: true },
    t.array(TournamentTeamMember.rowType),
    (ctx) => {
        const tournamentIds = getMyTournamentIds(ctx);
        if (tournamentIds.size === 0) return [];
        const results: any[] = [];
        for (const tid of tournamentIds) {
            for (const team of ctx.db.TournamentTeam.tournament_id.filter(tid)) {
                for (const member of ctx.db.TournamentTeamMember.team_id.filter(team.id)) {
                    results.push(member);
                }
            }
        }
        return results;
    }
);
```

### Pattern 5: GroupPhaseRecord (Discretion: Add as 8th View)
**What:** GroupPhaseRecord has a `tournament_id` btree index and is essential for TOs managing group-phase tournaments.
**Recommendation:** Add `view_my_tournament_group_standings` as an 8th view. Same direct-filter pattern as views 2-4. Without this, TOs running group-stage tournaments would still need a full-table subscription for standings data.

### Anti-Patterns to Avoid
- **`.iter()` on any table:** Always use btree index `.filter()` calls. The existing `view_lobby_browser` demonstrates scanning via individual stage filters to avoid iter().
- **Column projection for TO views:** D-01/D-02 explicitly prohibit custom projected structs. Use `.rowType` directly.
- **Server-side aggregation:** D-03 explicitly prohibits. Do not count rows server-side.
- **Duplicating tournament set resolution:** Extract the shared helper once; do not repeat the two-path organizer+assistant logic in each view.
- **Using `ctx.from.Table`:** This is the query-builder form for anonymousViews. Procedural views (which these are) should use `ctx.db.Table.index.filter()`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TO tournament set resolution | Inline organizer+assistant check in each view | Shared `getMyTournamentIds(ctx)` helper | Same logic needed 6-8 times; mirrors `buildVisibleMatchIds` pattern |
| Admin/Mod bypass in views | Permission checking inside views | N/A -- views are data filters, not permission gates | Views scope data by organizer identity; admin sees all tournaments via raw table subscription (tables are public) |

**Key insight:** These views are pure data filters, not security gates. All tournament tables are `public: true`, so any subscriber can still see all data via raw table subscriptions. The views reduce bandwidth for TO clients who only need their own tournament data.

## Common Pitfalls

### Pitfall 1: Missing UserIdentity Mapping
**What goes wrong:** `ctx.sender` returns an Identity (cryptographic principal), not a userId. Forgetting to resolve via `UserIdentity.identity.find()` causes lookups to fail silently.
**Why it happens:** New views may skip the identity resolution step.
**How to avoid:** Every authenticated view starts with `const mapping = ctx.db.UserIdentity.identity.find(ctx.sender); if (!mapping) return [];` -- this is baked into the shared helper.
**Warning signs:** View returns empty results for a logged-in TO.

### Pitfall 2: MatchResultRecord.bracketMatchId is Optional
**What goes wrong:** Casual (non-tournament) match results have `bracketMatchId = undefined`. Filtering by bracketMatchId will miss these (correct) but the btree index filter must handle optional values gracefully.
**Why it happens:** MatchResultRecord serves both casual and tournament matches.
**How to avoid:** The navigation is BracketMatch.tournament_id -> bracketMatchId -> MatchResultRecord.bracket_match_id.filter(bm.id). Since we start from BracketMatch rows (which always have an id), the filter value is always defined. Only tournament-linked MatchResultRecords will match.
**Warning signs:** N/A -- this is actually self-filtering correctly by design.

### Pitfall 3: Lobby.bracketMatchId is Also Optional
**What goes wrong:** Non-tournament lobbies have `bracketMatchId = undefined`. The `bracket_match_id` btree on Lobby only returns tournament lobbies.
**Why it happens:** Same pattern as MatchResultRecord -- lobbies serve both casual and tournament contexts.
**How to avoid:** Same navigation pattern: start from BracketMatch, filter Lobby by `bracket_match_id`. Only tournament-linked lobbies will match.
**Warning signs:** N/A -- correct by design.

### Pitfall 4: TournamentTeamMember Index Mismatch
**What goes wrong:** TournamentTeamMember has `by_tournament_and_user` (2-column) and `team_id` (single-column) indexes, but no single-column `tournament_id` index. Attempting `TournamentTeamMember.tournament_id.filter(tid)` will fail at compile/publish time.
**Why it happens:** The table was designed for per-user lookups (by_tournament_and_user) and per-team lookups (team_id), not bulk tournament lookups.
**How to avoid:** Navigate via TournamentTeam.tournament_id -> team.id -> TournamentTeamMember.team_id.filter(team.id). This is an extra N+1 hop but acceptable at scale (D-10).
**Warning signs:** Publish error or runtime error referencing missing index accessor.

### Pitfall 5: Import Ordering in securityViews.ts
**What goes wrong:** New table imports added to securityViews.ts but not in the right order, or forgetting to import tables that are only used indirectly (e.g., TournamentAssistant for the helper).
**Why it happens:** securityViews.ts currently imports 18 symbols; adding 6-8 more tables requires careful import management.
**How to avoid:** Add imports alphabetically within the existing import groups. Verify all table references in the helper and view bodies have corresponding imports.
**Warning signs:** TypeScript compile errors on publish.

## Discretion Recommendations

### 1. TournamentTeamMember: Separate View (7th view)
**Recommendation:** Add `view_my_tournament_team_members` as a separate view.
**Rationale:** TournamentTeam rows contain team metadata (name, captain, seed). TournamentTeamMember rows contain membership (which users are on which teams). These are distinct subscriptions for the frontend -- a TO managing seeds only needs teams, not members. Merging them would require a custom projected struct (violating D-02) or returning both row types from one view (not supported by SpacetimeDB views).

### 2. GroupPhaseRecord: Add as 8th View
**Recommendation:** Add `view_my_tournament_group_standings` view.
**Rationale:** GroupPhaseRecord has a direct `tournament_id` btree index. TOs running group-stage tournaments need standings data. Without this view, TOs must subscribe to the full GroupPhaseRecord table. Same simple pattern as views 2-4.

### 3. Lobby View Return Type
**Recommendation:** Use raw `Lobby.rowType`. No projection needed.
**Rationale:** Per D-01/D-02, views return full row types. The Lobby table is already public, and TOs need full lobby config (timers, budgets, stage) to monitor match progress.

## Open Questions

1. **Tournament table `public: true` -- are raw table subscriptions still available?**
   - What we know: All tournament tables have `public: true`. Views are an optimization, not a security gate.
   - What's unclear: Whether the frontend should eventually migrate to view-only subscriptions and make tables private.
   - Recommendation: Out of scope for this phase. Tables stay public. Document in architecture docs that views are the recommended subscription path for TO clients.

2. **View re-evaluation performance with 8 views**
   - What we know: Each authenticated view is re-evaluated per subscriber when underlying tables change. With 8 TO views, a single tournament row update triggers re-evaluation for all TO subscribers of all 8 views.
   - What's unclear: Whether SpacetimeDB optimizes view re-evaluation when the shared helper's output hasn't changed.
   - Recommendation: Acceptable at project scale (100 users, few TOs). Document as a future optimization area if TO count grows significantly.
