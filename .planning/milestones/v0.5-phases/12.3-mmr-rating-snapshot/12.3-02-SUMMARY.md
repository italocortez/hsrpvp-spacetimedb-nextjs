# Phase 12.3 Plan 02: Finalization Read-Path Switch Summary

One-liner: Replaced the buggy `HsrAccount.isActive` re-query in `processMatchMmr` with a direct read of the `MatchResultParticipant.accountRatingSnapshot` column (populated by Plan 12.3-01), closing the race window for both the standalone-ranked and tournament-batch ELO paths in a single line-per-team change.

## Status

- Task 1: **COMPLETE** — committed as `dd1696f`

## Objective (Recap)

`processMatchMmr` is the shared ELO helper called from two call sites:
1. `finalizationHelpers.ts:411` (standalone-ranked via `runFinalization` step 11, passing `effectiveParticipants` which are MRP rows)
2. `matchFinalization.ts:116` (tournament batch via `process_tournament_mmr`, passing `[...ctx.db.MatchResultParticipant.match_result_id.filter(mr.id)]` directly)

Before this plan, the helper re-queried `HsrAccount.user_id.filter(p.userId).find(a => a.isActive)` at ELO time. That read happened AFTER the MRP row was inserted, so any of the following post-capture mutations could silently change the ELO input:
- `set_active_hsr_account` flipping `isActive`
- `batch_upsert_characters` / `batch_remove_characters` mutating `accountRating`
- `migrate_roster` remapping account ownership

Plan 12.3-01 already persists the snapshot at `start_draft` (the lobby `Waiting → Drafting` transition) via the max-across-LMA rule. This plan closes the loop by making the consumer read the persisted field instead of re-querying.

## Before / After: processMatchMmr account-modifier read (lines 84-93)

### Before — `spacetimedb/src/helpers/finalizationHelpers.ts:85-92`

```typescript
    // 5. Apply account rating modifier (Fair MMR always in Phase 5)
    const blueAccountRatings = blueParticipants.map((p: any) => {
        const activeAccount = [...ctx.db.HsrAccount.user_id.filter(p.userId)].find((a: any) => a.isActive);
        return activeAccount?.accountRating ?? 0;
    });
    const redAccountRatings = redParticipants.map((p: any) => {
        const activeAccount = [...ctx.db.HsrAccount.user_id.filter(p.userId)].find((a: any) => a.isActive);
        return activeAccount?.accountRating ?? 0;
    });
```

### After — `spacetimedb/src/helpers/finalizationHelpers.ts:84-93`

```typescript
    // 5. Apply account rating modifier (Fair MMR always in Phase 5)
    // D-readpath-01 (Phase 12.3): read the persisted snapshot from MRP instead of
    // re-querying HsrAccount.isActive. The snapshot was captured at start_draft
    // (draftClassic.ts line ~204) with the max-across-LMA rule, so post-capture
    // mutations to isActive or accountRating cannot affect the ELO delta here.
    // D-readpath-02: both runFinalization step 11 (standalone-ranked) and
    // process_tournament_mmr (tournament batch) call this helper — one edit fixes
    // both paths by construction.
    const blueAccountRatings = blueParticipants.map((p: any) => p.accountRatingSnapshot);
    const redAccountRatings = redParticipants.map((p: any) => p.accountRatingSnapshot);
```

Everything else in `processMatchMmr` is unchanged: `blueRatings` / `redRatings` at 72-78, `calculateTeamEffective` at 81-82, `blueAvgAccount` / `redAvgAccount` aggregation at 94-99, the `if (blueAvgAccount > redAvgAccount)` branch at 102-106, the winner-determination block at 108-120, and the per-participant ELO delta loop at 123-175 are all preserved verbatim.

The concede-fallback at lines 260-270 (`concedeParticipants = lobbyMembers.map(...)`) is also unchanged — research question 3 in CONTEXT.md explicitly recommended SKIP for this hardening because the path is admin-only/unreachable via user reducers and the `?? 0` fallback (now `undefined` → `undefined` mapped via the usual NaN-safe average) is acceptable for the synthetic participants built from `LobbyMember` rows.
