# Phase 12.3: Code Review Report

**Reviewed:** 2026-04-11
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Phase 12.3 introduces the `accountRatingSnapshot` column on `MatchResultParticipant`, shifting ELO's account-modifier read path from a live `HsrAccount.isActive` query to a persisted per-match snapshot captured at `start_draft` with a monotonic-upward update hook in `select_match_account`. The phase also adds lobby-guard rejections on roster mutations, a tournament-stage ordering guard on `finalize_match_result`, and a new `rosterMutations` helper that centralises the mutate-chars + recompute-rating pattern.

Overall the implementation is coherent and the anti-gaming design (max-across-LMA at draft start + monotonic-upward during BetweenGames + persisted read at finalization) holds up under review. No critical bugs. Three warning-level issues relate to type consistency, an authorisation-ordering information leak, and a bandwidth cost that only matters at scale. Info items flag stylistic inconsistencies and minor pre-existing inefficiencies adjacent to the changed lines.

The cross-file contract (draftClassic writes snapshot -> accountSelection updates it monotonically -> finalizationHelpers reads it) is well-tested by construction: `processMatchMmr` is called from both `runFinalization` and `process_tournament_mmr`, so the single read-path edit covers both paths. The stand-in exclusion and `deselect_match_account` no-op are both explicitly documented as intentional.

## Warnings

### WR-01: Type mismatch between `accountRatingSnapshot` (f64) and source `HsrAccount.accountRating` (u32)

**File:** `spacetimedb/src/tables/matchResultParticipant.ts:9`
**Issue:** `accountRatingSnapshot` is declared as `t.f64()`, but the source column `HsrAccount.accountRating` is `t.u32()` (confirmed in `spacetimedb/src/tables/hsrAccount.ts:13`). Every other ELO-adjacent integer (matchesPlayed, rating) is a plain integer. Widening to f64 costs 4 extra bytes per row without precision benefit — for 100 users playing 10 ranked matches each with 10 participants, that's ~40KB of pure egress overhead across the tournament-reveal subscription window, and it introduces the possibility of a future float-rounding bug at the aggregation step in `processMatchMmr` (line 95-100) where `blueAvgAccount` divides a sum of integers by length.

**Fix:**
```ts
// spacetimedb/src/tables/matchResultParticipant.ts
export const matchResultParticipantColumns = {
    matchResultId: t.u32(),
    userId: t.u32(),
    teamSide: TeamSide,
    isCaptain: t.bool(),
    accountRatingSnapshot: t.u32(), // was t.f64() — match source column type
    createdById: t.u32(),
    ...
};
```
Since the column is new and no production rows exist with f64 values, migration is a simple republish. Verify `Math.max` in `accountSelection.ts:108` still compiles (it does — `Math.max` accepts numbers regardless of bigint/integer distinction at the TS type level in the STDB JS bindings).

### WR-02: Tournament-stage guard runs before authority check, leaking tournament state to unauthorised callers

**File:** `spacetimedb/src/reducers/matchFinalization.ts:46-60`
**Issue:** The D-H-01 tournament-stage ordering guard executes before the Mod/referee/TO authority check at lines 64-86. Any authenticated user can call `finalize_match_result(someMatchResultId)` and learn via the error message whether the parent tournament is still in-progress vs Completed/Cancelled. This is a minor information leak — match result IDs are not secret but the inference ("this tournament is still live") could aid scheduling/targeting.

More importantly, it costs extra ELO config reads and bracket-match index lookups for every unauthorized probe, which is wasted energy budget since the caller will be rejected at step 3 anyway.

**Fix:** Move the tournament-stage guard AFTER the authority check in step 3. Reorder so authorisation gates all other reads:
```ts
// 1. Auth + match lookup + Validated check (lines 18-28)
// 2. Authority check (move current step 3 up to here)
// 3. NEW position: Tournament-stage ordering guard (current lines 46-60)
// 4. Delegate to runFinalization
```
This matches the defence-in-depth ordering already used in `process_tournament_mmr` (auth via `ensureTournamentAccess` runs first at line 104 before stage and countTowardsMmr checks).

### WR-03: Monotonic snapshot hook runs on every `select_match_account` call, doubling MRP-index reads per account swap

**File:** `spacetimedb/src/reducers/accountSelection.ts:102-119`
**Issue:** The D-B-03 hook unconditionally executes two indexed reads (`MatchResultRecord.lobby_id.filter` + `MatchResultParticipant.by_result_and_user.filter`) plus an `HsrAccount.id.find` on every call, including the Waiting-stage case where MRP rows cannot exist. The comment block (lines 90-101) correctly documents that Waiting-stage calls are a harmless no-op, but the index reads still happen.

For a typical tournament with 10 players each selecting 3 accounts pre-draft in the Waiting stage, that's 30 wasted MRR lookups + 30 wasted MRP index reads per lobby — purely bandwidth burnt on the `stdb_session` subscription with nothing to show for it.

**Fix:** Short-circuit on lobby stage before the lookups:
```ts
// Only run the monotonic-upward hook when the draft has started —
// MRP rows are created at start_draft and cannot exist earlier.
if (lobby.stage.tag === 'Drafting' || lobby.stage.tag === 'Equipping' ||
    lobby.stage.tag === 'Playing' || lobby.stage.tag === 'BetweenGames' ||
    lobby.stage.tag === 'Scoring') {
    const mr = [...ctx.db.MatchResultRecord.lobby_id.filter(lobbyId)][0];
    if (mr) {
        // ... existing hook body unchanged
    }
}
```
Or equivalently, gate on `lobby.stage.tag !== 'Waiting'`. The Waiting short-circuit is also a self-documenting proof that pre-draft swaps cannot affect the snapshot (which is currently only proven by comment, not code).

**File:** `spacetimedb/src/reducers/roster.ts:111`
**Issue:** `const allBindings = ctx.db.HsrAccount.user_id.filter(user.id);` is used directly in a `for...of` loop without spreading into an array (`[...ctx.db.HsrAccount...]`), while line 120 just 9 lines later does spread the same query. Every other call site in the phase's diff (and the wider codebase) spreads iterators first. ```

### IN-02: `migrate_roster` copy mode does not check lobby binding on source, but the guard does — comment vs. code drift

**File:** `spacetimedb/src/reducers/roster.ts:272-281`
**Issue:** The D-G-01 comment says "EITHER side of the migration", and the code correctly checks both source and target. However, in copy mode the source account's characters are not mutated (`applyBatchRemove` runs only on move), so technically copy mode only needs to guard the target. The over-guarding is defensible (prevents a user from copying out of a live-lobby account that might mutate under them) but the comment should say so explicitly to avoid a future reviewer relaxing the check.

**Fix:** Amend the comment to document the copy-mode rationale:
```ts
// D-G-01 (Phase 12.3): reject when EITHER side of the migration is bound
// to a live lobby. Target is always mutated; source is also guarded even in
// copy mode to prevent reading from an account whose rating is frozen in an
// active MRP snapshot (symmetry with batch_upsert_characters).
```

### IN-03: `accountRatingSnapshot` default of 0 silently accepts missing LMA rows in casual matches

**File:** `spacetimedb/src/reducers/draftClassic.ts:213`
**Issue:** `let accountRatingSnapshot = 0;` — for casual non-MMR matches where a player has no LMA rows, the snapshot defaults to 0. The D-B-02 comment correctly notes this is only possible for casual matches (ranked/MMR-tournament reject at lines 59-73) and that 0 matches the pre-phase `?? 0` fallback at `finalizationHelpers.ts:87,91` (now deleted). This is fine, but the zero value is never actually read by a code path that does math with it, because `processMatchMmr` is gated on `matchResult.matchType.tag === 'Ranked' && !matchResult.isTournamentControlled` (finalizationHelpers.ts:411) or on tournament batch with `countTowardsMmr`. So the field becomes dead data on casual rows.

**Fix:** No code change — document that the column is semantically "unused for non-ranked matches" so future ELO features don't accidentally read `accountRatingSnapshot` on a casual-match row and treat 0 as "worst possible account" instead of "no data".

```ts
// spacetimedb/src/tables/matchResultParticipant.ts
export const matchResultParticipantColumns = {
    ...
    // accountRatingSnapshot: max HsrAccount.accountRating across the member's
    // LMA rows at start_draft, updated monotonically during BetweenGames swaps.
    // SEMANTICALLY UNUSED for casual non-MMR matches — value defaults to 0 and
    // is never read (processMatchMmr is gated on matchType=Ranked).
    accountRatingSnapshot: t.u32(),
    ...
};
```

### IN-04: `applyBatchRemove` duplicate-name handling silently throws on second delete

**File:** `spacetimedb/src/helpers/rosterMutations.ts:98-101`
**Issue:** If `names` contains a duplicate (e.g. `['Seele', 'Seele']`), the validate-all loop (lines 90-95) passes because `accountChars.find(row => row.characterName === name)` succeeds both times against the still-unchanged array. Then the delete loop runs `delete(row)` on the same object reference twice — the second call will no-op or throw depending on STDB binding behaviour. A reducer rollback is semantically fine but silently dropping duplicate names with a potentially misleading error is not user-friendly.

**Fix:** Dedupe the names array at entry:
```ts
export function applyBatchRemove(
    ctx: any,
    accountId: number,
    names: string[],
    actingUserId: number
): void {
    if (!Array.isArray(names) || names.length === 0) {
        throw new SenderError('applyBatchRemove: names must be a non-empty array');
    }

    // Dedupe — duplicate names are a client bug but should not panic
    const uniqueNames = [...new Set(names)];

    const accountChars = [...ctx.db.HsrAccountCharacter.hsr_account_id.filter(accountId)];

    for (const name of uniqueNames) {
        if (!accountChars.find(row => row.characterName === name)) {
            throw new SenderError(`Character "${name}" not found on this account`);
        }
    }

    for (const name of uniqueNames) {
        const row = accountChars.find(row => row.characterName === name)!;
        ctx.db.HsrAccountCharacter.delete(row);
    }

    updateAccountRating(ctx, accountId, actingUserId);
}
```

### IN-05: `processMatchMmr` calls `getOrCreateRating` 3x per participant (pre-existing, touched by diff)

**File:** `spacetimedb/src/helpers/finalizationHelpers.ts:73-78, 125, 136`
**Issue:** For each participant, the helper calls `getOrCreateRating` once in the blue/red ratings map (lines 73-78), once inside the per-participant loop at line 125, then re-queries the same MmrRating row via `by_user_mode_season.filter` at line 136. That's 3 index lookups per participant where 1 would suffice. For a 5v5 ranked match that's 30 wasted index reads per finalization — pure egress against the `stdb_session` energy budget with no correctness benefit.

This is pre-existing code NOT changed by Phase 12.3, but the phase's diff touches lines 92-93 immediately adjacent, so flagging now while the context is fresh. The Phase 12.3 changes themselves do not regress this.

**Fix:** Cache MmrRating rows in a Map keyed by userId on first pass, reuse in the per-participant loop. Defer to a standalone follow-up phase if out of scope for 12.3 cleanup.
