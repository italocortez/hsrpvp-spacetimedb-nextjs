# Phase 12.2: Code Review Report

**Reviewed:** 2026-04-09
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Phase 12.2 added `export const` to all unexported views, reworked `useAuth` to read
from typed view bindings (`view_my_profile`), disabled confirmed reads in
`providers.tsx`, and added `.catch()` error handling to reducer calls. The changes are
well-structured and the security view isolation patterns are consistently applied.

No critical security vulnerabilities were found. The warnings are concentrated in
`useAuth.ts` and `index.ts`: one pre-existing storage-cleanup ordering bug (storage
cleared before the reducer confirms), a suppressed TypeScript type-safety hole in the
ban-reconnect check, a spurious hook dependency, and a fragile empty-string sentinel in
`securityViews.ts`. Info items are maintenance notes.

## Warnings

### WR-01: Storage cleared before reducer confirms on guest account deletion

**File:** `components/features/auth/hooks/useAuth.ts:331-341`

**Issue:** `deleteGuestAccount` fires the reducer and then immediately clears
`localStorage`, removes the session cookie, and calls `signOut`. The `.catch()` only
logs — it does not restore any of the already-cleared state. If the reducer call is
rejected (network loss, server error), the user is logged out client-side but the guest
account survives server-side. On next reconnect the orphaned identity will re-match the
guest account via Strategy 2, but the cleared `USER_ID_KEY` means Strategy 1 misses,
and the cleared session cookie triggers `isOrphanedIdentity` until the view subscription
fires — creating a visible flash of the LOGIN screen.

```typescript
// Current
conn.reducers.deleteGuestAccount({}).catch((err: any) => {
    console.error('[useAuth] deleteGuestAccount failed:', err);
});
localStorage.removeItem(SPACETIMEDB_TOKEN_KEY);   // fires immediately regardless
localStorage.removeItem(USER_ID_KEY);
clearSessionCookie();
signOut({ callbackUrl: '/' });

// Fix: move cleanup into a then() so it only runs on success
conn.reducers.deleteGuestAccount({})
    .then(() => {
        localStorage.removeItem(SPACETIMEDB_TOKEN_KEY);
        localStorage.removeItem(USER_ID_KEY);
        clearSessionCookie();
        signOut({ callbackUrl: '/' });
    })
    .catch((err: any) => {
        console.error('[useAuth] deleteGuestAccount failed:', err);
        // surface error to user — do not clear storage
    });
```

### WR-02: Type assertion bypasses ban-check discriminant safety

**File:** `spacetimedb/src/index.ts:117`

**Issue:** The `checkProviderBan` call passes `{ tag: 'DiscordId', value: {} } as any`
to satisfy the provider parameter type. The `as any` cast silently suppresses TypeScript's
structural check. If the `ProviderType` enum's `DiscordId` variant ever gains a typed
`value` field (e.g. `{ discordId: string }`), this hardcoded `value: {}` would produce a
runtime mismatch — the ban check would either no-op or panic, meaning a banned user
reconnects successfully without enforcement.

```typescript
// Current (unsafe)
const isBanned = checkProviderBan(ctx, { tag: 'DiscordId', value: {} } as any, userPrivate.discordId);

// Fix: import the ProviderType and construct it properly so the compiler
// catches shape mismatches at the call site
import { ProviderType } from '../types/enums'; // or wherever ProviderType is defined

const provider: ProviderType = { tag: 'DiscordId', value: {} };
const isBanned = checkProviderBan(ctx, provider, userPrivate.discordId);
```

### WR-03: Spurious dependency in `loginGuest` callback causes unnecessary re-creation

**File:** `components/features/auth/hooks/useAuth.ts:307-316`

**Issue:** `loginGuest` lists `readProfileFromConnection` in its `useCallback` deps array
but never calls it inside the callback body. Because `readProfileFromConnection` is
itself a `useCallback` (line 113) with its own dependency chain, adding it as a dep
causes `loginGuest` to be re-created whenever `identity`, `session`, or `setResolvedUser`
change — on every auth state transition. This means any component holding a ref to the
old `loginGuest` (e.g. a memoized button) will silently receive a stale closure. It is
not a crash, but it indicates the dep was added by mistake and should be removed.

```typescript
// Current
const loginGuest = useCallback(() => {
    const conn = getConnection();
    if (!conn) { ... return; }
    conn.reducers.loginAsGuest({}).catch(...);
}, [getConnection, readProfileFromConnection]);  // readProfileFromConnection unused here

// Fix
const loginGuest = useCallback(() => {
    const conn = getConnection();
    if (!conn) { ... return; }
    conn.reducers.loginAsGuest({}).catch(...);
}, [getConnection]);
```

### WR-04: Empty-string sentinel for "rating-only" roster rows is fragile

**File:** `spacetimedb/src/views/securityViews.ts:512-515`

**Issue:** When `canSeeRating` is true but `canSeeRoster` is false, a row is pushed with
`characterName: ''` and `eidolonLevel: 0` as sentinels meaning "rating only, no
character data." Any consumer checking `if (row.characterName)` will treat `''` as
falsy and skip or mishandle this row. Since the `MyRosterAccountRow` type declares
`characterName` as `t.string().optional()`, the correct sentinel is `undefined`.

```typescript
// Current
results.push({
    lobbyId: lobby.id,
    memberUserId: member.userId,
    hsrAccountId: account.id,
    characterName: '',       // fragile — empty string, not undefined
    eidolonLevel: 0,
    accountRating: account.accountRating,
});

// Fix: match the optional type declaration
results.push({
    lobbyId: lobby.id,
    memberUserId: member.userId,
    hsrAccountId: account.id,
    characterName: undefined,
    eidolonLevel: undefined,
    accountRating: account.accountRating,
});
```

### IN-01: `USER_ID_KEY` constant declared inside hook body — re-declared on every render

**File:** `components/features/auth/hooks/useAuth.ts:86`

**Issue:** `const USER_ID_KEY = 'spacetimedb_user_id'` is declared inside the `useAuth`
function, causing it to be re-allocated (as a new string binding) on every render. There
is no correctness impact since JS interns short string literals, but it is unexpected
placement for a constant. Likewise `DISCORD_INTENT_KEY`, `DISCORD_INTENT_TIMEOUT_KEY`,
and `DISCORD_INTENT_TTL_MS` (lines 187-189) are re-declared each render. Move them to
module scope.

```typescript
// Move above the function declaration
const USER_ID_KEY = 'spacetimedb_user_id';
const DISCORD_INTENT_KEY = 'discord_login_intent';
const DISCORD_INTENT_TIMEOUT_KEY = 'discord_login_intent_ts';
const DISCORD_INTENT_TTL_MS = 5 * 60 * 1000;

export function useAuth() { ... }
```

### IN-02: `hasDiscordIntent` memo reads `sessionStorage` non-reactively

**File:** `components/features/auth/hooks/useAuth.ts:193-204`

**Issue:** `useMemo` with `[nextAuthStatus]` as the dep reads `sessionStorage` inside the
factory. `sessionStorage` is not a reactive dependency — if another part of the code
(e.g. a redirect callback) writes the intent flag between renders without changing
`nextAuthStatus`, the memo will not recompute and the flag will appear absent. The
current code works because the intent is always set just before `signIn()` (which
triggers a page reload and therefore a fresh mount), but this is an implicit ordering
assumption. A comment explaining this invariant would prevent future breakage.

**Fix:** Add an inline comment:
```typescript
// sessionStorage is read here. This is safe because loginDiscord() always sets the
// intent flag then calls signIn(), which triggers a full page reload. By the time
// this component mounts again, nextAuthStatus transitions to "loading" → "authenticated",
// ensuring this memo recomputes with the fresh flag in place.
const hasDiscordIntent = useMemo(() => { ... }, [nextAuthStatus]);
```

### IN-03: `withConfirmedReads(false)` — noted as deliberate, verify subscription timing

**File:** `app/providers.tsx:36`

**Issue:** `withConfirmedReads(false)` was added as part of Phase 12.2. This disables the
SDK-level guarantee that subscription queries complete before `onApplied` fires. The
`useAuth` hook relies on `onApplied` as the signal that `view_my_profile` data is
available (line 28-31 of `useAuth.ts`). With confirmed reads off, `onApplied` may fire
before the view subscription has actually populated `conn.db.view_my_profile`. The
existing `readProfileFromConnection` fallback chain handles the case where the view is
empty (falls through to Strategies 1-3), so there is no data loss — but the intent of
`onApplied` as a "data ready" signal is weakened. Ensure this was intentional and the
tradeoff (reduced latency vs. possible extra fallback reads) is documented in the phase
decision log.

**Fix:** No code change required if the decision is intentional. Add a comment:
```typescript
.withConfirmedReads(false)  // Phase 12.2: disabled for lower connection latency.
                             // onApplied may fire before subscription data is populated;
                             // useAuth fallback strategies (1-3) handle empty view reads.
```

### IN-05: `view_user_directory` full table scan on `User.iter()` is unauthenticated

**File:** `spacetimedb/src/views/securityViews.ts:170`

**Issue:** `view_user_directory` is declared as `spacetimedb.anonymousView` (line 166),
meaning unauthenticated clients can subscribe to it. The body does `[...ctx.db.User.iter()]`
which is a full table scan. This is currently acceptable at the documented scale (~100
users), and the `filter(u => !u.deletedAt)` on line 171 is correctly applied. This is
an info note: if the user base grows beyond a few thousand, this view will become a
bandwidth concern. No change needed now — just track this in architecture docs as a
scale boundary.

**Fix:** No code change. Confirm the `User` table scale ceiling is documented in
`docs/*/architecture.md`.
