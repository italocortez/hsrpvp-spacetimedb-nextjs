# Phase 10.5: Test Suite Stabilization - Context

**Gathered:** 2026-04-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Audit and stabilize the existing integration test suite so `npm run test:all` runs green end-to-end after a fresh `spacetime publish --clear-database` + bootstrap. Fix cross-file pollution, missing per-file cleanup, shared-state ordering issues, helper duplication (`promoteUser`×14, `ensureHsrAccount`×6), and stale assertions exposed by Phase 10.4 schema changes.

**In scope:** Existing test file fixes, helper extraction to `test/shared/helpers/`, strict afterAll cleanup, self-contained per-file seeding, runtime baseline documentation, audit report artifact.

**Out of scope:** New integration tests for untested reducers, CI pipeline changes, test framework migration, parallel test DBs, frontend tests.

</domain>

<decisions>
## Implementation Decisions

### Audit Strategy
- **D-01:** Failure-driven bisect. Run `npm run test:all` once against a fresh DB and collect the full failure list. For each failing file: run it alone to confirm it passes in isolation, then binary-search by prepending earlier-running files to identify the polluter. Only files that fail in the full suite get bisected — no blanket O(N²) pair-wise scan.

### Helper Extraction
- **D-02:** Helpers live in `test/shared/helpers/` subdir with per-domain files: `promoteUser.ts`, `hsrAccounts.ts`, `tournaments.ts`, `lobbies.ts` (add more domains as audit surfaces them). Test files import via `from '../../shared/helpers/promoteUser'`. No single-file dumping ground.

### Cleanup Contract
- **D-03:** Strict `afterAll` per resource opened. Every test file that creates a lobby, tournament, calendar event, or similar dynamic resource MUST close/cancel it in its own `afterAll`. Each file owns its full teardown — no shared cleanup registry, no global state tracking. Cleanup failures throw (not swallowed).

### Shared-State Ordering
- **D-04:** Self-contained seeding per file. Each test file seeds its own dependencies (ELO config, achievements, HSR accounts, etc.) via idempotent helpers. No cross-file ordering assumptions. Tests run in any order.

### Scope Boundary
- **D-05:** Pure audit/fix only. No new integration tests added in Phase 10.5. Missing coverage for reducers shipped in 10.1–10.4 (e.g., new TO views, account-selection edge cases) gets addressed in a follow-up `/gsd:add-tests` pass — not here.

### Baseline Runtime Documentation
- **D-06:** `test/README.md` gets a "Suite Runtime" section with the measured baseline and last-updated date, e.g., `npm run test:all: ~Xs on maincloud (2026-04-05)`. Git-tracked, lives with the tests. Future phases update when they materially change the suite.

### Audit Report Format
- **D-07:** Phase-scoped `AUDIT.md` at `.planning/phases/10.5-test-suite-stabilization/10.5-AUDIT.md`. Captures: full-suite failure inventory, file↔polluter matrix from bisect results, per-failure root-cause classification (pollution / missing-cleanup / ordering / stale-assertion). Artifact stays in phase dir as history.

### Rollback Safety
- **D-08:** Per-file atomic commits + full-suite verification. After each file fix: commit, run `npm run test:all`, confirm zero new failures. If regression: amend or revert that commit only. Every commit is a known-green state.

### Seed Baseline
- **D-09:** Only static game data is globally seeded: characters and lightcones from `test/data/*.json`, inserted via `admin_bulk_upsert` (idempotent — can re-run safely). All dynamic test data (users, lobbies, tournaments, ELO config rows, achievements, etc.) is created per-file.

### DB Reset Strategy
- **D-10:** Between `test:all` invocations (or when state gets corrupted), reset via `spacetime publish --clear-database`. This is SpacetimeDB's mechanism for full DB-wide cleanup — don't fight it with row-level teardown. Per-file `afterAll` (D-03) handles intra-run isolation; `--clear-database` handles inter-run.

### Minimum-Data Principle
- **D-11:** When fixing or refactoring any test, ask: *"What is the minimum amount of data I need to test this scenario?"* — and use only that. Current suite has tests that insert too many entities for no real gain. Trim aggressively during the audit pass.

### Server Identity Singleton
- **D-12:** The SpacetimeDB server identity is inserted **once** (via `register_server` during bootstrap) and the resulting `SPACETIMEDB_SERVER_TOKEN` is read-only from `.env` / `.env.local`. Every test harness that needs privileged reducers (`server_set_role`, `server_link_discord`) reads this same env var — no per-test server identity creation, no conflicts possible because it's read-only. Keep this shared. Do NOT treat server identity as per-file seed data during the audit.

### Claude's Discretion
- Exact bisect ordering (alphabetical / per-domain / failure-frequency)
- AUDIT.md schema (table format, sections)
- Which per-domain helper file each extracted helper belongs in (promoteUser → promoteUser.ts is obvious; edge cases at execution time)
- Whether to extract `getUsername`, `createTournamentArgs`, and other inline helpers alongside the named targets
- When to batch fixes per-file vs per-category during execution (D-08 allows atomic-per-file; planner decides granularity)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`TestHarness` + `createTestHarness()`/`createVerifiedTestHarness()`** (test/shared/connection.ts) — standard connection primitive used by all 38 integration test files; stable API
- **`queryPrivateTable(sql)`** (test/shared/connection.ts:194) — calls `spacetime sql` CLI for private tables (PlayerStat, HsrAccount after 10.4, etc.); already used in some files, can be used more widely after refactor
- **`expectReducerError(promise)`** (test/shared/connection.ts:168) — negative-test helper, used throughout
- **`nextUid()` / `createAccountArgs()` / `characterBatch()`** (test/shared/fixtures.ts) — existing factory patterns that set the precedent for per-domain helper organization
- **`admin_bulk_upsert` reducer** — already used in bootstrap for idempotent static data seeding; the mechanism for D-09 global seed
- **`register_server` reducer + `SPACETIMEDB_SERVER_TOKEN` env var** — one-time bootstrap sets up server identity (D-12); all harnesses call privileged reducers via this shared token

### Established Patterns
- **Test harness as first-class citizen** — tests don't mock SpacetimeDB, they connect to real maincloud DB (`hsrpvp-spacetimedb-nextjs-test1`). Integration-first culture.
- **Inline helper duplication** — `promoteUser` (14 files), `ensureHsrAccount` (6 files), plus `getUsername`, `setupRegistrationTournament`, `createTournamentArgs` all duplicated. This is the primary refactor target (success criterion 4 + D-02).
- **Opportunistic cleanup** — current files call `close_lobby`/`cancel_tournament` inline mid-test (e.g., lobby-lifecycle.test.ts line 159, 176, 212+ each close their own lobby). Good baseline, needs upgrading to strict `afterAll` enforcement per D-03.
- **Connection-per-harness model** — most files create 2–4 harnesses per test (admin, TO, p1, p2) in `beforeAll` and disconnect all in `afterAll`. Consistent pattern.

### Integration Points
- **Post-publish bootstrap** (test/shared/bootstrap.ts, scripts/post-publish.ts) — runs after `spacetime publish`, seeds global data. D-09 is about what stays global here vs what moves per-file.
- **Bindings** (src/module_bindings/) — regenerated on each publish; stale assertions catch rename churn from 10.1/10.4 at compile time via typecheck.
- **vitest integration runner** (`test:integration`, `test:all`) — single worker by default (SpacetimeDB sequential), test files run in alphabetical order — ordering assumptions leak here if unchecked.

</code_context>

<specifics>
## Specific Ideas

- **User's minimum-data rule:** *"While fixing the test ask your question 'what is the minimum amount of data that I need to test this scenario?' and use that; some of the tests are inserting too many entities for no real gain, check that carefully."* — Apply during every file touch, not just flagged failures.
- **Global seed scope:** *"The only data that should be seeded for everyone is the character and lightcone data that lives in test/data/*.json. These files are not insert as is, they use the admin bulk upsert but they only have to be inserted once."* — Idempotent bulk upsert is the canonical pattern.
- **SpacetimeDB cleanup philosophy:** *"For SpacetimeDb cleanup just do a cancel on ident (I guess this is a clear-database)."* — Don't invent row-level DB-wide cleanup tooling; use `spacetime publish --clear-database` when full reset is needed.
- **Server identity is shared, read-only, never per-file:** *"The server identity needs to only be inserted ONCE. Everyone uses that one and should not cause any conflict between tests as it is a read only env variable (through .env or .env.local)."* — Bootstrap writes `SPACETIMEDB_SERVER_TOKEN`; tests only read it.

</specifics>
