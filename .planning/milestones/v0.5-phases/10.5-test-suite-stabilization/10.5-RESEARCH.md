# Phase 10.5: Test Suite Stabilization - Research

**Researched:** 2026-04-05
**Domain:** Integration test suite audit — cross-file pollution, helper duplication, cleanup hygiene, stale assertions
**Confidence:** HIGH (codebase-grounded, counts verified against live test DB)

## Summary

Phase 10.5 is a pure audit/refactor of the 38 integration test files under `test/backend/`. The test DB (`hsrpvp-spacetimedb-nextjs-test1` on maincloud) currently holds **40 leaked tournaments, 51 leaked lobbies (many mid-state Drafting/AwaitingResult), 81 tournament_enrolled rows, 46 bracket_match rows, 301 users, 60 HSR accounts, 10 achievements** from prior test runs — hard evidence of systematic per-file cleanup failure.

The primary refactor target is the inline-duplicated helper pattern: `promoteUser` (15 copies), `promoteToRole/promoteToAdmin` (11 copies), `defaultLobbyArgs` (20 copies), `defaultSettingsArgs` (2 near-identical copies), `ensureHsrAccount` (6 copies), `getUsername` (3 copies), `setupRegistrationTournament` + `advanceToInProgress` (2 copies), `createTournamentArgs` (2 copies), `completeDraft`/`completeTournamentDraft` (5 copies), `startDraftAndSync` (4 copies), `advanceToScoring` (3 copies), `cleanupLobby` (4 copies with divergent signatures). These extract cleanly into `test/shared/helpers/` per D-02.

Stale-assertion risk is LOW: Phase 10.1 kept `submit_match_result({ winnerId })` as a reducer arg (verified in bindings); `override_match_result` test calls already use `winnerTeamSideTag`; `GroupStanding` and `TournamentParticipant` have zero test references; Phase 10.4 removal of `TournamentEnrolled.hsrAccountId` has zero stale references. The exposed failures from Phase 10.4 are almost certainly **pollution-driven** (absolute count assertions vs leaked rows), not rename-driven.

**Primary recommendation:** Execute D-01 bisect **after** extracting helpers (D-02) and enforcing afterAll cleanup (D-03) — both of which reduce the cross-file failure surface. Then bisect remaining failures against the cleaned baseline. Fix tournaments-leakage FIRST (highest row count, cascades to bracket/enrolled/matches).

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01: Audit Strategy — Failure-driven bisect.** Run `npm run test:all` once against a fresh DB and collect the full failure list. For each failing file: run it alone to confirm it passes in isolation, then binary-search by prepending earlier-running files to identify the polluter. Only files that fail in the full suite get bisected — no blanket O(N²) pair-wise scan.
- **D-02: Helper Extraction.** Helpers live in `test/shared/helpers/` subdir with per-domain files: `promoteUser.ts`, `hsrAccounts.ts`, `tournaments.ts`, `lobbies.ts` (add more domains as audit surfaces them). Test files import via `from '../../shared/helpers/promoteUser'`. No single-file dumping ground.
- **D-03: Cleanup Contract — Strict `afterAll` per resource opened.** Every test file that creates a lobby, tournament, calendar event, or similar dynamic resource MUST close/cancel it in its own `afterAll`. Each file owns its full teardown — no shared cleanup registry, no global state tracking. Cleanup failures throw (not swallowed).
- **D-04: Shared-State Ordering — Self-contained seeding per file.** Each test file seeds its own dependencies (ELO config, achievements, HSR accounts, etc.) via idempotent helpers. No cross-file ordering assumptions. Tests run in any order.
- **D-05: Scope Boundary — Pure audit/fix only.** No new integration tests added in Phase 10.5. Missing coverage for reducers shipped in 10.1–10.4 (e.g., new TO views, account-selection edge cases) gets addressed in a follow-up `/gsd:add-tests` pass — not here.
- **D-06: Baseline Runtime Documentation.** `test/README.md` gets a "Suite Runtime" section with the measured baseline and last-updated date, e.g., `npm run test:all: ~Xs on maincloud (2026-04-05)`. Git-tracked, lives with the tests. Future phases update when they materially change the suite.
- **D-07: Audit Report Format.** Phase-scoped `AUDIT.md` at `.planning/phases/10.5-test-suite-stabilization/10.5-AUDIT.md`. Captures: full-suite failure inventory, file↔polluter matrix from bisect results, per-failure root-cause classification (pollution / missing-cleanup / ordering / stale-assertion). Artifact stays in phase dir as history.
- **D-08: Rollback Safety — Per-file atomic commits + full-suite verification.** After each file fix: commit, run `npm run test:all`, confirm zero new failures. If regression: amend or revert that commit only. Every commit is a known-green state.
- **D-09: Seed Baseline.** Only static game data is globally seeded: characters and lightcones from `test/data/*.json`, inserted via `admin_bulk_upsert` (idempotent — can re-run safely). All dynamic test data (users, lobbies, tournaments, ELO config rows, achievements, etc.) is created per-file.
- **D-10: DB Reset Strategy.** Between `test:all` invocations (or when state gets corrupted), reset via `spacetime publish --clear-database`. Per-file `afterAll` (D-03) handles intra-run isolation; `--clear-database` handles inter-run.
- **D-11: Minimum-Data Principle.** When fixing or refactoring any test, ask: *"What is the minimum amount of data I need to test this scenario?"* — and use only that. Current suite has tests that insert too many entities for no real gain. Trim aggressively during the audit pass.
- **D-12: Server Identity Singleton.** The SpacetimeDB server identity is inserted **once** (via `register_server` during bootstrap) and the resulting `SPACETIMEDB_SERVER_TOKEN` is read-only from `.env` / `.env.local`. Every test harness that needs privileged reducers (`server_set_role`, `server_link_discord`) reads this same env var — no per-test server identity creation, no conflicts possible because it's read-only. Keep this shared. Do NOT treat server identity as per-file seed data during the audit.

### Pattern 1: Test File Layout (post-refactor)
**What:** Standard shape each integration test file should follow after Phase 10.5.
**When to use:** Every file in `test/backend/*/*.test.ts`.
**Example:**
```typescript
// Source: synthesized from test/backend/anonymous-play/anonymous-labels.test.ts + refactor
import { describe, it, expect, beforeAll, afterAll } from 'vitest';
import { createVerifiedTestHarness, hasServerToken, type TestHarness } from '../../shared/connection';
import { promoteUser } from '../../shared/helpers/promoteUser';
import { ensureHsrAccount } from '../../shared/helpers/hsrAccounts';
import { defaultLobbyArgs, cleanupLobby } from '../../shared/helpers/lobbies';
import { getUsername } from '../../shared/helpers/users';

describe.skipIf(!hasServerToken())('Feature Name', () => {
    let host: TestHarness;
    let blue: TestHarness;
    let red: TestHarness;
    // Track resources opened by THIS file for afterAll teardown
    const openedLobbyIds: number[] = [];

    beforeAll(async () => {
        host = await createVerifiedTestHarness();
        blue = await createVerifiedTestHarness();
        red = await createVerifiedTestHarness();
        await Promise.all([host.sync(), blue.sync(), red.sync()]);
    }, 60000);

    afterAll(async () => {
        // D-03: strict cleanup per resource opened
        for (const lobbyId of openedLobbyIds) {
            await cleanupLobby(host, [blue, red], lobbyId).catch(() => {});
        }
        await host?.disconnect();
        await blue?.disconnect();
        await red?.disconnect();
    });

    it('tests behavior', async () => {
        await host.call.createLobby(defaultLobbyArgs());
        await host.sync(1500);
        const lobbyId = [...host.conn.db.Lobby.iter()]
            .filter(l => l.hostUserId === host.userId).pop()!.id;
        openedLobbyIds.push(lobbyId);  // Register for teardown IMMEDIATELY
        // ... rest of test ...
    });
});
```

### Pattern 2: Minimum-Data Principle (D-11)
**What:** Ask "what is the minimum data needed for this scenario?" before seeding each test.
**When to use:** Every time you touch a test during audit.
**Example:** A lobby-creation test needs 1 host (not 4 harnesses). A join test needs host + joiner (not host + joiner + bystander + guest). A draft-completion test needs 16 unique character picks (not a full 5-account roster per user).

### Anti-Patterns to Avoid
- **Inline mid-test cleanup (no failure path):** `await host.call.closeLobby(...)` after assertions — if assertion fails, lobby leaks. See lobby-lifecycle.test.ts lines 159, 176, 193, 212, 228. Fix: track lobbyId in `openedLobbyIds[]`, clean up in `afterAll`.
- **Absolute count assertions without baseline snapshot:** `expect(awardsBefore.length).toBe(0)` in achievement-auto-award.test.ts:168 — fails if prior run leaked. Fix: capture `beforeCount` in `beforeAll`, assert delta (`toBe(beforeCount + 1)`). This pattern is already used correctly in season-admin.test.ts:88 and tournament-mmr.test.ts:417 — propagate elsewhere.
- **Shared-state `beforeAll` without teardown:** describe-level `beforeAll` creates a tournament, `it()` mutates it, no describe-level `afterAll` cancels it. See tournament-cancel-cleanup.test.ts "cancel from Registration" (line 168), "cancel from InProgress" (line 238) — these DO cancel as part of the test logic, so OK. Other files may not.
- **Per-test harness creation without try/finally:** Creates harnesses inline, asserts, never disconnects. Fix: always use `try { ... } finally { await h.disconnect() }` pattern (see disconnect-concede.test.ts for correct model).

## Common Pitfalls

### Pitfall 1: `fileParallelism: false` does NOT prevent cross-file pollution
**What goes wrong:** Tests run sequentially, so devs assume they're isolated. But sequential ≠ isolated — later files see state left by earlier files.
**Why it happens:** vitest config sets `fileParallelism: false` for SpacetimeDB WebSocket reasons (connection saturation), which prevents concurrent interference but not sequential leakage.
**How to avoid:** Never rely on fresh state from sequencing. Every test must either (a) self-seed what it needs or (b) assert deltas, not absolutes.
**Warning signs:** Test passes in isolation, fails in suite.

### Pitfall 2: `cancelTournament` from InProgress stage cascades
**What goes wrong:** A `cancelTournament` call on an InProgress tournament cascades delete of BracketMatch, TournamentTeam, TournamentAssistant, CalendarEvent (per Phase 8 D-21). If afterAll only tries `cancelTournament` for tournaments in Registration, bracket data leaks.
**Why it happens:** Cleanup logic might gate on stage.
**How to avoid:** `cancelTournament` works from any stage EXCEPT Completed/Cancelled (terminal). afterAll should call it unconditionally and swallow "already cancelled" errors.
**Warning signs:** `bracket_match` count grows without matching `tournament` count.

### Pitfall 3: `AwaitingResult` lobbies cannot be closed by `close_lobby`
**What goes wrong:** Per docs/lobby/contract.md D-48, `run_lobby_gc` skips AwaitingResult lobbies. `close_lobby` also may reject. Need admin-only resolution.
**Why it happens:** `defer_match` or auto-concede transitions lobby to AwaitingResult, locked awaiting admin_force_finalize/admin_void_match/admin_set_bracket_winner.
**How to avoid:** Test files that enter AwaitingResult state MUST have an admin harness + call `admin_void_match` in afterAll.
**Warning signs:** `SELECT stage FROM lobby WHERE id = X` returns `(awaitingResult = ())` after afterAll ran.

### Pitfall 4: 5-account HSR limit on reused users
**What goes wrong:** Each test reusing the same harness calls `ensureHsrAccount` — fine once. But tests that create MULTIPLE accounts per user (e.g., account-selection creates main + alt) hit the 5-account limit after enough test runs.
**Why it happens:** Users are immortal (never deleted); their hsr_account children accumulate.
**How to avoid:** Deterministic UID per-user keyed to test needs. If test needs N accounts for user, compute deterministic uids so re-runs don't add new rows.
**Warning signs:** "maximum 5 accounts per user" errors surface.

### Pitfall 5: `winnerId` in `submitMatchResult` is NOT stale — do not rename
**What goes wrong:** Audit sees `winnerId` references (12 occurrences), tries to rename to `winnerUserId` or `winnerTeamSide`.
**Why it happens:** Phase 10.1 kept the REDUCER parameter named `winnerId` for backwards compat (STATE.md line 127: "submit_match_result param renamed winnerId; converts to winnerTeamSide via MatchResultParticipant.teamSide lookup"). Only `override_match_result` switched to `winnerTeamSideTag`. The TABLE column `winnerUserId` exists but the REDUCER param is `winnerId`.
**How to avoid:** Verify against `src/module_bindings/submit_match_result_reducer.ts` — DO NOT rename.
**Warning signs:** None — it's already correct. Don't touch.

### Pitfall 6: Bisect order (D-01) may surface different polluters
**What goes wrong:** vitest integration runs files in alphabetical order by directory → file. The "polluter" depends on run order.
**Why it happens:** First file to break an invariant wins attribution.
**How to avoid:** D-01 prescribes binary-search WITHIN the actual run order. Use `vitest run --reporter=verbose` to see exact ordering; prepend candidate polluters via explicit file list to vitest CLI.
**Warning signs:** Fix a file's pollution, a different file's assertion starts failing. That's a SECOND polluter exposed by the first's fix.

## Risks

1. **Bisect relies on stable failure output (D-01).** vitest verbose reporter shows per-file results, but if a pollutee intermittently fails vs hard-fails, binary search is unreliable. → Mitigation: fix obvious bugs first (Plan 02/03), bisect against the cleaned-up baseline.

2. **Fixing cleanup may expose tests that silently depended on leaked state.** E.g., a test that expects "at least one tournament exists" may have been relying on leakage. → Mitigation: D-08 per-file commit + full-suite verify catches this immediately.

3. **`spacetime publish --clear-database -y` cycle is slow (~30–60s publish + bindings + bootstrap + seed).** Multiply by D-08's per-file verify → phase could take many hours of wall time. → Mitigation: `--clear-database` only needed when state corrupts, not per-commit. D-08 requires `test:all` verify, NOT clear-database-per-commit.

4. **`sequence.concurrent: false` + `fileParallelism: false`** means suite is fully sequential. If runtime is currently 15+ minutes, full-suite verify per file fix (D-08) is expensive. → Mitigation: Plan 01 measures baseline; planner may chunk D-08 verification (batch 3-5 fixes, verify once) if baseline is huge.

5. **`tournament-mmr.test.ts` batch-processing describe block has 180s timeout** — suggests heavy setup. If afterAll cleanup fails mid-way, partial state leaks. → Mitigation: Plan 03 handles tournaments/ domain first, with extra care on multi-tournament test files.

6. **AwaitingResult lobbies require admin-only resolution (`admin_void_match`).** Tests creating Drafting lobbies that may transition via concede need an admin harness for cleanup. → Mitigation: Plan 03 adds admin harness to afterAll where needed.

7. **Sequential cleanup in afterAll can exceed hookTimeout (30s).** If a file opens many lobbies, iterating closeLobby in afterAll may hit timeout. → Mitigation: Parallelize cleanup with `Promise.all([...])` where safe; bump `hookTimeout` per-file if needed.
