# Phase 12.1: Identity Garbage Collection - Research

**Researched:** 2026-04-08
**Domain:** SpacetimeDB scheduled reducers, identity lifecycle, GC patterns
**Confidence:** HIGH

## Summary

Phase 12.1 adds identity garbage collection on top of the mature auth system built in Phase 12. The codebase already contains a fully working scheduled-reducer pattern (LobbyGcJob + run_lobby_gc) and cascade-deletion infrastructure (hardDeleteLobby, performUserDeletion) that this phase replicates and extends. All new code follows existing project patterns with zero new dependencies.

The key findings are: the ScheduleAt self-requeue pattern is confirmed verbatim from lobbyGc.ts, UserPrivate cascade is already correctly handled in userDeletionHelper.ts, MatchResultRecord is fully covered by existing finalization flows (hardDeleteLobby handles MatchResult* at step 0a), and `ctx.timestamp` is pinned at reducer invocation so `durationMs` must store 0. The LobbyGcJob seed row is NOT in post-publish.ts — the planner must add an `insertIdentityGcJobSeed` step to post-publish.ts for the IdentityGcJob initial row.

**Primary recommendation:** Follow the LobbyGcJob/run_lobby_gc pattern exactly. No new patterns or libraries required — this is a pure application of established project conventions.

## Architecture Patterns

### Scheduled Reducer Pattern (LobbyGcJob)

**[VERIFIED: codebase read — lobbyGcJob.ts + lobbyGc.ts]**

The project uses a two-file pattern for scheduled reducers:

**File 1: Table file** (`tables/lobbyGcJob.ts`)
```typescript
// Pattern: deferred binding to avoid circular dependency
export let _runLobbyGcReducer: any;
export function setRunLobbyGcReducer(reducer: any) {
    _runLobbyGcReducer = reducer;
}

export const LobbyGcJob = table({
    name: 'lobby_gc_job',
    scheduled: () => _runLobbyGcReducer,  // lazy getter — set by reducer file
}, lobbyGcJobColumns);

// Columns: scheduledId (u64 PK autoInc), scheduledAt (scheduleAt())
```

**File 2: Reducer file** (`reducers/lobbyGc.ts`)
```typescript
// Source: lobbyGc.ts line 86-151
export const run_lobby_gc = spacetimedb.reducer(
    { arg: LobbyGcJob.rowType },      // reads the scheduled row as arg
    (ctx, { arg }) => {
        const now = ctx.timestamp;
        // ... GC logic ...

        // Self-requeue: insert next scheduled run
        const FIVE_MINUTES_MICROS = now.microsSinceUnixEpoch + BigInt(5 * 60 * 1_000_000);

            scheduledId: 0n,
            scheduledAt: ScheduleAt.time(FIVE_MINUTES_MICROS),

// Wire the reducer back into the table's lazy reference
setRunLobbyGcReducer(run_lobby_gc);
```

### Duration Measurement Pattern

**[VERIFIED: codebase read — lobbyGc.ts uses ctx.timestamp]**

SpacetimeDB reducers expose `ctx.timestamp` as a `Timestamp` object with `microsSinceUnixEpoch: bigint`. To measure reducer duration:

```typescript
// At reducer start:
const startMicros = ctx.timestamp.microsSinceUnixEpoch;

// At reducer end:
const endMicros = ctx.timestamp.microsSinceUnixEpoch;
// NOTE: ctx.timestamp is frozen at reducer invocation — start and end will be equal.
```

**IMPORTANT:** `ctx.timestamp` is set once at the start of a reducer call and does not advance during execution. This means `durationMs` measured purely from `ctx.timestamp` will always be 0. The GcResult `durationMs` column should either:
1. Always store 0 (acceptable — it's an audit table and the column is there for future use if SpacetimeDB adds wall-clock access), OR
2. Store a placeholder indicating measurement is not available in this runtime

**[ASSUMED]** SpacetimeDB does not provide wall-clock time inside reducers (they must be deterministic). This is consistent with the "no timers" rule in CLAUDE.md core concepts. The planner should decide: store 0, or omit from initial implementation.

### Identity GC Logic Pattern

**[VERIFIED: codebase read — userIdentity.ts indexes + lobbyGc.ts iteration pattern]**

UserIdentity has:
- PK: `identity` (identity type)
- btree index: `user_id` on `userId`

GC query approach (grouping by user):
```typescript
// Collect all identities grouped by userId
const identityMap = new Map<number, any[]>();
for (const ui of ctx.db.UserIdentity.iter()) {
    const arr = identityMap.get(ui.userId) ?? [];
    arr.push(ui);
    identityMap.set(ui.userId, arr);
}
```

Per-user GC logic (D-07: preserve newest even if stale, D-08: skip online users, D-06: skip guests):
```typescript
for (const [userId, identities] of identityMap) {
    const user = ctx.db.User.id.find(userId);

    // D-12: Orphaned identity (user not found) → delete immediately
    if (!user) {
        for (const ui of identities) {
            ctx.db.UserIdentity.identity.delete(ui.identity);
            itemsDeleted++;
        }
        continue;
    }

    // D-06: Skip guest users
    if (user.isGuest) continue;

    // D-08: Skip online users
    if (user.isOnline) continue;

    // Sort by lastSeenAt descending — preserve newest
    const sorted = [...identities].sort((a, b) =>
        Number(b.lastSeenAt.microsSinceUnixEpoch - a.lastSeenAt.microsSinceUnixEpoch)
    );
    const [newest, ...stale] = sorted;

    // Delete stale identities past TTL (preserve newest regardless)
    for (const ui of stale) {
        const idleMs = (nowMicros - ui.lastSeenAt.microsSinceUnixEpoch) / 1000n;
        if (idleMs >= TTL_MS) {
            ctx.db.UserIdentity.identity.delete(ui.identity);
            console.log(`[IDENTITY_GC] Deleted stale identity for user #${userId}`);
            itemsDeleted++;
        }
    }
}
```

## Common Pitfalls

### Pitfall 1: Scheduled Table Circular Dependency
**What goes wrong:** Importing the reducer file from the table file (or vice versa) creates a circular module dependency that breaks the SpacetimeDB build.
**Why it happens:** `LobbyGcJob.scheduled` needs the reducer reference, but the reducer file imports `LobbyGcJob`.
**How to avoid:** Use the mutable binding pattern from `lobbyGcJob.ts` — export a `setXxxReducer()` setter, call it from the reducer file after reducer definition.
**Warning signs:** Build error about circular imports or `undefined` reducer at runtime.

### Pitfall 2: BigInt Arithmetic for Timestamps
**What goes wrong:** Using JavaScript `Number` arithmetic on `microsSinceUnixEpoch` causes precision loss for large epoch values.
**Why it happens:** `microsSinceUnixEpoch` is `bigint` — mixing with `Number` silently truncates.
**How to avoid:** Keep all timestamp arithmetic in BigInt: `BigInt(90 * 24 * 60 * 60) * 1_000_000n` for 90-day TTL.
**Warning signs:** GC fires at wrong time, or never fires.

Example from lobbyGc.ts (line 90-91):
```typescript
const THIRTY_MINUTES_MICROS = BigInt(30 * 60 * 1_000_000);
```

For 90-day TTL:
```typescript
const IDENTITY_TTL_DAYS = 90;
const IDENTITY_TTL_MICROS = BigInt(IDENTITY_TTL_DAYS * 24 * 60 * 60) * 1_000_000n;
```

### Pitfall 3: `iter()` on UserIdentity vs index lookup
**What goes wrong:** Calling `ctx.db.UserIdentity.iter()` for the full GC sweep is correct, but calling `ctx.db.UserIdentity.user_id.filter(userId)` inside the per-user loop creates N redundant queries.
**How to avoid:** Build the `identityMap` in ONE iter() pass, then process per-user from the map. The `user_id` btree index is useful for point lookups (e.g., checking a specific user), not for the full GC sweep.

### Pitfall 4: Schema Registration Order in schema.ts
**What goes wrong:** New tables (GcResult, IdentityGcJob) not added to `schema.ts` → reducer calls `ctx.db.GcResult` and gets undefined at runtime.
**How to avoid:** Add both table imports and schema entries to `schema.ts` as part of the same plan that creates the files.

### Pitfall 5: GcResult durationMs Is Always 0
**What goes wrong:** Measuring `ctx.timestamp` at start and end of reducer yields the same value — SpacetimeDB timestamps are pinned at reducer invocation.
**Why it happens:** Reducers must be deterministic; wall-clock time is not accessible.
**How to avoid:** Store 0 for `durationMs` in initial implementation. Add a code comment explaining why. The column exists for API completeness and potential future use.

### Pitfall 6: admin_gc_lobbies Must Not Duplicate Rescheduling
**What goes wrong:** Copying `run_lobby_gc` verbatim into `admin_gc_lobbies` would include the self-requeue insert, adding an extra scheduled run on every admin trigger.
**How to avoid:** Extract shared GC logic into a helper function. Both `run_lobby_gc` (scheduled, adds requeue) and `admin_gc_lobbies` (admin-only, no requeue) call the shared helper. Same pattern applies for identity GC.

### Pitfall 7: lastSeenAt Bump — Only When User Row Exists
**What goes wrong:** `clientConnected` currently already handles the case where `mapping` is null (graceful return). Adding a `lastSeenAt` update must be inside the existing `if (mapping)` block, after the user is found.
**How to avoid:** Insert the update at line 66-70 of index.ts, after `ctx.db.User.id.update(...)`. The mapping is already resolved.

### Pitfall 8: Forgetting the IdentityGcJob Seed Row
**What goes wrong:** After publish, the IdentityGcJob table is empty — `run_identity_gc` never fires because there is no scheduled row to trigger it.
**Why it happens:** SpacetimeDB scheduled reducers only run when rows exist in the scheduled table. The table starts empty on a fresh publish.
**How to avoid:** Add seed call to post-publish.ts following the `adminSeedEloConfig` / `adminSeedRatingConfig` pattern. The seed reducer must be idempotent (check if table is already non-empty before inserting).
