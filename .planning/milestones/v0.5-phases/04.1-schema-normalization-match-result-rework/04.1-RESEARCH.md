# Phase 04.1: Schema Normalization & Match Result Rework - Research

**Researched:** 2026-03-19
**Domain:** SpacetimeDB schema migration, table/column renames, enum changes, new tables
**Confidence:** HIGH

## Summary

This phase is a retroactive schema rework on an existing codebase with 50 tables, 17 reducer files, 5 helper files, 12 test files, and extensive documentation. The changes are comprehensive: 14 schema change groups touching 10 table definitions, 2 enum definitions, 4 reducer files, 1 helper file, 1 admin reducer, 1 schema registration file, 17+ documentation files, and 10+ planning files. Client bindings (`src/module_bindings/`) are auto-generated and will be fully regenerated after publish -- they are NOT manually edited.

The blast radius analysis below is exhaustive. Every file in the project has been checked against every change in the specification. The changes are structurally safe because: (a) no reducer currently CREATES MatchResultRecord rows (creation is Phase 5 scope), so existing reducer logic is modifying a table definition that has no live data paths yet beyond confirmation/submission/dispute; (b) the tables being structurally reworked (PlayerStats, CharacterStats, MatchSessionHistory, MatchSessionStepHistory, MmrHistory) are skeleton definitions with no reducer logic written against them; (c) BracketMatch and GroupStanding column renames affect active reducers but are straightforward find-replace operations.

**Primary recommendation:** Execute changes in 3 waves: (1) enums + type definitions, (2) table definitions + schema registration + reducers, (3) docs + planning files. Publish with `--clear-database`. Regenerate bindings. Update all tests.

## Architecture Patterns

### Change Classification

Each schema change falls into one of these categories, which determines execution approach:

| Category | Description | Migration Impact |
|----------|-------------|------------------|
| **Column Remove** | Drop a column from a table definition | Destructive -- requires `--clear-database` |
| **Column Rename** | Change a column name | Destructive -- requires `--clear-database` |
| **Column Add** | Add a new column to an existing table | Non-destructive IF optional; destructive if required |
| **Column Type Change** | Change column type (e.g., u8 to enum, string to u32) | Destructive -- requires `--clear-database` |
| **PK Change** | Modify primary key composition | Destructive -- requires `--clear-database` |
| **Index Change** | Add/remove/rename indexes | Varies; rename is destructive |
| **New Table** | Create a table that didn't exist before | Non-destructive |
| **New Enum** | Add a new enum type | Non-destructive |
| **Enum Rename** | Rename an existing enum | Destructive -- requires `--clear-database` |
| **Table Rename** | Change the `name` property in table() | Destructive -- requires `--clear-database` |

**All 14 changes in this phase are destructive.** A single `--clear-database` publish handles them all.

### Recommended File Change Order

Within a single commit, TypeScript compilation order matters:

```
1. types/enums.ts          (new enums, rename MatchResult -> MatchOutcome)
2. types/structs.ts        (PlayerSnapshot removal check -- still used by matchSessionHistory)
3. tables/*.ts             (all table definition changes)
4. schema.ts               (new table registrations, import renames)
5. helpers/*.ts            (any helper changes for renamed columns)
6. reducers/*.ts           (all reducer changes for renamed columns)
7. spacetime publish       (--clear-database)
8. spacetime generate      (regenerate client bindings)
9. docs/**/*.md            (documentation updates)
10. .planning/**/*.md      (planning file updates -- informational only)
```

### Anti-Patterns to Avoid
- **Partial rename:** Renaming a column in the table definition but forgetting to update the reducer that reads it causes a TypeScript compile error (good -- caught at build time) or a runtime mismatch (bad -- if using `as any` casts)
- **Index accessor mismatch:** When renaming a column referenced by an index accessor, the accessor name must also be updated or TypeScript will fail
- **Stale doc references:** Updating code but leaving old column names in docs causes confusion in later phases

## SpacetimeDB Migration Notes

### --clear-database Is Required

**Confidence: HIGH** (verified from project history and SpacetimeDB documentation)

SpacetimeDB does NOT support incremental schema migrations for destructive changes. The following change types require `--clear-database`:

1. **Column removal** -- SpacetimeDB cannot remove columns from an existing table in-place
2. **Column rename** -- There is no ALTER TABLE equivalent; the engine sees a new column and a missing column
3. **PK type change** -- Changing a primary key type (e.g., string to u32) is a fundamental table structure change
4. **PK composition change** -- Adding columns to a composite PK changes the table's physical structure
5. **Enum rename** -- The enum type name is part of the schema hash; changing it invalidates existing data
6. **Table name change** -- SpacetimeDB uses the table name string for identity; changing it creates a new table

**All 14 changes in this phase are destructive.** A single `--clear-database` publish handles them all.

### What --clear-database Does

- Wipes ALL data from ALL tables (not just affected ones)
- Resets autoInc counters to 0
- Publishes the new schema as if from scratch
- Client bindings must be regenerated after publish

### This Is Acceptable Because

- This is a development milestone, not production
- No persistent user data exists (test data only)
- The post-publish bootstrap script can re-seed static data (characters, lightcones, cost tables)
- Previous phases (03-01, 04-01) also used `--clear-database` for similar structural changes

### SpacetimeDB Enum Changes

**Adding variants** to an existing enum is a NON-destructive change. SpacetimeDB handles this.
**Renaming** an enum (MatchResult -> MatchOutcome) IS destructive.
**Adding a new enum** (MatchType) is NON-destructive.

Since we're already doing `--clear-database` for other reasons, enum changes are covered.

### Client Binding Regeneration

After publish, `spacetime generate` produces fresh `src/module_bindings/` files. These files are:
- Fully auto-generated (never manually edited)
- Include new table definitions, column names, and enum types
- Must be committed after generation

## Common Pitfalls

### Pitfall 1: Forgetting `as any` Casts After Renames

**What goes wrong:** SpacetimeDB's TypeScript SDK uses enum tags as `{ tag: 'VariantName', value: {} }`. After renaming a column that holds an enum value, the spread operator `...row` carries the old shape, but the type system expects the new column name.
**Why it happens:** The codebase extensively uses `{ ...existingRow, newField: value, ...auditUpdate() } as any` pattern. The `as any` hides type errors.
**How to avoid:** After all renames, run `npx tsc --noEmit` WITHOUT `as any` casts temporarily to verify all column names resolve. Then re-add `as any` where needed for enum tags.
**Warning signs:** Module publishes but reducers throw "column not found" at runtime.

### Pitfall 2: Missing a participant1Id -> team1Id Reference in bracketAdvancement.ts

**What goes wrong:** bracketAdvancement.ts has 6 functions, each with multiple references to participant1Id/participant2Id/winnerId. Missing even ONE reference causes a runtime error.
**Why it happens:** The file is 420+ lines with the same column names appearing in different contexts (placeParticipantInNextMatch, removeParticipantFromMatch, updateGroupStandings, reverseGroupStandings, advance_bracket_match, submit_and_advance_bracket, rollback_bracket_match).
**How to avoid:** Use find-and-replace with word boundaries. After replacing, search for any remaining `participant1Id`, `participant2Id`, or bare `winnerId` (not `winnerTeamId` or `winnerUserId`).
**Warning signs:** TypeScript compile error or `npx tsc --noEmit` output showing undefined property.

### Pitfall 3: PlayerSnapshot Removal Breaking Other Imports

**What goes wrong:** Removing PlayerSnapshot from structs.ts while something else still imports it.
**Why it happens:** PlayerSnapshot is defined in structs.ts and imported by matchSessionHistory.ts. If any other file imports it, removal breaks.
**How to avoid:** Verified via grep: PlayerSnapshot is ONLY imported by `matchSessionHistory.ts` and module bindings (auto-generated). Safe to remove.
**Warning signs:** TypeScript import error.

### Pitfall 4: admin_delete_row MatchSessionHistory PK Type Change

**What goes wrong:** The admin_delete_row reducer has a 'MatchSessionHistory' case that does `ctx.db.MatchSessionHistory.id.find(primaryKeyJson)` -- this passes a string directly as the PK. After changing the PK to u32, this silently fails or throws.
**Why it happens:** The admin reducer was written when MatchSessionHistory had a string PK. The PK change to u32 means the find/delete calls need `Number(primaryKeyJson)`.
**How to avoid:** Update both the MatchSessionHistory and MatchSessionStepHistory cases in admin.ts.
**Warning signs:** Admin panel delete operations fail silently.

### Pitfall 5: BracketMatchDescriptor Interface in Helper vs Table Column Names

**What goes wrong:** The BracketMatchDescriptor interface in `helpers/bracketGeneration.ts` uses `participant1Id`, `participant2Id`, `winnerId` as field names. These are the SAME names as the table columns. If you rename the table columns but forget the interface, the reducer's `insertBracketMatches` function will write to wrong property names.
**Why it happens:** The interface mirrors the table column names intentionally. They must stay in sync.
**How to avoid:** Rename both the interface fields AND the table columns in the same wave.
**Warning signs:** TypeScript property mismatch errors, or bracket matches inserted with undefined team slots.

### Pitfall 6: GroupStanding PK Includes the Renamed Column

**What goes wrong:** GroupStanding has a composite PK `['tournamentId', 'groupId', 'participantTeamId']`. After renaming the column to `teamId`, the PK array must also change to `['tournamentId', 'groupId', 'teamId']`. The delete pattern in bracketGeneration.ts line 154-158 builds composite PK objects -- these must use the new column name.
**Why it happens:** Composite PK delete operations construct key objects with column names.
**How to avoid:** Update both the table definition PK array AND all composite-PK-based delete operations.
**Warning signs:** GroupStanding rows fail to delete during bracket regeneration.
