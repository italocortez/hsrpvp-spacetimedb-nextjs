# Phase 04.1: Schema Normalization & Match Result Rework - Context

**Gathered:** 2026-03-19
**Status:** Ready for planning
**Source:** Architecture discussion in conversation (not discuss-phase)

<domain>
## Phase Boundary

Retroactive schema normalization across the entire match result pipeline and related tables. No new features — this is a naming/structural cleanup before Phase 5 builds on top. All changes are destructive (require --clear-database publish). No live data at risk (maincloud can be wiped).

Scope: table column renames, column removals, column additions, new tables, enum renames, new enums, PK type changes, FK retargets, reducer rewrites, documentation updates, test updates, planning file updates.

Out of scope: implementing the finalize_match_result reducer, implementing process_tournament_mmr reducer, implementing the actual ephemeral deletion flow, implementing stat aggregation logic. Those are Phase 5.

</domain>

<decisions>
## Implementation Decisions

### Team Side Naming — Standardize on Blue/Red
- All match result columns using player1/player2 or team1/team2 numbering MUST use teamBlue/teamRed naming
- Pattern: `teamBlue*` prefix (not `blueTeam*`) — matches majority usage in Lobby, MatchSession, TimerState
- MatchResultGame: player1Score → teamBlueScore, player2Score → teamRedScore (and all 12 columns)
- MatchSessionHistory: blueTeamMembers → REMOVE (replaced by junction table), redTeamMembers → REMOVE
- BracketMatch keeps positional team1Id/team2Id (brackets are positional slots, not Blue/Red — that mapping happens at lobby level)

### MatchResultRecord — Column Changes
- REMOVE player1Id, player2Id — MatchResultParticipant is source of truth
- REMOVE team1Confirmed, team2Confirmed — replaced by MatchResultParticipant.isConfirmed
- RENAME winnerId → winnerUserId — disambiguate from BracketMatch.winnerTeamId
- RENAME isTournamentMatch → isTournamentControlled — behavioral flag: lobby inherits tournament config + TO gets authority. NOT just a category flag.
- UPGRADE matchType from u8 magic number → MatchType enum (Casual, Ranked, Tournament)
- isTournamentControlled and matchType both stay — different purposes. matchType is for client filtering. isTournamentControlled is behavioral (triggers config inheritance + authority delegation).
- This table becomes conceptually ephemeral (deleted after processing) — but the deletion LOGIC is Phase 5 scope. Schema is ready now.

### MatchResultParticipant — New Columns
- ADD isCaptain (bool) — always true for 1v1, flagged for team formats. Used for confirmation authority.
- ADD isConfirmed (bool) — replaces team1Confirmed/team2Confirmed. Captain confirms on behalf of team.

### MatchResultGame — Column Renames + Type Change
- All player1*/player2* columns → teamBlue*/teamRed*
- winnerId (u32 optional) → winnerTeamSide (TeamLabel enum) — per-game winner is which SIDE won, not a person
- validatedById → validatedByUserId — consistency with *UserId naming pattern

### BracketMatch — Column Renames
- participant1Id → team1Id — these are TournamentTeam.id values, not participant IDs
- participant2Id → team2Id
- winnerId → winnerTeamId — this is a TournamentTeam.id, not a userId

### GroupStanding — Column Rename
- participantTeamId → teamId — shorter, consistent with BracketMatch.team1Id/team2Id

### MatchSessionHistory — Structural Changes
- id: string UUID → u32 autoInc — consistent with every other table in the schema
- REMOVE blueTeamMembers (PlayerSnapshot[]) — replaced by MatchParticipantHistory junction table
- REMOVE redTeamMembers (PlayerSnapshot[]) — replaced by MatchParticipantHistory junction table
- result (MatchResult enum) → outcome (MatchOutcome enum) — avoid name collision with table concept
- PlayerSnapshot struct can be REMOVED after this (only used by MatchSessionHistory)

### MatchSessionStepHistory — FK Type Change
- matchId (string) → matchHistoryId (u32) — FK to MatchSessionHistory after PK type change

### MmrHistory — FK Retarget
- matchResultId (u32) → matchHistoryId (u32) — FK should point to permanent MatchSessionHistory, not ephemeral MatchResultRecord

### MatchResult Enum → MatchOutcome Enum
- Rename to avoid conceptual collision with MatchResultRecord table
- Variants unchanged: BlueWins, RedWins, Draw, Aborted

### NEW: MatchType Enum
- Variants: Casual, Ranked, Tournament
- Replaces u8 magic numbers (0, 1, 2) on MatchResultRecord.matchType

### PlayerStats → PlayerStat (singular, reworked)
- PK: userId → [userId, gameMode, draftMode]
- ADD gameMode (GameMode enum), draftMode (DraftMode enum)
- REMOVE bestAllyUserId — derived from PlayerRelationship on client
- REMOVE nemesisUserId — derived from PlayerRelationship on client
- KEEP matchesSpectated — needed for UI feature (easy access without count operation)

### CharacterStats → PlayerCharacterStat (reworked)
- PK: [userId, characterName] → [userId, characterName, gameMode, draftMode]
- ADD gameMode (GameMode enum), draftMode (DraftMode enum)

### NEW TABLE: PlayerRelationship
- PK: [userId, otherUserId, gameMode, draftMode]
- Columns: matchesAsAlly (u32), winsAsAlly (u32), matchesAsOpponent (u32), winsAsOpponent (u32)
- Serves: best ally, nemesis, rivalry stats, head-to-head — all from one subscription per user profile

### NEW TABLE: MatchParticipantHistory
- PK: [userId, matchHistoryId]
- Columns: userId (u32), matchHistoryId (u32 FK to MatchSessionHistory.id), teamSide (TeamLabel)
- Purpose: indexed "show me all matches user X played" query. Replaces non-indexable PlayerSnapshot arrays.

### Tournament MMR — Batch at Tournament End (Phase 5 scope, but schema implications now)
- mmrProcessedAt stays on MatchResultRecord — becomes the gate for "safe to finalize and delete"
- Tournament matches: MMR calculated when tournament ends/cancelled, not per-match
- Non-tournament matches: MMR processed immediately on validation
- Rollbacks during tournament are free (no MMR to reverse yet)
- New reducers (finalize_match_result, process_tournament_mmr) are Phase 5 scope — NOT this phase

### Claude's Discretion
- Exact index definitions for new tables (accessor names, column combinations)
- Whether to update .planning/ files (informational, low priority — code and docs are critical)
- admin.ts MatchSessionHistory/MatchSessionStepHistory delete cases — must update PK type from string to u32

</decisions>
