# Phase 10.1: Match Schema Rework — Research

**Researched:** 2026-04-03
**Domain:** SpacetimeDB schema refactoring — table renames, splits, column replacements, enum changes, new reducers
**Confidence:** HIGH (primary source: actual codebase files)

## Summary

This phase performs 6 interrelated schema restructurings (A-F) that touch 25+ source files and 15 test files (122 occurrences). The research maps every file, column, and cross-reference that changes, resolves all 7 research questions from the ROADMAP, and identifies dependency ordering for safe execution.

The critical finding is that `winnerUserId` permeates the finalization pipeline in ways that require careful surgical replacement — it appears in MMR calculation (determining actual result), PlayerStat increments, PlayerRelationship pairs, character stat attribution, and bracket advancement. Each of these 5+ consumers uses `winnerUserId` differently and must be updated to use `winnerTeamSide` with team-based logic instead of user-based logic.

The TournamentParticipant split (Scope C) is the largest change by call-site count: 14 source files reference `TournamentParticipant` or `teamGroupId`, with `tournamentTeams.ts` alone containing 38 occurrences across 6 reducers. The split into `TournamentEnrolled` + `TournamentTeamMember` eliminates the `teamGroupId` column entirely, replacing it with a proper join table.

**Primary recommendation:** Execute in strict dependency order: Enums first (D-32 MatchEndReason), then table definitions (A, C, D, F schema), then reducers/helpers (B series management, C team rewiring, D winnerTeamSide), then E (ParticipantStatus lifecycle), then tests last.

### Pattern 1: Delete+Re-Insert for Composite PK Updates
**What:** SpacetimeDB composite PK tables cannot use `.update()` on PK accessor. Must delete then re-insert.
**When to use:** TournamentEnrolled (PK: tournamentId, userId), TournamentTeamMember (PK: teamId, userId), GroupPhaseRecord (PK: tournamentId, groupId, teamId).
**Example:** (established in codebase, 30+ existing instances)
```typescript
// Source: tournamentRegistration.ts line 177-183
ctx.db.TournamentParticipant.delete(current);
ctx.db.TournamentParticipant.insert({
    ...current,
    teamGroupId: undefined,
    status: { tag: 'Withdrawn', value: {} } as any,
    ...auditUpdate(ctx, current, user.id),
} as any);
```

### Pattern 2: Captain Transfer on Disconnect (Phase 10 D-34)
**What:** When a captain leaves/disconnects, transfer captain flag to next eligible teammate (lowest userId).
**When to use:** DQ captain-transfer in TournamentTeam (D-21, D-22), lobby captain transfer on DQ during active match (D-25).
**Source:** `flagTransferHelpers.ts` lines 8-43
```typescript
// transferCaptain picks lowest userId candidate on same team
const candidates = members
    .filter(m => slotTeam(m.lobbySlot) === team && !slotIsCoach(m.lobbySlot) && !m.voluntarilyLeft && m.userId !== leavingUserId)
    .sort((a, b) => a.userId - b.userId);
if (candidates.length > 0) { /* promote candidates[0] */ }
```
This same pattern (deterministic lowest-userId) should be replicated for `TournamentTeam.captainUserId` transfer on DQ/withdrawal.

### Pattern 3: Stage Flow Checking
**What:** Lobby stage checks appear in GC, concede, disconnect, draft, and lifecycle reducers.
**Current active stages list:** `['Drafting', 'Equipping', 'Scoring']` used in:
- `concede.ts` line 129: concede_match
- `concede.ts` line 202: claim_forfeit
- `concede.ts` line 280: defer_match
- `lobbyLifecycle.ts` line 360: leave_lobby active match handling
- `lobbyGc.ts` line 92: GC active stage check
- `disconnectHelpers.ts` line 9: ensureMatchAlive

**After Phase 10.1:** `BetweenGames` must be added to some of these checks (e.g., concede_match per D-10, GC per D-17), while `Shelved` needs explicit handling in GC (D-16 skip), leave_lobby (D-19 exemption), and cancel_tournament cascade (D-18).

### Anti-Patterns to Avoid
- **Using winnerUserId to determine team side:** Currently `finalizationHelpers.ts` does `participants.find(p => p.userId === matchResult.winnerUserId)` then reads `teamSide.tag`. After D-30, use `matchResult.winnerTeamSide.tag` directly -- no participant lookup needed.
- **Assuming GroupStanding still exists:** After rename to GroupPhaseRecord, every `ctx.db.GroupStanding.*` call becomes `ctx.db.GroupPhaseRecord.*`.
- **Mixing old and new enum names:** `MatchOutcome` enum and `matchOutcome` field both rename. The enum becomes `MatchEndReason`, the field becomes `matchEndReason`. The variants change too: `BlueWins`/`RedWins` are REMOVED (redundant with winnerTeamSide).

## Research Questions Resolved

### 1. TournamentStandIn: works without TournamentParticipant?
**YES.** `TournamentStandIn` has PK `(bracketMatchId, userId)` with NO reference to TournamentParticipant or teamGroupId. It links a user directly to a bracket match. The `approve_stand_in` reducer in `tournamentLobby.ts` only reads TournamentStandIn rows, not TournamentParticipant. **No changes needed** (D-28 confirmed).

### 2. TournamentPlayerAccount: reference TournamentEnrolled or TournamentTeamMember?
**TournamentPlayerAccount** has PK `(tournamentId, userId, hsrAccountId)` with index `by_tournament_and_user`. It is a snapshot of which HSR accounts a user had at registration time. It references the enrolled user via `(tournamentId, userId)` which maps directly to `TournamentEnrolled` PK. **No changes needed** to TournamentPlayerAccount table definition (D-29 confirmed). The cascade delete in `tournamentHelpers.ts` iterates participants to find user IDs -- will iterate TournamentEnrolled instead.

### 3. Withdrawal cascade: orphaned enrolled users?
Per D-24: "Orphaned enrolled members stay enrolled, teamless. Can join another team or form new one." When captain withdraws:
1. Delete all TournamentTeamMember rows for that team
2. Delete TournamentTeam row
3. Other enrolled members (previously on that team) now have no TournamentTeamMember row = teamless
4. Set withdrawing captain's TournamentEnrolled status to Withdrawn
5. Other members stay Registered/CheckedIn -- they can join another team

### 4. DQ flow: delete TournamentTeamMember rows?
Per D-23 (non-captain): delete their TournamentTeamMember row only. Team continues short-handed.
Per D-21 (captain): transfer captain flag to next team member first (update `TournamentTeam.captainUserId`), THEN the DQ'd player's TournamentTeamMember row is deleted.
Only when the LAST member is DQ'd: team is destroyed (delete all remaining TournamentTeamMember + TournamentTeam row).
TournamentEnrolled status always updated to Disqualified regardless.

### 5. How does lobby know Blue = team1Id or team2Id?
**Convention already established:** team1 = Blue, team2 = Red. Evidence:
- `concede.ts:65`: `winnerTeamSide === 'Blue' ? bracketMatch.team1Id : bracketMatch.team2Id`
- `adminMatchTools.ts:72`: `bracketMatch.team1Id === winnerTeamId ? 'Blue' : 'Red'`
- `create_tournament_lobby` in `tournamentLobby.ts` places team1 members as Blue, team2 as Red during lobby creation

### 6. MMR processing: new query path?
`process_tournament_mmr` currently uses `MatchResultRecord.tournament_id.filter(tournamentId)`.
After removing tournamentId:
1. Find all BracketMatch rows: `BracketMatch.tournament_id.filter(tournamentId)`
2. For each bracket match with a linked match result, find the MatchResultRecord via `MatchResultRecord.lobby_id.filter(lobbyId)` where lobbyId comes from `Lobby.bracketMatchId` reverse lookup
3. OR add an index on `MatchResultRecord.bracketMatchId` to enable: for each BracketMatch.id, find MatchResultRecord by bracketMatchId

**Recommendation:** Add a `bracket_match_id` btree index to MatchResultRecord. This makes the query path: BracketMatch.tournament_id.filter -> for each, MatchResultRecord.bracket_match_id.filter -> process.

### 7. ParticipantStatus: which variants survive?
All 6 existing ParticipantStatus variants survive unchanged on TournamentEnrolled:
- `Registered` -- set on registration (already wired)
- `CheckedIn` -- set by new check_in_tournament reducer (D-36)
- `Active` -- set in bulk at InProgress transition (D-39)
- `Eliminated` -- set on final bracket loss (D-40)
- `Disqualified` -- set by dq_participant (already wired)
- `Withdrawn` -- set by withdraw_from_tournament (already wired)

## Common Pitfalls

### Pitfall 1: Forgetting to Update MatchSessionHistory.outcome Type
**What goes wrong:** MatchSessionHistory uses `MatchOutcome` for its `outcome` column. If you rename the enum to `MatchEndReason` but forget to update MatchSessionHistory, the module won't compile.
**How to avoid:** The type import in `matchSessionHistory.ts` line 2 imports `MatchOutcome` -- must change to `MatchEndReason`.

### Pitfall 2: process_tournament_mmr Query Path After tournamentId Removal
**What goes wrong:** `process_tournament_mmr` relies on `MatchResultRecord.tournament_id.filter()` which is being removed. If the new query path isn't implemented correctly, tournament MMR processing breaks silently (finds 0 results).
**How to avoid:** Must add `bracket_match_id` btree index to MatchResultRecord AND rewrite the query to go through BracketMatch first.

### Pitfall 3: GC Deleting Shelved Lobbies Too Early
**What goes wrong:** Current GC iterates all lobbies and only skips AwaitingResult. Without adding Shelved to the skip list, casual shelved lobbies get deleted after 30 min idle.
**How to avoid:** Add explicit `Shelved` skip in GC, then add separate 72h TTL check for casual shelved lobbies (D-16).

### Pitfall 4: finalizationHelpers winnerUserId Replacement is Not 1:1
**What goes wrong:** Currently `winnerUserId` is used to determine the winning TEAM SIDE in multiple places (steps 6, 11, 13, 15, 16, 17). Simply replacing the field name isn't enough -- the LOGIC changes. With `winnerTeamSide`, you no longer need to look up a participant to determine which team won; you read the tag directly.
**How to avoid:** Map each `winnerUserId` usage to understand whether it's used for (a) identifying a person, (b) identifying a team side, or (c) both. Most are (b) and become simpler with winnerTeamSide.

### Pitfall 5: TournamentTeamMember Cascade on Tournament Cancel
**What goes wrong:** `cascadeCleanupTournament` currently iterates TournamentParticipant to delete TournamentPlayerAccount rows. After the split, it must also delete all TournamentTeamMember rows.
**How to avoid:** Add TournamentTeamMember cascade deletion step in `cascadeCleanupTournament`, positioned before TournamentTeam deletion (child rows before parent).

### Pitfall 6: Best-of-1 Matches Must Not See BetweenGames
**What goes wrong:** If bestOf=1, the stage flow should never hit BetweenGames. The advance_stage logic after Scoring must check if the series is won.
**How to avoid:** In postDraft.ts stage transition: `if (seriesBestOf === 1 || gamesWon >= ceil(seriesBestOf/2)) -> AwaitingResult; else -> BetweenGames`.

### Pitfall 7: Concede in BetweenGames Must Concede Entire Series
**What goes wrong:** D-10 says concede in BetweenGames surrenders the entire series, not just one game. The concede logic must set the match as fully conceded, not trigger a "next game".
**How to avoid:** `performConcede` already transitions to AwaitingResult. Just ensure the activeStages array in `concede_match` includes `BetweenGames`.

### Captain Transfer on DQ (TournamentTeam level)
```typescript
// In dq_participant, after setting TournamentEnrolled.status to Disqualified:
function transferTournamentCaptain(ctx, teamId, dqUserId, actingUserId) {
    const team = ctx.db.TournamentTeam.id.find(teamId);
    if (!team || team.captainUserId !== dqUserId) return; // not captain

    const otherMembers = [...ctx.db.TournamentTeamMember.team_id.filter(teamId)]
        .filter(m => m.userId !== dqUserId)
        .sort((a, b) => a.userId - b.userId); // deterministic: lowest userId

    if (otherMembers.length > 0) {
        // Transfer captain
        ctx.db.TournamentTeam.id.update({
            ...team,
            captainUserId: otherMembers[0].userId,
            ...auditUpdate(ctx, team, actingUserId),
        });
    }
    // Delete DQ'd member's TTM row
    const dqMember = [...ctx.db.TournamentTeamMember.by_tournament_and_user
        .filter([team.tournamentId, dqUserId])][0];
    if (dqMember) ctx.db.TournamentTeamMember.delete(dqMember);

    // If no members left: destroy team
    if (otherMembers.length === 0) {
        ctx.db.TournamentTeam.id.delete(teamId);
    }
}
```

## Open Questions

1. **MatchSessionStepHistory PK with gameNumber**
   - What we know: Current PK is `['matchHistoryId', 'sequence']`. Adding `gameNumber` to PK would make it `['matchHistoryId', 'gameNumber', 'sequence']`.
   - What's unclear: If gameNumber is NOT part of PK, two history rows from different games with the same sequence number would conflict (e.g., game 1 step 1 and game 2 step 1 both have matchHistoryId=X, sequence=1).
   - Recommendation: Make gameNumber part of the PK: `['matchHistoryId', 'gameNumber', 'sequence']`. This is the only safe option since step sequences reset per game.

2. **BetweenGames ready-up confirmation**
   - What we know: D-14 specifies BetweenGames -> start_next_game -> Drafting flow. No explicit mention of ready-up.
   - What's unclear: Should both teams confirm readiness before start_next_game proceeds?
   - Recommendation: NO ready-up. The advance_to_next_game reducer is called by authorized personnel (D-07). If players aren't ready, the caller simply doesn't fire the reducer. This keeps it simple and matches the existing pattern (start_draft doesn't have a ready-up either -- that's handled by the Waiting stage confirm/unconfirm).

3. **Lobby.bestOf default value in create_lobby**
   - What we know: D-11 says "u8, default 1". The Lobby table definition will have the column, but SpacetimeDB doesn't support column defaults.
   - Recommendation: Set bestOf=1 in the create_lobby reducer when the param is 0 (sentinel for default). Same pattern as costSetId=0.
