# Phase 10.1: Match Schema Rework — Multi-Draft, Team-Centric Model, winnerTeamSide - Context

**Gathered:** 2026-04-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Three structural fixes before frontend, plus merged Phase 10.2 scope:

**A.** Rename GroupStanding → GroupPhaseRecord
**B.** Best-of-N multi-draft: gameNumber on steps, BetweenGames + Shelved stages, series management reducers, reset-in-place model
**C.** Replace TournamentParticipant with TournamentEnrolled + TournamentTeamMember, captain-transfer on DQ/withdrawal
**D.** Replace winnerUserId with winnerTeamSide on MatchResultRecord, rename MatchOutcome → MatchEndReason (Completed/Draw/Concede)
**E.** Wire ParticipantStatus lifecycle: CheckedIn (tournament-level), Active (stage transition), Eliminated (final bracket loss)
**F.** (Merged from 10.2) Remove tournamentId from MatchResultRecord, remove lobbyId from BracketMatch

All changes require `--clear-database` publish. No live data at risk (maincloud can be wiped).

</domain>

<decisions>
## Implementation Decisions

### A. GroupStanding Rename
- **D-01:** Rename `GroupStanding` → `GroupPhaseRecord`. The table tracks W/L/D/points per team per group (standings), not individual matches. "GroupPhaseRecord" avoids confusion with `TournamentStandIn`.

### B. Best-of-N Game Transition Model
- **D-02:** Reset-in-place model. Same `MatchSession` row throughout the series. Between games, reset turnIndex, draftSequence, budgets, pauses. Only carry over: `gamesWonBlue`, `gamesWonRed`, `currentGameNumber`.
- **D-03:** Two new `LobbyStage` variants: `BetweenGames` (brief post-game transition) and `Shelved` (long-term pause). Both skipped entirely for `bestOf=1` matches.
- **D-04:** Player-initiated shelving, NOT auto-shelve. After scoring completes (series not won), lobby transitions to `BetweenGames`. Players/referee choose: start next game, shelve, or concede.
- **D-05:** Shelving only between games, not mid-game. Mid-draft disconnect handling stays as Phase 10 designed.
- **D-06:** `refereeControlsShelving` lobby option (default `true`). When enabled + 3rd party referee present, only referee controls shelve/continue decisions in `BetweenGames`.
- **D-07:** Series management authority (advance, shelve, resume): lobby host, TO, TO assistant, admin, mod. Referee also if `refereeControlsShelving=true`.
- **D-08:** Unshelve gate: at least 1 player per team present (not all players). Missing players can rejoin later or team plays short-handed.
- **D-09:** 3rd party referee not required for unshelve or resumed match. Different referee can join. Referee presence is optional after shelving.
- **D-10:** Concede available in `BetweenGames` stage — extends `concede_match` to work in this stage. Surrenders the entire series.
- **D-11:** `Lobby.bestOf` (u8, default 1) added to Lobby table. Casual lobbies can run best-of-N series.
- **D-12:** `MatchSession` gains 4 columns: `currentGameNumber` (u8), `gamesWonBlue` (u8), `gamesWonRed` (u8), `seriesBestOf` (u8, copied from Lobby.bestOf or BracketMatch.bestOf at match start).
- **D-13:** `gameNumber` (u8, 1-indexed) added to `MatchSessionStep` and `MatchSessionStepHistory`. Game 1 = 1, game 2 = 2. Matches existing `MatchResultGame.gameNumber` convention.
- **D-14:** Stage flow for best-of-N: `Scoring → BetweenGames → (start_next_game) → Drafting → Equipping → Scoring → ...`. When series won: `Scoring → AwaitingResult → Finalization`.
- **D-15:** Shelve flow: `BetweenGames → (shelve_series) → Shelved → (resume_series) → BetweenGames → (start_next_game) → Drafting`.

### B2. Shelved Lobby Lifecycle
- **D-16:** GC must skip `Shelved` lobbies. Apply 72h TTL for casual (hard-delete after expiry). Tournament shelved lobbies persist until `cancel_tournament` cascade.
- **D-17:** GC treats `BetweenGames` like active stages (only delete if ALL members offline + idle > 30 min).
- **D-18:** `cancel_tournament` cascade extended: find lobbies linked to bracket matches via `BracketMatch.lobbyId` → `hardDeleteLobby` before deleting bracket match rows.
- **D-19:** Empty auto-close exemption for `Shelved` stage — all members leaving does NOT trigger `hardDeleteLobby` (they're expected to return).

### C. TournamentParticipant Split
- **D-20:** Split `TournamentParticipant` into two tables:
  - `TournamentEnrolled` (PK: tournamentId, userId) — registration record: status, isWaitlisted, approvedByToAt, anonymousAlias, allowRandomTeamAssignment, hsrAccountId, audit cols.
  - `TournamentTeamMember` (PK: teamId, userId) — team assignment link. Plus `tournamentId` column + btree index for direct `by_tournament_and_user` lookups.
- **D-21:** Captain DQ → transfer captain flag to next team member (`TournamentTeam.captainUserId` updated). Team survives. Only destroy team when last member is DQ'd/withdrawn.
- **D-22:** Captain withdrawal → also captain-transfer (same as DQ). Team survives with new captain.
- **D-23:** Non-captain DQ/withdrawal → delete their `TournamentTeamMember` row only. Team continues short-handed.
- **D-24:** Orphaned enrolled members (only when team destroyed after last member leaves) stay enrolled, teamless. Can join another team or form new one.
- **D-25:** DQ during active lobby (Drafting/Equipping/Scoring): kick DQ'd player from lobby. Captain DQ: transfer captain, team plays on. If last member DQ'd: force-concede match.
- **D-26:** DQ during Shelved/BetweenGames lobby: remove player's TTM row. Captain DQ: transfer captain. If last member: hard-delete the shelved lobby.
- **D-27:** Bracket impact: team survives = no bracket change. Team destroyed (last member DQ'd) = auto-advance opponent on the one active match.
- **D-28:** `TournamentStandIn` unchanged — works independently (separate table, no TournamentParticipant reference).
- **D-29:** `TournamentPlayerAccount` unchanged — stays as (tournamentId, userId) snapshot.

### D. winnerTeamSide + MatchEndReason
- **D-30:** Replace `winnerUserId` (u32?) with `winnerTeamSide` (TeamSide?) on `MatchResultRecord`. Values: Blue/Red/undefined (draw or unresolved).
- **D-31:** Rename `matchOutcome` field → `matchEndReason`. Rename `MatchOutcome` enum → `MatchEndReason`.
- **D-32:** `MatchEndReason` variants: `Completed` / `Draw` / `Concede`. Removes `BlueWins`/`RedWins` (redundant with `winnerTeamSide`).
- **D-33:** Both fields kept — `winnerTeamSide` answers WHO won (operational routing: bracket advance, stats, MMR), `matchEndReason` answers HOW it ended (display, history, concede branching).
- **D-34:** Current draw mechanics preserved: draws block bracket advancement, referee breaks tie via `override_match_result`.

### E. ParticipantStatus Lifecycle
- **D-35:** Tournament-level check-in only. New `TournamentStage.CheckIn` variant between Registration and Seeding.
- **D-36:** `check_in_tournament(tournamentId)` reducer. Sets participant status to `CheckedIn`.
- **D-37:** Stage transitions: Registration → CheckIn (if `Tournament.checkInEnabled=true`) → Seeding. When TO advances from CheckIn, unchecked-in participants auto-removed.
- **D-38:** Per-round check-in (`checkInPerRound`, `BracketMatch.checkInRequired`) stays unwired — deferred to future phase.
- **D-39:** `Active` status set in bulk when tournament advances to `InProgress`. All checked-in (or registered, if no check-in stage) participants become Active.
- **D-40:** `Eliminated` status set on final bracket loss: single elim = any loss, double elim = losers bracket loss (2nd loss), group phase = don't advance from group.
- **D-41:** All three statuses (CheckedIn, Active, Eliminated) are informational only — no reducer gating. Frontend displays status badges. Existing permission checks already gate behavior.

### F. Merged Phase 10.2 Scope
- **D-42:** Remove `tournamentId` column and btree index from `MatchResultRecord`. Derive from `bracketMatch.tournamentId` via `MatchResultRecord.bracketMatchId`.
- **D-43:** Remove `lobbyId` column and btree index from `BracketMatch`. Relationship navigated via `Lobby.bracketMatchId`.
- **D-44:** Update all consumers: `finalizationHelpers`, `bracketAdvancement`, `matchResultSubmission`, `tournamentAdmin`, `draftClassic` (match result creation), `process_tournament_mmr` (needs new query path through bracket matches).

### Claude's Discretion

- Whether `BetweenGames` requires a ready-up confirmation before `start_next_game`
- Implementation details of step archival between games (archive game N steps to history before resetting)
- Test update strategy (batch vs per-file)
- Order of schema changes within plans
- `MatchSessionStepHistory` PK adjustment (whether `gameNumber` becomes part of the composite PK or stays a column)

<specifics>
## Specific Ideas

- Captain-transfer on DQ/withdrawal mirrors the disconnect flag transfer pattern from Phase 10 (D-34) — "transfers to next non-coach player on same team"
- The BetweenGames → Shelved → resume flow should feel lightweight to users — quick ready-check, not a full lobby setup
- GC TTL for casual shelved lobbies = 72 hours — long enough for "play tomorrow" but not forever
- Tournament shelved lobbies persist until cancel — TOs have full control
- Per-round check-in is explicitly deferred — the schema columns exist but no reducer wiring in this phase

</specifics>
