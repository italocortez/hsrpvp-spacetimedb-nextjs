### 🟡 Reclassified: Phase 5 MMR account rating source — promoted from tech debt to planned fix (Phase 12.3)

The integration checker's original "design note" was deeper than it looked. A debug session (`.planning/debug/phase-5-mmr-account-rating-source.md`) traced it to the scientific-method root cause and confirmed it is a real bug, though low severity in practice. Key findings:

- `processMatchMmr` runs at step 11 of `runFinalization` (line 411), long before `hardDeleteLobby` at step 19 — LMA is still alive, the `isActive` lookup is a deliberate choice, not forced by data deletion.
- `set_active_hsr_account` (`roster.ts:75-96`) has NO lobby guard. `batch_upsert_characters`, `batch_remove_characters`, and `migrate_roster` are similarly unguarded — users can mutate their active account or its roster mid-match without any rejection.
- `delete_hsr_account` DOES guard on LMA presence (`roster.ts:112-115`), proving the team's intent was "LMA is the per-match source of truth" — the MMR path just wasn't migrated when Phase 10.4 introduced per-match account selection.
- The `process_tournament_mmr` tournament-batch path is the most dangerous: LMA is already cascade-deleted when this runs, so `isActive` is the only signal available, making the bug silent and unfixable in-place.

After an architecture discussion, the stats schema was confirmed to be **100% user-level, never account-level** — `MmrRating`, `PlayerStat`, `PlayerCharacterStat`, `MatchResultParticipant`, and `MatchParticipantHistory` are all keyed by `userId`, not `hsrAccountId`. This simplified the fix: only the rating VALUE needs to be frozen, not the account identifier.

**Resolution:** Phase 12.3 (MMR Rating Snapshot) was inserted after Phase 12.2 to close the bug before v0.5 ships. Scope: add `accountRatingSnapshot: f64` column to `MatchResultParticipant`, snapshot at insert time inside `runFinalization`, switch `processMatchMmr` to read the snapshot, add defense-in-depth lobby guards to the four mutator reducers, five new test cases, two doc updates. See `.planning/phases/12.3-mmr-rating-snapshot/CONTEXT.md` for the full phase brief.

### ℹ️ Clarified: `durationMs` column absence is intentional, not drift

The Phase 12.1 verifier flagged the absence of the `durationMs` column on `gc_result` as a minor informational drift note. **This is not drift — the column was intentionally removed** because SpacetimeDB reducers are fire-and-forget with `ctx.timestamp` pinned at invocation start, so wall-clock elapsed time cannot be measured within a reducer. The `12.1-01-SUMMARY.md` key-decisions section already documented this (the field "would always store 0"), so the decision was to drop it rather than keep a perpetually-zero column. No action required; this is a correction to the verifier's informational note, not a finding.

## Tech Debt

**Phase 5 — MMR Account Rating Source (design note, low severity):**
`processMatchMmr` in `spacetimedb/src/helpers/finalizationHelpers.ts:85-92` reads `HsrAccount.user_id.filter(uid).find(a => a.isActive)` rather than the `LobbyMemberAccount` row for the specific match. Per Phase 10.4 D-29, `LobbyMemberAccount` is explicitly ephemeral (deleted in `hardDeleteLobby` cascade), so there's no audit trail of which account was used for MMR. A player can toggle their globally-active account between match start and finalization — the MMR modifier will reflect the new account, not the one actually played.

- **Affected REQs:** MMR-01, ROST-08, ARCH-01
- **Severity:** Low — may be intentional per Phase 10.4 D-29, but semantically inconsistent with the per-match selection goal.
- **Recommended:** Document in Phase 5 or Phase 10.4 contract as known limitation, or schema change to persist the selected account identifier on `MatchResultRecord`/`MatchResultParticipant`.

**Phase 14 — Deferred Auth View Tests (explicit deferral):**
`auth-views.test.ts` real view integration tests (TEST-MODERN-03) explicitly deferred per CONTEXT.md D-05 — auth view subscription patterns may change during v1 frontend work.
